# 通知链路修复方案

日期：2026-09-10
对照基线：`4bfc335`（2026-09-09）
范围：`/api/workspaces/{workspaceId}/notifications*` 全套后端链路 + 前端通知中心接入
结论一句话：**通知的"写"是齐的（6 个业务触发点都在），"读"是坏的——SSE 端点查了不存在的列，列表端点把 6 种形状不一的 payload 当成同一种解析，导致除自动化任务外的所有通知标题正文都是空的。**

## 1. 设计原则

1. **payload 自描述**：通知的展示文案（标题/正文/关联对象）属于写入方最清楚的上下文，写进 payload，读取侧不再猜测。
2. **读取侧只做一种解析**：列表与 SSE 共用同一个查询和同一个映射函数，杜绝"两条路径两套口径"。
3. **向后兼容**：历史行没有 `title`/`body`，读取侧按 `kind` 兜底渲染，不要求回填。
4. **不引入新表**：`content.notifications` 结构不动，避免迁移碎片化（当前 0013-0025 已是追加式迁移，见 `v2-全面差距与架构分析报告` 的卫生债项）。
5. **契约同步**：改响应就改 openapi，并给契约测试加字段级断言。

## 2. 后端修复

### B1. 定义统一的通知 payload 契约

所有写入点把展示所需信息写进 `payload`，键名固定为：

```json
{
  "title": "审核通过",                  // 必填，列表/推送的标题
  "body": "《知识库建设指南》已发布",      // 必填，正文摘要
  "object_type": "publication_request", // 可选，关联对象类型
  "object_id": "<uuid>",                // 可选，关联对象 id
  // 以下是业务字段，按 kind 各自保留，前端可按需使用
  "request_id": "...", "asset_id": "...", "status": "...", "reason": "..."
}
```

**注意键名是 `body`，不是 `message`**（现状读取侧读 `message`，写入侧写 `body`，这是 N2 的直接成因）。

各 kind 的文案与关联对象约定：

| kind | title | body | object_type / object_id |
| --- | --- | --- | --- |
| `publication.submitted` | 有新内容待审核 | `《{资产标题}》提交了发布申请` | publication_request / request_id |
| `publication.approved` | 审核通过 | `《{资产标题}》已通过审核并发布` | publication_request / request_id |
| `publication.rejected` | 审核驳回 | `《{资产标题}》被驳回：{reason}` | publication_request / request_id |
| `publication.cancelled` | 发布申请已取消 | `《{资产标题}》的发布申请因{reason}自动取消` | publication_request / request_id |
| `publication.scheduled_failed` | 定时发布失败 | `定时发布未执行，原定时间 {scheduled_at}` | publication_request / request_id |
| `system`（删除） | 删除完成 | `{resource_type} 已删除` | deletion_job / deletion_job_id |
| `system`（自动化） | 沿用 payload.title | 沿用 payload.body | task_run / 任务 id |

实现要点：
- 资产标题在写入点取。`review/service.go` 与 `asset/lifecycle.go` 的写入都在事务内、已持有 `asset_id`，用同事务内一次 `SELECT title FROM asset.assets WHERE ...` 补齐即可（不新增跨服务调用）。
- 若某写入点确实取不到标题，退化为 `《未命名资产》`，不阻断主流程。
- 自动化那条把 `body` 保持（它已经对了），只补 `message` → 不需要，因为读取侧统一读 `body`。

### B2. 列表与 SSE 共用查询与映射

在 `internal/httpapi/notifications.go` 内抽出两个私有函数，替换现有两套逻辑：

```go
// notificationRow 是一次查询的原始行。
type notificationRow struct {
    streamID    int64
    id          string
    workspaceID string
    kind        string
    payload     []byte
    readAt      *time.Time
    createdAt   time.Time
}

const notificationColumns = `stream_id, id::text, workspace_id::text, kind, payload, read_at, created_at`

// presentNotification 把 (kind, payload) 渲染成对外结构；历史行缺 title/body 时按 kind 兜底。
func presentNotification(row notificationRow) finalNotification
```

- `listNotifications`：SQL 改为 `SELECT ` + `notificationColumns` + ` ... ORDER BY stream_id DESC LIMIT $n`，扫描后调 `presentNotification`。
- `streamNotifications`：SQL 同样改为 `notificationColumns` + `... AND stream_id > $4 ORDER BY stream_id LIMIT 100`，扫描后调 `presentNotification`。**这是 N1 的修复点**：删除对 `type/title/body/object_type/object_id/metadata` 六列的引用。
- `presentNotification` 逻辑：
  1. `payload` 反序列化到 `map[string]any`；
  2. `Title` = `payload.title`，缺省按 kind 兜底（表见 B1）；
  3. `Body` = `payload.body`，缺省兜底；
  4. `ObjectType`/`ObjectID` = payload 同名键；
  5. `Type` = 数据库 `kind`（对外字段名保持 `type`，见 B4）；
  6. `Metadata` = 完整 payload（前端可按需取业务字段）。
- 两条路径共用一个函数后，`unread-count` / `read` / `read-all` 无需改动（它们不返回内容）。

### B3. 补齐权限校验（N4）

- `markAllNotificationsRead`：在 `rejectUnknownWorkspace` 之后补 `deps.WorkspacePolicy.Require(r.Context(), principal, workspaceID, "", "workspace.read")`，失败 403 `workspace_access_denied`——与 `listNotifications:40` 完全一致。
- `markNotificationRead`：单条端点路径里没有 workspaceId，无法直接校验工作区策略。两种做法：
  - **推荐**：SQL 的 WHERE 增加组织级校验（已有 `organization_id = $1`），并在 `UPDATE ... RETURNING workspace_id` 后按返回值做一次策略检查；无行则 404，保持不变。
  - 或者：接受"只按 recipient 归属"的现状，但把该端点写进文档说明（因为 UPDATE 已限定 `recipient_user_id = 自己`，不存在越权改他人通知的可能，仅是语义不一致）。

  说明：N4 不是越权漏洞——两个端点的 UPDATE 都带 `recipient_user_id = principal.UserID`，只能动自己的行。修的是"同级端点校验口径不一致"。

### B4. 契约同步（N3）

`openapi.yaml:6929-6937` 的 `Notification` schema 改为实现真实返回：

```yaml
Notification:
  type: object
  properties:
    id: { type: string, format: uuid }
    workspace_id: { type: string, format: uuid }
    type: { type: string, description: "Notification kind, mirrors content.notifications.kind" }
    title: { type: string }
    body: { type: string }
    object_type: { type: string }
    object_id: { type: string }
    metadata: { type: object, additionalProperties: true }
    read_at: { type: string, format: date-time, nullable: true }
    created_at: { type: string, format: date-time }
```

同时给 `internal/httpapi/openapi_contract_test.go` 加一条字段级断言：解析 `Notification` schema 的 properties 集合，与 `finalNotification` 的 json tag 集合做双向比对。当前契约门只比路径+方法（`:307`），字段漂移抓不到，这条测试补上后同类问题不会再漏。

### B5. 补测试（N7）

新增 `internal/httpapi/notifications_test.go`（真库集成测试，参照 `tmp_qa/itd_p*.py` 覆盖不到的 Go 侧行为）：

1. **列表映射矩阵**：对 6 种 kind 各插一行，断言 `title`/`body` 非空且符合 B1 约定；再插一行"只有业务字段、无 title/body"的历史行，断言兜底渲染生效。

3. **SSE 断点续传**：带 `Last-Event-ID: N` 时不发 reset，只推 `stream_id > N` 的行。

5. **权限**：非成员访问 `read-all` / `list` 返回 403；`unread-count` 只统计自己的行。
6. **契约字段**：B4 的字段比对。

### 3.2 接入点

`src/components/app-shell/app-topbar.tsx:156-171` 现在是 `disabled` 的 Bell 按钮（`aria-label="通知功能即将开放"`）。替换为 `NotificationBell`：未读角标取自 `useUnreadCountQuery(workspaceId)`，点击展开列表。

### 3.3 数据源约束（必须按 N5 的现状设计）

通知接口是**工作区维度**的。前端有两种上下文：

- **工作区内**（`/workspaces/[workspaceId]/...`）：`workspaceId` 从路由取，直接调该工作区的三个端点，最简单。
- **全局态**（`/home`、`/workspaces`、`/admin/*`）：没有单一 `workspaceId`。首版采用**聚合**——对当前用户可见的工作区列表并发取 `unread-count` 求和，列表则按工作区分别拉取后按 `created_at` 归并。工作区数量小（通常个位数）时可接受；超过 10 个建议等 N5 的组织级接口。

前端不要假设有全局未读数接口，把这段逻辑封装在 `useAggregateUnreadCount()` 里，N5 上线后只改这一个函数。

### 3.4 实时更新：先用轮询，SSE 修复后可选

- **首版**：`useUnreadCountQuery` 设 `refetchInterval: 30_000` + `refetchOnWindowFocus: true`（参照 `src/features/workspaces/api/member-queries.ts:25` 的既有做法）。零风险，不依赖 N1 修复。
- **SSE 接入（B2 修复后）**：用 `EventSource` 连 `/api/workspaces/{workspaceId}/notifications/stream`。注意三点：
  1. `EventSource` 不能自定义请求头，`Last-Event-ID` 由浏览器自动管理，断线自动重连——这正好匹配后端实现；
  2. `EventSource` 无法感知 401，会话过期时它只会静默重连，必须配合轮询兜底；
  3. 同源请求自动带 cookie，与 `apiRequest` 的 `credentials: "include"` 一致，无需额外配置。
  建议：SSE 只负责"有新通知就 invalidate 列表"，不直接往缓存里塞数据（避免与轮询结果打架）。

### 3.5 交互与文案

- 未读用 `Badge variant="primary"` 显示数量，超过 99 显示 `99+`。
- 列表项：`title` 加粗 + `body` 次要色 + 相对时间（`Intl.DateTimeFormat("zh-CN")`，参照 `knowledge-base-page.tsx:66-81`）。
- 点击条目：调 `markRead`，并按 `object_type` 跳转（`publication_request` → 知识库待审核页；`deletion_job` → 资产详情）。无法定位的条目只标已读。
- 顶部提供"全部标为已读"（调 `read-all`）。
- 空态用 `EmptyState`，加载用 `PageSkeleton`，错误用 `ErrorState`（`@/components/feedback`）。
- 文案硬编码简体中文，沿用"局部常量映射表"风格（如 `KIND_LABELS`），不引入 i18n。

### 3.6 Mock 与测试

- `notifications/mocks/handlers.ts` 覆盖 5 个端点，并在 `src/mocks/handlers.ts:49-55` 追加 `...notificationHandlers`（否则 Mock 模式下顶部栏请求会落到网络失败）。
