## 4. G2 display_path 变更自动 301

### 4.1 现状与锚点

- 修改路径入口已存在:`UpdateBinding`(`internal/site/binding.go:340-453`),`UpdateBindingInput.DisplayPath *string`,变更分支在 `:379-396`(事务内、binding 行已 FOR UPDATE、`current.DisplayPath` 可得),`:436` bumpSiteRevision、`:443` 发 `site.binding_changed`/`site.site_changed` 自动整站失效。
- 未知路径现状:直接 404(`internal/delivery/service.go:384-386` 冒泡 `ErrSiteNotFound` → `writeDeliveryError` 映射 404)。设计文档已留白:`docs/公开站点SSR投递与样式参数空间设计方案.md:357`。
- 无任何 redirect/history 表(0001-0021 grep 零命中)。

### 4.2 设计

**新表**(0022 段②,风格照 `site.style_presets`):

```sql
CREATE TABLE site.path_redirects (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    organization_id uuid NOT NULL REFERENCES organization.organizations(id),
    site_id uuid NOT NULL,
    from_path text NOT NULL CHECK (from_path ~ '^[a-z0-9][a-z0-9/-]{0,120}[a-z0-9]$'),
    to_path text NOT NULL CHECK (to_path ~ '^[a-z0-9][a-z0-9/-]{0,120}[a-z0-9]$'),
    binding_id uuid,
    created_by uuid NOT NULL REFERENCES identity.users(id),
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (organization_id, id),
    UNIQUE (site_id, from_path)
);
```

正则与 `displayPathPattern`(`internal/site/validate.go:27`)逐字一致——**to_path 只允许本站合法 display_path,从数据层封死开放重定向**(301 目标永远 `/sites/{slug}/posts/{to_path}`,不含 scheme/host)。

**写入(自动,无需用户操作)**:`UpdateBinding` 的 `:379-396` 分支内,当 `displayPath != current.DisplayPath` 时同事务执行两步:

```sql
INSERT INTO site.path_redirects (organization_id, site_id, from_path, to_path, binding_id, created_by)
VALUES ($1,$2,$3,$4,$5,$6)
ON CONFLICT (site_id, from_path) DO UPDATE SET to_path = EXCLUDED.to_path, updated_at = now();
UPDATE site.path_redirects SET to_path = $new, updated_at = now()
WHERE site_id = $site AND to_path = $old;  -- 链式扁平化:A→B、B 改 C 时把 A→B 改写为 A→C
```

`DeleteBinding`(`binding.go:479-490`)**不**写 redirect(删除后旧路径 404,不给「删除即跳首页」的隐式行为;如产品后续要,是加一行的事)。

**查询与响应**:`Service.Post` 的 build 闭包错误分支(`service.go:384-386`)在 `errors.Is(err, site.ErrSiteNotFound)` 时调新方法 `s.Reader.PathRedirect(ctx, slug, displayPath)`;命中则返回 `renderOutput{kind: "redirect", location: "/sites/"+slug+"/posts/"+to}`。错误页本就不进缓存(键只存 200 渲染),301 同样不进缓存,`binding_changed` 整站失效自动覆盖 redirect 变更后的正确性。`writeDeliveryPage`(`internal/httpapi/delivery_routes.go:51-67`)补 redirect kind:写 `Location` 头 + `Cache-Control: private, max-age=30`(301 可短缓存,但别 immutable)。

**优先级语义**:渲染先查 binding(现行为),未命中才查 redirect——旧路径被新文章占用时新文章自然优先,redirect 行惰性留存不冲突。

**Agent 面**:零工具。用户「把这篇文章的网址改成 xxx」→ Agent 走现有 binding PATCH(未来补 `update_binding` 工具时同样自动获得 301),301 由服务端自动发生,这是对「传统 CMS 手工配映射表」的关键差异点。

### 4.3 验收

- 改 display_path 后:旧 URL 301 → 新 URL(且 `Location` 为本站路径);新 URL 200;`path_redirects` 链式改写正确(A→C)。
- redirect 目标非法路径被 CHECK 拒绝;外部域名的开放重定向不可构造。
- `delivery_routes_test.go` 路由表无新增(复用 posts 路由),但补一条 301 行为的集成断言。

## 5. G3 display_path AI 建议工具(suggest_display_path)

### 5.1 现状与关键约束

- 文章路径纯手工+冲突 409(`binding.go:250-252`、`:288-299`);标签已有自动 slug(`internal/tag/normalize.go:112-150` DeriveSlug)。
- **硬约束**:`displayPathPattern` 只允许小写 ASCII 字母/数字/`-`/`/`。中文标题经 `NormalizeKey`+`DeriveSlug` 会保留汉字(letter),产出**不合法** display_path——所以纯规则派生不可行,必须 LLM 转写(英译或拼音),本地只做规整与校验。这正是 suggest_resource_model「LLM 起草 + 本地 Validate 收口」模式的复刻。

### 5.2 设计

**ReadOnly 工具,纯计算形态**(零审批,`registry.go:242-247` 默认仅 HighWrite 打断):

- 注册三件套:`tools/builtins.go` builtinSpecs 加 `suggest_display_path`(risk=read, capabilities=`["asset.read"]`——**默认集含,开箱可用**)+ `BuiltinHandlers` 加字段 + `tool_factory.go` 加 handler 闭包。
- 参数:`{asset_id: string}`(读标题/摘要;或 `{title: string}` 直传)。
- 流程(照 `internal/agentruntime/style_suggest.go:65-100` 先例):pinned structured endpoint(`f.Models.ResolveStructuredEndpoint`)→ 提示词要求输出 3 个候选(英文短语 slug,≤6 词,连字符分隔)→ 每个候选本地小写化 + `ValidDisplayPath` 校验(不过规整重验一轮,自愈一次,同 style_suggest 模式)。
- **不做 binding 冲突查询**(审计裁决:v1 纯计算、零主数据访问——冲突留给应用链路自然 409,由 Agent 拿错误 detail 自愈加 `-2` 后缀,与 builtin 工具错误回传机制配套;查询绑定需要 site.read action,会把一个开箱即用的纯建议工具变成需要显式授权的工具,得不偿失)。
- 返回:`{candidates: [{path}]}` + 附注"应用时系统会查重,冲突自动加后缀"。**不落库**,应用走既有 binding 创建/更新。

### 5.3 验收

- 中文标题 → 3 个合法候选(全部通过 `ValidDisplayPath`)。
- 无结构化端点可用时工具报 `tool_unavailable`(结构化错误码,`builtins.go:194-197`),不产生半成品。
- 默认 capability 集即可调用(开箱可用断言:不配置 allowed_capabilities 也能跑通)。

## 6. G4 定时发布

### 6.1 现状与锚点

- 发布模型=审核批准即上线:PublicationRequest 状态机 `pending/approved/rejected/cancelled`(`internal/review/contract.go:7-40`,CHECK 镜像 `0005_assets.sql:541-573`,0008-0021 无 ALTER)。`decide`(`internal/review/service.go:537-673`)approve 分支单事务:锁行 → 状态 UPDATE(:596-601)→ policy 门禁(:624)→ **指针切换 `asset.SetPublishedPointerTx`(:632-637)** → `asset.published` 事件(:644-651)→ 通知/审计/commit。
- `SetPublishedPointerTx`(`internal/asset/lifecycle.go:78-119`)published_at CASE 语义已正确(切版本才刷 now)。
- 周期 job 先例充足:`cmd/worker/main.go:246-269` PeriodicJobs(1m 粒度三个);JobArgs 模板 `internal/worker/worker.go:365-371`。
- 版本前进自动取消 pending 请求已存在:`CancelPendingRequestsTx`(`lifecycle.go:179`)。

### 6.2 设计

**核心语义:定时=「已批准的发布意图,等待时刻」。审批与定时解耦——审批模式仍必须人批;direct 模式提交即自动批准(不绕过任何 policy,policy 本身免审)。**

**迁移(0022 段①)**:

```sql
ALTER TABLE asset.publication_requests
    ADD COLUMN scheduled_at timestamptz,
    ADD COLUMN executed_at timestamptz;
ALTER TABLE asset.publication_requests DROP CONSTRAINT publication_requests_status_check;
ALTER TABLE asset.publication_requests
    ADD CONSTRAINT publication_requests_status_check
    CHECK (status IN ('pending','approved','rejected','cancelled','scheduled'));
ALTER TABLE asset.publication_requests DROP CONSTRAINT publication_requests_cancel_reason_check;
ALTER TABLE asset.publication_requests
    ADD CONSTRAINT publication_requests_cancel_reason_check
    CHECK (cancel_reason IN ('user_cancelled','new_version','asset_archived','admin_cancelled','execution_failed'));
CREATE INDEX publication_requests_scheduled_due_idx
    ON asset.publication_requests (scheduled_at) WHERE status = 'scheduled';
```

**状态机扩展**:`pending --approve--> scheduled`(scheduled_at 未来)/ 现行为(立即执行→approved);`scheduled --worker 到点--> approved + executed_at`;`scheduled --cancel/reject--> cancelled`(用户取消/新版本/归档/执行失败)。`ValidRequestStatus`/`ValidCancelReason`(`contract.go:23/:33`)同步;列表筛选与通知认得 scheduled。

**Submit**(`review/service.go:155-285`):请求体加可选 `scheduled_at`(ISO8601,校验 `> now()+60s`,否则 422 `scheduled_at_invalid`)。存列即可,不动状态。

**decide 改造(approve 分支)**:`:624` policy 门禁后分叉——`scheduled_at` 存在且未来:状态 UPDATE 写 `'scheduled'`,**跳过指针切换与 asset.published 事件**,照发 `publication_request.approved` 事件+通知(前端可显示「已批准,将于 xx 生效」),commit;否则走现行为不变。

**direct 模式(审计修订:不走 Submit)**:现状 Submit 对 direct 模式资产**硬拒 409**(`internal/review/service.go:223-232`,注释明示理由:direct 提交会以 per-asset pending 唯一索引永久占位)——本方案**不反转该门**。direct 的定时发布改走 **publish 端点扩展**:成员 publish / Agent `publish_asset` 工具请求体加可选 `scheduled_at`(未来时间);带此参数时 publish 不立即切指针,而是调 review 域新服务方法 `CreateScheduledDirect`:校验 policy.Mode==direct(approval 模式返回 409 引导走 Submit)+ scheduled_at 合法后,直接落一行 `status='scheduled'` 的 request(`submitted_by=decided_by=操作者`——direct 的免审来自 policy 本身,不构成 self-approval 违例;事件/审计 metadata 标 `mode=direct, auto=true` 以区分人工批准)。幂等键语义沿用 publish 端点现行为。approval 模式的定时仍走 Submit(scheduled_at)→ 人 approve → scheduled,审批链零弱化。**Agent「明早 9 点发布这篇」**:direct 模型→publish_asset(scheduled_at);approval 模型→publication.submit(scheduled_at)+ 等人批。

**worker 到点执行**:新 `ScheduledPublicationArgs{}`(仿 `CleanupExpiredRowsArgs`,`worker.go:365-371`),PeriodicJobs 加 1m 间隔(`cmd/worker/main.go:246`)。Work 内:

```sql
SELECT ... FROM asset.publication_requests
WHERE status='scheduled' AND scheduled_at <= now()
ORDER BY scheduled_at LIMIT 10 FOR UPDATE SKIP LOCKED
```

逐条执行(独立事务,单条失败不拖批次):资产已归档 → `cancelled/asset_archived`;否则走**共享事务函数**——把 decide 的「指针切换+事件+通知+审计」后段(`service.go:632-669`)抽取为 `executeApprovedTx(ctx, tx, request, actor, metadata)`,approve 立即路径与 scheduled 到点路径**共用同一函数,禁止复制事务代码**。执行:`LoadLifecycleTx` → `executeApprovedTx`(切 `request.asset_version_id`,**不是当前 working 指针**,与人工 approve 语义一致)→ 置 `approved + executed_at=now()`。执行 DB 层失败重试 3 次(River MaxAttempts)后置 `cancelled/execution_failed` + **通知发起人**(不只审计——静默取消定时违背「人做判断」) + 审计留痕。**事件发出后 delivery.cache 与 retrieval.projection 消费者自动生效,零额外失效代码**(invalidator.go:31 / eventing.go:128-175 现状已覆盖)。

**自动取消联动**:`CancelPendingRequestsTx`(`lifecycle.go:179`)的谓词从 `status='pending'` 扩为 `status IN ('pending','scheduled')`——新版本提交、归档时定时意图一并取消(通知/审计照发,该函数 443baef 轮已具备补事件能力)。

## 7. G5 响应式图片变体

### 7.1 现状与关键约束

- 媒体路由 `/sites/{slug}/media/{id}` 是**代理流式直出**(`internal/httpapi/delivery_routes.go:414-453`):`Objects.Get(ObjectRef{Key})` → `io.Copy`,`Content-Type` 取 DB 的 `media_type`,`Cache-Control: immutable`。
- `ObjectStore` 接口(`internal/objectstore/objectstore.go:10-25`)只有 `Put/Get/Delete`,`ObjectRef{Key}` 单字段——**x-oss-process 现在无法穿过这条链**;handler 也不读 query。
- CSP `img-src 'self' data:`(delivery_routes.go:26)——同源 media 路由是唯一图片通道;`immutable` 头要求变体必须进 URL(同 URL 永不变形)。

### 7.2 设计

**受控 variant 枚举(不是透传!)**——安全红线:绝不把用户输入拼进 `x-oss-process`(那是 OSS 的指令语言,透传=注入面,与 L2 CSS 清理器同一教训)。变体表写死在代码:

| variant | OSS process | 目标 Content-Type | 用途 |
|---|---|---|---|
| `full` | `image/resize,w_1280` | 随源(jpeg/png) | 详情页大图、og:image(审计修订:og 与 cover 合并为一个 full,1280 与 1200 的 og 推荐宽差异无实质影响) |
| `card` | `image/resize,w_640/format,webp` | `image/webp` | 列表卡片 |
| `thumb` | `image/resize,w_320/format,webp` | `image/webp` | 卡片 srcset 小档 |

**接口扩展**:`ObjectRef` 加 `Process string`(零破坏,其他实现忽略);OSS `Get`(`internal/objectstore/oss.go:85-107`)在 Process 非空时经 `oss.Process(p)` option 挂查询参数。阿里云 OSS 图片处理是默认开通的标准能力,无新增配置。

**路由**:`deliverySiteMedia` 读 `?variant=`,非上表值 → 400(`variant_invalid`,不 404 以便调试);variant 有效时 `ObjectRef.Process` 用映射值,`Content-Type` 用上表目标值(**白名单映射优先,不信任 OSS 响应头**——防 Content-Type 嗅探)。URL 含 variant 参数,immutable 语义保持。**降级**:process 请求失败(OSS 报错)→ 记日志并去掉 Process 重取原图,响应仍 200(宁可大图不可裂图)。

**模板**:`card.html:2` 与 `detail.html:5` 的 `<img>` 加:

```html
<img src="{{.}}?variant=card"
     srcset="{{.}}?variant=thumb 320w, {{.}}?variant=card 640w, {{.}} 1280w"
     sizes="(max-width: 640px) 100vw, 640px" alt="..." loading="lazy">
```

详情页 cover 用 `sizes="(max-width: 900px) 100vw, 860px"`(src 用 `?variant=full`)。G1 的 og:image 用 `?variant=full`。

**封面资格沿用现状**(≤5MB、clean、image/%,`attachment/service.go:412-416` 与 `pages2.go:140-163` SQL)——超大原图本期不做「上传时拒收」,体检工具(G6)会提示。

### 7.3 验收

- `?variant=card` 返回 `Content-Type: image/webp`、体积显著小于原图;`?variant=bogus` → 400;无参数 → 原图不变(回归)。
- HTML 断言:卡片/详情 img 含 srcset 三档。
- 降级路径:mock/本地 ObjectStore 忽略 Process(接口零破坏验证)。

## 12. 安全红线

1. **301 目标封死本站**:to_path 正则 CHECK 与 display_path 同规;渲染层 Location 只拼 `/sites/{slug}/posts/{to_path}`,永不接受外站值。开放重定向不可构造。

## 15. 风险与开放问题

1. **worker 单点到点粒度**:1m periodic → 定时发布实际生效时刻有 ≤1m 滞后。产品可接受(业界同类多为分钟级);若要秒级,改 5s 间隔即可(成本=空轮询 SQL,有 partial index 很便宜)。默认 1m,验收写明容差。
2. **direct 模式 Submit 自动批准的审计语义**:decided_by=submitted_by 在 direct 模式下是预期形态,但审计与 `publication_request.approved` 事件的 metadata 必须标 `mode=direct, auto=true`,避免与人工批准混淆。实施时在 appendEventTx 载荷里带上。
3. **向量回灌取哪块**:chunk 平均向量 vs 首块向量,检索质量差异未知。v1 取**首块**(实现最简、语义最接近标题段),p10 里用真实数据观察;不佳再换平均(一行 SQL 改动)。
4. **OSS 图片处理计费**:图片处理按量计费(有免费额度)。量级(个人站)远低于阈值;文档登记,不做事前限制。
5. **apply_content_pattern 的 replace 模式**:本期只 append。覆盖语义(清空再插)涉及数据销毁,等产品确认「HighWrite+预览确认」形态后再议,不悄悄实现。
6. **suggest_display_path 的拼音 vs 英译**:structured endpoint 提示词让 LLM 自选(英文短语优先);若用户偏好拼音,是提示词层调整,零代码。
7. **301 的历史深度**:链式扁平化保证一跳;不设过期(量级小)。若未来要「301 保留期」,是后台清扫 job 的事,不影响本期。
8. **与 §21.2「定时调度裁撤」的边界(审计补)**:2026-09-02 裁撤的是 automation 域的通用定时任务管理面、外部回调与空转工作流图(过度设计裁撤轮);G4 是发布域的单一 River PeriodicJob(worker main 现有 6 个同类先例),无管理面、无 cron 配置暴露、无外部回调——是发布能力的实现细节,不是调度框架回潮。实施与产品文档回写时写明此定位。
9. **capability 配置通道是硬前置(审计补)**:§11.5 P0 未做前,G6-alt/G8 的四个工具对线上应用不可见(SQL 直设可临时解锁);itd_p10 的 alt/样板用例依赖 P0 落地或临时 SQL fixture。
