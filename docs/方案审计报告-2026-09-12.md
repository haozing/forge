## 1. 站点方案（D1–D17）问题清单

### 🔴 1.1 D16「已发布版本列表」没有数据基础（文档称"数据全部现成"）

**文档断言**（§8.5、D16）：详情页更新记录列出最近 10 条**已发布版本**，每条 = 版本号 + 日期 + 版本说明 + 溯源标签；「`asset_versions` 已有 `origin`、`confirmation_status`——数据全部现成」。

**代码事实**：
- `asset.asset_versions` 的列是 `id/version_no/origin/confirmation_status/confirmed_by/confirmed_at/title/summary/markdown/fields/parent_version_id/content_checksum/sealed_at/created_by/created_at`（`db/migrations/0005_assets.sql:82-112`）。**没有 `published_at`，也没有任何"曾发布"状态列**。
- "已发布"只以**单一指针**表达：`asset.assets.current_published_version_id` + `asset.assets.published_at`，并有硬 CHECK 把 `publication_status='published'` 与 `published_at IS NOT NULL` 绑死（`0005_assets.sql:34,41`）。
- 结论：`origin`/`confirmation_status` 确实现成（这部分属实），但**"哪些历史版本曾被发布、何时发布"这条时间线在库里不存在**；一个版本被新版取代后，"它曾发布过"这个事实就丢了（只可能零星残留在审计事件里）。
- 另外 `asset.asset_versions` 上还有不可变触发器（`0005_assets.sql:158-190`）拦住对 title/markdown 等列的任何 UPDATE，只放行 `sealed_at` 从 NULL 到时间戳。

**影响**：D16 的核心展示（版本轨迹）无法实现；把 `change_note` 加在 `asset_versions` 上也不理想——该表语义是"不可变的内容版本"，而"发布"是一个可重复发生的动作（新版发布、回滚重发同一版本），变更说明属于**发布动作**而非**版本内容**。

**建议**：新增发布历史表，一步解决两个问题：

```sql
asset.asset_publications (
  id, organization_id, workspace_id, asset_id, asset_version_id,
  published_at timestamptz NOT NULL, published_by, change_note text NULL,
  superseded_by_publication_id NULL, origin/confirmation_status 快照...
)
```
发布时写一行；「更新记录」直接查该表（倒序、限 10）；`dateModified` 取最近一行。`change_note` 落在发布记录上，既避开触发器，也天然支持"同一版本重复发布各带说明"。

### 🔴 1.2 `DROP site_content_bindings` 会被外键阻塞

**文档断言**（§4.1、§12.1）：绑定表整表废弃 / drop。

**代码事实**：`site.path_redirects` 有外键指向它——`FOREIGN KEY (organization_id, binding_id) REFERENCES site.site_content_bindings (organization_id, id)`（`db/migrations/0022_delivery_seo_scheduled_patterns.sql:49-50`），且无 `ON DELETE`。直接 drop 会被拒绝。

**影响**：迁移脚本会在 drop 处失败（或在有 redirect 数据时失败）。

**建议**：迁移清单补一步——先重建 `site.path_redirects`（去掉 binding FK，改为指向新的 slug 体系），再 drop bindings。

### 🔴 1.3 §5.3「复用 PathRedirect」在数据来源上不成立

**文档断言**（§5.3、§4.1）：标题变更 →「复用 `PathRedirect` 301 到当前 slug」，「下线时 slug 行保留（301 语义）」。

**代码事实**：
- `PathRedirect` 机制**存在但不在 `internal/delivery`**，在 `internal/site/public.go:619-640`（delivery 只是调用，`internal/delivery/service.go:419`）。
- 它查的是 `site.path_redirects.from_path → to_path`（`public.go:629-632`），而这些行是**由 binding 的 display_path 变更时写入**的（`internal/site/binding.go:437-441` → `recordPathRedirectTx`，`binding.go:606-620`），并带上述 binding FK。

**影响**：绑定表一退役，301 的**写入源**和**承载表**同时消失——新方案里"旧 slug 自动 301"没有落地路径，不是"复用"而是"重建"。

**建议**：文档改为「重建 301 链路」——写入源从 binding.display_path 改为 `site_slugs` 的 `is_current=false` 历史行；`path_redirects` 去掉 binding FK，并考虑加 `kind`（内容/分类）维度；迁移清单同步。

### 🔴 1.5 D14 分类公开化的真实缺口被低估一个数量级

**文档断言**（§8.2、§8.1）：骨架"约六成现成"，缺"分类维度公开面 + 引用内链 + 分类级 SEO 元数据"三件事；分类 slug 可手工改 + 301 + 分类名按 locale 渲染。

**代码事实**：
- 分类树本身**有**：`content.containers` 的 `parent_id`/`sort_key`（`0003_workspace.sql:147-170`），深度护栏 16 层（`internal/folder/folder.go:25`），`content.container_assets` 挂资产（`0005_assets.sql:592-611`）。✅
- 但 container 的列只有 `id/workspace_id/kind/title/status/visibility/parent_id/sort_key/revision/asset_id`。**没有 `slug`、没有 `locale`、没有任何 SEO 列**（`visibility` 取值 `workspace|organization|public`，且 folder 创建路径根本不写它，`internal/folder/folder.go:158-163`）。
- 挂载**不校验 kind**：`internal/asset/member_relations.go:78-99` 只校验 container 存在/active/同工作区，没有 kind 过滤。
- 全库**没有任何翻译数据模型**（grep `locale|translation` 零命中）——所以"分类名按 locale 渲染"**连数据来源都不存在**，不只是缺一列。

- `containers.kind` 的实际闭集是 `note/document/faq/content_field/custom/chat/note_folder/doc_folder`（`0019`、`0026` 收窄过），文档若假定"doc_folder 专挂文档"需补这条业务校验（当前数据库不拦）。

**影响**：D14 不是"补齐字段"，而是**新建 container 的 slug + 公开标记 + SEO 元数据 + 分类路径 301 + 完整翻译数据模型**五项独立建模工作。

**建议**：把 D14 从 P1「SEO 基座」拆出为独立子阶段；先做最小闭环（container.slug + 公开标记 + `/c/{path}` + 分类级 title/description + 面包屑），**「分类名按 locale 渲染」明确延到多语言阶段**（依赖 §1.6 的翻译模型一同设计）。

### 🔴 1.6 D11 多语言：内容层与分类层要一起设计，且与兜底路由有冲突

**已核实**：`asset.assets` **无** `locale/translation_group_id`；`site.public_sites` **无** `default_locale/enabled_locales`；`internal/delivery` 零 locale 概念。所以 D11 是全新能力（文档已承认）。

**新增风险（文档未提）**：
1. **locale 前缀 vs 兜底路由**：`/sites/{slug}/` 被注册为**站点级 404 兜底**（`router_groups.go:56`；`delivery_routes_test.go` 明确把"未知深层路径必须命中一个 handler"钉为契约）。因此 `/sites/{slug}/en/posts/x` **必须显式注册**，否则落到兜底 404 页——功能上安全，但规划里必须列出每个 locale 子路由，不能指望通配。
2. **locale 前缀与保留字碰撞**：自定义页 slug、分类 slug、`model_key` 都可能等于 `en`/`zh`/`posts`/`tags`/`about`/`archive`/`search`/`media`/`sections`。需要一份**保留字表**（禁止页面/分类 slug 取这些值），否则 `/sites/x/en` 到底是"英文首页"还是"叫 en 的自定义页"无法判定。
3. **about 路由搬迁**：现 `/sites/{slug}/about/`（`router_groups.go:69`）由 binding `content_type='about'` 驱动；新方案改 `/p/about`，需 301 旧地址。
4. **集合页路由参数写错**：文档写 `/sections/{model_key}`，代码实际是 `/sections/{sectionSlug}` 按 `section_slug` 过滤，`model_key` 只是 `?model_key=` 查询参数（`public.go:1018-1025`、`httpapi/public_sites.go:229`）。新方案要改成按 model 驱动，属语义变更，需明确"旧的 section_slug 概念整体作废"。

### 🟠 1.7 `site.manage` 仅 admin ⇒ editor 用不了「设计」Tab

**代码事实**：`site.manage` 只有 admin 持有；editor/reviewer/viewer 仅有 `site.read`（`internal/authz/roles.go:80` vs `:105/:119/:128`）。

**与文档的冲突**：站点方案 §3/§13 让"用户在设计 Tab 手工改"，§10.3 又把"应用会话结果"与"发布"标为 `site.manage`（admin）。结论：**只有 admin 能配置站点外观**，而内容主力 editor 连设计 Tab 都进不去。这既是产品问题（最有动力调外观的人被挡），也让 §13「设计 Tab」的权限前提自相矛盾。

**建议**：把 `site.manage` 拆成 `site.design`（配置外观/页面，授予 editor）+ `site.lifecycle`（建站/停用/域名/发布 release，留 admin）。两文档都要改；这也顺带解决 §10 设计会话"agent 需要 site.design"的表述（当前文档写的是"能力清单 site.design"但角色只有 site.read）。

### 🟠 1.8 slug 生成时机：在草稿阶段重生成会打断线上 URL（设计漏洞）

**文档断言**（§5.3）：标题 PATCH → 重新生成 → 旧行 `is_current=false` → 301。

**问题**：slug 是**已发布状态**的属性。若用户编辑一条**已发布**内容的标题（产生新草稿版本），按现文档逻辑 slug 会立刻挪走，但线上仍在渲染旧版本内容 → **线上 URL 404（或 301 到尚未发布的内容）**，直到重新发布。

**建议**：明确「slug 与 301 只在**发布时**重算」（或至少在 commit 时），草稿标题变更不动 live slug；收录清单展示 live slug。
顺带一个边界：若标题改回**该资产自己的历史 slug**，应允许**回收**（该历史 slug 正好 301 回自己），而不是加时间后缀；文档 §5.2 的"历史 slug 全部占用"需加这条例外。

### 🟠 1.9 交付端无头截图的信任边界（安全）应写进方案

`chromedp` + 容器内 chromium 渲染的是**用户内容**（标题、markdown 正文、模块参数）。虽然 markdown 已过 bluemonday 白名单、图片只走同源 `/media`（`internal/delivery/markdown.go:47,54`），但在浏览器里执行 SSR 产物仍是**新攻击面**（布局溢出、超长文本、外部字体/图片若有遗漏路径）。

**建议**：截图池补三条约束写进文档——容器内**禁网**（外部请求一律阻断）、渲染禁用 JS 或仅允许本站内联脚本、单页超时与内存上限；并把"只渲染本站已授权内容"写成不变量（而非"安全面小"的口头结论）。

### 🟠 2.1 决策 B「废除两表 + 统一走角色矩阵」的实现面被严重低估

**文档断言**（§5.2、§3）：drop `workspace_agent_applications` 与 `agentAllowedActions`，agent 判权"只有一个答案来源"。

**代码事实**：

**影响**：删一张表 ≠ 单一答案来源。要真正做到，需要：合并四套词表为一份"Agent 能力"枚举；在 `ScopeResolver`/`OpenAPIQuery`/`AssetService.Create/Update` 三条绕过路径上补角色校验；并把 `asset.archive` 这类漏项一起修掉。

**建议**：P0 范围改写为「合并词表 + 三处角色校验补点 + 修 archive 漏项 + 废两表」，不要写成"删两表即可"。

### 🟠 2.2 member-only 的 `require` 面比"三处"大得多——需按工具可达性收窄

**文档断言**（§1）："MemberService.require member-gated 三处拒绝 agent principal"，dfa4e0a 已修。

**代码事实**：dfa4e0a **只改了 `internal/asset/member.go`**（`internal/asset/member.go:145-157`：先 `HasCapability` 再 `Policy.Require`）。其余仍是**第一行 member-only 拒绝**，至少覆盖：review（`internal/review/service.go:127-139`，且 `decide` 另有显式拒绝 `:659`）、resourcemodel（`internal/resourcemodel/service.go:109-113`）、site（`internal/site/service.go:143-146`）、automation、conversation（`internal/conversation/list.go:184-193`）、asset transfer（`internal/asset/transfer.go:92-96`）、deletion、content（多处）、workspace（`internal/workspace/service.go:113-121`）、organization（`internal/organization/service.go:70-73`）。

但并非全部需要改：**transport 层 `requireMemberSession` 让 agent 永远拿不到 HTTP 会话**（`internal/httpapi/member_session.go:15-26`；登录只认 `user_type='member'`，`internal/auth/identity.go:62`），所以 agent 只能走 MCP/react 工具。按工具可达性，**真正要改的是工具链会触达的包**：asset、query、resourcemodel、site、review（提审）、content。其余 12 处属"改不改都不影响 agent"，应在文档里说明而不是列进 P0。

**建议**：文档把"三处"改为"工具链可达的 5-6 个 service require 需改造；其余 member-only 因 agent 无 HTTP 会话而不可达，列为后续一致性整改"。

### 🟠 2.3 agent editor 可直接发布内容 → 与「AI 起草·人工确认」叙事冲突

**代码事实**：editor 的角色矩阵含 `asset.write` **与** `asset.publish`（`internal/authz/roles.go:85-106` 区域）；发布是否走审核由 `publishing.mode`（direct/moderated）决定。

**冲突**：站点方案 D16 的核心卖点是「AI 起草 · 人工确认」的透明标签，而成员方案 C 给 agent 的 editor 角色**能在 direct 模式下直接发布**——AI 内容可未经任何人确认直达公开站点。两份文档合起来把"AI 不能自己发布"讲成了一个卖点，实际权限模型允许。

**建议**（需你决策）：二者取一——
1. agent 的能力清单**不含 `asset.publish`**（agent 只能 create/confirm，发布必须人做）；或
2. 保留能力但**强制 agent 提交走 moderated**（`publication.submit`），人审后发布。
建议选 1（与"AI 永不直接发布"叙事一致，也少一个 policy 分支）。

### 🟠 2.4 agent 提审会让审批事务崩溃（现存缺陷，必须先修）

**代码事实**：审批决策的邮件入队在 `internal/review/service.go:457-464`，对 `submitted_by` 执行 `SELECT email FROM identity.users` 并 `Scan` 进 `string`。agent 的 email 为 NULL（`identity.users` 只强制 member 有 email，`0002_organization_identity.sql:30-32`），**NULL 扫描报错且不是 `ErrNoRows`**，不会被 `:459-461` 吞掉 → **approve/reject 整个事务回滚**。触发条件：`Cipher != nil && BaseURL != ""` 且 agent 提审后由人审批。

**建议**：这是 agent 入内容流的**前置修复项**，列入 P0：邮件入队改为 `email IS NOT NULL` 过滤 / `COALESCE(email,'')` + 空则跳过。

### 🟠 2.5 附件路径对 agent 无条件开放

**代码事实**：`internal/attachment/service.go:78-96` 的 `requireWorkspaceMember` **只查 `workspace_members` 且 `role <> 'viewer'`，不校验 `user_type`**。agent 以 editor 入成员后，附件 Upload/List/Link/Delete/Download（调用点 `:101,:279,:322,:363,:395,:430,:499`）直接对 agent 开放。

**影响**：这是一个"绕过其他闸门"的横向路径（附件是媒体授权链的上游）。

**建议**：文档 §7 安全规则补一条明确决策——agent 是否需要附件写权限；若需要，走能力清单显式授予；若不需要，在此处补 `user_type` 校验。

### 🟠 2.6 决策 D（min 角色）零实现，且现状是"agent 全量能力"

**文档断言**（D、§4、§7.1）：产品内会话 effective = min(agent 角色, 发起人角色)。

**代码事实**：

**影响**：防提权目前不存在——viewer 发起的会话里 agent 全量能力干活（这正是决策 D 要防的）。

**建议**：文档明确标为"待实现"，并在 P0 给实现位置（`tool_factory.go` 构造 principal 处做角色交集，或工具回调里加 effective 判定）。

### 🟡 2.7 事实性修正

1. **§1「agent 用户无 email/password」不准确**：`identity.users` 只约束 member 必须有 email/password（`0002:30-32`），**未强制 agent 为 NULL**（实际创建路径不写，`internal/admin/agent.go:126-131`）。且 `UNIQUE(email)` 存在，agent 若有 email 会撞唯一键。

## 5. 应补设计的点（🔵）

1. **locale 保留字表 + 显式子路由注册**（§1.6）——否则前缀与 slug 碰撞、未注册路径落兜底 404。
2. **面包屑层级归属**：D14 后分类成为中间层，但现有 BreadcrumbList 是 home→**section**→post（`internal/delivery/service.go:687-700`）。需定：新的组合是 home→category 路径→post？section（模型集合页）还留在面包屑里吗？两者同时存在会产生"两条父子链"。
3. **引用反向索引可复用 `asset_relations`**：已存在通用关系图 `asset.asset_relations`（source/target 双向，含 target 索引，`0005_assets.sql:359-379`）与 `content.asset_relations`（`0007_content_runtime.sql:108-123`）。但**它们不会解析正文协议、也不会自动抽取引用边**，且 invalidator **无反向传播**（`internal/delivery/invalidator.go:38-44` 只做 asset→site）。建议 D13 明确"写正文时抽取引用边写入 relations 表 + invalidator 加一层反查"，而不是新建一张专用的反向索引表。
4. **`public_view` 下沉后的生效时机要写清**：资源模型版本被内容 pin（`asset_versions.resource_model_version_id`），所以字段公开范围**随内容重新发布才变**，不随站点 release 变。这是相对今天（站点 release 冻结白名单）的语义变化，差异面板与用户预期都要改。同时 `site_releases.config.model_views` 应删除或降级为兼容字段。
5. **默认首页生成依赖新数据**：§7.1 默认首页含"顶级分类导航块"，而分类公开标记/分类 slug 是新建能力 → 建站向导的"零配置默认首页"在 D14 落地前无法生成该块，分期依赖要写明。
6. **locale 在内容创建时的默认值**：文档只写"文档默认取站点默认语言、记录类 NULL"。FAQ、从表记录创建的文档、MCP `create_document` 各走哪个默认？建议统一写一条"创建时按内容形态给默认 locale"的规则表。
7. **截图池安全约束**（§1.9）：禁网 + 禁外部资源 + 超时/内存上限，写成不变量。
