# 检索引擎架构设计（R3）

状态：设计基线

范围：R1 结构化与 PGroonga 全文检索、R2 语义向量召回、R3 混合召回与重排。

本设计以当前代码为基线，不引入外部 RAG 编排平台，不把检索索引作为资产权威数据源，也不把大模型输出作为权限裁决。

## 1. 目标与边界

### 1.1 目标

检索请求支持结构化条件、关键词、自然语言和混合条件，返回：

- 当前组织和当前调用主体有权访问的资产；
- 当前发布版本；
- 满足资源模型出口策略和最低质量的结果；
- 可回源、可校验的片段引用；
- 可解释的召回通道、分数和降级状态。

R1、R2、R3 的能力边界：

| 阶段 | 能力 | 交付标准 |
| --- | --- | --- |
| R1 | 结构化查询、PGroonga 中文全文查询、权限过滤、发布指针复核 | 不泄漏权限；投影可重建；全文结果可定位到资产版本 |
| R2 | chunk 投影、embedding 生成、向量 Top-K 召回 | 语义召回可关闭、可重试、可按模型版本重建 |
| R3 | 全文和向量并行召回、RRF 融合、Cross-Encoder 重排 | 结果稳定、可解释、可降级；重排只处理已授权候选 |

### 1.2 非目标

- R3 不实现答案生成、Agent 对话编排或知识库聊天页面。
- R3 不允许 LLM 直接生成 SQL、授权策略或对象存储 URL。
- R3 不维护一份独立于 PostgreSQL 的资产、版本或权限真相。
- R1-R3 只检索资产标题、规范化 markdown 和结构化 fields；附件二进制或附件文本不纳入索引。附件抽取需要独立的受控 extractor 事件和权限边界。
- R3 不承诺所有领域、所有语言和所有数据规模都达到相同质量；比较基准是权限正确性、引用准确性、更新延迟、召回质量和运维成本。

## 2. Clean-slate 设计前提

本方案从空库和新 API 开始，不迁移旧检索表、不保留旧查询路由、不兼容旧事件 payload。资产、资产版本、发布指针、资源模型和授权表属于业务主数据；检索服务只消费这些主数据产生派生投影。

基础不变量：

1. `asset_version` 发布后不可变；内容变更必须创建新的 asset version。
2. 每个 asset version 只属于一个 organization、asset 和 resource model，数据库用复合外键保证一致性。
3. 检索只使用当前发布版本；撤销发布由查询时的发布指针和授权条件立即生效。
4. R1 就创建 chunk-first 投影；全文、向量和引用都围绕同一批 chunk，不维护 asset 级重复全文表。
5. 统一查询入口只有 `POST /api/open/v1/query`；引用详情是同一查询响应的一部分，不另设兼容查询路由。

为使检索表的复合外键可执行，主数据 schema 必须先提供以下唯一键：

~~~sql
ALTER TABLE asset.assets
  ADD CONSTRAINT assets_org_id_uq UNIQUE (organization_id, id);
ALTER TABLE asset.asset_versions
  ADD CONSTRAINT asset_versions_org_id_uq UNIQUE (organization_id, id),
  ADD CONSTRAINT asset_versions_scope_uq
  UNIQUE (organization_id, id, asset_id, resource_model_id);
~~~

## 3. 总体架构

~~~text
Client / Eino Agent
        |
        v
HTTP API
  - API Key / Session authentication
  - Query request validation
        |
        v
Query Service
  1. Query Parser -> constrained QueryPlan
  2. ScopeResolver -> AuthorizedScope
  3. Structured candidate query
  4. PGroonga lexical Top-K
  5. Vector Top-K
  6. RRF merge
  7. Cross-Encoder rerank
  8. PostgreSQL final authorization and citation materialization
        |
        +----------------------+
        |                      |
        v                      v
PostgreSQL + PGroonga     pgvector / embedding provider
  asset/version authority    chunk embeddings only
        ^
        |
Outbox -> EventDispatcher -> Queue Worker
        |
        +-> chunk/fulltext projector
        +-> embedding job
        +-> projection retry/dead-letter
~~~

PostgreSQL 仍是资产、版本、发布状态和权限关联的唯一权威来源。全文索引、chunk 和 embedding 都是可删除、可重建的派生投影。

PGroonga 负责中文关键词、前缀和字段文本检索。PGroonga 官方也提供 semantic KNN operator class，但该能力要求特定版本、插件和语言模型；本设计默认使用独立的 pgvector embedding 表，以便明确控制模型版本、维度、重建和评测。PGroonga 全文索引参考：[PGroonga CREATE INDEX](https://pgroonga.github.io/reference/create-index-using-pgroonga.html)。

R3 的 reranker 初期固定为内网本地 Docker 部署的 BGE-Reranker。查询服务只通过内部网络访问该服务，不调用云端 rerank API；云端 provider 不纳入初期可用路径。

## 4. 统一查询契约

### 4.1 QueryRequest

统一入口为 `POST /api/open/v1/query`。请求直接进入 QueryPlan，不存在旧查询路由或兼容转换层。

~~~json
{
  "query": "适合夜景的人像镜头",
  "mode": "hybrid",
  "model_ids": ["uuid"],
  "filters": {
    "quality_gte": "human_confirmed",
    "fields": {
      "mount": {"eq": "E"}
    }
  },
  "top_k": 10,
  "cursor": null
}
~~~

允许的 mode：

- structured：只执行结构化条件；
- fulltext：只执行 PGroonga；
- semantic：只执行向量召回；
- hybrid：执行全文和向量召回并融合。

客户端不能传入 SQL、表名、列名、embedding、权限主体或后端 URL。

### 4.2 QueryPlan

Query Parser 输出受限结构，不输出 SQL：

~~~json
{
  "keywords": ["夜景", "人像", "镜头"],
  "phrases": [],
  "model_ids": ["uuid"],
  "field_predicates": [
    {"field": "mount", "operator": "eq", "value": "E"}
  ],
  "quality_gte": "human_confirmed",
  "mode": "hybrid",
  "parser": "deterministic",
  "parser_version": 1
}
~~~

R3 初期以确定性解析为主：model_id、UUID、枚举、数值范围和明确字段过滤由服务端解析。自然语言关键词可以直接作为全文 query，并生成向量。LLM Query Understanding 只能作为可选 parser，必须输出同一个 QueryPlan，并经过 schema、字段白名单、操作符白名单和最大复杂度校验。

### 4.3 SearchResponse

~~~json
{
  "mode": "hybrid",
  "degraded": false,
  "policy_revision": 42,
  "parser_version": 1,
  "items": [
    {
      "asset_id": "uuid",
      "asset_version_id": "uuid",
      "chunk_id": "uuid",
      "final_score": 0.87,
      "ranking_method": "rerank",
      "channels": {
        "fulltext_rank": 3,
        "vector_rank": 7,
        "rrf_score": 0.0289,
        "rerank_score": 0.87
      },
      "title": "镜头资产",
      "snippet": "夜景人像时建议使用……",
      "citation": {
        "source": "chunk_markdown",
        "source_locator": {"type": "markdown_heading", "value": "heading-2"},
        "char_start": 310,
        "char_end": 352,
        "source_checksum": "sha256",
        "chunk_checksum": "sha256",
        "canonicalizer_version": "v1",
        "projection_run_id": "uuid"
      }
    }
  ],
  "top_k": 10,
  "next_cursor": null,
  "has_more": false,
  "total": null
}
~~~

citation 中的 locator 和 checksum 必须能回到当前发布版本。`final_score` 的语义由 `ranking_method` 固定：`rerank` 时为归一化 rerank score，`rrf` 时为 RRF score，`vector`/`lexical` 时为对应通道 score；不同 ranking_method 的分数不可横向比较。重排分数不能替代权限条件，也不能单独作为审计依据。

R3 统一接口使用不透明、签名且可设置过期时间的 `search_session` cursor。查询首次执行时固化候选 ID、通道 rank、排序分数、授权指纹和 active projection fingerprint；后续 cursor 只读取该快照，不重新用 OFFSET 扫描实时表。`total` 默认不返回，`has_more` 由快照中的剩余结果决定；`top_k` 受服务端上限约束。

## 5. 权限模型

### 5.1 AuthorizedScope

每次查询先解析：

~~~text
principal
  -> organization_id
  -> user_type = agent
  -> AllowedModelIDs(principal, asset.read)
  -> requested model_ids intersection
  -> per-resource-model policy map
  -> policy revision
~~~

AuthorizedScope 至少包含：

- organization_id；
- allowed_resource_model_ids；
- requested_model_ids；
- policy_by_resource_model（required_outlets、minimum_quality、policy_version）；
- policy_revision；
- principal_id 和 initiator_id（仅用于审计，不进入搜索文本）。

### 5.2 硬过滤规则

全文候选、向量候选和最终回源都必须满足：

授权出口按查询 mode 解析，不能用一组对所有模式都相同的伪条件：

| mode | 必需出口策略 | 质量策略来源 |
| --- | --- | --- |
| structured | `agent_tool` | `outlets.agent_tool.min_quality` |
| fulltext | `agent_tool`、`fulltext` | 两者中更严格者 |
| semantic | `agent_tool`、`semantic` | 两者中更严格者 |
| hybrid | `agent_tool`、`fulltext`、`semantic` | 三者中更严格者 |

每个候选和最终回源都必须满足 `organization_id`、`allowed_resource_model_ids`、当前发布指针、`publication_status = 'published'`，并按候选所属 `resource_model_id` 查找 `policy_by_resource_model` 中的全部出口和最低质量。`QueryService` 必须读取 `resource_model_version.policy` 生成该映射，并读取 `authorization.policy_revisions` 作为 `policy_revision`；不能把一个全局 minimum_quality 套用到所有资源模型。

任何近似向量索引只影响排序和召回效率，不改变最终授权。候选不足时可以扩展扫描，但不能放宽权限。

pgvector 官方说明了近似 HNSW 在 WHERE 过滤下可能先扫描后过滤，导致有效结果不足；大规模部署需要 iterative scan、部分索引或按 organization/resource_model 分区，并以过滤后的 Recall@K 验证结果。[pgvector filtering](https://github.com/pgvector/pgvector#filtering)。

### 5.3 不允许的做法

- 先查全库向量，再在 Go 中过滤权限；
- 先返回未经回源的 RRF 结果；
- 用 initiator member 的权限和 Agent 用户权限做隐式交集；
- 将未授权结果数量用于 total；
- 将 query text、embedding 或未授权标题写入普通日志。

## 6. 数据模型

### 6.1 retrieval.chunks

~~~sql
CREATE TABLE retrieval.chunks (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid NOT NULL REFERENCES organization.organizations(id),
  asset_id uuid NOT NULL REFERENCES asset.assets(id) ON DELETE CASCADE,
  asset_version_id uuid NOT NULL REFERENCES asset.asset_versions(id) ON DELETE CASCADE,
  resource_model_id uuid NOT NULL REFERENCES model.resource_models(id),
  ordinal integer NOT NULL CHECK (ordinal >= 0),
  content text NOT NULL,
  chunk_checksum text NOT NULL,
  projection_run_id uuid NOT NULL,
  projection_generation bigint NOT NULL CHECK (projection_generation > 0),
  source_type text NOT NULL,
  source_locator jsonb NOT NULL DEFAULT '{}'::jsonb,
  char_start integer NOT NULL CHECK (char_start >= 0),
  char_end integer NOT NULL CHECK (char_end >= char_start),
  page_no integer,
  chunker_version text NOT NULL,
  canonicalizer_version text NOT NULL,
  status text NOT NULL DEFAULT 'ready'
    CHECK (status IN ('pending', 'ready', 'failed', 'deleted')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (asset_version_id, projection_generation, ordinal, chunker_version),
  FOREIGN KEY (organization_id, asset_id)
    REFERENCES asset.assets (organization_id, id),
  FOREIGN KEY (organization_id, asset_version_id, asset_id, resource_model_id)
    REFERENCES asset.asset_versions (organization_id, id, asset_id, resource_model_id)
);

CREATE INDEX chunks_scope_idx
  ON retrieval.chunks
     (organization_id, resource_model_id, projection_generation, asset_version_id, status);

CREATE INDEX chunks_search_idx
  ON retrieval.chunks
  USING pgroonga (content pgroonga_text_full_text_search_ops_v2);
~~~

resource_model_id 在投影时从 asset_version 固化写入，避免查询时临时推导；复合外键保证 organization、asset、asset_version 和 resource_model 一致，并用于组织和资源模型范围索引。

chunk 建议规则：

- 中文正文目标 300-600 tokens；
- overlap 50-100 tokens；
- 标题、字段名和表格头作为 chunk 前缀；
- 不跨 asset_version；
- chunker_version 变化时生成新世代，不覆盖旧世代；
- 空文本、超长单词和 JSON 原始结构按确定性规则处理。

坐标约定必须固定：`char_start/char_end` 指向 asset_version 的规范化 canonical source（标题、markdown 和 fields 的确定性拼接），不指向加了标题前缀或 overlap 后的 chunk 文本；`source_locator` 记录 markdown heading、field path、page 等业务定位。chunk 前缀只用于召回和重排，不能改变引用坐标。

`source_checksum` 是 asset_version 的 canonical source 校验和，`chunk_checksum` 是当前 `chunk.content` 的校验和，二者不可混用；`canonicalizer_version` 记录规范化规则版本。

### 6.2 retrieval.chunk_embeddings

默认使用 pgvector；embedding provider 可以是内网模型服务或受控 API，不保存权限数据。

~~~sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE retrieval.chunk_embeddings (
  chunk_id uuid NOT NULL REFERENCES retrieval.chunks(id) ON DELETE CASCADE,
  organization_id uuid NOT NULL REFERENCES organization.organizations(id),
  model_name text NOT NULL,
  model_version text NOT NULL,
  dimensions integer NOT NULL CHECK (dimensions = 1024),
  projection_generation bigint NOT NULL CHECK (projection_generation > 0),
  projection_run_id uuid NOT NULL,
  embedding vector(1024) NOT NULL,
  status text NOT NULL DEFAULT 'ready'
    CHECK (status IN ('pending', 'ready', 'failed', 'deleted')),
  error_code text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (chunk_id, model_name, model_version, projection_generation)
);

CREATE INDEX chunk_embeddings_scope_idx
  ON retrieval.chunk_embeddings
     (organization_id, model_name, model_version, projection_generation, status);

CREATE INDEX chunk_embeddings_hnsw_idx
  ON retrieval.chunk_embeddings
  USING hnsw (embedding vector_cosine_ops);
~~~

1024 只是默认部署维度；模型切换必须使用新 model_version 和新索引，不允许同一索引混合不同维度。

### 6.3 active projection 配置

查询不能只接收客户端传入的 model_name/model_version；每个组织和资源模型必须有一个服务端选择的 active projection 世代。R1 可以只有 lexical projection，R2 才为该世代配置 embedding。

~~~sql
CREATE TABLE retrieval.projection_configs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid NOT NULL REFERENCES organization.organizations(id),
  resource_model_id uuid NOT NULL REFERENCES model.resource_models(id),
  model_name text,
  model_version text,
  dimensions integer CHECK (dimensions IS NULL OR dimensions = 1024),
  chunker_version text NOT NULL,
  active_projection_generation bigint NOT NULL CHECK (active_projection_generation > 0),
  status text NOT NULL DEFAULT 'warming'
    CHECK (status IN ('warming', 'active', 'retired')),
  activated_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (organization_id, resource_model_id, active_projection_generation),
  CHECK (
    (model_name IS NULL AND model_version IS NULL AND dimensions IS NULL)
    OR (model_name IS NOT NULL AND model_version IS NOT NULL AND dimensions IS NOT NULL)
  )
);

CREATE UNIQUE INDEX projection_configs_active_idx
  ON retrieval.projection_configs (organization_id, resource_model_id)
  WHERE status = 'active';
~~~

向量查询只能 join `status = 'active'` 且 `model_name/model_version/dimensions` 非空的配置，并同时匹配 `model_name`、`model_version`、`chunker_version` 和 `active_projection_generation`。这里的 `projection_generation` 是投影配置世代，不是每次内容更新的计数；asset_version 本身不可变，内容更新通过新的 asset_version、checksum 和 projection_run 表达。模型或 chunker 升级先创建 warming 配置并完成整批投影、维度校验和评测，再在事务中切换 active；旧世代保留到回滚窗口结束。客户端不能覆盖这个选择。

### 6.4 projection_runs

~~~sql
CREATE TABLE retrieval.projection_runs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid NOT NULL REFERENCES organization.organizations(id),
  asset_version_id uuid NOT NULL REFERENCES asset.asset_versions(id),
  source_checksum text NOT NULL,
  canonicalizer_version text NOT NULL,
  projection_config_id uuid NOT NULL,
  status text NOT NULL
    CHECK (status IN ('queued', 'running', 'ready', 'failed', 'stale')),
  error_code text,
  expected_chunk_count integer NOT NULL DEFAULT 0 CHECK (expected_chunk_count >= 0),
  ready_chunk_count integer NOT NULL DEFAULT 0 CHECK (ready_chunk_count >= 0),
  expected_embedding_count integer NOT NULL DEFAULT 0 CHECK (expected_embedding_count >= 0),
  ready_embedding_count integer NOT NULL DEFAULT 0 CHECK (ready_embedding_count >= 0),
  started_at timestamptz,
  completed_at timestamptz,
  FOREIGN KEY (organization_id, asset_version_id)
    REFERENCES asset.asset_versions (organization_id, id),
  CHECK ((embedding_model IS NULL) = (embedding_model_version IS NULL)),
  UNIQUE (asset_version_id, source_checksum, canonicalizer_version, projection_config_id)
);
~~~

由于 projection_runs 在文档中独立定义，建表顺序完成后执行以下外键约束：

~~~sql
ALTER TABLE retrieval.chunks
  ADD FOREIGN KEY (projection_run_id) REFERENCES retrieval.projection_runs(id);
ALTER TABLE retrieval.chunk_embeddings
  ADD FOREIGN KEY (projection_run_id) REFERENCES retrieval.projection_runs(id);
ALTER TABLE retrieval.projection_runs
  ADD FOREIGN KEY (projection_config_id) REFERENCES retrieval.projection_configs(id);
~~~

projection_runs 是运维状态，不是查询权限来源。只有 `ready_chunk_count = expected_chunk_count` 且 `ready_embedding_count = expected_embedding_count`（R1 无 embedding 时 expected 为 0）时，projection run 才能进入 `ready`；查询只使用 ready generation。权限始终回到 asset、asset_version、resource_model_version 和授权策略版本。

每个 organization/resource_model 的 projection generation 只在投影配置切换时单调递增，分配和 active 切换必须在同一事务中完成且不得复用。发布新 asset_version 不创建新的 generation，只创建该 generation 下新的 projection_run。这样已退休 generation 的延迟事件可以安全标记 stale，而同一 generation 的重复事件由 projection_run_id + asset_version_id + source_checksum 幂等。

### 6.5 search_sessions

分页使用短期搜索快照，避免实时索引变化导致跨页不一致：

~~~sql
CREATE TABLE retrieval.search_sessions (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid NOT NULL REFERENCES organization.organizations(id),
  principal_id uuid NOT NULL,
  query_hash text NOT NULL,
  policy_revision bigint NOT NULL,
  projection_fingerprint text NOT NULL,
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE retrieval.search_session_items (
  session_id uuid NOT NULL REFERENCES retrieval.search_sessions(id) ON DELETE CASCADE,
  ordinal integer NOT NULL CHECK (ordinal >= 0),
  asset_id uuid NOT NULL,
  asset_version_id uuid NOT NULL,
  chunk_id uuid NOT NULL,
  lexical_rank integer,
  vector_rank integer,
  rrf_score double precision,
  rerank_score double precision,
  final_score double precision NOT NULL,
  ranking_method text NOT NULL CHECK (ranking_method IN ('lexical', 'vector', 'rrf', 'rerank')),
  PRIMARY KEY (session_id, ordinal),
  UNIQUE (session_id, asset_version_id, chunk_id)
);
~~~

快照只保存已通过候选授权的 ID 和分数，不保存正文。每次响应仍对快照 item 做最终发布指针和策略复核；撤权后 item 会被过滤而不是重新补入未快照候选。cursor 是 `{session_id, ordinal}` 的签名封装并带过期时间。

### 6.6 部署前置条件

部署基线固定为受控 PostgreSQL 镜像（明确 pin 的 PostgreSQL、PGroonga 和 pgvector 版本），启动检查必须验证 `CREATE EXTENSION pgroonga` 和 `CREATE EXTENSION vector` 均成功；禁止使用 `latest` 标签，也不在部署时临时决定 PGroonga semantic KNN 或 pgvector 二选一。embedding provider 和 BGE-Reranker 镜像、模型 artifact、digest 也必须写入同一份版本清单。

## 7. 投影和事件流程

### 7.1 发布/编辑/下线

资产发布或版本变更写事务产生 `retrieval.projection_requested` 事件：

~~~json
{
  "asset_version_id": "uuid",
  "operation": "rebuild",
  "source_checksum": "sha256",
  "canonicalizer_version": "v1",
  "projection_config_id": "uuid"
}
~~~

事件由写事务写入 Outbox 和队列任务。事件不能携带完整正文；payload schema 只有一个版本，schema 校验失败、无 consumer 或投递失败进入死信并告警。

embedding 不再通过第二套事件驱动；projection worker 在同一个 projection run 内完成 chunk 写入和 embedding 任务编排，embedding job 只携带 `projection_run_id`、`chunk_id` 和 projection config ID。

### 7.2 Worker 流程

~~~text
retrieval.projection_requested delivery
  -> load immutable asset_version
  -> verify checksum and current publication state
  -> deterministic chunking
  -> insert retrieval.chunks for projection_run_id
  -> atomically set expected_chunk_count and ready_chunk_count
  -> create projection run counters
  -> enqueue embedding jobs for this run
  -> mark projection_runs ready only after counters close

embedding job
  -> load the event's projection_run_id and chunk checksum
  -> call configured embedding provider
  -> validate dimensions/model_version
  -> upsert chunk_embeddings for that projection run
  -> atomically increment ready_embedding_count or mark failed/retry/dead
~~~

不同 projection generation 的 chunk 和 embedding 行彼此隔离，worker 不得用新世代覆盖旧世代。事件 projection config 若为 `retired`，或 source checksum 与不可变 asset_version 不匹配，才标记为 stale 并拒绝回写；处于 `warming/active` 的配置仍可处理。相同 projection run 的重复事件必须幂等。

取消发布或发布版本替换时：

- chunks 和 embeddings 标记 deleted 或由 generation 隔离；
- 查询 SQL 立即通过当前发布指针排除旧版本；
- 异步删除允许滞后，但不能影响权限结果。

### 7.3 幂等

投影幂等键：

~~~text
projection_run_id
+ asset_version_id
+ source_checksum
+ canonicalizer_version
+ chunk ordinal
~~~

重复事件不能重复创建 chunk、embedding、queue job 或审计记录。模型切换只创建新世代，验证通过后再把 active embedding 配置切换到新世代。

## 8. 查询执行流程

### 8.1 阶段一：请求校验

- method、body 大小、query 长度、top_k/cursor 和最大候选数；
- model_ids 必须是 UUID；
- filters 按 ResourceModelVersion.field_schema 校验；
- 只允许声明的字段和操作符；
- 拒绝未知字段、嵌套深度过大、数组过大和正则表达式。

### 8.2 阶段二：权限范围

调用 ScopeResolver 获取 allowed model IDs。model_ids 是用户请求的进一步限制，只能与允许集合求交，不能扩大范围。

### 8.3 阶段三：结构化候选

结构化候选直接查 asset.current_published_version_id 和 JSONB/字段索引。R1 先支持：

- eq、in；
- numeric/date range；
- exists；
- quality_gte；
- resource_model_id。

Query AST 转 SQL 时使用参数化表达式，不拼接列名。字段名只从服务端 schema 白名单映射。

### 8.4 阶段四：PGroonga 候选

输入是 QueryPlan.keywords/phrases。召回 Top 100，条件内包含 AuthorizedScope。返回：

- chunk_id 或 asset_version_id；
- pgroonga_score；
- 真正的命中片段；
- source_locator。

R1 起全文结果直接从 chunks 返回；asset_id/asset_version_id 只作为权限和结果聚合字段。
全文 SQL 必须 join `projection_runs` 并要求 `status = 'ready'`，同时匹配 active `chunker_version`、`projection_generation` 和该 run 的 `source_checksum`；不能查询仅完成 chunk 写入但 embedding 或投影计数尚未闭合的 run。

### 8.5 阶段五：向量候选

查询向量不能脱离 active 配置生成。先按 AuthorizedScope 中的 resource_model 分组读取 active model config；不同 `model_name/model_version/dimensions` 必须分别生成 query embedding、执行召回，再在统一的授权候选集合中合并。R2 初期可以限制一个 organization 内只能有一个 active embedding model，但该限制必须由配置校验强制执行，不能把一个向量送给多个模型。

查询 SQL（单一 active config 分组）如下：

~~~sql
SELECT c.id, c.asset_id, c.asset_version_id,
       1 - (e.embedding <=> $query_embedding) AS vector_score
FROM retrieval.chunk_embeddings e
JOIN retrieval.chunks c ON c.id = e.chunk_id
JOIN asset.assets a ON a.id = c.asset_id
JOIN asset.asset_versions v ON v.id = c.asset_version_id
JOIN model.resource_model_versions mv ON mv.id = v.resource_model_version_id
JOIN retrieval.projection_runs pr
  ON pr.id = c.projection_run_id
 AND pr.status = 'ready'
JOIN retrieval.projection_configs emc
  ON emc.organization_id = a.organization_id
 AND emc.resource_model_id = a.resource_model_id
 AND emc.status = 'active'
WHERE e.organization_id = $organization_id
  AND e.model_name = emc.model_name
  AND e.model_version = emc.model_version
  AND e.projection_generation = emc.active_projection_generation
  AND e.projection_run_id = c.projection_run_id
  AND e.status = 'ready'
  AND c.status = 'ready'
  AND c.organization_id = $organization_id
  AND c.resource_model_id = a.resource_model_id
  AND c.chunker_version = emc.chunker_version
  AND c.projection_generation = emc.active_projection_generation
  AND a.current_published_version_id = c.asset_version_id
  AND a.organization_id = $organization_id
  AND a.resource_model_id = ANY($allowed_model_ids)
  AND a.publication_status = 'published'
  AND COALESCE(NULLIF(mv.policy #>> '{outlets,agent_tool,enabled}', '')::boolean, false)
  AND COALESCE(NULLIF(mv.policy #>> '{outlets,semantic,enabled}', '')::boolean, false)
  AND CASE v.quality
        WHEN 'raw' THEN 1
        WHEN 'agent_prepared' THEN 2
        WHEN 'human_confirmed' THEN 3
        WHEN 'high_quality' THEN 4
        ELSE 0
      END >= CASE COALESCE(NULLIF(mv.policy #>> '{outlets,semantic,min_quality}', ''), 'raw')
        WHEN 'raw' THEN 1
        WHEN 'agent_prepared' THEN 2
        WHEN 'human_confirmed' THEN 3
        WHEN 'high_quality' THEN 4
        ELSE 99
      END
ORDER BY e.embedding <=> $query_embedding
LIMIT $candidate_limit;
~~~

上面是 semantic 通道的 SQL 模板；fulltext 和 hybrid 使用同一套 scope 编译器，但分别替换为 `outlets.fulltext` 或 `outlets.fulltext + outlets.semantic` 的 required outlets，不能把 semantic 条件硬编码到所有 mode。

R2 在 resource_model_version.policy 中增加 `outlets.semantic.enabled` 和 `outlets.semantic.min_quality`。R1 不读取 semantic 出口；R2/R3 的 semantic/hybrid 候选必须同时满足 semantic、agent_tool 和当前版本质量策略。

生产环境需要根据数据规模选择 HNSW 过滤策略、iterative scan、partial index 或 organization 分区。R3 先保证正确性和评测，再调近似召回。

### 8.6 阶段六：RRF

全文和向量结果各自按 rank 排序，使用：

~~~text
rrf_score = lexical_weight / (rrf_k + lexical_rank)
          + vector_weight  / (rrf_k + vector_rank)
~~~

默认：

- rrf_k = 60；
- lexical_weight = 1.0；
- vector_weight = 1.0；
- 每通道 Top 100；
- 去重键为 asset_version_id + chunk_id；
- 同一 asset 的多个 chunk 只保留最高分并记录其他引用；
- 最终排序必须有稳定的 `asset_version_id, chunk_id` 作为并列分数的 tie-breaker；排序结果写入 search_session，cursor 只引用 session，不在续页时重新执行召回。

RRF 不把未经权限复核的候选直接返回；它只是授权候选的排序算法。

首个窗口获取完整的候选窗口，完成 RRF、重排、最终授权后写入 search_session，再返回 `top_k`。后续 cursor 只读取 session 中尚未返回的 ordinal；如果最终授权复核过滤了 item，不重新补入候选。

### 8.7 阶段七：Cross-Encoder 重排

R3 对 RRF Top 50 执行重排，初期实现为本地 Docker BGE-Reranker：

~~~text
rerank_input = query text + chunk title/context + chunk content
rerank_output = relevance score
~~~

这是一个必须版本化的内部协议：模型 artifact、模型版本、容器镜像 digest、最大输入 token 数、批大小和分数范围都由配置显式声明，不能只写一个模型家族别名。Query Service 在发送前按声明的 `max_input_tokens` 对 query/context/content 做确定性截断；一条候选对应一个 query-pair，超出 `reranker_batch_size` 必须分批且受总超时约束。模型特定的分数归一化只用于排序展示，`rerank_score` 永远不是权限条件。

内部 HTTP 契约至少提供 `/healthz`、`/readyz` 和 `/rerank`：ready 响应包括 `model_version` 和 `max_input_tokens`；rerank 响应必须逐项返回 candidate ID、分数、模型版本和协议版本。服务端禁止记录请求原文、chunk 正文或 query 文本。

部署约束：

- 使用固定的 BGE-Reranker 模型和镜像 digest，模型文件只读挂载；
- reranker 容器只加入内部网络，不暴露宿主机公网端口，不需要云端 API Key；
- Query Service 是唯一调用方，候选必须已经通过 AuthorizedScope 硬过滤，最多发送 RRF Top 50；
- 容器启动必须完成模型加载和 warm-up，readiness 未通过时不接收查询；
- 设置最大并发、请求队列长度、CPU/GPU/内存上限，避免重排拖垮 API 和 PostgreSQL；
- 通过内部 `RerankerProvider` 接口封装地址、协议和模型版本，后续可替换实现，但不能改变权限流程。

重排请求必须设置连接、请求和总耗时上限。初期建议连接超时约 100ms、请求超时 500ms-1s，并把该预算纳入统一 query timeout。重排失败时：

- 保留 RRF 顺序；
- response.degraded = true；
- 不使用其他 session 或过期 session 冒充新结果；
- 记录 reranker_failure 指标。

重排只处理已通过硬权限条件的 chunk，不能把权限判断交给模型。

本地 BGE-Reranker 容器不可用、未 ready、超时、OOM 或返回非法分数时，统一保留 RRF 顺序并返回 `degraded=true`；不能因为重排失败而扩大候选集，也不能回退到云端 API。

### 8.8 阶段八：最终复核和引用

最终 `top_k`（默认 10，受服务端上限限制）在一个 PostgreSQL 查询中回源确认：

- 当前发布指针仍是该 asset_version；
- organization_id、allowed model IDs 和 outlet 策略仍满足；
- chunk checksum、`projection_run_id`、`projection_generation` 和 active embedding 配置仍有效；
- 当前版本没有被删除或替换。

引用正文从 PostgreSQL 当前 chunk 读取，不能使用 reranker 或 embedding provider 返回的原文作为权威内容。

全文结果的 `snippet` 必须是命中词附近的确定性窗口（PGroonga 命中片段函数或等价实现）。引用响应必须同时返回 `source_type/source_locator/char_start/char_end/source_checksum/chunk_checksum/canonicalizer_version`，并在回源时校验这些值与当前发布版本和 chunk。

## 9. API 设计

### 9.1 R3 统一接口

POST /api/open/v1/query

认证、主体和权限规则与现有 Open API 一致：

- API Key 解析出的 Agent 用户是数据权限主体；
- initiator member 只保留在会话和审计上下文；
- 不接受 member_id、department_id、group_id 作为数据范围参数；
- mode=hybrid 时必须同时满足 fulltext、semantic 和 agent_tool 出口；
- vector 服务不可用时允许降级为 fulltext，但必须返回 degraded=true；
- 统一接口使用 `cursor`/`next_cursor` 和 `has_more`；cursor 指向短期 search_session 快照，`top_k` 只表示本次返回窗口；默认不计算 total，只有在显式请求且成本预算允许时才返回精确 total。

### 9.2 Agent Tool 接入

Eino Tool 和受控外部调用只使用受限的只读查询和引用接口。R3 不把 embedding、内部 chunk 表、reranker URL 或 QueryPlan 内部字段暴露给模型。

Agent Tool 的只读边界必须由技术能力强制执行：使用带 `query.read`、`reference.read` capability 的专用 API key（或等价 read-only principal），并在 HTTP handler 的授权层拒绝该 principal 调用资产创建、更新、发布、删除等 mutation 路由。不能只依赖模型提示词，也不能把普通资源读取权限误当成完整的只读隔离。

## 10. 缓存和一致性

- 不缓存未经主体和 scope 绑定的最终结果；
- 可缓存 query embedding，键为 query_hash + embedding_model + embedding_model_version + dimensions；
- 可缓存 QueryPlan，键为 normalized_query + parser_version，但最终权限仍每次解析；
- 不缓存跨用户的 total、引用正文或授权结果；
- search_session 只保存授权候选 ID 和分数，按 TTL 清理，不能作为权限事实来源；
- 发布/撤权不依赖 session 删除才能生效，因为每页 SQL 总是检查当前发布指针和授权条件；撤权后的快照项直接被过滤。

## 12. 评测方案

建立人工标注的 golden set：

1. 关键词查询；
2. 同义词和自然语言查询；
3. 结构化过滤 + 文本混合查询；
4. 中文、英文、型号、标签和数字规格；
5. 发布版本替换；
6. Agent 权限差异；
7. 撤权和跨组织访问；
8. 无向量、embedding 失败和 reranker 超时。

每个结果同时验证：

- 是否命中正确资产；
- 是否是当前发布版本；
- 引用是否包含正确 chunk；
- source_checksum、chunk_checksum、canonicalizer_version 和 projection_run_id 是否匹配；
- 未授权资产是否完全不存在；
- 降级标志是否准确。

比较基准包括 R1 lexical、R2 semantic 和 R3 hybrid；不能只比较答案主观好看程度。

## 13. 实施计划

### R1：结构化 + PGroonga 全文

1. 定义按 resource_model 分组的 AuthorizedScope 和统一最终授权 SQL。
2. 为 filters 增加 field_schema 校验和受限 Query AST。
3. 创建 chunk-first 全文投影、引用坐标和 projection_runs。
4. 定义唯一的 `retrieval.projection_requested` payload 和 schema 校验。
5. 增加权限泄漏、撤权、发布替换、投影失败和中文命中测试。

R1 完成标准：

- 无语义依赖也能稳定运行；
- 发布/撤权结果即时正确；
- projection 可由 asset_version 全量重建；
- citation 可回源；
- 权限泄漏测试为 0。

### R2：embedding

1. 创建 retrieval.chunk_embeddings 和 retrieval.projection_configs，固定 chunker_version、embedding model_version、维度和 active projection generation。
2. projection worker 产生 chunk 并在同一 projection run 内编排 embedding job。
3. 增加向量召回能力，查询只使用 ready generation。
4. 增加 embedding provider 超时、重试、维度校验和死信。
5. 使用过滤后的 Recall@50 评测向量质量。

R2 完成标准：

- semantic mode 可独立开关；
- embedding provider 故障不影响 structured/fulltext；
- 任何向量结果都可回到当前发布 chunk；
- 模型升级可新建世代并回滚。

### R3：RRF + rerank

1. 完成 POST /api/open/v1/query 和 search_session cursor。
2. 全文和向量并行 Top 100；
3. RRF 合并 Top 50；
4. 使用本地 Docker BGE-Reranker 重排 Top 50；
5. Top 10 最终权限和 citation 复核；
6. 使用 search_session cursor，默认不计算全局 total；
7. reranker/vector 故障可降级；
8. 接入质量、权限和延迟仪表盘。

R3 完成标准：

- hybrid 结果优于单通道基线的 nDCG@10 或 MRR@10；
- citation_current_version_rate = 100%；
- permission_leakage_total = 0；
- 降级结果显式可见；
- 发布到可检索延迟达到约定 SLO。

任何降级都不能使用未经重新授权的缓存结果。

## 16. 安全审查清单

初期 BGE-Reranker 仅部署在内部网络，不开放公网入口，不配置云端 API Key；失败重试不得自动切换到外部 rerank 服务。

- API、Worker、embedding provider 和 reranker 使用最小网络权限。
- embedding provider 不接收 organization 以外的权限信息，不返回可直接对外的引用正文。
- QueryPlan、candidate 和 rerank 日志只记录 hash、ID、rank 和耗时。
- 所有 SQL 使用参数绑定。
- 所有结果在 final authorization 阶段重新检查当前发布指针。
- 新增表按 organization_id、asset_version_id 和 model_version 建索引。
- 模型、chunker、embedding 和 reranker 版本写入结果 metadata。
- 手工重建必须是受控运维操作，并记录审计。

## 17. 最终决策

R1-R3 的推荐组合是：

~~~text
PostgreSQL = 权威主数据、权限和最终复核
~~~
