# AgentChunzhi v2 阶段 1 实施方案

> 文档状态：实施基线  
> 适用范围：阶段 0 验收通过、首次共享部署前可随时重建的 v2 空库代码线  
> 目标读者：后端、测试、产品、架构与运维  
> 关联文档：[产品文档 v2](./产品文档-v2.md)、[阶段 0 实施方案](./产品文档-v2-阶段0实施方案.md)、[标签系统最终设计架构](./标签系统最终设计架构.md)

## 1. 文档结论

阶段 1 只解决一件事：让一个组织及其多个工作区可以被真实、安全地创建、登录、邀请和治理，为后续资产、标签、检索、Agent 和公开站点提供稳定的租户与权限边界。

阶段 1 完成后，系统必须具备以下闭环：

1. 运维可以创建组织和首位组织管理员。
2. 组织管理员可以通过邮件邀请新成员并预分配多个工作区角色；工作区管理员可以邀请普通成员进入自己管理的工作区。
3. 被邀请人可以一次性完成账号激活、设置密码并进入已授权工作区。
4. 已有组织成员可以被工作区管理员直接加入工作区，不再重复发邀请。
5. 用户可以用全局唯一邮箱登录、退出、查看并撤销自己的会话、修改或找回密码。
6. 组织管理员可以治理组织资料、成员状态、组织角色和工作区生命周期。
7. 工作区管理员可以治理工作区资料和成员，但不能越过组织边界。
8. 组织管理员没有隐式的工作区内容权限；需要查看内容时必须先获得显式 membership。
9. 所有治理写操作都在同一事务内写入业务数据、审计记录和领域事件。
10. 所有 HTTP 契约进入 OpenAPI，并有数据库、服务、权限和接口测试兜底。

阶段 1 不是现有 workspace API 的修补工程。当前代码中的重复邀请表、模糊成员标识、角色别名、直接 SQL handler 和进程内限流都会被目标模型替换，不保留旧接口、旧数据和兼容分支；旧 identity/workspace 路由只按 `docs/route-retirement-ledger.md` 在 v2 contract test 通过后删除，其他领域旧路由不由本阶段处理。

阶段 1 仍是首次共享部署前的开发检查点。所有最终 schema 直接折叠回阶段 0 的领域空库基线并重建数据库，不保留阶段 0 测试数据，不创建阶段追加迁移，也不得把本阶段结果部署到需要保留数据的共享环境。

## 2. 阶段边界

### 2.1 前置条件

开始阶段 1 前，阶段 0 必须已经满足其退出门槛，尤其包括：

- v2 使用干净空库基线，不再运行 v1 兼容迁移。
- 独立 migrator 和受限运行角色已经生效；API、worker 不执行迁移或 seed。
- `organization_role` 与 `workspace_members.role` 已分离。
- 工作区角色只剩 `admin`、`editor`、`reviewer`、`viewer`。
- Action 常量、`WorkspacePolicy`、事务、审计和 outbox 基础接口已经存在；阶段 1 在相同模式上补齐 `OrganizationPolicy`。
- `/api/v2` 路由骨架、统一错误体、游标分页、`Idempotency-Key` 和 `If-Match` 基础能力已经存在。
- `docs/route-retirement-ledger.md` 已建立；阶段 1 只负责 identity/workspace 所属旧路由，其他领域旧路由仍为 `planned`。
- 审核子系统已经收口为 `PublicationRequest`，`reviewer` 角色仍然存在。

阶段 1 不接受“先沿用 v1 表和路由，后续再清理”的实施方式。若阶段 0 尚未达到上述状态，应先完成阶段 0，而不是在阶段 1 中添加双轨代码。

### 2.2 阶段 1 包含

- 登录、登出、当前用户、会话管理。
- 密码修改、忘记密码、密码重置和跨实例认证限流。
- 组织资料、组织管理员和普通成员治理。
- 组织邀请、邀请邮件、账号激活。
- 工作区创建、修改、归档、恢复。
- 工作区成员授权、角色调整、退出和移除。
- 用户偏好中的默认工作区与时区。
- 组织与工作区治理审计、领域事件和通知投递基础。
- 对应的 OpenAPI、测试、bootstrap 和运维配置。

### 2.3 阶段 1 不包含

- 资产录入、版本编辑、附件上传和内容处理能力建设。
- 标签定义、标签挂载和标签治理界面。
- 全文检索、向量检索和问答。
- Agent 应用、MCP、API Key 管理扩展。
- 公开站点、博客主题、域名和 SEO。
- Web 前端页面；仓库当前只有 Go 后端，本阶段交付稳定 API，前端统一在阶段 6 实现。
- 公开注册、社交登录、SSO、SCIM、MFA。
- 部门、用户组以及计费、分成和收益能力。
- 一名用户跨多个组织切换。v2 当前模型是一名用户只属于一个组织。

## 3. 当前代码审计

本节描述的是阶段 0 实施前的实际仓库，用于说明阶段 1 为什么需要这些改造，不代表继续沿用其模型。

### 3.1 登录键与租户模型冲突

[当前 session 实现](../internal/auth/session.go)只按 `login_name` 查询用户，但数据库只保证 `(organization_id, login_name)` 唯一。在存在多个组织时，同名用户可能返回多行，登录行为不确定。

同时，当前认证只检查用户状态，没有把组织 `active/suspended` 状态纳入认证判断。被暂停组织中的已有 session 仍可能继续访问；API Key 认证也必须执行同一组织状态检查，不能因为是机器身份而绕过挂起。

阶段 1 必须改为：

- 成员使用规范化邮箱作为全局唯一登录键。
- 用户名不再承担认证含义；如保留，只作为可选公开 handle。
- 每次 session 和 API Key 认证同时验证用户/技术主体状态和 organization 状态；`organization.status != active` 时立即拒绝，即使凭证未过期。任何缓存的 Principal 都不得跨越组织状态 revision 使用。

### 3.2 会话能力不完整

当前 `identity.sessions` 只保存 token hash 和绝对过期时间：[认证代码](../internal/auth/session.go)没有空闲过期、会话列表、单会话撤销、密码修改后的全端下线和设备元数据。

[登录限流](../internal/httpapi/ratelimit.go)是单进程内存桶，多实例部署时无法形成统一约束；键值仍以旧 `login_name` 为中心。

[session 审计](../internal/auth/session_audit.go)和 workspace 审计采用异步 fire-and-forget 写入，进程退出或数据库瞬时失败时会丢失。治理类写操作不能继续采用这种方式。

### 3.3 邀请模型重复且不能真正交付

当前数据库同时存在 `organization.invitations` 和 `content.workspace_invitations`，职责重叠；运行代码实际只使用后者。

[当前邀请服务](../internal/workspace/final.go)存在四个关键问题：

1. 创建邀请时只保存 token hash，应用层拿不到原始 token，也没有邮件投递器，邀请无法送达。
2. 因用户表没有 email 字段，服务运行时查询 `information_schema`，再决定用 email 还是 `login_name` 匹配。
3. 接受邀请要求请求者已经登录并且已经属于同一组织，新成员无法通过邀请完成首次入驻。
4. `ON CONFLICT` 会直接覆盖既有 membership 的角色，使“接受邀请”同时承担“修改授权”的职责。

阶段 1 必须只保留一套组织邀请模型。工作区角色作为邀请附带的初始授权，而不是另一种邀请实体。

### 3.4 角色、成员标识与授权存在歧义

[当前 workspace policy](../internal/authz/workspace.go)仍包含 `owner`、`member` 和默认角色 fallback，与 v2 四角色模型不一致。

[当前 workspace 服务](../internal/workspace/final.go)允许成员接口同时把路径 ID 解释成 membership ID 或 user ID，并可通过 query 参数补 `workspace_id`。同一个 URL 因数据库现状不同而指向不同实体，不可作为稳定接口。

[当前 scope 计算](../internal/authz/scope.go)给予组织 admin 全部 ResourceModel，违反“组织治理权不等于工作区内容权”的 v2 原则。

当前移除和改角色逻辑也没有可靠保护最后一位组织管理员或最后一位工作区管理员，两个并发请求可以同时通过应用层检查。

### 3.5 handler、service 与 repository 边界混杂

[当前 workspace handler](../internal/httpapi/frontend_workspace_final.go)和[当前 identity handler](../internal/httpapi/frontend_identity_final.go)直接执行 SQL。workspace 逻辑又分散在 [service.go](../internal/workspace/service.go) 与 [final.go](../internal/workspace/final.go) 中，角色判断、事务和返回模型重复。

[当前路由](../internal/httpapi/router.go)集中注册 `/api/frontend`、`/api/me`、`/api/sessions` 等历史端点；现有 OpenAPI 没有覆盖实际组织与 workspace 行为。

阶段 1 必须让 handler 只完成协议适配，所有业务不变量进入 domain service，所有持久化进入 repository。

### 3.6 工作区列表与偏好模型不稳定

当前 workspace 列表通过相关子查询读取资产、容器和旧审核表计数，列表成本会随着内容量线性放大，而且仍依赖已废弃的 `asset.asset_reviews`。

当前 `content.member_preferences` 保存任意 JSON，偏好字段没有契约，也被放在了内容域。阶段 1 将偏好归入 identity 域，并只开放明确字段。

## 4. 阶段 1 最终领域模型

### 4.1 聚合边界

```text
Organization
├── OrganizationMember（由 User 表达）
├── OrganizationInvitation
│   └── InvitationWorkspaceGrant[]
└── Workspace[]
    └── WorkspaceMembership[]

Identity
├── User
├── Session[]
├── PasswordReset[]
└── UserPreference
```

边界规则：

- `Organization` 负责租户状态和治理权。
- `User` 是组织成员身份，一名成员只属于一个组织。
- `Workspace` 是内容权限边界，任何内容访问必须由显式 membership 或内容 visibility 规则授予。
- `OrganizationInvitation` 只负责创建一个新组织成员，可附带零到多个工作区初始角色。
- 已存在组织成员加入工作区时直接创建 membership，不创建 invitation。
- 用户、组织和工作区不做硬删除；使用状态迁移保留审计链。

产品映射保持一致：个人专家、专业创作者小团队和企业都使用 `Organization -> Workspace`，区别只是成员数和工作区数。单人起步也创建一个组织和一个显式 membership，使其后续可以直接邀请团队协作者；不建立 PersonalTenant、ExpertProfile 或 Department。个人品牌、作者 slug 和专家主页继续由后续 PublicSite 表达，阶段 1 不提前向 User 塞入公开站点字段。

### 4.2 Organization

字段：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 组织 ID |
| `slug` | 全局唯一、不可变 | URL 与运维识别符 |
| `name` | 1-100 字符 | 展示名称 |
| `status` | `active` / `suspended` | 组织状态 |
| `revision` | bigint，初始 1 | 乐观锁版本 |
| `created_at` / `updated_at` | timestamptz | 审计时间 |

状态规则：

- 只有 `active` 组织允许登录和业务访问。
- `suspended` 不删除数据，但所有成员 session 在鉴权时失效。
- 阶段 1 不提供普通 API 创建组织；使用运维 bootstrap 命令创建组织和首位管理员。
- 组织暂停/恢复属于平台运维动作，不混入组织管理员 API。

### 4.3 User

字段：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 用户 ID |
| `organization_id` | FK，必填 | 唯一所属组织 |
| `user_type` | `member` / `agent` | 人员与 Agent 主体区分 |
| `email` | member 必填，全局唯一 | 登录与通知地址，保存规范化值 |
| `display_name` | 1-80 字符 | 展示名称 |
| `password_hash` | member 必填 | Argon2id hash |
| `status` | `active` / `disabled` / `deleted` | 用户状态 |
| `organization_role` | member 为 `admin` / `member` | 组织治理角色 |
| `last_login_at` | 可空 | 最近成功登录时间 |
| `revision` | bigint | 乐观锁版本 |
| `created_at` / `updated_at` | timestamptz | 审计时间 |

邮箱规范化规则：

- 去除首尾空白并按 Unicode case fold 后转为小写。
- 不擅自删除 `+tag`，不修改 Gmail 点号，不做服务商特例。
- 数据库对规范化结果建立唯一索引。
- API 只返回规范化邮箱；原始输入不另存一份。

用户状态规则：

- `active` 可以登录。
- `disabled` 不能登录，已有 session 立即失效；membership 保留，便于恢复。
- `deleted` 是不可恢复的业务终态，但记录和审计仍保留；其邮箱不能自动释放复用。
- 阶段 1 的组织 API 只开放 `active <-> disabled`，不开放 deleted。

### 4.4 Session

字段：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 对外会话 ID |
| `user_id` | FK | 会话所有者 |
| `token_hash` | SHA-256，唯一 | 只保存 token hash |
| `created_at` | timestamptz | 创建时间 |
| `last_seen_at` | timestamptz | 最近活动时间 |
| `idle_expires_at` | timestamptz | 24 小时空闲过期 |
| `absolute_expires_at` | timestamptz | 7 天绝对过期 |
| `revoked_at` | 可空 | 撤销时间 |
| `ip_prefix` | 可空 | 截断后的 IP，用于用户识别会话 |
| `user_agent` | 最大 300 字符 | 设备描述来源 |

会话规则：

- token 使用 CSPRNG 生成 32 字节随机值，cookie 中只放原始 token，数据库只存 hash。
- 每次认证检查 session、user 和 organization 三层状态。
- `last_seen_at` 最多每 5 分钟更新一次，避免每个请求写库。
- 登出撤销当前 session；用户可以撤销自己的其他 session。
- 修改密码或重置密码后，撤销除当前修改密码会话外的全部 session；重置密码则撤销全部 session。
- cookie 为 `HttpOnly`、`SameSite=Lax`、path `/` 且不设置 Domain。生产使用 `Secure` 和 `__Host-agent_session`；本地开发使用独立的非 Secure 名称，不能由请求动态决定。
- 所有浏览器发起的非安全方法都必须校验受信 `Origin`，包括尚未认证但会设置 cookie 的登录和邀请接受；缺失或不匹配返回 `403 origin_not_allowed`。机器调用只进入 `/api/open/v2` 并使用 API Key，不绕过成员 API 的 Origin 规则。
- `/api/v2` 成员 API 只接受 session cookie，不接受 member Bearer token；本阶段不签发成员 access token。`/api/open/v2` 只接受技术身份 API Key，两类凭证不得跨入口复用。

### 4.5 AuthRateLimit

认证限流使用 PostgreSQL 共享状态，不保留单进程内存桶，也不在阶段 1 同时支持第二种实现。

`security.auth_rate_limits` 字段：

| 字段 | 说明 |
| --- | --- |
| `bucket_type` | `login_email`、`login_ip`、`password_reset_email`、`password_reset_ip`、`invitation_ip` |
| `key_hash` | 对规范化 email 或 IP 前缀做 HMAC-SHA-256 |
| `window_started_at` | 窗口起点 |
| `attempt_count` | 当前窗口次数 |
| `blocked_until` | 可空；封禁截止时间 |
| `updated_at` | 更新时间 |
| 主键 | `(bucket_type, key_hash)` |

计数通过单条 UPSERT 原子更新，多实例共享同一结果。默认策略为：登录每 email 每 15 分钟最多 5 次失败、每 IP 前缀最多 30 次；密码重置每 email 每小时最多 3 次、每 IP 前缀最多 20 次；邀请 token 接口每 IP 前缀每 15 分钟最多 20 次失败。成功登录清除 email bucket，但不清除 IP bucket。

客户端 IP 只在直连时读取 RemoteAddr；只有 RemoteAddr 命中 `TRUSTED_PROXY_CIDRS` 时才解析标准转发头。IPv4 使用 `/24`、IPv6 使用 `/56` 前缀，再以 `RATE_LIMIT_HMAC_KEY` 做 HMAC；原始 email 和 IP 不进入限流表。密钥由 secret manager 提供。

### 4.6 PasswordReset

只保存一次性 token 的 hash：

| 字段 | 约束 |
| --- | --- |
| `id` | UUID PK |
| `user_id` | FK |
| `token_hash` | SHA-256，唯一 |
| `expires_at` | 创建后 30 分钟 |
| `consumed_at` | 可空 |
| `created_at` | timestamptz |

同一用户申请新 token 时，使之前未消费 token 失效。申请接口无论邮箱是否存在都返回 `202`，避免枚举用户。

### 4.7 OrganizationInvitation

最终表名为 `organization.member_invitations`，工作区授权明细表为 `organization.invitation_workspace_grants`。

字段：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 邀请 ID |
| `organization_id` | FK | 目标组织 |
| `email` | 规范化、必填 | 新成员邮箱 |
| `display_name` | 可空 | 邀请人预填名称 |
| `organization_role` | `admin` / `member` | 初始组织角色 |
| `authority_scope` | `organization` / `workspace` | 创建邀请时的治理范围 |
| `scope_workspace_id` | workspace scope 必填 | 限定 workspace admin 后续查看和操作范围 |
| `token_hash` | SHA-256，唯一 | 原始 token 不落库 |
| `status` | `pending` / `accepted` / `revoked` / `expired` | 状态 |
| `expires_at` | 默认 7 天 | 过期时间 |
| `invited_by` | FK user | 邀请人 |
| `accepted_by` | 可空 FK user | 接受后生成的用户 |
| `accepted_at` / `revoked_at` | 可空 | 状态时间 |
| `revision` | bigint | 重发、撤销的乐观锁版本 |
| `created_at` / `updated_at` | timestamptz | 审计时间 |

约束：

- 同一邮箱在全系统最多有一个 `pending` 邀请。因为一名用户只属于一个组织，不能允许两个组织同时发出最终只能有一个成功的邀请。
- 创建新邀请时若命中已经过期但尚未清理的 pending 记录，事务先将旧记录标记为 `expired`，再创建新邀请；不能让清理任务是否及时运行影响正常邀请。
- 邮箱已经存在于 `identity.users` 时不能创建组织邀请；已有成员应走 workspace grant。
- 组织 admin 可邀请 `admin/member`，并附带任意同组织工作区 grants。
- workspace admin 也可以创建同一个聚合，但邀请固定为 `authority_scope=workspace`、`organization_role=member`，只能附带 `scope_workspace_id` 对应的一个 grant，不能借邀请获得组织治理权。
- workspace admin 只能查看、重发或撤销自己当前管理工作区 scope 的邀请；组织 admin 可以治理组织内全部邀请。
- token 只能接受一次；resolve 接口不得返回 token hash、组织内部信息或 workspace ID。
- resend 使旧 token 立即失效，生成新 token 并更新过期时间。
- revoke、resend、accept 都必须锁定 invitation 行后判断状态。

`organization.invitation_workspace_grants` 字段：

| 字段 | 约束 |
| --- | --- |
| `invitation_id` | FK |
| `workspace_id` | FK，必须同组织 |
| `role` | `admin` / `editor` / `reviewer` / `viewer` |
| 主键 | `(invitation_id, workspace_id)` |

邀请接受事务中创建 User，并按 grants 创建 memberships。任何一个 grant 失效或跨组织时整个事务失败，不产生半激活用户。

### 4.8 Workspace

字段：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 工作区 ID |
| `organization_id` | FK | 所属组织 |
| `slug` | 组织内唯一、不可变 | 稳定标识 |
| `name` | 1-100 字符 | 名称 |
| `description` | 最大 1000 字符 | 描述 |
| `status` | `active` / `archived` | 生命周期 |
| `revision` | bigint | 乐观锁版本 |
| `created_by` | FK user | 创建人 |
| `archived_at` / `archived_by` | 可空 | 归档信息 |
| `created_at` / `updated_at` | timestamptz | 审计时间 |

规则：

- 只有组织管理员可以创建工作区。
- 创建者同时获得该工作区 `admin` membership；这仍是显式授权，不是组织 admin 的隐式内容权限。
- 工作区 admin 可以修改名称和描述。
- 组织 admin 可以归档或恢复工作区；workspace admin 不能改变生命周期。
- 归档后拒绝所有内容写操作、workspace admin 的成员变更和 workspace scope 邀请，但允许已有成员只读查看元数据；organization admin 仍可通过组织治理路由调整显式 membership，为恢复做准备。
- 归档工作区立即从所有内容出口消失：workspace 内容 API、organization published 查询、Agent、OpenAPI 和 PublicSite 的 scope compiler/final authorizer 都必须要求 `workspace.status=active`。归档不改写 Asset 状态和 published pointer；恢复后内容按原有 visibility/policy 重新可见，不需要重新发布。
- 归档事务撤销该 workspace scope 下的 pending invitations、取消其未发送邮件并清空成员的默认工作区。organization scope invitation 中的 grant 保留，接受后可以形成 archived workspace membership。
- 恢复前必须至少有一名 active user 的 admin membership；恢复不自动恢复旧默认工作区。
- 不提供 DELETE API。需要永久清除时由独立的数据保留策略处理，不属于阶段 1。

阶段 0 中 visibility 是内容实体的发布可见性，不应再作为 workspace settings。当前 workspace 的 `private/internal/public` 设置从目标模型移除。

### 4.9 WorkspaceMembership

最终表名为 `content.workspace_members`。

字段：

| 字段 | 约束 |
| --- | --- |
| `id` | UUID PK，唯一对外成员关系 ID |
| `organization_id` | FK；用于复合外键锁定租户边界 |
| `workspace_id` | FK |
| `user_id` | FK |
| `role` | `admin` / `editor` / `reviewer` / `viewer` |
| `granted_by` | FK user |
| `revision` | bigint |
| `created_at` / `updated_at` | timestamptz |
| 唯一约束 | `(workspace_id, user_id)` |

规则：

- user 与 workspace 必须属于同一 organization，由 service 校验，并由 `organization_id + workspace_id/user_id` 两组复合外键兜底。
- 所有成员接口使用 membership ID；查找用户时使用显式 `user_id` 字段，不允许一个路径参数兼容两类 ID。
- active workspace 至少保留一名 active user 的 workspace admin；archived workspace 由 organization admin 治理，可暂时没有 active admin，但恢复前必须补齐。
- 成员可以主动退出，但 active workspace 的最后一名 active admin 不能退出。
- workspace admin 可添加同组织 active 成员、调整角色和移除成员。
- workspace admin 不能通过成员删除接口移除自己，必须调用显式 `leave` command；organization admin 的治理接口可以撤销自己的 membership，但仍受 active workspace 最后一位 admin 约束。
- 组织 admin 即使不是 workspace member，也可通过独立的组织治理接口授予或撤销 membership；进入内容 API 前仍需自己的 membership。

### 4.10 UserPreference

替换当前任意 JSON：

| 字段 | 约束 |
| --- | --- |
| `user_id` | PK/FK |
| `default_workspace_id` | 可空；必须是自己在 active workspace 中的 membership |
| `timezone` | IANA timezone，默认 `UTC` |
| `email_notifications_enabled` | boolean，默认 true |
| `revision` | bigint |
| `updated_at` | timestamptz |

成员失去默认工作区 membership，或对应工作区被归档时，同一事务将 `default_workspace_id` 置空；恢复工作区不自动恢复旧偏好。`email_notifications_enabled` 只控制普通业务通知，不能关闭邀请、密码重置和账号安全邮件。

## 5. 权限模型

### 5.1 Principal

成员请求认证后构造不可变 `MemberPrincipal`：

```text
user_id
organization_id
user_type=member
organization_role=admin|member
session_id
```

workspace role 不写进全局 Principal，也不从客户端 claim 接收。`WorkspacePolicy` 按目标 workspace 查询 membership 后判断动作，因此同一用户在不同工作区可以有不同角色。`allowed_actions` 也调用同一个 policy evaluator 生成，不能在 DTO mapper 中维护第二份角色矩阵。

Agent Principal 不含 organization role 和 member session；它继续由阶段 0 的 AgentAccessPolicy 处理，不能进入本阶段的组织成员治理接口。

### 5.2 Action 目录

阶段 1 使用阶段 0 已冻结的动作常量：

```text
organization.read
organization.manage
organization.member.read
organization.member.manage
organization.invitation.manage
workspace.read
workspace.manage
workspace.create
workspace.archive
workspace.restore
audit.read
```

不得在 handler、SQL 或 service 中直接比较字符串角色。所有入口先构造 `Principal`，再调用 `OrganizationPolicy.Authorize` 或 `WorkspacePolicy.Authorize`。

### 5.3 组织权限矩阵

| 动作 | Organization admin | Organization member |
| --- | --- | --- |
| 读取组织基本资料 | 允许 | 允许 |
| 修改组织名称 | 允许 | 拒绝 |
| 读取完整组织成员目录 | 允许 | 拒绝 |
| 邀请新成员 | 允许 | 拒绝 |
| 修改组织角色和状态 | 允许 | 拒绝 |
| 创建、归档、恢复工作区 | 允许 | 拒绝 |
| 读取组织治理审计 | 允许 | 拒绝 |
| 读取任意工作区内容 | 仅有 membership 时 | 仅有 membership 时 |

workspace admin 通过当前工作区下的 eligible-members 接口查找可加入成员。该接口由 `WorkspacePolicy(workspace.manage)` 授权，只返回同组织 active 且尚未加入当前工作区的 `user_id`、`display_name` 和 masked email；不返回完整邮箱、组织角色、会话或审计信息。

### 5.4 工作区权限矩阵

| 动作 | Workspace admin | editor | reviewer | viewer |
| --- | --- | --- | --- | --- |
| 读取工作区元数据 | 允许 | 允许 | 允许 | 允许 |
| 修改工作区名称和描述 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 读取成员列表 | 允许 | 允许 | 允许 | 允许 |
| 添加、改角色、移除成员 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 邀请新成员进入当前工作区 | 允许；只能创建普通组织成员 | 拒绝 | 拒绝 | 拒绝 |
| 主动退出 | 非最后 admin 时允许 | 允许 | 允许 | 允许 |
| 内容权限 | 按阶段 0 矩阵 | 按阶段 0 矩阵 | 按阶段 0 矩阵 | 按阶段 0 矩阵 |

组织治理接口和工作区内容接口使用不同 policy。不得用 `organization_role == admin` 给 `WorkspacePolicy` 设置通配权限。

### 5.5 最后一位管理员并发保护

仅在 service 中先 count 再 update 不足以防止并发降权。阶段 1 固定采用父实体行锁：所有角色、状态和 membership 变更先锁 Organization；涉及工作区时，再按 workspace UUID 升序锁定对应 Workspace，随后重新统计 active admin，再执行变更。全系统只允许 `Organization -> Workspace` 这一种锁顺序。

admin 计数只包含 `users.status=active` 的显式 membership。禁用一个用户前，service 必须找出他担任 workspace admin 的全部 active 工作区并按序加锁；任一 active 工作区没有另一名 active admin 时，整个禁用事务失败。这样，用户禁用与 membership 降权/移除并发时也不能共同绕过不变量。

该方案便于稳定返回 `last_organization_admin_required` 或 `last_workspace_admin_required`，不再同时设计 deferred trigger 方案。

## 6. 核心业务流程

### 6.1 创建初始组织

```text
operator CLI
  -> validate slug/email/password
  -> transaction
     -> create Organization(active)
     -> create User(active, organization_role=admin)
     -> append audit
     -> append outbox event
  -> print IDs, never print password/hash
```

[当前 bootstrap](../cmd/bootstrap/main.go)使用 `ADMIN_LOGIN`。阶段 1 改为显式子命令，例如：

```text
agentchunzhi bootstrap organization \
  --slug acme \
  --name "Acme" \
  --admin-email admin@example.com \
  --admin-name "Admin"
```

密码通过安全交互输入或只读文件描述符传入，不放在命令参数和普通日志中。相同 slug 或 email 重复执行应失败，不做隐式 upsert。

### 6.2 邀请新组织成员

```text
Organization admin or Workspace admin
  -> POST invitation + authorized workspace grants
  -> validate email is not an existing user
  -> validate every workspace belongs to organization
  -> workspace admin additionally constrained to member + current workspace
  -> transaction
     -> create invitation with token_hash
     -> create workspace grants
     -> create encrypted email delivery
     -> append audit + outbox event
  -> worker sends activation link
```

原始 token 只存在于事务内存和加密投递 payload 中。事件 payload 只携带 `delivery_id`，不能携带 token。

### 6.3 接受邀请

```text
Anonymous user
  -> resolve token, receive organization name + masked email + expiry
  -> submit token + display_name + password
  -> read token hash only to locate organization and grants
  -> transaction
     -> lock Organization, granted Workspaces in UUID order, then Invitation FOR UPDATE
     -> re-read and verify pending/not expired/token hash/grants
     -> create active User
     -> create all WorkspaceMembership rows
     -> mark invitation accepted
     -> append audit + outbox event
  -> create session in a second transaction
  -> return current user and workspace list
```

用户和 memberships 必须原子创建。session 创建失败不回滚已经完成的账号激活，客户端可直接登录。

### 6.4 添加已有成员到工作区

```text
Workspace admin
  -> search current workspace eligible members
  -> POST /workspaces/{workspaceId}/members { user_id, role }
  -> lock workspace
  -> verify same organization, active user, active workspace
  -> insert membership
  -> audit + event in same transaction
```

若 membership 已存在，返回 `409 membership_exists`，不把创建接口变成隐式角色更新。

### 6.5 禁用组织成员

同一事务必须：

1. 锁定 organization，保护最后一位 active organization admin。
2. 查询该用户担任 admin 的 active 工作区，按 UUID 升序加锁，并保证每个工作区仍有另一名 active admin。
3. 将 user 状态改为 `disabled` 并增加 revision。
4. 撤销该用户所有 session。
5. 清空其默认工作区。
6. 保留所有 workspace memberships。
7. 写入审计和 outbox event。

恢复用户只恢复登录资格，不自动改变原有 memberships。

### 6.6 修改或重置密码

修改密码需要当前密码。成功后保留当前 session，撤销其他 session。

忘记密码流程先写入 password reset 和加密邮件投递，再异步发送。重置成功后消费 token、更新密码并撤销全部 session。旧密码 hash、原始 token和完整 email 都不能进入日志或事件。

## 7. 邮件投递模型

阶段 1 同时需要邀请与密码重置邮件，不能让 domain service 直接调用 SMTP，否则数据库提交与邮件发送无法保证一致。

新增 `notification.email_deliveries`：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID PK |
| `organization_id` | 必填；邀请和有效的密码重置都属于确定组织 |
| `template` | `organization_invitation` / `password_reset` |
| `recipient_email` | 规范化邮箱 |
| `key_version` | 加密密钥版本 |
| `encrypted_payload` | 使用应用投递密钥加密的短期敏感参数 |
| `status` | `pending` / `sending` / `sent` / `failed` / `cancelled` |
| `attempt_count` | 重试次数 |
| `next_attempt_at` | 下次重试时间 |
| `locked_by` / `locked_until` | worker 租约，可回收崩溃任务 |
| `sent_at` | 可空 |
| `provider_message_id` | 可空；供应商回执 ID |
| `last_error_code` | 分类错误，不保存供应商完整响应 |
| `created_at` / `updated_at` | 时间 |

要求：

- payload 使用 AES-256-GCM、随机 nonce，并把 delivery ID 与 template 作为 associated data；`EMAIL_DELIVERY_KEYS` key ring 由 secret manager 提供，不写入仓库或数据库，当前写入版本单独配置。
- worker 在短事务中使用 `FOR UPDATE SKIP LOCKED` 领取任务、写入租约后立即提交，再调用外部邮件服务，最后用 `locked_by` 条件更新结果；禁止持有数据库事务调用 SMTP/API。进程崩溃后其他 worker 可回收过期租约。失败指数退避，最多 8 次。
- 发送成功、取消或达到最大失败次数进入终态后立即清空 `encrypted_payload`；只有仍会重试的 delivery 保留密文。
- 轮换密钥时旧版本必须保留到对应 pending/sending delivery 为零；不得因删除旧 key 让合法任务永久不可解密。
- invitation 被 revoke/resend 时取消对应未发送 delivery。
- 邮件链接只由配置项 `PUBLIC_APP_BASE_URL` 生成，不能信任请求 Host。
- SMTP/API provider 通过 `Mailer` 接口适配，以 delivery ID 作为供应商幂等键；无法提供幂等能力的供应商按至少一次投递处理，一次性 token 保证重复邮件不会重复激活。本地开发使用 capture mailer，将邮件写入受控测试邮箱服务，不打印 token 到普通日志。

### 7.1 必需运行配置

| 配置 | 规则 |
| --- | --- |
| `APP_ENV` | `development/test/production`；production 强制安全 cookie 和 HTTPS base URL |
| `MEMBER_ALLOWED_ORIGINS` | 成员 Web 客户端 Origin 精确列表，不支持 `*` |
| `TRUSTED_PROXY_CIDRS` | 可为空；只有可信代理可提供客户端 IP 转发头 |
| `PUBLIC_APP_BASE_URL` | 邀请和密码重置链接唯一基准；production 必须为 HTTPS |
| `RATE_LIMIT_HMAC_KEY` | 至少 32 bytes，由 secret manager 注入 |
| `EMAIL_DELIVERY_KEYS` | 版本化 AES-256 key ring，由 secret manager 注入 |
| `EMAIL_DELIVERY_CURRENT_KEY_VERSION` | 新 delivery 使用的 key 版本 |
| `MAILER_PROVIDER` | `smtp` 或仅限非生产的 `capture` |
| `MAIL_FROM` | 固定发件人 |
| `SMTP_HOST/PORT/USERNAME/PASSWORD` | SMTP provider 配置；密码只从 secret 注入 |

production 中任一必需项无效时进程启动失败；不能自动降级为不安全 cookie、任意 Origin、请求 Host 生成链接或日志打印邮件。

## 8. HTTP API 契约

### 8.1 全局规则

- 统一前缀 `/api/v2`；邀请 resolve/accept 和密码重置使用 `/api/public/v2`。
- 所有响应使用阶段 0 定义的统一 data/error envelope。
- 所有列表使用 cursor pagination，默认 20，最大 100。
- 所有资源响应提供 `ETag: "<revision>"`。
- PATCH、角色修改、状态修改必须携带 `If-Match`；缺失返回 `428 precondition_required`，版本不符返回 `412 revision_mismatch`。
- 创建、邀请、邀请接受、resend、密码重置完成、归档、恢复和 membership command 必须携带 `Idempotency-Key`；缺失返回 `428 idempotency_key_required`。
- 业务冲突返回稳定错误码，不把数据库 constraint 名直接暴露给客户端。
- handler 不接受 organization_id 作为普通 body 参数；租户从 authenticated principal 和父资源解析。

## 9. 数据库实施方案

### 9.1 空库基线策略

阶段 1 只面向阶段 0 生成的 v2 空库，不写 v1 数据转换、旧列回填、双写或兼容 view。

阶段 1 直接改写阶段 0 的 `0002_organization_identity.sql`、`0003_workspace.sql`、`0011_audit_eventing.sql` 等领域基线并重建数据库；不创建 `0013/0014/0015` 阶段追加迁移。最终 schema 只能有一套 invitation 和一套 membership 定义。独立 migrator 使用 `DATABASE_MIGRATION_URL`；API、worker 使用受限 `DATABASE_URL` 且不解析 migration/seed 文件。

### 9.2 删除的目标对象

- 删除 `content.workspace_invitations` 和旧 `organization.invitations`，只创建 `organization.member_invitations` 与 `organization.invitation_workspace_grants`。
- 删除 `content.member_preferences`，改为 `identity.user_preferences`。
- 删除 workspace settings 中旧 visibility 字段和 revisions 表；workspace revision 直接覆盖名称、描述和状态并发控制。
- 不创建 department、group、workspace owner、workspace member 等兼容结构。

### 9.3 数据库必须保证的不变量

- member email 全局唯一。
- organization slug 全局唯一；workspace slug 组织内唯一。
- invitation token hash、session token hash、password reset token hash 唯一。
- 全局同一 email 只能有一个 pending invitation。
- membership `(workspace_id, user_id)` 唯一。
- invitation grant `(invitation_id, workspace_id)` 唯一。
- invitation grant、membership 两端组织一致。
- invitation 的 `authority_scope/scope_workspace_id/organization_role` 组合由 CHECK 保证：workspace scope 必须指向 workspace 且只能创建普通组织成员，organization scope 的 scope workspace 必须为空。
- revision 单调递增。
- 枚举字段使用 CHECK 或 PostgreSQL enum，不能接受未知角色和状态。
- email delivery 状态迁移与 attempt_count 合法。

跨组织一致性统一使用冗余 `organization_id`、父表 `(id, organization_id)` 唯一键和复合外键表达。`workspace_members` 分别以 `(workspace_id, organization_id)` 和 `(user_id, organization_id)` 引用父表；invitation grants 同样复合引用 invitation 与 workspace。阶段 1 不为这些关系引入 constraint trigger，也不把租户边界只留在 Go 代码中。

### 9.4 索引

至少包括：

```text
identity.users(email)
identity.users(organization_id, status, created_at, id)
identity.sessions(user_id, revoked_at, absolute_expires_at)
organization.member_invitations(organization_id, status, created_at, id)
UNIQUE organization.member_invitations(email) WHERE status = 'pending'
organization.member_invitations(token_hash)
content.workspace_members(user_id, workspace_id)
content.workspace_members(workspace_id, role, id)
content.workspaces(organization_id, status, created_at, id)
identity.password_resets(token_hash)
security.auth_rate_limits(bucket_type, key_hash)
notification.email_deliveries(status, next_attempt_at, id)
```

所有 cursor 查询的索引必须包含排序字段和 ID tie-breaker。

## 10. 事务、审计与事件

### 10.1 事务规则

治理事务统一锁序为：`Organization -> Workspace(s，UUID 升序) -> Invitation/User/Membership`。事务外可以做只读定位，但任何状态判断都必须在拿锁后重新读取。密码修改只锁 User/Session，邮件 worker 只锁 EmailDelivery；它们不得持有这些行后反向请求 Organization 或 Workspace 锁。

下列操作必须在同一数据库事务中完成业务写入、审计 append 和 outbox append：

- 组织资料修改。
- 邀请创建、重发、撤销和接受。
- 成员组织角色或状态变更。
- 工作区创建、修改、归档和恢复。
- membership 创建、改角色、删除和主动退出。
- 成功登录时的 session、last_login_at 和安全审计，以及 session 撤销。
- 密码修改、密码重置申请和密码重置完成；有效账号的重置申请同时写 reset token 与 email delivery。

不允许 transaction commit 后调用 goroutine 补审计。`store.AppendAudit` 应提供接受 `DBTX`/`Tx` 的版本，event store 继续复用阶段 0 的 `AppendTx`。

登录失败属于无业务事务事件，可同步写入安全日志或专用 login attempt 表；不能因为审计写失败而泄露不同登录响应。

### 10.2 审计事件

```text
organization.updated
organization.member.invited
organization.member.activated
organization.member.role_changed
organization.member.disabled
organization.member.enabled
organization.invitation.resent
organization.invitation.revoked
workspace.created
workspace.updated
workspace.archived
workspace.restored
workspace.member.granted
workspace.member.role_changed
workspace.member.revoked
workspace.member.left
identity.password.changed
identity.password.reset
identity.session.revoked
```

审计 payload 保存 actor、target、旧值摘要、新值摘要、request_id 和 reason；不得保存密码、session token、invitation token、reset token、加密 payload 或完整邮件正文。

### 10.3 领域事件

事件名采用过去式：

```text
organization.updated
organization.member_invited
organization.member_activated
organization.invitation_resent
organization.invitation_revoked
organization.member_role_changed
organization.member_status_changed
workspace.created
workspace.updated
workspace.archived
workspace.restored
workspace.membership_changed
identity.password_changed
```

事件名只表达已经发生的业务事实，不带 `.v1` 后缀；payload 使用阶段 0 约定的 `payload_version` 演进。邮件投递由事务内 `email_deliveries` 任务表驱动，不额外发布 `notification.*_requested` 事件。

事件 envelope 必须包含阶段 0 已冻结的 `event_id`、`occurred_at`、`organization_id`、`workspace_id`（适用时）、`aggregate_type`、`aggregate_id`、`aggregate_version`、`payload_version` 和 actor 描述。actor 使用 `{type, id?}` 表达 member、invite、password_reset 或 system，不伪造匿名 user ID。`workspace.membership_changed` 通过 `operation=granted/role_changed/revoked/left` 与 old/new role 表达具体事实。敏感 token 永远不进入 outbox；不得同时增加 `schema_version`。

关键 payload：

| 事件 | payload，不含通用 envelope |
| --- | --- |
| `organization.member_invited` | `invitation_id`, `authority_scope`, `scope_workspace_id`；不含 email |
| `organization.member_activated` | `invitation_id`, `user_id`, `workspace_ids` |
| `organization.invitation_resent/revoked` | `invitation_id`, `authority_scope`, `scope_workspace_id` |
| `organization.member_role_changed` | `user_id`, `old_role`, `new_role` |
| `organization.member_status_changed` | `user_id`, `old_status`, `new_status` |
| `workspace.created/updated/archived/restored` | `workspace_id`, `changed_fields`（适用时） |
| `workspace.membership_changed` | `workspace_id`, `membership_id`, `user_id`, `operation`, `old_role`, `new_role` |
| `identity.password_changed` | `user_id`, `method=change/reset`, `revoked_session_count` |

## 13. 测试方案

### 13.1 单元测试

- email 规范化和校验。
- 密码策略与 Argon2id verify。
- session idle/absolute expiry。
- invitation 与 password reset 状态机。
- OrganizationPolicy 与 WorkspacePolicy 全动作矩阵。

权限矩阵使用 table-driven tests，要求每个 Action 对每种角色都有显式断言，未知角色一律 deny。

### 13.2 PostgreSQL 集成测试

- 全局 email 唯一。
- 跨组织 invitation grant 和 membership 失败。
- pending invitation 部分唯一索引。
- 同一 invitation token 并发 accept 只有一个提交。
- 两个请求并发降级/移除 admin 时至少一个收到 `last_*_admin_required`。
- 用户禁用与其 workspace admin membership 的并发降权/移除不能共同留下零名 active admin，且锁顺序无死锁。
- membership 删除同步清空默认工作区。
- 禁用 user 同步撤销 sessions。
- suspended organization 下 session 和 API Key 均被拒绝；恢复组织前不得通过缓存 Principal 访问。
- 归档 workspace 撤销其 workspace scope pending invitations、取消未发送 delivery 并清空相关默认工作区。
- 归档 workspace 后，workspace/organization/Agent/OpenAPI/PublicSite 的任何内容读取均为空或 404；恢复后原 published 内容重新可见，Asset pointer 未被改写。
- archived workspace 没有 active admin 时不能恢复；组织治理路由补齐 admin 后可以恢复。
- 业务写、audit、outbox 任一失败时全部回滚。
- email worker 多实例 `SKIP LOCKED` 不重复领取。

集成测试必须使用真实 PostgreSQL，不用 SQLite 模拟约束和行锁。

### 13.3 服务集成测试

至少覆盖：

```text
bootstrap -> login -> create workspace
invite with grants -> resolve -> accept -> login -> list workspaces
existing member -> direct workspace grant -> role change -> revoke
disable member -> old session rejected -> enable -> login succeeds
forgot password -> delivery -> complete -> old sessions rejected
archive workspace -> writes rejected -> restore -> writes allowed
org admin without membership -> content denied -> self grant -> content allowed
```

### 13.4 HTTP 契约测试

- cookie 属性与生产/开发名称。
- unsafe method 的 Origin 校验。
- Idempotency-Key 重放返回相同结果，body 不同返回 conflict。
- If-Match 缺失 428、冲突 412。
- cursor 稳定性和最大 page size。
- public resolve 不泄露内部 ID。
- login/password reset 不可枚举用户。
- membership 路径不能用 user ID 冒充 membership ID。
- 阶段 1 路由退役台账中的 identity/workspace 旧路由为 404；tag、import/export、query 等由后续阶段负责的旧路由不作为本阶段 404 门槛。

### 13.5 安全测试

- 暴力登录和密码重置限流跨实例有效。
- token 至少 256 bit entropy，DB 只存 hash。
- token、密码、cookie、encrypted payload 不进入日志、审计和事件。
- suspended organization 无法复用旧 session。
- CSRF Origin policy 覆盖全部 cookie 写接口。
- 邀请 URL 只使用可信 base URL。
- SQL 查询都带明确组织边界或通过已校验父资源执行。

### 13.6 建议验证命令

```text
go test ./internal/auth/... ./internal/authz/...
go test ./internal/identity/... ./internal/organization/... ./internal/workspace/...
go test ./internal/notification/... ./internal/httpapi/...
go test -race ./internal/...
go test ./...
go vet ./...
```

数据库集成测试命令按阶段 0 固定的 testcontainer/测试数据库入口执行；CI 不允许自动跳过。

## 14. 实施顺序与提交边界

依赖顺序：

```text
S1-1 Identity/auth
  ├── S1-2 Organization
  │     └── S1-3 Invitation
  │            └── S1-4 Mail/password reset
  └── S1-5 Workspace/membership
         └── S1-6 Profile/activity

S1-2..S1-6 -> S1-7 HTTP/OpenAPI -> S1-8 Ops -> S1-9 Cleanup
```

推荐提交边界：

1. 最终 schema、模型和 repository，不开放未完成路由。
2. auth/session/password 与 policy。
3. organization/member service。
4. invitation、delivery、password reset。
5. workspace/membership service。
6. v2 handler、OpenAPI 和 middleware。
7. bootstrap、metrics、cleanup jobs。
8. 删除旧 runtime，并完成全量回归。

每个提交都必须编译通过。不得在主分支同时暴露新旧两套可写 API；新 v2 route 只在完整 service 和 OpenAPI 就绪时注册。

## 15. 阶段 1 退出门槛

以下条件全部满足才算完成：

### 模型

- 只有一套组织邀请模型，没有 workspace invitation 旁路。
- member email 是全局唯一登录键，`login_name` 不再参与认证。
- 组织角色与 workspace 四角色严格分层。
- 工作区成员关系使用唯一 membership ID。
- 不存在 department、group、owner、member 角色兼容层。

### 行为

- 新成员可从邀请邮件独立完成首次激活。
- 已有成员可被直接授权到工作区。
- 最后一位组织/workspace admin 在并发下仍受保护。
- 用户、组织或 session 失效后不能继续访问。
- 密码重置和会话撤销闭环可用。
- 组织 admin 无隐式 workspace 内容权限。

### 一致性与安全

- 所有治理写操作的业务数据、审计和 outbox 原子提交。
- token、密码和敏感投递 payload 不出现在日志、审计、事件和普通查询结果中。
- cookie、Origin、限流、幂等和乐观锁契约经过 HTTP 测试。
- 成员 `/api/v2` 只接受 session cookie；member Bearer 与 API Key 进入成员路由均被拒绝。
- 数据库约束能够拒绝跨组织关系和重复活动实体。

### 工程

- `/api/v2` 实际路由与 OpenAPI 一致。
- handler 零直接 SQL，service 零 HTTP 类型，repository 零角色决策。
- 阶段 1 台账中的旧 session/me、identity/workspace 路由和旧邀请实现已删除；阶段 2/3/4-6 负责的旧路由仍按各自台账推进。
- `go test ./...`、race tests、PostgreSQL integration tests、OpenAPI lint 全部通过。
- 阶段 2 可以只依赖 `Principal + WorkspacePolicy + membership` 开始标签领域，不需要再修改身份和租户模型。

## 16. 工期估算与主要风险

按一名熟悉当前仓库的后端工程师估算：

| 工作 | 预计工程日 |
| --- | ---: |
| Identity/auth/session/password | 3-4 |
| Organization/member/policy | 2-3 |
| Invitation/email/password reset | 3-4 |
| Workspace/membership | 2-3 |
| HTTP/OpenAPI/bootstrap/observability | 2-3 |
| 集成、安全、并发测试与清理 | 3-4 |
| 合计 | 15-21 |

主要风险不是 CRUD 数量，而是：

1. 邀请 token 的可靠而不泄露的交付。
2. 最后一位管理员和 invitation accept 的并发一致性。
3. 从组织治理权中彻底移除隐式内容权限。
4. 一次性删除当前分散的 direct SQL 和旧路由后，确保 OpenAPI 与运行态一致。

这些风险必须通过事务、数据库约束和真实 PostgreSQL 并发测试解决，不能依赖人工测试或代码约定。

## 17. 最终交付物

阶段 1 的交付物是：

- 最终 identity、organization、workspace、invitation 和 notification schema。
- 可运行的组织 bootstrap 命令。
- 完整的登录、会话、密码恢复和邀请激活能力。
- 组织与工作区治理 service、policy 和 repository。
- `/api/v2` OpenAPI 与实现。
- 事务审计、outbox 事件和可靠邮件投递 worker。
- 单元、数据库、服务、HTTP、并发与安全测试。
- 删除旧 invitation、旧角色、旧路由和 direct SQL handler 后的干净代码树。

阶段 1 的最终判定标准不是“接口已经写完”，而是：一个新组织从 bootstrap 开始，能够安全邀请一个从未注册的成员，把他加入一个工作区，并在权限变更、禁用、归档和密码恢复后始终保持租户隔离、事务一致和完整审计。
