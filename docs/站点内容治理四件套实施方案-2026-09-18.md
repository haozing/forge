## 0. 定位原则与既有对应物（已代码核实，防重复建设）

原则：**不新建平行设施，全部挂在既有承重墙上**。llm_wiki 是单机单用户桌面应用，我们是多租户服务端，借鉴机制不借鉴形态。

| llm_wiki 概念 | forge 既有对应物（核实位置） | 本方案补的缺口 |
|---|---|---|
| purpose.md | `site.public_sites.name/description`（0042）+ `update_site` 工具（builtins.go:124） | 无"定位/受众/为什么"载体；不进 agent 上下文 |
| Lint | `publish_checklist` 工具（builtins.go:154，资产级、advisory） | 无**站点级**体检；人没有入口（现仅 agent 可调） |
| log.md | `audit.audit_log`（0011，含 actor/initiator/agent_application_id）+ `asset.asset_publications`（0034，发布历史，已喂公开站更新记录块） | 站点域审计覆盖不全；无站点视角的时间线视图 |
| two-step ingest | `suggest_resource_model`（纯计算）→`create_resource_model`（物化）先例（builtins.go:147-148）；`agenttask` 单任务 1..20 资产、幂等 requestHash；react runs 通道 | 无批量**内容**建模的计划→人审→生成链 |

哲学对齐（印证既有决策，不改动）：llm_wiki 的 "Human curates, LLM maintains" 即我们的动作级 human_only（`asset.publish` 发布必须人做）；其把 LLM review 动作约束成预定义枚举（防幻觉动作）即我们 tool_policy 控制台化 + PATCH 未知字段 422 的同一认知。

## F1 站点简报（brief）

### 动机

llm_wiki 发现只有 schema（结构规则）不够，还缺放"为什么"的地方：目标、受众、范围。LLM 每次 ingest/query 都读 purpose.md。我们现状：agent 写内容/改主题时对站点定位的唯一感知是站名+description，两者都没有"给谁看、突出什么、语气如何"的语义；同一个工作区的建模产出与站点定位容易漂移。

### 决策

**F1-D1 单列 markdown 文本，不做结构化字段。**
llm_wiki purpose.md 的教训："为什么"是散文不是表单。结构化（定位/受众/关键词三字段）会带来 DisallowUnknownFields 面、表单 UI、字段增删迁移；纯文本上限 2000 rune，agent prompt 友好。参照 0042 description 的落法。

- 迁移 `0043_site_brief.sql`：`ALTER TABLE site.public_sites ADD COLUMN IF NOT EXISTS brief text NOT NULL DEFAULT '';`
- `siteColumns`（`internal/site/service.go:163`）加列——**必须同步 `internal/site/theme_query.go` 与 `internal/site/pages_service.go` 两处手写 Scan**（0042 教训：22 vs 21 目标静默 500）。

**F1-D2 注入 react run 指令（主通道），不靠工具自取。**
llm_wiki 的 purpose 是每次操作必读（不建模态），对应我们的做法是在指令组装点注入，而不是加一个"读简报"工具等模型自觉调用：

- 注入点：`internal/agentruntime/persistent_react.go:62` 组装 `ReActRequest` 处（此处已有 run 的 workspace 上下文）。工作区存在活跃站点且 brief 非空时，追加固定段落：`## 站点简报（本工作区公开站的定位；内容写作与设计决策须与之一致）` + brief（超 2000 rune 截断）。
- 只注入 react runs（rag chat 无工具链路，不掺和）。每次 run 多一次按 workspace 取站点行的查询，可接受。
- 安全边界：brief 是站点管理员控制的 server-side 配置，与 application instruction 同级（模型可见的受信指令面），不属于 fixedReActInstruction 声明的 untrusted 数据；写权限收敛在 site.design。

**F1-D3 写通道三条，全部沿用 description 的既有路。**
① `update_site` 工具加可选 `brief` 参数（`site_theme_tools.go` UpdateSite handler，与 name/description 同款）；② HTTP `UpdateSiteRequest` 加 `brief *string`（≤2000 rune，空串合法=清除）；③ 前端站点设计工作台"配置"Tab（站名/语言面板）加简报 textarea。openapi.yaml 同步。

**F1-D4 不进公开渲染。**
brief 是内部工作文档；公开 meta description 继续由 description 兜底链负责。是否随 release 快照：施工时对齐 name/description 的现行快照行为即可（0040 后 release 快照以 theme_revision 为主，brief 属工作配置，不影响已发布站渲染）。

### 验收

- 真后端：PATCH brief → 发起 react run → run 的首条模型输入可见注入段落（日志或 checkpoint 断言）。
- MSW e2e 仅测前端编辑器往返（写路径验收必须真后端——既有教训）。

## F2 站点体检（site lint）

### 动机

llm_wiki 三操作中，Ingest（建模）/Query（渲染）我们都有，Lint 缺位。现状痛点：`chunzhi-asset://` 引用是 fail-closed 渲染（死引用静默变纯文本，人看不见）；孤儿内容、空分类、翻译组断链没有系统性发现手段——此前全链路走查靠人肉。已有的 `publish_checklist` 是资产级且仅 agent 可调：补两口——**站点级规则集**与**人的入口**。

### 决策

**F2-D1 纯函数引擎，仿 validate.go 哲学。**
`internal/site/lint.go`：`LintInput`（各来源快照）→ `[]LintFinding{Check, Severity(error|warn|info), ResourceType, ResourceID, Message, Hint}`。依赖注入数据，规则无 DB 依赖，可无库单测。空结果必须序列化 `[]`（显式 `[]LintFinding{}`，nil 教训）。

**F2-D2 v1 检查项（L1-L8）：**

| # | 检查 | 级别 | 数据来源（复用） |
|---|---|---|---|
| L1 | 死引用：已收录正文 `chunzhi-asset://` 指向已删/被排除/未收录资产 | error | `markdown.go AssetRefIDs` + 收录派生视图 |
| L2 | 301 失效：`path_redirects` 目标 display_path 已无收录内容 | warn | site_slugs/path_redirects |
| L3 | 孤儿内容：已收录、无入链、无分类挂载、非精选 | info | 引用反向索引 + category_container_id |
| L4 | 空公开分类：public_flag 分类子树无收录内容 | warn | 分类树查询（category.go） |
| L5 | SEO 基线：站 description 空；自定义页 seo_description 空；自定义页 body_markdown 含一级标题（与主题 h1 冲突） | warn/info | 站点行 + 自定义页 |
| L6 | locale 断链：翻译组内某已开 locale 无对应内容（hreflang 落空） | warn | translation_group_id + 站点 locales |
| L7 | 待发布积压：N 条已发布资产存在未发布新版本 | info | 发布指针 vs 草稿（diff 面板同源数据） |
| L8 | 引用图缺 alt：正文引用 media 缺 alt | info | 对齐 publish_checklist 的 alt 检查，站点级聚合 |

**F2-D3 暴露三面：**
① HTTP `GET /api/v1/workspaces/{ws}/sites/{id}/lint`（权限 site.read，打开即算不缓存）；② agent 工具 `site_lint`（ReadOnly，advisory——与 publish_checklist "warnings never block publishing" 同哲学；**capability 词表施工时核实**：site.read 是否在 supportedAgentCapabilities，缺则补，注意四套词表同步的既有坑）；③ 前端两入口：站点工作台**发布确认 Dialog 前置体检摘要**（error 红/warn 黄徽章+可展开明细，**不阻断**）与内容清单 Tab「体检」按钮（全量报告抽屉）。

**F2-D4 资产级补口（薄封装）：**
`publish_checklist` 核心逻辑抽成 service 函数，补 HTTP 端点，资产发布对话框（change_note 同处）可选展示——让"人点发布时看到体检报告"在两个层级都成立。

### 验收

- 单测：每条规则正反例（无库）。
- 真后端：构造死引用/空分类/翻译组断链数据 → lint 报告命中；发布对话框展示摘要且**可继续发布**（不阻断契约）。

## F3 站点动态时间线（audit 补覆盖 + 站点视图）

### 动机

llm_wiki log.md 的可借鉴点是**全操作入账 + 机器可解析 + agent 动作可见**。我们双底座已齐（audit_log 安全审计向 + asset_publications 发布史），差距在站点域覆盖不全、且没有站点视角的消费视图（audit page 是工作区级、安全事件风味）。

### 已核实的覆盖现状

有审计：`site.created`/`site.updated`（service.go:360,461）、`site.release_published`（release.go:213）、`asset.publish`（asset/service.go:115、member.go:960）、`inclusion_excluded`/`inclusion_restored`（binding.go:212）。
**无审计**：设计会话 Apply 写回（design_session.go）、主题草稿保存（theme_service.go）、分类公开切换（folder SetCategoryPublication）、自定义页 CRUD（pages_service/manage_pages 工具路径）、精选 featured 切换、locale 配置变更。

### 决策

**F3-D1 补覆盖，不建新表。** 统一走 `recordSiteAudit` 模式（事务内）。action 词表：`site.theme_saved`、`site.design_applied`、`site.category_publication_changed`、`site.custom_page_created|updated|deleted`、`site.featured_changed`、`site.locale_changed`。每事件 metadata 定最小字段表（变更对象、前后值摘要）；actor 走 principal，agent 发起自带 agent_application_id 溯源。

**F3-D2 站点「动态」视图。** 站点详情页概览 Tab 下沉时间线：audit_log（resource=本站 或 resource 属本站收录面）∪ asset_publications，按时间合并；agent 行带 Agent 徽章（对齐成员列表 principal_type 徽章）。端点二选一：扩 `GET /workspaces/{ws}/audit` 加 site 过滤参数，或新 `GET sites/{id}/activity`（倾向后者，合并双源语义更清晰）。权限 site.read。

**F3-D3 公开面零改动。** 更新记录块继续只吃 asset_publications；audit metadata 含内部信息（前后值摘要），**绝不外溢到公开站**（D16 泄密面结论维持）。

### 验收

- 真后端：六类补覆盖事件逐个触发 → 动态视图出现且 agent 行有徽章；公开站 HTML 不含任何 audit 元数据。

## F4 两步建模（批量内容建模：先分析、后生成）

### 动机

llm_wiki 两步 ingest 的收益：①分析阶段上下文独立（不被生成任务挤占，判断"这是什么、放哪、链谁"更准）；②生成阶段链接已定（计划里给的是真实 ID，杜绝模型自由联想 ID）。我们的批量场景：存量附件/资产批量结构化为模型记录、公开站内容缺口补齐（孤立资产/稀疏分类的成批建模）。

### 承载（已核实）

react runs 是建模唯一通道（既有决策）；`create_internal_asset`/`update_internal_asset`/`create_relation` 均 LowWrite（不打断 waiting_approval，适合批量）；agenttask 的幂等模式（requestHash）与 1..20 上限可参照；`suggest_resource_model` 已示范"纯计算返回草稿、人物化"的两步形态。

### 决策

**F4-D1 计划落库：迁移 `0044_modeling_plans.sql`，`content.modeling_plans`。**
列：id/organization_id/workspace_id/target_model_id（可空=计划里建议）/intent/sources jsonb/plan jsonb/status(`draft|approved|rejected|applied|failed`)/created_by/agent_application_id/created_at。plan 内条目为行级 JSON（source_asset_id、建议标题、字段骨架（key+label，走 D17 词表）、分类容器、links[]（chunzhi-asset 目标，必须为已存在资产 ID）、dedupe 候选、条目状态与产出 asset_id）。**不做条目独立子表**（v1 够用，重跑/断点按条目状态判断）。

**F4-D2 第一步 analyze＝ReadOnly 工具 `plan_batch_modeling`，计划由人保存。**
输入：source asset IDs（≤20，对齐 agenttask 上限）+ intent + 可选 target_model_id。内部复用 `get_asset`/`get_attachment_text` 读源、`suggest_resource_model` 的骨架推理与校验器；输出建模计划 JSON（不落库）。**保存动作走 HTTP 由人发起**（前端"保存为计划"）——llm_wiki "人策展、LLM 维护"的最强形式，同时避开 agent 写新表的判权面。capability：asset.read + schema.read。

**F4-D3 人审分诊台（前端）。**
建模计划列表页（工作区资产域入口 + 站点内容清单 Tab 入口）：计划详情行级勾选/改标题/改分类 → 批准（status=approved）/驳回。llm_wiki review queue 的对应物；预生成信息（链接建议、去重候选）已在计划里，人只做取舍。

**F4-D4 第二步 generate＝消费已批准计划的 react run。**
HTTP 触发（人点"执行计划"）：创建 run，计划 JSON 注入 run query（或配套 ReadOnly 工具 `get_modeling_plan` 按需读取）。agent 按条目调用既有 LowWrite 工具；**硬约束写进 run 指令与工具描述：引用链接只允许计划内 ID**（llm_wiki 约束动作枚举的同款理由：防幻觉 ID）。产出全部是草稿 + 挂起关系（create_relation 本就 parking 到 commit）；confirm/publish 走既有 human_only 门，不动。

**F4-D5 收口与幂等。**
条目执行成功即在计划内记 created asset_id；重跑跳过已产出条目（断点恢复，对应 llm_wiki 持久 ingest 队列）。全部条目完成 → status=applied。发起人角色下限 min(agent, 发起人) 决定第二步工具可用性（既有机制，分诊台按钮按此置灰）。

### 验收

真后端全链：3 条源（1 附件 + 2 存量资产）→ analyze 出计划（含合法链接建议与 1 组去重候选）→ 保存 → 分诊（驳回 1 条）→ 执行 → 2 条草稿 + 挂起关系 → 人 confirm/publish → 公开站可见 + 引用内链成活。MSW 只测分诊台交互。
