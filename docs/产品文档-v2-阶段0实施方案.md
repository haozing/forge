# 产品 v2 阶段 0 详细实施方案

状态：待实施
适用基线：[产品文档-v2.md](/D:/code2/agentchunzhi/docs/产品文档-v2.md)
实施原则：只面向全新数据库和 v2 契约，不迁移旧数据，不保留旧状态、旧角色或字段别名；阶段 0 至阶段 6 都处于首次共享部署前，允许重写空库基线并重建数据库，不存在阶段间升级兼容；旧路由按“路由退役台账”分阶段下线，未到所属阶段的旧路由只能作为待退役遗留物存在，不得新增调用、文档或业务能力。

## 1. 阶段 0 的目标

阶段 0 是“最终契约收口和旧概念清场”，不是标签、Agent 或公开站点的功能开发阶段。

阶段结束后，代码库必须只有一套可以继续实现 v2 的基础语义：

1. 组织、工作区和成员角色只有一套权限来源。
2. Asset 负责发布状态，AssetVersion 是不可变快照，ProcessingJob 负责处理状态。
3. 保留发布审核子系统和 `reviewer` 角色，把当前与 AssetVersion 状态耦合的实现重构为独立的单级 PublicationRequest 聚合，不删减队列、评论、批量、统计、通知和审计能力。
4. AssetDraft 承担自动保存和附件暂存，AssetVersion 只表示不可变快照。
5. 可见性只描述数据边界，不再混用登录方式和含义模糊的历史别名。
6. ResourceModel 的内容出口和检索能力分开建模。
7. API、错误、分页、幂等、并发控制和事件命名形成唯一 v2 契约。
8. 数据库可以从空库一次性建立，不包含为旧数据准备的转换 SQL。
9. 后续阶段只能在这些契约上实现，不再自行发明状态、角色和事件名。

阶段 0 不交付最终前端体验，但必须交付受本次契约重构影响的可运行后端闭环：权限、AssetDraft、不可变版本、发布生命周期和完整单级审核。否则“基础语义收口”会以删除现有能力为代价，无法作为可验证基线。

## 2. 不属于阶段 0 的范围

以下内容只冻结接口和数据归属，不在阶段 0 完成业务实现：

- 标签管理、标签绑定和标签筛选的完整服务，留到阶段 2；
- 全文、语义、混合检索改造，留到阶段 3；
- Agent 整理、问答和应用运行时，留到阶段 4；
- PublicSite、博客渲染和站点查询，留到阶段 5；
- v2 管理端和工作区前端，留到阶段 6；
- 性能压测、容灾和生产发布，留到阶段 7。

阶段 0 可以创建 Tag、PublicSite 等对象的最终表结构和纯契约类型，但不提供尚未完成的 Tag、Site 业务接口。AssetDraft 和 review 是版本不可变与能力迁移的必要组成，不属于可以延后的占位接口。

阶段 0 是开发检查点，不是部署版本。阶段完成后仍不得接入共享数据或共享环境；阶段 1 至阶段 6 可以继续直接改写空库基线。每个工作包必须同时修改它需要的 schema、代码和测试，并在该提交上从空库启动，禁止先提交依赖不存在表/列的代码，再等待后续“数据库提交”补齐。

## 3. 当前代码事实

### 3.1 资产状态存在三套重叠语义

初始表把 Asset 状态定义为 `internal/published/archived`，并在 AssetVersion 上放了处理和审核混合状态，见 [0001_core.sql:176](/D:/code2/agentchunzhi/db/migrations/0001_core.sql:176) 和 [0001_core.sql:189](/D:/code2/agentchunzhi/db/migrations/0001_core.sql:189)。后续迁移又把它们转换成：

- Asset：`draft/published/archived`；
- AssetVersion.workflow_status：`draft/submitted/approved/rejected/published/retired`；
- AssetVersion.review_status：另一套审核状态。

转换逻辑位于 [0023_yxt_final_contract.sql:13](/D:/code2/agentchunzhi/db/migrations/0023_yxt_final_contract.sql:13)。实际成员资产创建已经写入 `draft`，见 [member.go:409](/D:/code2/agentchunzhi/internal/asset/member.go:409)，发布和归档则更新 Asset 指针，见 [member.go:643](/D:/code2/agentchunzhi/internal/asset/member.go:643) 和 [member.go:603](/D:/code2/agentchunzhi/internal/asset/member.go:603)。

问题不在于枚举名字不统一，而在于 AssetVersion 同时承担了内容快照、处理任务和审核流程三种职责。

### 3.2 AssetVersion 在声明不可变的同时仍被原地更新

产品 v2 把 AssetVersion 定义为不可变版本，但 [member_versions.go:168](/D:/code2/agentchunzhi/internal/asset/member_versions.go:168) 的 `UpdateVersion` 会直接执行 `UPDATE asset.asset_versions`，[member_versions.go:199](/D:/code2/agentchunzhi/internal/asset/member_versions.go:199) 还会原地修改标题、正文、字段和 JSONB 标签。

如果不在阶段 0 定死不可变规则，后续标签、检索和公开站点都会遇到“同一个 version_id 内容发生变化”的缓存、审计和引用错误。

### 3.3 工作区实际有六种角色

数据库当前允许 `owner/admin/editor/reviewer/member/viewer`，见 [0026_yxt_member_role.sql:3](/D:/code2/agentchunzhi/db/migrations/0026_yxt_member_role.sql:3)。工作区创建会自动插入 `owner`，见 [final.go:52](/D:/code2/agentchunzhi/internal/workspace/final.go:52) 和 [final.go:84](/D:/code2/agentchunzhi/internal/workspace/final.go:84)。权限矩阵则散落在 [workspace.go:100](/D:/code2/agentchunzhi/internal/authz/workspace.go:100)。

### 3.4 当前审核实现与 v2 产品边界冲突

当前代码已经包含：

- `asset.asset_reviews` 和 `review_status`；
- `internal/review` 服务；

### 3.5 可见性同时表达权限、登录方式和历史别名

### 3.7 HTTP 和依赖边界已经过度集中

## 4. 阶段 0 最终契约

### 4.1 组织与工作区

最终所有权链固定为：

```text
Organization
  -> Workspace
    -> ResourceModel
    -> Asset / AssetDraft / AssetVersion
    -> Tag
    -> PublicSite
    -> AgentApplication binding
```

规则：

- 用户和 Agent 技术身份都属于一个 Organization；
- 一个 Organization 可以有多个 Workspace；
- 所有内容对象必须直接保存 `organization_id` 和 `workspace_id`；
- 不建立 Department、department_id 或部门继承；
- Container 只是内容组织结构，不得承担组织部门或权限继承职责；
- 跨组织引用在数据库外键和服务校验两层都拒绝。

### 4.2 两层成员角色

组织级身份和工作区角色分开：

| 层级 | 最终字段 | 最终值 | 含义 |
| --- | --- | --- | --- |
| Organization | `identity.users.organization_role` | `admin`, `member` | 组织管理身份，仅成员用户有值 |
| Workspace | `content.workspace_members.role` | `admin`, `editor`, `reviewer`, `viewer` | 工作区内的实际协作角色 |
| Agent | 无成员角色 | 由 AgentAccessPolicy 决定 | 不继承组织或工作区成员权限 |

具体规则：

1. 只有组织 `admin` 可以创建工作区。
2. 创建者同时成为工作区 `admin`，不再生成 `owner`。
3. 组织 `admin` 可以停用工作区和管理成员关系，但没有显式 membership 时不能读取或修改工作区内容。
4. 普通组织 `member` 必须存在 workspace membership 才能进入工作区、读取 working version 或执行工作区动作；`organization` 可见的 published version 可以通过组织级查询读取。
5. 组织 admin 为自己授予 workspace 角色也必须写 membership 和审计记录，不允许隐式权限旁路。
6. 工作区 `admin` 可以邀请 `admin`、`editor`、`reviewer` 或 `viewer`。
7. 工作区至少保留一个显式 admin；删除或降级最后一个 admin 返回 `409 last_workspace_admin_required`。
8. `editor` 可以创建、编辑和归档资产；是否可以直接发布由已发布 ResourceModelVersion 的 publication policy 决定。
9. `reviewer` 可以查看版本、评论和处理发布请求，不能修改资产内容。
10. `viewer` 只能读取有权访问的工作区资产和使用查询能力。
11. 不存在 workspace `owner/member` 角色；Organization 是所有者，组织 `member` 是另一层身份。

### 4.4 Asset 发布状态

唯一发布状态保存在 Asset：

```text
create -> draft --publish/direct--> published
           |                    |
        archive              archive
           |                    |
           +-------> archived <-+
                        |
                     restore
                        |
                      draft

draft --submit(approval)--> draft + PublicationRequest.pending
PublicationRequest.pending --approve--> published
PublicationRequest.pending --reject--> draft
published --publish(new version)--> published
published --submit(new version)--> published + PublicationRequest.pending
published + PublicationRequest.pending --approve--> published(new pointer)
published + PublicationRequest.pending --reject/cancel--> published(old pointer)
```

准确转移规则：

| 当前状态 | 命令 | 结果 | 说明 |
| --- | --- | --- | --- |
| 无 | create | `draft` | 创建 Asset 和第一个版本 |
| `draft` | publish | `published` | 设置当前发布版本 |
| `draft` | submit | `draft` + pending request | `approval` 策略下创建单级发布审批请求 |
| `published` | create_version | `published` | 新工作版本不影响线上版本 |
| `published` | submit | `published` + pending request | 旧 published pointer 继续提供线上内容 |
| `published` | publish | `published` | 用新版本替换当前发布版本 |
| `published` | archive | `archived` | 清空发布指针 |
| `draft` | archive | `archived` | 允许归档从未发布的资产 |
| `archived` | restore | `draft` | 只恢复为草稿，不自动重新发布 |

不允许 `archived -> published` 的跳转，必须先 restore，再显式 publish；`approval` 策略下 publish 只能由批准动作触发。

Asset 指针不变量：

- `current_working_version_id` 始终非空，并指向本 Asset 最新版本；
- `publication_status = published` 当且仅当 `current_published_version_id` 非空；
- `draft` 和 `archived` 的 `current_published_version_id` 必须为空；
- `publication_status = published` 当且仅当 `published_at` 非空；draft/archived 的 `published_at` 必须为空；
- published version 可以早于 working version；
- 两个指针必须引用同一个 Asset 的版本；
- 所有状态和指针更新在一个事务中完成；
- Asset 增加 `revision bigint`，每次状态、可见性和当前指针变化都递增，用于并发控制和事件 aggregate version。
- direct publish 或 approval approve 首次设置或切换 published pointer 时写入 `published_at=transaction_timestamp()`；同一幂等命令重放不得改变它；归档时与 published pointer 一起清空。

PublicationRequest 被拒绝或取消时不改变 Asset 的 publication_status。若 Asset 原为 published，则继续使用旧 published pointer；若原为 draft，则保持 draft。

产品文档中的版本状态 `internal` 必须改为 Asset 状态 `draft`。`internal` 不再是任何数据库枚举。

### 4.5 AssetDraft 和 AssetVersion 不可变性

每个 Asset（包括 archived Asset）恰好有一个 AssetDraft。归档后 draft 只读保留，恢复后继续使用，不删除未提交内容：

```text
id
organization_id
workspace_id
asset_id
base_version_id
revision
committed_revision
title
summary
markdown
fields
origin
updated_by
updated_at
```

AssetDraft 规则：

1. 自动保存使用 `PATCH /assets/{assetId}/draft` 和 `If-Match: draft-revision`，只递增 draft revision，不创建 AssetVersion。
2. 每个 Asset 同时只有一个共享 draft；Asset 保存非空 `draft_id`，并通过可延迟复合外键 `(asset_id, draft_id)` 与 Draft 的 `(asset_id, id)` 形成数据库级一对一闭环。并发修改使用 revision 冲突返回 `412 draft_revision_mismatch`（缺少 `If-Match` 返回 `428`），`409` 只表示业务状态冲突。
3. `asset_draft_tags` 和 `asset_draft_attachments` 可以随 draft 修改，且与 draft revision 一起提交。
4. clean 的定义唯一固定为 `revision = committed_revision`，dirty 固定为 `revision <> committed_revision`。自动保存只增加 revision；不得通过比较正文或依赖内存状态猜测 dirty。
5. `commit-draft`、direct publish 和 publication submit 都必须携带预期 draft revision；dirty draft 在同一事务中物化为新版本。clean draft 的 direct publish/submit 直接使用 current working version，不创建重复版本。
6. 版本提交成功后，draft 的 base_version_id 指向新版本，draft revision 再增加一次并把 committed_revision 设为该新 revision；Asset current_working_version_id 同事务切换。
7. 归档 Asset 不删除 draft，也不重置 revision；所有 draft 写入和 commit 返回 `409 asset_archived`。restore 只解除写冻结，不隐式 commit 或 publish。
8. Agent 只能按 AgentAccessPolicy 更新 draft 或创建候选版本，不能把 confirmation_status 写为 human_confirmed。
9. Draft 不保存“已确认”事实；任何标题、正文、字段、标签或附件关系变更都清空可能缓存的来源确认元数据，提交版本一律按新快照重新判断确认状态。确认只发生在版本快照上。

AssetVersion 只表示一次内容快照，最终字段包括：

```text
id
organization_id
workspace_id
asset_id
resource_model_id
resource_model_version_id
version_no
origin
confirmation_status
confirmed_by
confirmed_at
title
summary
markdown
fields
source_raw_input_id
parent_version_id
content_checksum
created_by
created_at
```

必须删除：

- `workflow_status`；
- `processing_started_at`；
- `review_status`；
- `tags jsonb`。

写入规则：

1. 编辑标题、正文、字段、附件或标签只修改 AssetDraft；提交 draft 时一次性创建新版本。
2. `PATCH /asset-versions/{id}` 不存在；版本只有创建和读取，自动保存不得调用版本接口。
3. AssetVersion 增加 `sealed_at`。创建事务先插入未封存版本及其 tag/attachment relations，完成后设置 sealed_at；deferred constraint trigger 保证事务结束时任何 AssetVersion 都已封存。封存后触发器拒绝 AssetVersion 内容 UPDATE，以及 relation 的 INSERT/UPDATE/DELETE。
4. 新版本 `version_no = max(version_no) + 1`，创建时锁定 Asset，避免并发重复。
5. `parent_version_id` 必须属于同一 Asset。
6. `content_checksum` 覆盖标题、摘要、正文、规范化字段、附件关联和正式标签 ID。
7. 版本创建和 `current_working_version_id` 更新必须同事务提交。

`asset_version_tags` 和 `asset_version_attachments` 也是版本快照的一部分。它们只能在父版本 `sealed_at IS NULL` 的创建事务中插入；父版本封存后，触发器拒绝后续 INSERT/UPDATE/DELETE。应用运行角色不得直接 UPDATE AssetVersion 或删除关系，所有 materializer 共用同一封存 repository。

附件采用独立 Attachment、`asset_draft_attachments` 和 `asset_version_attachments`：

- 上传先创建归属当前 organization/workspace/uploader 的 Attachment，状态为 `uploading/scanning/clean/rejected/failed`；
- 上传完成后绑定 AssetDraft，不直接绑定 AssetVersion；
- Attachment 必须记录 `expires_at`，未被 draft 或 version 引用的对象由清理任务删除；
- 只有 `clean` Attachment 可以随 draft 提交到 asset_version_attachments；
- draft 放弃、附件移除和扫描失败只修改暂存关系，不触碰历史版本；
- 版本创建后不能继续追加、替换或删除附件关联。

### 4.6 处理状态、内容来源和人工确认

处理状态只属于 `content.processing_jobs`：

```text
queued -> running -> succeeded
                  -> failed
queued/running -> cancelled
```

ProcessingJob 通过 `source_type/source_id` 指向 RawInput 或 AssetVersion，通过 `output_version_id` 指向候选版本。失败、重试和取消不会修改源 AssetVersion。

AssetVersion 的来源和确认是两个正交事实：

- `origin` 只允许 `human/imported/ai_generated/ai_assisted`；
- `confirmation_status` 只允许 `unconfirmed/human_confirmed`；
- `human_confirmed` 必须同时记录 `confirmed_by/confirmed_at`，其余状态二者必须为空；
- `confirmation_status` 与其他版本内容一样不可更新。

`POST /asset-versions/{id}/confirm` 要求 `asset.confirm`，创建内容相同、parent_version_id 指向原版本的派生版本，并写入 `human_confirmed`、`confirmed_by` 和 `confirmed_at`；它同时更新 current_working_version_id、重置 AssetDraft base 并取消原 pending request，但不改变旧 published pointer。发布或审核批准不自动确认版本；当 policy.require_human_confirmation=true 时，direct publish 和 publication submit 都拒绝 unconfirmed 版本。若从已确认版本初始化可编辑 draft，draft 必须从 `unconfirmed` 开始，不能继承旧确认事实。

### 4.7 可见性

最终只保留三个值：

| 值 | 读取范围 |
| --- | --- |
| `workspace` | 当前工作区成员，以及获得明确策略的 Agent |
| `organization` | 同一组织的已登录成员 |
| `public` | 匿名访客，但仅限当前已发布版本和允许的公开渠道 |

规则：

- 删除 `login/private/internal`；
- `login` 是认证方式，`internal` 语义不确定；v2 的“我的笔记”只是作者/贡献者筛选，不建立个人 private 数据域；
- AssetDraft 和未发布 working version 始终只允许有 `asset.read` 的工作区成员或明确允许 draft scope 的 Agent 读取；
- `organization/public` 只扩大当前 published version 的读取范围，不公开 working version；
- Agent 不通过 visibility 自动获得访问权，仍必须满足 AgentAccessPolicy；
- 公开站点还必须同时满足站点 active、绑定有效、ResourceModel 开启 public_site channel；
- 返回 404 隐藏越权资源存在性，只有已确认资源存在且调用方属于其边界时才返回 403。

### 4.9 发布审批模型

v2 保留发布审核子系统和 `internal/review` 领域边界。当前 `asset.asset_reviews`、AssetVersion.review_status 和旧 frontend 路由不作为最终契约；它们在空库基线中重构为独立的单级 `PublicationRequest` 聚合及 v2 路由。重构不得删除审核队列、详情、筛选、评论、批量处理、待审核统计、通知和审计能力。

`PublicationRequest` 最终字段：

```text
id
organization_id
workspace_id
asset_id
asset_version_id
status: pending / approved / rejected / cancelled
submitted_by
decided_by
decision_comment
cancelled_by
cancel_reason: user_cancelled / new_version / asset_archived / admin_cancelled
submitted_at
decided_at
revision
```

`PublicationComment` 最终字段：

```text
id
organization_id
workspace_id
publication_request_id
body
author_user_id
created_at
```

发布策略固定为：

- `direct`：拥有 `asset.publish` 的成员可以直接发布；
- `approval`：editor、admin 或获得 `publication.submit` 的 Agent 提交请求，只有 admin/reviewer 执行 `publication.approve` 后才能发布。

审批规则：

1. 一个 Asset 同时只能有一个 pending PublicationRequest，数据库使用 partial unique index 保证。
2. 拒绝只改变 PublicationRequest，不修改 AssetVersion。
3. draft Asset 提交后保持 draft；published Asset 的新 working version 提交后保持 published，旧 published pointer 在审核期间继续对外服务。
4. AssetDraft 提交形成新 working version 时，旧 pending request 自动取消；必须对新版本重新提交审批。
5. 批准动作在同一事务中校验请求状态、Asset working pointer、版本 checksum 和 publication policy，然后更新 published pointer。
6. `reviewer` 不能通过 `asset.publish` 绕过 approval policy。
7. `decided_by` 不能等于 `submitted_by`，approval 模式不允许自审自批。
8. 创建新 working version 或归档 Asset 时，自动把该 Asset 的 pending request 改为 cancelled，并记录 cancel_reason。
9. 请求提交者可以取消自己的 pending request；workspace admin 可以取消工作区内的 pending request。
10. 评论线程可以在 pending/approved/rejected/cancelled 请求下读取和追加；决定说明只在 approve/reject 命令中写入，不用评论代替决定事实。
11. 批量 approve/reject 必须逐项执行同一领域命令，返回每项结果，不能绕过权限、自审、checksum、pointer 或 policy 校验。
12. 待审核统计从 PublicationRequest 实时或投影计算；submitted/approved/rejected/cancelled 事件驱动通知并保留完整审计。
13. v2 不提供多级审批、部门审批和审批流编排，但保留单级审核所需的讨论与运营能力。

人工确认通过以下事实表达：

- `AssetVersion.confirmation_status = human_confirmed`；
- `confirmed_by/confirmed_at`；
- Asset 发布审计中的 `actor_user_id`；
- 必要时由 ProcessingJob 保存 Agent 输出和人工采用结果。

审核批准和人工确认是两个独立动作：批准不能修改 AssetVersion，也不能把 unconfirmed 版本变为 human_confirmed。阶段 0 要迁移审核领域实现，而不是删除审核子系统；所有现有能力必须在新的 PublicationRequest、PublicationComment、事件和 v2 API 中有明确落点。

## 6. 数据库实施方案

### 6.1 采用首次部署前可重写的空库基线

当前迁移执行器按文件名和 checksum 记录迁移，见 [store.go:77](/D:/code2/agentchunzhi/internal/store/store.go:77) 和 [store.go:121](/D:/code2/agentchunzhi/internal/store/store.go:121)。直接修改已经执行过的旧文件会产生 checksum 冲突。

本阶段明确不支持旧库或阶段间数据保留，因此处理方式是：

1. 删除当前 `db/migrations/0001` 至 `0045` 的历史链；
2. 从最终 v2 结构重新生成按领域拆分的空库迁移；
3. 阶段 0 至阶段 6 的开发、测试数据库在每次基线变化后全部重建；这些阶段不得连接共享数据库或保存需要保留的数据；
4. 不编写 `UPDATE old_status`、复制 JSONB 标签或旧角色转换 SQL；
5. 不为旧库提供启动旁路。

迁移执行契约必须同时收口：`cfg.MigrationPath` 指向一个迁移根目录，独立 `cmd/migrate` 只枚举该目录的直接子级 `*.sql` 并按文件名排序；禁止迁移子目录。API 和 worker 不执行迁移、不重放 seed，只使用受限运行连接。内置模型 seed 是普通、确定性、可重复执行的基线迁移内容，不再通过运行进程按文件名重放。

数据库连接和权限固定为：

- `DATABASE_MIGRATION_URL`：只提供给 `cmd/migrate` 和显式运维任务，角色拥有 schema/object owner 权限；
- `DATABASE_URL`：只提供给 API、worker、bootstrap 领域命令，角色不是表 owner，只拥有明确的 SELECT/INSERT/UPDATE/DELETE 或函数 EXECUTE grant；
- API/worker 启动时只校验 schema marker 和 checksum manifest，不执行 DDL；
- 每个 migration 文件的 SQL 与 `system.schema_migrations` checksum 记录必须在同一显式数据库事务中提交，并在事务内持有 advisory lock；崩溃后只能得到“全部提交”或“全部回滚”；
- 阶段 0 至阶段 6 每次改变已存在的基线文件后直接重建数据库，不在原数据库上再次执行变更 checksum 的文件；
- 首次共享部署后才冻结 checksum 并启用 append-only，本组阶段文档不定义该部署后的升级迁移。

### 6.2 必须由数据库保证的不变量

数据库至少增加以下约束：

- 所有下级表使用 `(organization_id, workspace_id)` 复合外键；
- ResourceModel、Asset、Tag、PublicSite 的 workspace 必须属于同一 organization；
- Asset 两个版本指针使用 `(asset_id, version_id)` 复合外键，不能指向其他 Asset；
- `UNIQUE (asset_id)` 保证每个 Asset 最多一个 AssetDraft，draft.base_version_id 必须属于同一 Asset；
- draft tags、draft attachments 与 draft 必须属于同一 organization/workspace；
- AssetVersion 的 parent version 使用 `(asset_id, parent_version_id)` 复合外键；
- `UNIQUE (asset_id, version_no)`；
- `UNIQUE (workspace_id, normalized_key)` 和 `UNIQUE (workspace_id, slug)`；
- `UNIQUE (asset_version_id, tag_id)`；
- partial unique index 保证同一 Asset 同时最多存在一个 pending PublicationRequest；
- PublicationComment 必须通过复合外键属于同一 organization/workspace 的 PublicationRequest；
- Asset 发布状态和 published pointer 通过 CHECK 保持一致；
- AssetVersion 内容字段禁止 UPDATE；
- AssetVersion 必须在创建事务结束前 sealed；sealed version 的 tag/attachment relation INSERT/UPDATE/DELETE 全部被拒绝；
- `human_confirmed` 与 confirmed_by/confirmed_at 的非空关系由 CHECK 保证；
- Agent 用户的 `organization_role IS NULL`；
- workspace role 只允许 `admin/editor/reviewer/viewer`；
- publication policy 只允许 `direct/approval`；
- visibility 只允许 `workspace/organization/public`。

跨表 CHECK 无法表达的约束使用简短、可测试的 constraint trigger，不依赖 handler 自觉维护。

处理规则：

- `asset.published`：重建新版本，删除 previous version 投影；
- `asset.archived`：删除 previous version 投影；
- `publication_request.submitted/approved/rejected/cancelled/commented`：供通知、审核队列统计和审计消费者使用；检索只消费批准事务产生的 `asset.published`，不消费审批事件修改投影；
- `asset.visibility_changed`：重新判断当前发布版本是否应进入对应查询范围；
- `tag.created`：不触发资产重建；标签目录直接读取主表，消费者只记录可选的目录刷新；
- `tag.updated`：重建使用该标签的当前发布版本；
- `tag.archived`：刷新标签聚合；已有历史版本关联保留，不自动改写版本；
- `tag.restored`：刷新标签聚合；不自动重写任何 AssetVersion；
- `resource_model.policy_published`：标记模型相关投影 stale 并批量重建。

现有 outbox、delivery recovery、River queue 和失败重试保留，不重新实现消息系统。

### 8.2 全局响应规则

错误统一为：

```json
{
  "error": {
    "code": "asset_not_found",
    "message": "Asset was not found",
    "request_id": "...",
    "details": {}
  }
}
```

固定规则：

- 输入格式错误和字段校验失败：`422`；
- 未认证：`401`；
- 已认证但动作不允许：`403`；
- 不可泄露的越权资源：`404`；
- `If-Match` 缺失：`428`；revision 或 ETag 不匹配：`412`；业务状态冲突：`409`；
- 必需的 `Idempotency-Key` 缺失：`428`；
- 幂等键相同但请求内容不同：`409`；
- 服务暂不可用：`503`；
- 所有错误返回稳定业务 code 和真实 request id。

列表统一使用 cursor：

```json
{
  "items": [],
  "page": {
    "next_cursor": null,
    "has_more": false
  }
}
```

写操作规则：

- 创建、发布、归档、恢复、批量操作必须支持 `Idempotency-Key`；
- 更新 Asset 元数据使用 `If-Match` 对应 Asset revision；
- 自动保存 AssetDraft 使用 `If-Match` 对应 draft revision；
- commit、发布和提交审核同时校验 draft revision 与 base_version_id；
- 不允许 handler 自己生成基于时间戳的 request id；由 middleware 注入。

### 8.3 路由和依赖拆分

把当前单体 router 拆为注册函数：

```text

registerV2WorkspaceRoutes
registerV2AssetRoutes
registerV2ReviewRoutes
registerOpenV2Routes
registerPublicV2Routes
```

阶段 0 先完成结构拆分和审核能力的 v2 垂直链。旧 review 路由的替代入口必须先通过 contract test，再按路由退役台账下线；其他领域旧路由不得在阶段 0 越权删除。进入后续阶段后，新实现只注册到 v2 路由族。

`Dependencies` 分成基础设施和领域接口。除 health/readiness 外，v2 handler 不获得 `Store`。

   同提交修改角色 schema、动作矩阵、调用方与权限测试。
4. `phase0: refactor review workflow`
   同提交建立 PublicationRequest schema，迁移完整 review service、v2 API、统计和通知，并删除旧 review 运行入口。
5. `phase0: introduce sealed versions and asset drafts`
   同提交建立 AssetDraft、sealed AssetVersion/relations、published_at，迁移全部写入/lineage/workflow 调用方。
6. `phase0: canonicalize visibility and model policy`
   同提交切换 schema、seed、读取入口和 channels/retrieval policy。
7. `phase0: publish domain events`
   同提交完成事件目录、资产解耦和阶段 0 临时 retrieval consumer。
8. `phase0: enforce HTTP and architecture contracts`
   拆路由、统一错误和增加守护测试。

禁止提交“代码先引用新字段，后续再补 schema”或“先删 schema，后续再改调用方”。审核、AssetDraft、sealed version 和 policy 都必须按一条垂直链同时完成。阶段 0 每个提交都只承诺空库重建后可运行，不承诺保留上一个提交产生的数据。

## 12. 阶段 0 退出门槛

只有同时满足以下条件，才能进入阶段 1：

- [ ] `draft/published/archived` 只属于 Asset，AssetVersion 不含发布或审核状态。
- [ ] workspace role 只有 `admin/editor/reviewer/viewer`。
- [ ] Organization admin 无 membership 时不能读取工作区内容，治理动作有唯一实现和审计。
- [ ] review 子系统完整保留，并以单级 PublicationRequest/PublicationComment 实现队列、评论、决定、批量、统计和通知。
- [ ] AssetDraft 承担自动保存、标签编辑和附件暂存，提交后才生成 AssetVersion。
- [ ] AssetVersion 不含 workflow、review 和 tags JSONB 字段。
- [ ] AssetVersion 内容不可原地更新。
- [ ] visibility 只有 `workspace/organization/public`。
- [ ] ResourceModel policy 只有 `visibility/channels/retrieval/publishing` 最终结构。
- [ ] Asset 包不依赖 retrieval 包。
- [ ] 业务事务会写标准领域事件和 audit。
- [ ] 空数据库可以一次性完成迁移和 seed。
- [ ] migrator 与 API/worker 使用不同数据库角色；运行角色不是对象 owner，API/worker 启动不执行 DDL 或 seed replay。
- [ ] migration SQL 与 checksum 记录原子提交，故障注入后可无人工修复地重试。
- [ ] API 与 worker 可同时启动并通过 readiness。
- [ ] 单元测试、数据库集成测试和 `go test ./...` 全部通过。
- [ ] `openapi-v2.yaml` 通过 lint 和 route contract test。
- [ ] v2 HTTP handler 不直接访问 Store。
- [ ] 仓库中没有旧状态 alias、双写和新代码对旧路由的依赖；旧路由已建立退役台账，阶段 0 只删除已迁移的 review 旧路径。
- [ ] API 与 worker 不再硬编码 `0043_builtin_resource_model_seeds.sql`，迁移和 seed 都通过同一 manifest/根目录契约启动。
- [ ] 迁移文件全部位于 `MIGRATION_PATH` 直接目录，且有递增文件名和空库/重复启动测试。
- [ ] 路由退役台账包含每条旧路由的 owner、替代 v2 路径、删除阶段和 contract test。

建议在 CI 增加以下负向扫描作为退出门槛，而不是依赖人工 review：

```powershell
rg -n -g '!**/*_test.go' "asset_reviews|review_status|submit-review" internal db/migrations
rg -n -g '!**/*_test.go' '"owner"' internal/authz internal/workspace
rg -n -g '!**/*_test.go' "workflow_status|processing_started_at" internal db/migrations
rg -n -g '!**/*_test.go' '"login"|"private"|"internal"' internal/access internal/asset internal/workspace internal/query db/migrations
rg -n -g '!**/*_test.go' "policy\.outlets|agent_tool" internal/resourcemodel internal/query internal/attachment db/migrations
```

以上命令在限定目录中必须无结果；workspace role 的完整集合由 schema contract test 精确断言为 admin/editor/reviewer/viewer，避免用文本扫描误伤 organization member。测试样例若需要验证旧键拒绝，应集中放在带有 `legacy_rejected` 命名的测试用例中，并从扫描中显式排除测试文件。

## 13. 工期和风险

按一名熟悉现有代码的后端工程师估算，阶段 0 约为 15 至 22 个工程日。AssetDraft/附件暂存、完整审核迁移、数据库基线重建和版本不可变改造是主要工作量；原 8 至 12 日估算无法覆盖这些闭环。前后端或 Agent 功能开发不应与 S0-2 至 S0-7 并行，因为这些工作包会改变权限、状态和 policy 契约。

主要风险：

| 风险 | 控制方式 |
| --- | --- |
| 审核迁移时遗漏评论、批量、统计或通知 | 能力映射表 + v2 contract test + 端到端审核测试 |
| 版本不可变后附件、自动保存和 Agent 流程仍尝试原地更新 | AssetDraft 集成测试 + 数据库不可变触发器 |
| 组织 admin 再次获得隐式内容权限 | 组织治理 action 与 workspace content action 分离测试 |
| policy 改名后查询静默丢数据 | 旧键明确校验失败，不做 alias；seed 和查询集成测试 |
| 事件改造造成投影漏删或重复 | published/archived/visibility/tag 事件矩阵 + 重复投递测试 |
| 重建迁移遗漏旧模块仍需要的表 | API/worker 空库启动 + `go test ./...` + schema verification |
| 开发人员误连旧库 | schema contract marker + 启动时明确拒绝 |

## 14. 阶段 0 最终交付物

阶段 0 完成后应形成以下可审查产物：

1. 修订后的产品 v2 文档和标签架构文档。
2. `openapi-v2.yaml` 全局契约和领域路径骨架。
3. 唯一角色、动作、状态、可见性和 policy 实现。
4. 完整的单级审核子系统、AssetDraft 自动保存和无 AssetVersion 原地更新的运行代码。
5. 以领域拆分的全新空库迁移和内置模型 seed。
6. typed 领域事件目录和基于 outbox/River 的消费者注册。
7. 安全的开发/测试数据库重建脚本和 schema 验证脚本。
8. 权限、状态、数据库约束、事件和 HTTP 契约测试。
9. CI 中的空库启动、OpenAPI 校验和旧概念负向扫描。

阶段 0 的核心判断不是“是否写了很多基础代码”，而是：后续任何开发者面对角色、状态、可见性、出口、事件和 API 时，都只能找到一个答案。
