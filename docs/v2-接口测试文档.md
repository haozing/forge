## 1. 文档说明

### 1.1 测试目标

1. 验证四阶段全部接口按契约工作：身份与会话、组织治理、邀请、工作区成员、资产与草稿、版本与发布、审核流（PublicationRequest）、标签领域、检索配置与投影、统一查询、开放 API。
2. 验证两轮审计修复（681f9d4、443baef）真实闭环：幂等重放、publishing policy 全链路、事件投影、邮件投递、跨工作区越权、SQL 修复（facet 别名、tags_all 别名、游标类型、jsonb 绑定）。
3. 以真人使用逻辑串联接口，暴露"单接口正确但流程断裂"的问题。

### 1.2 不在本档范围

- 非四阶段核心接口（automation、agent-applications、conversation、agent-sessions/runs 细节等）：由 `.tools/api_route_smoke_test.py` 冒烟覆盖，本档仅在旅程中作为依赖引用。
- 前端 UI、性能压测（容量另有 `scripts/capacity-baseeline.ps1`）。
- 退役路由回归：按台账 `docs/route-retirement-ledger.md` 的 retired 清单做"必须 404"抽查即可。

### 1.3 术语

| 术语 | 含义 |
| --- | --- |
| 会话 cookie | 登录后 `Set-Cookie: agent_session=...`（生产为 `__Host-agent_session`，Secure+HttpOnly+SameSite=Lax+无 Domain） |
| 主体 Principal | 成员（cookie）或开放 API 应用（凭据），下文"成员 X"指持有该角色会话的真人账号 |
| 双过期 | 会话 idle 过期（默认 24h 滑动，5 分钟节流刷新）+ absolute 过期（默认 7 天） |

| PublicationRequest | 审核聚合（阶段0 起），approve 同事务切换 published 指针 |

## 3. 通用约定（所有用例默认遵守）

### 3.1 认证
- 成员面/公开面写操作靠会话 cookie；开放 API 靠应用凭据。
- 未认证访问 `/api/*` → 401；认证但无权限 → 403 `action_not_allowed`（角色动作矩阵见 authz/roles.go）。
- 资源不存在**或**不属于当前主体 → 404（不区分，防探测）；合法但无权 → 403。

### 3.2 错误信封
- 所有错误响应含 `error.code`（机器码）与 `request_id`；断言必须同时校验状态码 + 错误码。
- 常用错误码速查（附录 B 有全表）：`precondition_required`(428)、`idempotency_key_invalid`(422)、`idempotency_conflict`(409)、`draft_revision_mismatch`(412)、`state_conflict`(409)、`self_approval_not_allowed`(409)、`human_confirmation_required`(409)、`attachments_not_clean`(409)、`required_field_missing`(409)、`last_admin_required`(409)、`webhook_conflict`(409)、`retrieval_profile_unavailable`(503)。

### 3.3 幂等（v2 写命令）
- ``/api`、`/api/open` 的 POST/PATCH/PUT/DELETE **必须携带** `Idempotency-Key`（≥16 字符）：缺失 → 428 `precondition_required`；长度 <16 → 422 `idempotency_key_invalid`。
- 同 key 同体重放 → 返回首次缓存的完整响应（同状态码/同 body）+ 响应头 `Idempotency-Replayed: true`，**业务不重复执行**。
- 同 key 不同体 → 409 `idempotency_conflict`。
- 非 2xx 响应不缓存：同 key 重试会重新执行业务（允许重试语义）。
- 排除项（只读/流式，不带也不校验）：`POST .../query`、`POST .../references/validate`、`.../stream`；`/api/public` 全部（一次性 token 自身即重放边界）。
- webhook 特例：中间件层重放回放原响应；穿透业务层时由 `external_ref` 幂等（200 + `replayed:true`），两层不叠合。

### 3.4 乐观锁（If-Match / ETag）
- 草稿 PATCH（`PATCH /api/assets/{id}/draft`）必带 `If-Match`：缺失 → 428；revision 不匹配 → 412 `draft_revision_mismatch`。
- `If-Match: *` 表示"资源存在即可"，跳过 revision 相等校验（RFC 9110）。
- 同类要求适用于：tag PATCH/生命周期、organization PATCH、me/preferences PATCH（以各端点契约为准）。

### 3.5 分页
- 列表接口统一 `limit`（默认 20，上限 100，个别端点上限 200）+ 不透明 cursor（base64，含排序键指纹）；cursor 非法/与排序不匹配 → 422。
- 成员列表、标签列表、资产列表、审核评论均为 keyset 分页：翻页不得重复/丢行。

### 3.6 领域词汇（勿按旧称断言）
- 资产生命周期：`draft / published / archived`（无 internal/private 旧值）。
- 可见性：`workspace / organization / public` 三值。
- 版本不可变：sealed 版本内容列禁改；历史版本无"回退"，只能复制为新 draft 再发布；`restore` 仅恢复软删除。

### 3.7 断言纪律
- 每个写用例除 HTTP 断言外，视情况追加数据库断言（资产行、事件 outbox、审计行）。
- 时间敏感断言允许 ±2 分钟容差；所有用例记录实际响应耗时（为时效分层报告积累数据）。

## 8. 通过准则与缺陷报告

### 8.1 通过准则

1. SMOKE 全绿；全部 N 类用例通过；E/B/S/I/C/X 类预期全部复现"拒绝/钳制"行为。
2. §7 映射表中每一条修复点至少一条用例通过（修复回归零失败）。
3. 负向扫描门槛：reset 后 verify 输出 `schema_contract_ok` 且无 fail 行。
4. 无 P1/P2 级未闭环缺陷；P3 缺陷需登记且有结论（修/缓/接受）。

### 8.2 缺陷报告字段（每条缺陷必填）

- 编号、标题、严重级（P1 阻断 / P2 重要 / P3 次要）、所属用例编号
- 复现步骤（含最小请求样本、夹具名）、预期 vs 实际（状态码+错误码+响应体摘录）
- 时效标注：首次发现时间、复现确认耗时、影响面（即时/窗口期/累积）
- 状态五态：新建 / 已确认 / 修复待验 / 已验证关闭 / 挂起（挂起必附原因与解挂条件）
- 安全类缺陷：只描述行为与影响，不在报告正文粘贴任何凭据/密钥/内部路径；涉密细节走独立加密附件
- 闭环要求：每条缺陷关联验证用例编号；"修复待验"必须有回归用例可执行

### 8.3 执行顺序建议

1. §2 环境准备 → §4 SMOKE → §5 M1→M13（按真人旅程顺序）→ §6 横切专项 → §7 映射表核对。
2. 限流依赖用例（AUTH-004、OAG-011、X7）放各模块末尾。
3. 每轮结束后跑一遍 `.tools` 三套脚本作交叉对照，报告产物归档 `tmp_qa/`。
