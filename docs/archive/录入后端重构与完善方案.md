# 录入后端重构与完善方案

## 1. 方案边界

本方案只处理后端和数据模型，不实现前端，不保留旧 API 兼容层。目标是让 Chat、Note、Document、FAQ 和段落级派生共用一套可审计的 Container + Block 内核，同时保持 Dify Agent 选择权限与 Agent 数据权限分离。

本期不建设社群/贴吧功能，后期通过开放 API 复用 Block 协议。附件继续使用 OSS 抽象。

核心链路：

```text
Workspace 绑定 Agent Application
  -> 成员选择可用 Agent
  -> 创建 Chat，同时创建唯一 Note
  -> 多轮对话和 Note 草稿整理
  -> 结束讨论形成结果 Note
  -> 选择 independent / reference / merge
  -> 编辑、发布、检索和 Agent 工具调用
```

## 2. 统一业务流程

### 2.1 Chat、Note、Document、FAQ

| 对象 | 规则 |
| --- | --- |
| Chat | 保存完整 transcript；一个 Chat 永远只对应一个 Note |
| Note | 创建 Chat 时同步创建；是该 Chat 的持续整理结果 |
| Document | 经确认后可发布的资产；从 Note 快照派生，不把 Note 原地改成 Document |
| FAQ | 由 `qa` 父 Block 和 `question`、`answer` 子 Block 组成 |

主 Chat 和派生 Chat 都遵循同一规则：

```text
Chat A  <---- 1:1 ---->  Note A
  |
  | 从消息、段落或 FAQ Block 派生
  v
Chat B  <---- 1:1 ---->  Note B
```

派生不会裁剪源 transcript，只固化选中 BlockRevision 和上下文摘要作为新 Chat 的初始上下文。

### 2.2 段落发起讨论

```text
选择源 Block
  -> 固化源 BlockRevision 和相邻上下文
  -> 创建新 Chat + 新 Note
  -> 继续讨论
  -> 结束 Chat，形成结果 Note
  -> finalize：independent / reference / merge
```

创建 Chat 时不要求用户决定最终归属，归属决策后置到讨论结束。

### 2.3 三种归属

| disposition | 后端行为 |
| --- | --- |
| `independent` | 从结果 Note 快照创建独立 Document；不创建可见来源关系，但保留 Derivation 审计事实 |
| `reference` | 从结果 Note 快照创建独立 Document；创建成对 Relation，并在两端创建受控 `link` Block |
| `merge` | 以目标 Document 指定版本为基线创建新 AssetVersion，按块插入/替换/追加；不创建新的独立 Document |

三种 finalize 都必须幂等，同一 Derivation 只能完成一次归属。`merge` 同时校验源版本、目标资产版本和目标 ContainerVersion；任一基线变化返回 `409 merge_base_conflict`。

## 3. 统一 Block 模型

### 3.1 核心模型

所有正文都必须由一个稳定的 `ContentContainer` 承载。Container 负责归属、生命周期和当前版本指针，不解释 Block 业务语义。

四层版本核心为：`ContentContainerVersion`、`BlockPlacement`、`BlockRevision`、`Block`。不再为 Chat、Note、FAQ 维护平行正文树。

```text
ContentContainer
  ContentContainerVersion
    BlockPlacement
      BlockRevision
        Block
```

Block 类型是受控 Schema，而不是独立数据结构：

- `message`：Chat 消息父 Block，发送者、角色、Provider ID 放在 props/MessageBlock 元数据中；
- `paragraph`、`heading`、`list`、`code`、`quote`：通用正文 Block；
- `qa`、`question`、`answer`：FAQ 结构 Block；
- `link`：引用 Container、Block、Revision 或 Asset 的导航 Block；
- `attachment`、`callout`：通用扩展 Block。

FAQ 约束由 Schema 和 Placement 校验：一个 `qa` 父 Block 在同一 ContainerVersion 下必须恰好有一个 `question` 和一个 `answer` 子 Block，角色由 `role_in_parent` 表示。`link` 的目标信息放在 props，跨资产审计以 AssetRelation 为准，不增加 `link_block` 表。

### 3.2 版本和树约束

- `ContentContainer` 是必需的稳定身份；创建 Container 时同一事务创建初始 ContainerVersion，并设置 `current_version_id`。
- `BlockRevision(block_id, revision_no)` 唯一且不可变；复制产生新的 Block 身份和 Revision。
- `BlockPlacement` 只能追加到新的 ContainerVersion，不能修改已发布版本；同一父节点下 `position` 唯一。
- Placement、Revision、ContainerVersion、Block 必须属于同一 organization；禁止跨租户引用。
- `parent_placement_id` 必须属于同一 ContainerVersion；服务端校验父子循环、最大深度、根块数量和 role。
- 所有修改携带 `expected_container_version_id`，事务内锁定基线、复制受影响节点并原子更新当前指针；冲突返回 `409 version_conflict`。
- Markdown、全文、PGroonga、RAGFlow 都是投影，不是权威正文；由 Block renderer 生成。

### 3.3 自定义结构的 `content` 字段

自定义资源模型字段明确区分普通值和 Block 内容：

| 字段类型 | 存储 | 是否使用 Block |
| --- | --- | --- |
| `markdown` | AssetVersion 的 Markdown/字符串 | 否 |
| `text`、`textarea`、`enum`、`number` 等 | `AssetVersion.fields` | 否 |
| `content` | 绑定 `ContentContainer(kind=content_field)` 的版本 | 是，Block 树是权威正文 |

示例：

```json
{
  "fields": [
    {"key": "shot_name", "type": "text", "required": true},
    {
      "key": "analysis",
      "type": "content",
      "required": false,
      "allowed_block_types": ["heading", "paragraph", "list", "quote", "attachment", "link"],
      "max_depth": 4
    }
  ]
}
```

写入请求分离普通字段和内容字段：

```json
{
  "fields": {"shot_name": "夜景远景"},
  "content_fields": {
    "analysis": {"blocks": [{"type": "paragraph", "content": "..."}]}
  }
}
```

约束：

1. 只有字段 Schema 明确声明 `type=content` 时才创建内容 Container；普通字段不自动转换。
2. 服务端校验 allowed block types、深度、父子角色、顺序和必填根块。
3. 编辑 content 字段必须创建新的 BlockRevision、ContainerVersion 和 AssetVersion，不能原地修改已发布版本。
4. `AssetVersion.fields` 只保存普通字段和内容摘要，不保存整棵 Block JSON；客户端不能提交 container_id 绕过资产权限。
5. `asset_version_content_field` 绑定 `asset_version_id`、`field_key`、`resource_model_version_id`、`container_id`、`container_version_id`，并校验同一 organization。一个 Container 不得被多个字段复用。
6. 可选字段未提交时不创建绑定；required 字段必须有合法根块。
7. 内容块不参与普通 JSONB 等值/范围过滤；检索使用投影并返回 AssetVersion/Block 引用。

## 4. 后端分层

```text
HTTP API
  -> Authentication / Authorization
  -> Workspace Application Service
  -> Conversation Application Service
  -> Derivation Application Service
  -> Content Application Service
  -> Asset Lifecycle / Query / Retrieval Service

Domain
  ContentContainer / ContainerVersion / Block / Revision / Placement
  Conversation / MessageBlock / NoteBinding / Derivation / Relation
  ContentAsset / AssetVersion / ProcessingJob

Infrastructure
  PostgreSQL repositories
  Dify blocking/streaming Adapter
  OSS / ASR adapters
  Outbox / River workers / projection adapters
```

领域服务不依赖 HTTP、Dify SDK 或具体数据库实现。建议新增 `internal/content`，Conversation、Derivation 和 Asset 服务只能调用它，不能自行拼接 Markdown 或维护第二套块结构。

## 6. Dify 与权限

### 6.1 成员选择 Agent

1. 用户选择 Workspace，服务读取默认 Agent Application。
2. 临时切换 Agent 时校验成员的 `agent.use` 和 WorkspaceAgentApplication.enabled。
3. 创建 Conversation 时固化 `agent_application_id`、`bound_agent_user_id`、agent_session_id 和权限快照。
4. 用户界面操作使用 member principal；只有 Dify 工具调用使用 Agent principal。工具调用每次重新解析 AgentAccessPolicy，历史快照只用于审计。

### 6.2 AgentAccessPolicy

Agent 用户是技术身份，不是第三种业务角色；不得进入 WorkspaceMember，也不得参与部门、用户组或角色继承。

```text
agent_access_policy
  id
  organization_id
  workspace_id
  agent_user_id
  resource_model_id
  action: read | create | edit | publish | archive
  scope_type: workspace | asset_ids | filter
  scope_value jsonb
  status: active | revoked
  policy_version bigint
  created_by
  created_at
  updated_at
  UNIQUE (workspace_id, agent_user_id, resource_model_id, action)
```

首期可只实现 `scope_type=workspace`，表示该 Agent 可访问该 Workspace 内该 ResourceModel 的符合可见性和发布规则的资产。HTTP/领域动作统一映射为 `asset.read/create/edit/publish/archive`，不维护另一套动作命名。

### 6.3 Dify 请求边界

Dify Adapter 只负责 Provider 协议和 SSE 解析；业务服务负责权限、消息落库、Block 版本、Outbox 和幂等。服务端为每次工具调用生成短期 `agent_invocation_context`，包含 organization、workspace、agent_user、conversation、policy_version 和过期时间。工具 API 只接受该上下文并再次校验 AgentAccessPolicy，不信任前端或模型传入的资源范围、用户身份和 Agent ID。

## 7. API 约束

新 API 统一使用 `/api/v1`，历史接口已删除，不做转发兼容。

### 7.1 Conversation 和 Chat

```text
GET    /api/v1/workspaces
GET    /api/v1/workspaces/{workspaceId}
POST   /api/v1/workspaces/{workspaceId}/conversations
GET    /api/v1/conversations
GET    /api/v1/conversations/{conversationId}
PATCH  /api/v1/conversations/{conversationId}
POST   /api/v1/conversations/{conversationId}/complete
POST   /api/v1/conversations/{conversationId}/archive
GET    /api/v1/conversations/{conversationId}/messages
POST   /api/v1/conversations/{conversationId}/chat
POST   /api/v1/conversations/{conversationId}/chat/stream
```

不公开 `POST /messages`；用户消息统一从 `/chat` 或 `/chat/stream` 进入。事务边界为：写入 human/pending MessageBlock 并提交，调用 Dify，流结束后写 assistant/completed Block 和 Outbox。Provider 失败不能回滚已提交的 human 消息。

### 7.2 Note 和资产生命周期

```text
GET    /api/v1/conversations/{conversationId}/note
PATCH  /api/v1/conversations/{conversationId}/note
POST   /api/v1/conversations/{conversationId}/note/refresh
POST   /api/v1/assets/{assetId}/publish
POST   /api/v1/assets/{assetId}/archive
POST   /api/v1/assets/{assetId}/restore
```

`restore` 仅管理员使用，把 archived 恢复为 internal，不直接恢复为 published。发布必须携带 `expected_working_version_id`，并校验 ContainerVersion、字段 Schema 和投影前置条件。

### 7.3 派生和 finalize

```text
POST   /api/v1/conversations/{conversationId}/derivations
GET    /api/v1/derivations/{derivationId}
POST   /api/v1/derivations/{derivationId}/finalize
POST   /api/v1/asset-relations/{relationId}/disconnect
```

创建派生只创建新 Conversation、新 Note、DerivationSource 和上下文快照：

```json
{
  "operation": "create_chat",
  "source_block_revision_ids": ["...", "..."],
  "context_policy": "summary_only",
  "title": "可选标题"
}
```

finalize 请求：

```json
{
  "disposition": "independent | reference | merge",
  "target_asset_id": "merge 时必填",
  "expected_source_asset_version_id": "merge 时必填",
  "expected_target_asset_version_id": "merge 时必填",
  "expected_container_version_id": "merge 时必填",
  "merge_mode": "insert_after | replace_block | append",
  "target_block_id": "insert_after/replace_block 时必填"
}
```

所有写接口要求 `Idempotency-Key`。同 key 同请求只返回第一次结果；同 key 不同请求体返回 `409 idempotency_key_reused`。finalize 同时校验成员源/目标权限、Agent 工具调用的 AgentAccessPolicy、版本基线和幂等键，并在同一事务写入 Relation、link Block 或新 AssetVersion。

### 7.4 Block 和 content 字段

```text
GET    /api/v1/containers/{containerId}/blocks
POST   /api/v1/containers/{containerId}/blocks
PATCH  /api/v1/blocks/{blockId}

POST   /api/v1/blocks/{blockId}/copy
POST   /api/v1/blocks/{blockId}/reference
POST   /api/v1/containers/{containerId}/blocks/merge

GET    /api/v1/assets/{assetId}/versions/{versionId}/content-fields/{fieldKey}

```

Block 写入必须携带 `expected_container_version_id`；content 字段接口只对 Schema 声明为 `type=content` 的字段开放，并先校验资源模型、字段 Schema 和资产权限。

### 7.5 媒体

```text
POST   /api/v1/conversations/{conversationId}/media
GET    /api/v1/conversation-media/{mediaId}
POST   /api/v1/conversation-media/{mediaId}/transcribe
```

写接口统一要求 `Idempotency-Key`；服务端保存请求摘要和结果，避免重复创建消息、版本、Relation、Job 或 Provider 请求。

## 8. 状态、事件和 Worker

### 8.1 状态机

```text
Conversation: active -> completed | archived | failed
MessageBlock: pending -> completed | failed | cancelled
Asset: internal -> published -> archived
       archived -> internal (admin restore)
AssetVersion: immutable snapshot; processing state belongs to ProcessingJob
Derivation: requested -> discussing -> result_ready -> finalizing -> completed
           requested | discussing -> cancelled
           discussing | finalizing -> failed
ProcessingJob: queued -> running -> succeeded | failed | cancelled
```

### 8.2 事件和 Worker

核心事件：`conversation.created`、`conversation.message.created`、`conversation.message.completed`、`content.block.created`、`content.block.revised`、`conversation.note.sync_requested`、`conversation.derivation.requested`、`conversation.derivation.result_ready`、`conversation.derivation.finalized`、`conversation.media.transcription_requested`。

| Worker | 作用 |
| --- | --- |
| `conversation.note_sync` | 以 message sequence 和 Note 版本为基线生成候选，不覆盖人工版本 |
| `conversation.derivation` | 固化上下文并创建派生 Chat/Note |
| `conversation.derivation_finalize` | 执行三种最终归属 |
| `conversation.transcription` | 调 ASR，并把结果写入 Message/Paragraph Block |
| `asset.projection` | 发布后生成 Markdown、PGroonga、RAGFlow 投影 |

ProcessingJob 必须有租约、重试上限和幂等键。Note 同步携带 `input_version_id` 和 `last_synced_message_sequence`；基线变化时只生成 candidate 或返回 `note_version_conflict`，不能覆盖用户版本。

## 9. 权限矩阵

### 9.1 成员角色

首期只实现 Workspace 级 `admin` 和 `editor`：

| 角色 | 权限 |
| --- | --- |
| `admin` | 管理成员、资源模型、Agent Application 和全部资产；可发布、归档、恢复 |
| `editor` | 创建、编辑、派生、发布和归档工作区资产；不能管理成员、模型和 Agent Application |

操作权限：`workspace.read`、`workspace.write`、`agent.use`、`conversation.read/write/derive`、`content.write`、`note.write`、`asset.publish`、`asset.archive`、`asset.restore`、`source.read`。

### 9.2 执行主体

- 页面读取、编辑、派生、finalize：使用 member principal，并校验 WorkspaceMember、可见性和资产权限；
- Dify 工具调用：使用绑定 Agent principal，并校验 AgentAccessPolicy；
- Agent 权限不能替代成员对源文档和目标文档的操作权限；
- 工具调用每次重新解析实时 AgentAccessPolicy，历史快照只用于审计。

## 10. 实施顺序

### 第 1 阶段：统一内容内核

建立基线迁移和 Repository：Workspace、WorkspaceMember、WorkspaceAgentApplication、Container、ContainerVersion、Block、Revision、Placement、Conversation、MessageBlock、ContentAsset、NoteBinding、Derivation、DerivationSource、Relation、RelationBlock、ProcessingJob、AgentAccessPolicy、asset_version_content_field。先完成 Block Schema、复制、引用、版本快照和乐观锁。

### 第 2 阶段：Chat 持久化闭环

创建 Chat 时同步创建 Chat Container、Note Container 和 Note Asset；改造 Dify blocking/streaming Adapter，落库 MessageBlock，保证序号、Provider ID、幂等和失败恢复。

### 第 3 阶段：Note 与检索投影

实现 Note 同步和人工确认；由 Block renderer 生成 Markdown、全文、PGroonga/RAGFlow 投影，只索引 published 内容。

### 第 4 阶段：段落派生闭环

实现段落/消息/FAQ Block -> 新 Chat + 新 Note + 上下文快照 -> 三种 finalize，验证双向引用、块级合并、冲突、回滚、关系断开和幂等。

### 第 5 阶段：媒体与发布

接入 OSS、ASR 和受控下载；完成 `internal -> published -> archived`、检索和 Agent 工具真实环境测试；最后删除旧 Handler、DTO、人工审核链路和旧 OpenAPI 路径。

### 10.1 数据切换与清理边界

- 不保留旧 API 兼容层，不对旧路径做转发。
- 新 Service 完成后停止旧 workflow、人工审核任务和授权继承链的写入。
- 旧数据只做一次性离线转换：已发布版本转为 published，草稿转为 internal，审核记录转为审计事件；不得线上双写。
- 切换前完成数据库备份、迁移校验和投影重建；回滚只允许恢复备份或回退应用版本。
- 删除旧表前保留只读归档或导出文件，并校验资产数量、checksum、关系和权限范围。

## 12. 完成标准

1. Chat、Note、Document、FAQ 全部使用 Container + Block，不维护平行正文转换模型。
2. 每个 Chat 创建时有且只有一个 Note；消息可查询、审计和恢复。
3. 段落、消息、FAQ 派生遵循“先新 Chat、后归属”，三种 finalize 均幂等。
4. merge 具备源版本和目标版本乐观锁、冲突返回和版本回滚能力。
5. Dify 只使用成员明确选择且有 `agent.use` 权限的 Agent，工具访问使用该 Agent 的实时数据权限。
6. 只有 published 内容进入 PGroonga/RAGFlow，internal transcript 不被错误检索。
