## 1. 当前代码基线

### 1.1 已有能力

| 现有位置 | 当前职责 | 可复用部分 |
| --- | --- | --- |
| `internal/httpapi/handler.go` | 所有路由、DTO、鉴权调用和大量业务编排集中在一个文件 | 路由行为、错误输出、已有请求校验可作为迁移参考，但不能继续扩张 |
| `internal/content` | Conversation、Message、Note sync/publish、Derivation、Media/Transcription | 会话持久化、消息序号、派生和媒体处理领域逻辑 |
| `internal/asset` | Agent API Key 下的资产创建、更新、发布、归档；动态字段校验 | 资产版本写入、内容 checksum、字段 schema 基础校验、幂等 |
| `internal/query` | R3 fulltext/semantic/hybrid 查询和 AssetReference | 检索候选、游标、投影策略、引用校验基础 |
| `internal/agenttask` | Agent `prepare_asset` 单任务创建和查询 | Agent 整理处理记录和幂等模式 |
| `internal/agentapp` | 成员启动 Agent application session | Agent 绑定和会话审计 |
| `internal/auth` | member session、Agent API Key 认证 | 两种 principal 的认证入口 |
| `internal/authz` | 根据 principal 和 capability 查询允许的 resource model / application | 权限查询基础，但需要扩展 workspace/member/action 维度 |
| `internal/attachment` | 上传、状态、下载、对象存储元数据 | 附件上传、受控下载和审计 |
| `internal/eventing`、`internal/worker` | Outbox/event delivery、投影、Agent、转写 worker | 异步 job、租约、重试和投影事件模式 |
| `db/migrations/0001_core.sql` | 基础组织、资源模型、资产、版本、附件、关系、审计 | 资产和 resource model 的历史基础 |
| `db/migrations/0006_content_core.sql` | workspace/content container/block/conversation 等内容内核 | 内容块、容器、会话和 workspace 草案 |

| `docs/yxt/app.js` | 静态页面、mock 数组、本地状态和 setTimeout 模拟 | 只能复用视觉和交互结构，不能复用数据模型 |

### 1.2 当前阻塞点

1. `resource_models` 和 `assets` 当前主要按 organization 归属，不能满足契约要求的 workspace 强隔离。
2. 现有 workspace/content 表与 asset/resource model 之间没有统一强约束，部分 `workspace_id` 可空。
3. `asset` 写接口只接受 Agent principal；成员端没有同一领域能力的 API。
4. `internal/query` 的授权路径偏 Agent outlet，成员端查询需要独立的 visibility、review 和 workspace 过滤。
5. `task_attempt` worker 消费、folder membership 的批量游标已补齐；完整领域审计和活动读模型仍需增强。
6. `content.Service` 和 `asset.Service` 都直接持有 store 并在 handler 中被逐个调用，缺少统一 application service 和 workspace policy。
7. `handler.go` 仍保留历史 member/Agent/admin DTO 和 handler 实现，路由已迁出但错误/DTO 清理尚未完成。
8. 前端没有任何真实 API 调用；镜头字段、列表列、状态、统计、文档树和问答回复均为静态数据。

## 2. 目标架构

```text
HTTP routes
  -> transport DTO / request validation
  -> authentication middleware
  -> workspace authorization policy
  -> application services
       WorkspaceService
       ResourceModelService
       AssetService
       ReviewService
       ContainerService
       ConversationService
       QueryService
       AutomationService
       AttachmentService
  -> repositories / transaction boundary
  -> PostgreSQL + object store
  -> outbox/eventing -> workers -> retrieval/projection/Agent/ASR
```

`internal/content` 可以在第一阶段作为底层实现继续存在；第二阶段将其对外的 Conversation/Note/Derivation API 收敛到 `internal/conversation` application service，避免出现第二套正文或块模型。`internal/asset` 不应被删除，而是拆出 member 和 Agent 两个 transport 入口，共用同一个 lifecycle service。

### 2.2 启动和依赖注入改造

当前 `cmd/api/main.go` 负责组装 database、auth、query、asset、content、agentapp、agenttask、attachment 和 worker 依赖。每新增一个 application service，必须在这里完成一次显式组装，禁止在 handler 内部临时创建 store 或 provider。

目标依赖关系：

```text
cmd/api/main.go
  -> repositories (store)
  -> WorkspacePolicy
  -> WorkspaceService / ResourceModelService / AssetLifecycleService
  -> ReviewService / ContainerService / ConversationService
  -> MemberQuery / AgentQuery
  -> AutomationService / AttachmentService
  -> httpapi.Dependencies
```

`cmd/worker/main.go` 需要注册模型迁移、asset projection、task run、import/export、conversation note sync、derivation、transcription 等 worker。`internal/config` 增加 schema 限制、任务重试、cursor secret、SSE 超时、导入导出大小和 workspace 默认值配置，并在启动时校验必填配置。

## 3. 数据库重构计划

### 3.1 新的数据库基线

由于不考虑旧数据兼容，开发和测试环境直接重建数据库。建议将当前迁移链整理为新的 Forge 基线，或者新增一个明确的 `0016_yxt_contract.sql` 作为重建边界；不要在线双写旧表和新表。

新的核心表和约束如下：

```text
workspace
workspace_member
workspace_agent_application

resource_model
resource_model_version
resource_model_migration

asset
asset_version
asset_review
asset_tag / asset_version_tag

container
container_asset
document_parent

automation_job
task_run
task_attempt

workspace_settings
member_preferences
```

现有 `model.resource_models`、`model.resource_model_versions`、`asset.assets`、`asset.asset_versions` 可以保留表名，但必须补齐并强制：

- `workspace_id NOT NULL`
- `resource_model.workspace_id` 与 asset workspace 一致
- `asset_version.workspace_id/resource_model_id/resource_model_version_id` 三元一致
- `content_kind`：`record | document | faq`
- `resource_model_version.list_schema`
- `asset.visibility`
- 独立的 `review_status` 派生查询，不把 `pending_review` 写进 publication status
- 历史版本不可更新的服务层约束和数据库触发/权限边界

### 3.2 资源模型 schema

`resource_model_version` 增加：

```text
field_schema jsonb NOT NULL
form_schema jsonb NOT NULL
list_schema jsonb NOT NULL
policy jsonb NOT NULL
schema_checksum text NOT NULL
validated_at timestamptz
published_at timestamptz
retired_at timestamptz
```

需要在数据库迁移或应用校验中保证：

1. `field_schema` 的用户字段 key 不覆盖 `title/markdown/tags/source/attachments`。
2. `form_schema` 和 `list_schema` 只能引用当前字段，不能包含脚本、HTML 或远程组件。
3. published 版本不可 UPDATE；发布通过事务切换 `current_version_id`。
4. 一个 resource model 最多一个当前 published version。

### 3.3 审核和状态

新增 `asset_reviews`：

```text
id
workspace_id
asset_id
asset_version_id
status: pending | approved | rejected | superseded | cancelled
submitted_by
reviewer_id nullable
comment
created_at
decided_at nullable
```

建立部分唯一约束：同一个 `asset_version_id` 最多一个 `pending` review。发布事务必须锁定 asset、asset_version 和 approved review，校验 ETag 后切换发布指针。

### 3.4 容器和关系

新增：

```text
containers(id, workspace_id, parent_id, name, sort_key, status, created_by, ...)
container_assets(container_id, asset_id, created_at, created_by)
document_parents(child_asset_id, parent_asset_id, created_at, created_by)
```

服务层必须检查同 workspace、无环和文档模型类型。删除文件夹要求没有子目录和资产关系，返回 `container_not_empty`。

### 3.5 自动化任务

新增：

```text
automation_jobs(
  id, workspace_id, name, operation, agent_application_id,
  trigger, timezone, concurrency_policy, input_scope,
  max_attempts, retry_backoff, enabled, created_by, ...
)

task_runs(
  id, workspace_id, automation_job_id nullable,
  source, operation, status, progress, input_asset_ids,
  candidate_version_ids, attempt_count, error_code, ...
)

task_attempts(
  id, task_run_id, attempt_no, status, error_code, ...
)
```

`source` 为 `automation | manual | agent`；同一 job 的 `forbid/replace/allow` 并发策略在数据库锁和 service 层双重执行。

### 3.6 导入、导出和索引

复用现有 `asset.import_batches/import_rows/export_jobs`，补 workspace、model version、字段映射快照和权限快照。模型版本发布、字段 searchable/filterable/sortable 变化必须写入 projection job；未完成索引准备时，API 返回明确的 `index_pending` 状态。

## 5. 前端编码规划

### 5.1 前端分层

当前 `docs/yxt/app.js` 是单文件渲染器。第一步不必引入大框架，但必须拆出：

```text
docs/yxt/
  api/client.js             fetch、cookie、错误、ETag、幂等键
  api/workspaces.js
  api/models.js
  api/assets.js
  api/reviews.js
  api/conversations.js
  api/automation.js
  state/store.js             当前 workspace、模型、列表查询、编辑版本
  render/schema.js           field/form/list schema 通用渲染
  render/table.js
  render/editor.js
  render/chat.js
  app.js                     路由和页面组合
```

### 5.2 前端接入顺序

1. 登录后加载 workspace、member role、counts、默认 resource model。
2. 加载 model detail 和当前 version 的三个 schema。
3. 以 list schema 渲染镜头/FAQ/文档表格；以 form schema 渲染编辑器。
4. 接入资产列表、详情、创建、编辑、ETag 冲突。
5. 接入 review queue 和 publish flow。
6. 接入 conversation list、chat stream、references。
7. 接入 container tree、attachments、automation jobs。
8. 最后接 stats/activity/import/export。

### 5.3 前端状态规则

- 当前 workspace 必须进入 URL 或可恢复的路由状态，刷新后重新加载。
- 当前模型版本、工作版本 ID、ETag 和编辑状态必须在 store 中明确保存。
- 任何写操作成功后以服务器响应更新状态，不根据 toast 猜测状态。
- 401 清理 session 并进入登录态；403 显示权限错误；409 进入冲突处理；422 显示字段级错误。
- SSE 断线不能重复发送 human message；使用 client message id 和服务端 message id 做幂等。

## 6. 测试与质量门槛

### 6.1 单元测试

必须覆盖：

- schema 字段/表单/列表校验和类型匹配
- workspace membership/action policy
- visibility 过滤
- asset version 创建、ETag、幂等
- review 状态机和自动发布
- container 环检测和非空删除
- migration preview 的字段映射和默认值
- automation concurrency/retry/cancel
- cursor 编码、过期和权限快照

### 6.2 Repository/数据库集成测试

- organization/workspace/resource model/asset 的复合归属约束
- 一个模型只有一个 published version
- 一个 asset version 最多一个 pending review
- 发布指针和审核记录原子更新
- workspace 查询不会返回其他 workspace
- folder、document parent、asset membership 不能形成环
- task run 的并发和唯一幂等键

### 6.3 HTTP 契约测试

每个新接口至少测试：

```text
200/201/202/204 成功响应
401 未登录
403 无 workspace/action 权限
404 不存在或不可见
409 ETag/状态/幂等冲突
422 schema/字段校验
```

OpenAPI schema、实际 JSON、状态码和 `ETag/Location` 必须一致；测试不允许只验证 HTTP 200。

### 6.4 真实环境测试

1. Docker PostgreSQL + PGroonga/R3 projection（已通过；见上方真实环境验证记录）。
2. OSS 上传、受控下载和附件审计。
3. Eino RAG/ReAct streaming、断线恢复和模型错误。
4. Agent API Key + agent outlet policy + 成员 workspace policy 交叉授权。
5. 模型版本发布、迁移、重新索引和已发布资产查询。
6. Worker 崩溃恢复、lease 过期、重试和取消。

## 7. 开发提交和验收顺序

每个阶段按以下顺序提交，避免 HTTP 先行导致逻辑散落：

1. migration + repository
2. domain model + service + policy
3. worker/event/outbox（如有异步动作）
4. HTTP DTO/router/openapi
5. unit/repository/HTTP tests
6. frontend API adapter and page integration
7. 删除对应 mock 和无效旧路径

阶段合入门槛：

- 所有新增表和状态都有唯一约束、外键或服务层不变量。
- 领域 service 不导入 HTTP、Eino adapter 或前端结构。
- handler 不直接拼 SQL，不直接修改多个领域表。
- 失败路径有明确错误码和审计。
- 关键写接口有幂等和并发测试。
- 前端不再为已接入模块保留 mock 数据。
