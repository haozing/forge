## 一、总体结论

**系统骨架质量较高**：三态生命周期、版本链、发布指针切换、Agent 用户与成员权限双轨隔离、密钥哈希存储与轮换即失效等核心安全机制经实测成立；引用校验拒绝未发布资产在公开通道上成立（**成员检索通道的泄漏属性因 P0-1 未经过真实数据返回场景的有效验证**——已完成代码路径和数据库约束核查，但业务查询结果恒为空）。SSE 流式问答在 2026-08-26 测试窗口内真实打通外部 LLM（DeepSeek，属单次观测，可复现性见 §八说明）。

**但存在 2 个导致关键功能整体不可用的 P0 缺陷**：

1. **统一查询 API 三种检索模式恒返回空结果**——产品文档的核心能力（§6.10 统一查询、验收标准10）。根因已定位到行级：Go 空切片绑定成 SQL NULL。
2. **资源模型版本迁移任务必失败**——模型演进闭环断裂（§6.2 模型迁移要求）。

另有一批"功能存在但契约裂缝"类 P1 问题（角色管理接口不可用、邀请无法被接受、审计日志不达文档要求、附件下载出口配置死锁、检索词表与文档不一致等），以及若干**文档与实现的方向性矛盾**（internal 改名 draft、六种成员角色超出 admin/editor 基线、定时任务 cron 不自动调度、CSV 导入不支持文件格式且无失败行报告下载等）。

## 二、P0 问题（已复核确认）

### P0-1 统一查询（member query）三种模式恒返回空

**现象**：`POST /api/frontend/workspaces/{WS}/query` 在 lexical/semantic/hybrid 下均返回 `items: []`。数据侧完全就绪：工作区内有 7 个 published 资产、`retrieval.chunks` 中存在 ready 状态命中分块、139 条向量齐备；用日志中抓到的**真实绑定参数**手工执行同一 SQL 可返回 1 行。

**根因**（通过 Postgres 语句日志抓取实测参数定位）：`internal/query/member_search.go` 的召回 SQL 使用

```sql
AND (cardinality($9::text[]) = 0 OR a.visibility = ANY($9::text[]))
AND (cardinality($10::text[]) = 0 OR a.publication_status = ANY($10::text[]))
```

当请求不带 visibility/publication 过滤时，Go 侧 `req.Visibility`、`req.PublicationStatus` 是 nil 切片，pgx 将其绑定为 **NULL**（日志实锤：`$9 = NULL, $10 = NULL`）。而 SQL 里 `cardinality(NULL)=0` 结果为 NULL 不是 true，整个 WHERE 变 NULL → 所有行被丢弃 → 恒空。同等写法存在于 member 词法召回、向量召回与会话翻页三处查询。

**影响**：
- 成员前台搜索、RAG 引用召回全部失效（report_D 实测 react 应用反复调工具直至 "tool call budget exceeded"，因为工具永远查不到数据）；
- 由于业务面永远查不出数据，"internal 不泄漏"这一安全属性从未真正经过业务验证（代码层面召回与回读 SQL 也确无 publication_status 强过滤，依赖索引只含已发布内容这一点兜底）；

**修复建议**（任选其一或并用）：
1. Go 侧把 nil 切片规范化为空切片再传参；
2. SQL 判空改为 `($9 IS NULL OR cardinality($9::text[])=0 OR ...)`。

### P0-2 资源模型版本迁移必失败

**现象**：worker 日志三次复现 `create migrated asset version: conn busy`（job_kind=background.process_jobs），对应 `model.resource_model_migrations` 记录 status=failed。

**定性**："conn busy" 是 pgx 单连接被并发使用的错误——后台任务的迁移逻辑在同一连接上嵌套/并发执行了资产版本创建查询。属于确定的并发缺陷，非偶发环境问题。

**影响**：违反 §6.2「字段/枚举/策略变化→创建新模型版本→可重试迁移」的承诺，模型一旦变更无法完成存量数据迁移，新旧版本通道断chain。

## 四、P2 摘要（体验/一致性问题，完整清单见各分区报告）

- 全局幂等中间件先于方法路由：PATCH/pause/resume/comments 等不带 Idempotency-Key 一律 422，而非 405 或业务错误码。
- 非 UTF-8 字节体照存乱码；空白消息可入库；归档会话发消息报404而非冲突语义。
- 错误码命名误导：invitation 流程报 workspace_not_found；scope 类拒绝统一映射 404 asset_not_found；「端点不可用」与「未授权」共用一个403。
- 分页伪实现（成员列表）、集合端点 PUT/DELETE 返 422 应为 405、不存在的工作区返 403 非 404、乐观锁 428/412/422 口径混乱、agent runs JSON 为 PascalCase 与全站 snake_case 冲突。
- default_visibility 五值枚举与文档四档可见性不一致；重复 publish 同一版本返 200 幂等（建议在文档明确）。
- 版本列表无分页；migration-previews 强制幂等键；删除后的资产无法 restore。
- 工作区 Agent 应用视图 `enabled` 字段序列化缺失。

## 六、文档 ↔ 实现 方向性矛盾（需要产品侧拍板）

1. **生命周期术语失效**：迁移 0023 把资产态从 `internal/published/archived` 改名 `draft/published/archived`，产品文档通篇的 internal 已不存在于生产约束；版本层另引入 review_status/workflow_status 多态。

4. **"CSV 导入 + 失败行报告下载"未兑现**（§6.3/P0-5）。
5. **Webhook/定时同步输入方式零实现**（全仓 grep 无 webhook）。
6. **限流承诺未兑现**（§11 非功能"稳定分页与限流"）：无任何 rate limit 组件或配置位。
7. **OpenAPI 规范覆盖严重不足**：admin spec 6/6 一致；open spec 10/11（缺 automation callback）；**frontend spec 仅 14 条 vs 实际约 96 条前端路由**——工作区/成员/资源模型/资产/评审/容器/导入导出/通知/ModelEndpoint/自动化 等 100% 未入规范。"按 Agent 权限动态生成接口说明"（§6.8.3）未实现。
8. **认证架构为逐 handler 自查**（无全局鉴权中间件）。本次扫描未发现漏配（豁免面仅 healthz/readyz/api/public/*），但属结构性风险：新增路由无人兜底。
