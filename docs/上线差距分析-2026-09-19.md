# 上线差距分析——固定阅读样式 + 部署上线（2026-09-19）

## 0. 目标确认

本轮方向（已与用户对齐）：

1. **不做可编辑样式的博客页面**。现有样式编辑能力（站点工作台的 AI 设计会话、主题模板编辑、外观预设）**冻结不动**——不投入、不删除、不重构。
2. 文章展示**固定一套样式**：干净、无花哨装饰、以阅读为核心、适合多数人通用。当前默认主题（760px 阅读宽度、衬线标题、暖纸色）就是这个定位，需要的是**打磨补齐**，不是另起炉灶。
3. 当前唯一优先级是**部署上线**，验收标准就两条：**有文章可看、有 agent 可用**。其余（M3 可访问性审计、主题导入导出、多语言翻译组跳转、自定义角色 UI、语义嵌入、蒸馏卡迁移等）全部延后。

**总体判断：核心链路全部已上线且经过真实验证，差距不大且集中。** 真正卡住两条验收标准的，一个是**数据门禁**（文章可见性），一个是**证书**（域名 TLS），一个是**发钥入口**（agent 自助接入）。代码层面只有一个 S 级改动（正文排版 CSS，恰好就是"固定好好阅读的样式"本身）。

以下所有数据均为 2026-09-19 线上真实环境（101.35.49.253 / agentchunzhi-postgres-1）核对结果。

## 2. 差距清单

### 主线 A：有文章可看

#### A1（关键路径｜数据）768 篇文章被可见性门挡住，一篇都上不了站

线上实测数据（ITD-S5-b095af 工作区，已发布资产）：

| 模型 | 可见性 | 数量 |
|---|---|---|
| builtin_document | **workspace** | **768** ← agentblog 知识库主体 |
| builtin_document | organization | 23 |
| builtin_document | public | 1 |
| knowledge_card | organization | 1182 |

收录三道闸 = 已发布 ✓ + **资产可见性 ∈ 站点 scope 天花板** ✗ + 模型 public_site 通道 ✓（已开）。

而站点 `itd-site-b095af` 的 `default_content_scope = public` → 只有那 1 篇 public 文章能上站。**首页实测只有 1 张卡片。**

**修法（纯数据操作，无代码改动）**：
1. 站点 scope `public → organization`（PATCH site）；
2. 768 篇 builtin_document 可见性 `workspace → organization` 批量 PATCH（模型 policy 白名单 `["workspace","organization","public"]` 允许，已核实）；
3. 注意发布缓存（300s TTL）——改完抽查页面，必要时触碰站点触发失效事件；
4. knowledge_card 的 public_site 通道**未开**，1182 张卡不会混入站点，现状即安全（见 A4）。

#### A2（数据｜S）站点从未发布过 release

`itd-site-b095af` 的 `published_release_id` 为空（20 个站点里只有 3 个发过）。无 release 时渲染工作配置，能看但不正式。门禁数据修完后**做一次首次发布**，让站点进入版本化交付状态（发布历史、回滚、SEO 快照才完整）。

#### A3（代码｜S）默认主题正文区没有排版样式——"固定好好阅读的样式"就差这一段

`internal/theme/defaults/theme.css` 只定义了页面骨架（header/卡片/标题/meta），**`.article-body` 内部零规则**：正文里的 h2/h3、列表、代码块、行内代码、引用、表格、图片、链接全部是浏览器默认样式。

线上实测影响面：768 篇中 **417 篇含二级标题**、21 篇含代码块、1 篇含表格——过半文章观感受损。

**修法**：给 `theme.css` 补一段正文排版（约 30-40 行）：`h2/h3` 间距与尺寸、`p` 段距、`pre/code` 等宽字体+横向滚动+底色、`blockquote` 左边线、`table` 边框、`img{max-width:100%}`、CJK `word-break` 防溢出。改完重建 api 镜像部署即可（模板/CSS 是 go:embed，必须重建镜像）。这**正是**"固定一个能好好阅读的通用样式"的最后一块，不引入任何可编辑机制。

#### A4（决策）knowledge_card 是否上站——默认不上

1182 张知识卡是蒸馏卡形态，混进阅读站会是噪音。通道未开 = 现状安全。若将来要上，再开通道+考虑独立栏目。**本轮不动。**

#### A5（运营｜S）站点元数据是占位文字

站点名"ITD 站点"、描述为空（meta 兜底回退站名）。发布前改成正式名称+一句话描述；og:image 分享图未配（可选）。

### 主线 B：有 agent 可用

#### B1（主要差距｜前端 M）agent 用户创建与 API Key 签发没有界面

后端 API **齐全**（已核实）：`POST /api/admin/agent-users`（注册+发钥）、`access-policy`、`api-keys/rotate`、`api-keys/revoke-all`、`GET onboarding`（返回完整接入包：base_url、鉴权格式、能力清单、资源模型、sample curl）。成员列表里只有"API Key 接入"**占位**。

即：外部 agent 接入能力 100% 就位，差一个让管理员自助完成的界面。**最小解法二选一**：
- 快：把 onboarding 返回包 + `/settings/agent-access` 接入指南页补一段"管理员如何发钥"的操作文档（跑一次 admin API 即得）；
- 正：管理台补一个发钥面板（建 agent 用户 → 选能力 → 出 key 一次性展示 → 轮换/吊销）。建议 P1 做正式面板，上线当天用快解法。

#### B2（产品遗留｜S）key 能力清单与应用能力清单双份不同步

`api_keys.capabilities` 签发时冻结，PATCH 应用行的 capabilities 不回写已发 key。不阻塞上线，但会在"改了应用能力却不生效"时造成困惑。最小处理：发钥面板/文档里写明"改能力需轮换 key"；理顺（回写或单一来源）延后。

#### B3（验收）上线前用正式 key 跑一遍 MCP 冒烟

8 工具 conformance 与真实用户流 e2e 此前均 PASS，但用的是测试 key。上线验收清单里加一条：新签 key 走 `tools/list → search_assets → get_asset → create_document → confirm` 冒烟（发布类工具已 human_only，不在 agent 面）。注意 B4 证书问题会直接影响外部 agent 客户端。

### 主线 C：部署上线基础设施

#### C1（硬伤｜配置）域名证书是自签 IP 证书

`forgeapi.qidu.site` DNS 已解析到 101.35.49.253，但 443 出示的证书是 **CN=101.35.49.253 的自签证书**（2026-08-31 签发，10 年期）。后果：

- 浏览器访问公开站/管理台持续告警（现在靠手动豁免）；
- **外部 agent / MCP 客户端默认直接拒绝连接**（curl 实测 000），"有 agent 可用"对外部接入形同虚设；
- canonical 已指向域名（`https://forgeapi.qidu.site/...`），搜索引擎与正规客户端同样受影响。

**修法**：域名已在手，Let's Encrypt（certbot webroot/standalone 或 DNS-01）签一张正规证书，nginx `0-ip-443.conf` 换证书路径并 reload。这是**唯一真正的上线硬伤**。

#### C2（风险｜S）两仓 64 + 26 个提交未推送

部署走 tar+compose 不依赖 git，但 forge（64 commits）与 zck-web（26 commits）全部悬在本地——服务器一旦丢失，近三周全部工作无备份。**建议立即 push**（远端 haozing/forge 已配好）。

#### C3（卫生｜S）forge 工作区一个未提交改动

`internal/query/lexical_repository.go` 有一处未提交的 QUERY_LEX_DEBUG 调试日志（环境变量门控，无害）。是之前排查 MCP 检索"0 条"时加的——作为常驻调试开关注入合理，**建议提交**；不要留着悬空。

#### C4（延后项，不影响本轮验收）

语义嵌入未配置（fulltext 检索已可用）；11,201 张蒸馏卡未迁移；M3（Eino 已关闭、可访问性审计、主题导入导出）；多语言翻译组访客端跳转；自定义角色 UI。全部按目标确认第 3 条延后。
