# AgentChunzhi v2 阶段 3 实施方案

> 文档状态：实施基线  
> 适用范围：产品 v2 阶段 3  
> 前置文档：`产品文档-v2.md`、阶段 0、阶段 1、阶段 2 实施方案  
> 核心交付：已发布资产投影、结构化/全文/语义/混合统一查询、引用、稳定分页、权限终检、查询审计  
> 数据策略：只面向 v2 空库基线，不兼容已退役的旧表、旧枚举或旧数据；检索旧路由按 `docs/route-retirement-ledger.md` 退役，未到所属阶段的旧路由不得被新代码调用。

## 1. 文档结论

阶段 3 不是继续修补现有的“R3 检索”，而是在阶段 0 至阶段 2 的最终领域契约上重建检索读模型。

阶段结束后，系统必须只有一条检索主链路：

```text
Asset / AssetVersion / Tag 主数据
        │
        ├── 结构化查询：直接读取主数据
        │
        └── 已发布事实事件
                │
                ▼
       RetrievalProjection（可重建）
                │
                ├── PGroonga 全文召回
                └── pgvector 语义召回
                         │
                         ▼
                  UnifiedQueryService
                         │
               主数据权限与发布状态终检
                         │
                         ▼
                 成员 / Agent / OpenAPI / 未来站点
```

必须冻结以下决策：

1. PostgreSQL 中的 Asset、当前 published pointer、AssetVersion、ResourceModelVersion、Tag relation 和权限关系是唯一权威来源。
2. `structured` 直接查询主数据，不能依赖 chunk、embedding 或投影健康状态。
3. `fulltext`、`semantic`、`hybrid` 只检索 `Asset.current_published_version_id` 指向的不可变版本，不提供 draft/working 搜索假象。
4. 投影召回允许最终一致；任何结果返回前的发布状态、当前版本和访问权限必须强一致终检。
5. 所有入口共用一个 `UnifiedQueryService` 和一个 `QueryAccessScope`，不再维护成员版与 Agent 版两套 SQL。
6. 搜索会话冻结排序，不冻结授权。翻页时重新解析当前权限，失权条目跳过并向后补足页面。
7. 投影 run 一旦 ready 就不可修改；重建创建新 run，不能删除并重写仍可能被搜索会话引用的 chunk。
8. embedding 和 reranker 网络调用不得发生在数据库事务内。
9. 查询审计属于 QueryService 的必经边界，不由 handler、Agent runtime 或调用方各自“尽力记录”。
10. 只有 `structured/fulltext/semantic/hybrid` 四种模式；删除 `lexical` 别名和所有旧枚举兼容。

阶段 3 的完成标准不是“某个关键词能搜到”，而是：同一份当前已发布资产可以被所有受控调用方通过同一个服务准确召回，标签和字段过滤语义一致，排序可解释，引用可验证，权限变化立即影响返回，投影故障可重试且不阻塞发布。

## 2. 阶段边界

### 2.1 前置条件

开始阶段 3 前，阶段 0 至阶段 2 的退出门槛必须全部通过，尤其包括：

- 组织、工作区、成员与技术身份已经使用 v2 Principal 和 Policy；
- 工作区角色固定为 `admin/editor/reviewer/viewer`，`reviewer` 与发布审核子系统保留；
- AssetDraft 可变、AssetVersion 不可变，发布状态只在 Asset 上；
- visibility 只允许 `workspace/organization/public`；
- ResourceModelVersion policy 已采用 `visibility/channels/retrieval/publishing`，不存在 `outlets`；
- `origin` 与 `confirmation_status` 已替代旧 `quality/workflow_status` 混合语义；
- Tag、AssetDraftTag、AssetVersionTag 已是关系型模型，查询过滤使用阶段 2 的 `tag.Filter`；
- outbox、event delivery、River 和 dead/retry 机制可用；
- 新实现只允许注册 `/api/v2`、`/api/open/v2`、`/api/public/v2`；阶段 0/1/2/5 台账中的旧路由仅作为待退役遗留项存在，不能被 QueryService 或新 handler 调用；
- `docs/route-retirement-ledger.md` 已建立；阶段 3 只能把检索旧路由标记为 `retired`，不能把 identity、tag 或 PublicSite 路由一并删除；
- v2 空库 migration baseline 可从零创建并通过所有约束测试。

如果代码库仍处于当前事实状态，不能直接在 [fulltext.go](/D:/code2/agentchunzhi/internal/query/fulltext.go:1) 或 [projector.go](/D:/code2/agentchunzhi/internal/retrieval/projector.go:1) 上追加阶段 3 功能。必须先合入阶段 0 至阶段 2 的模型收口，否则会把旧 `outlets/quality/tags JSONB/publication_status` 再次固化进新检索层。

### 2.2 阶段 3 包含

- 统一查询领域 contract、planner、executor、authorizer、presenter；
- 工作区成员查询、组织级已发布查询、受控 OpenAPI 查询；
- `structured/fulltext/semantic/hybrid` 四种模式；
- ResourceModel 字段类型校验、关系型标签 any/all/none 过滤；
- 已发布资产 canonicalization、Markdown 分段、chunk、全文投影和 embedding；
- 组织级 projection profile 的 warming、active、retired 生命周期；
- 事实事件到内部投影 job 的可靠消费；
- profile backfill、单资产 rebuild、失败重试、状态与清理；
- PGroonga 全文索引、pgvector HNSW 向量索引；
- hybrid RRF 与可选 reranker；
- asset 级去重、引用定位、引用终检；
- 事务化搜索会话与 HMAC cursor；
- 查询执行审计、阶段耗时、投影 lag 和 provider 健康指标；
- v2 OpenAPI 契约、服务集成测试、真实 PostgreSQL 检索集成测试；
- 删除当前重复查询、旧检索路由和旧投影命令事件。

### 2.3 阶段 3 不包含

- AgentApplication、对话编排、答案生成与引用渲染；属于阶段 4；
- PublicSite、站点绑定、匿名访问和站点搜索适配器；属于阶段 5；
- 管理后台和检索 UI；属于阶段 6；
- 多区域、跨库检索、分片、冷热层、灾备演练和容量压测；属于阶段 7；
- 草稿正文全文/语义搜索；工作台对 working 内容继续使用阶段 0/2 的 AssetReadService 结构化列表；
- 附件二进制 OCR、ASR 或附件全文抽取；阶段 3 只投影已经进入 AssetVersion 的规范文本；
- 社区、计费、分成、收益；
- 字段级 ACL、部门层级、个人 private 数据域；
- 向量模型由租户自由填写任意 URL 或凭证；provider 必须由部署侧登记；
- 对旧 R3 表、旧 search session、旧 cursor、旧 `/api/frontend` 或 `/api/open/v1` 的兼容。

## 3. 当前代码审计

### 3.1 当前投影把外部网络调用包在数据库事务中

[projector.go:66](/D:/code2/agentchunzhi/internal/retrieval/projector.go:66) 在 `Rebuild` 开头开启事务，[projector.go:161](/D:/code2/agentchunzhi/internal/retrieval/projector.go:161) 在事务未提交时调用 embedding provider。HTTP 超时会长期占用连接、MVCC snapshot 和锁，provider 重试还会放大数据库压力。

同一实现还存在以下问题：

- 无配置时自动使用伪随机 HashEmbedding，[projector.go:37](/D:/code2/agentchunzhi/internal/retrieval/projector.go:37)；
- 投影时静默创建 active config，[projector.go:135](/D:/code2/agentchunzhi/internal/retrieval/projector.go:135)；
- 标题、Markdown 和 fields JSON 直接拼接，[projector.go:127](/D:/code2/agentchunzhi/internal/retrieval/projector.go:127)，缺少 summary、标签、字段顺序和来源定位；
- 重试时删除并重建同一 run 的 chunk，[projector.go:146](/D:/code2/agentchunzhi/internal/retrieval/projector.go:146)，破坏 session 引用稳定性；
- embedding 失败后把 expected count 改成 0，最终仍将 run 标为 ready，[projector.go:178](/D:/code2/agentchunzhi/internal/retrieval/projector.go:178)，健康状态失真；
- `Delete` 用三个独立语句修改 chunk、embedding 和 run，[projector.go:84](/D:/code2/agentchunzhi/internal/retrieval/projector.go:84)，任一失败都会形成部分删除。

### 3.2 当前使用下游命令冒充领域事实

[projector.go:247](/D:/code2/agentchunzhi/internal/retrieval/projector.go:247) 写入 `asset.retrieval_projection_requested`；注册表只订阅这个事件，[eventing.go:125](/D:/code2/agentchunzhi/internal/eventing/eventing.go:125)。Asset service 因此直接依赖 retrieval 包，并决定“rebuild/delete”技术动作。

最终架构应由 retrieval consumer 订阅 `asset.published`、`asset.archived`、`asset.visibility_changed`、`tag.updated` 等领域事实，再在 retrieval 边界内生成 River job。Asset 聚合只陈述事实，不了解 chunk 或 embedding。

### 3.3 当前有两套重复且语义分裂的 Query

[fulltext.go](/D:/code2/agentchunzhi/internal/query/fulltext.go:1) 和 [member_search.go](/D:/code2/agentchunzhi/internal/query/member_search.go:1) 分别实现 Agent/Open 与成员查询。二者复制候选召回、RRF、rerank、session 和 cursor，却返回不同粒度：成员路径按 asset 去重，另一条路径可能返回同一资产的多个 chunk。

SQL 仍读取已经被阶段 0 删除的 `policy.outlets` 和 `quality`，例如 [fulltext.go:224](/D:/code2/agentchunzhi/internal/query/fulltext.go:224)；标签仍通过 `v.tags` JSONB 拼回通用过滤函数，[fulltext.go:409](/D:/code2/agentchunzhi/internal/query/fulltext.go:409)。继续修补其中任意一条都会再次产生契约漂移。

### 3.4 当前 structured 并不是真正的结构化查询

当前 `structured` 复用 lexical candidate 路径，只是允许 query 为空；候选仍来自 `retrieval.chunks`，数量又被固定候选上限截断。因此：

- 未发布 working version 即使接口接受，也永远不在召回集合中；
- 还未投影、投影失败或 profile 切换中的已发布资产无法被结构化查询找到；
- 纯标签/字段查询会被 chunk 数量和全文排序影响；
- 一个资产的多个 chunk 会挤占候选窗口。

最终 `structured` 必须从 Asset 当前 published pointer 出发，直接连接不可变版本、ResourceModelVersion 和标签关系。

### 3.5 当前 filter 只检查字段存在，不检查字段类型和 operator

[filters.go:167](/D:/code2/agentchunzhi/internal/query/filters.go:167) 只验证字段是否存在于所有请求模型；[filters.go:113](/D:/code2/agentchunzhi/internal/query/filters.go:113) 对所有字段开放同一组 operator。数据库函数 [0015_retrieval_r3.sql:28](/D:/code2/agentchunzhi/db/migrations/0015_retrieval_r3.sql:28) 再对任意 JSONB 做动态判断。

这无法保证 date、number、enum、multiselect 和 boolean 的比较语义，也无法输出准确错误位置。阶段 3 必须先基于请求指定的 ResourceModelVersion 编译 typed predicate，再生成固定 SQL 片段。

### 3.6 当前 search session 不是可靠快照

[fulltext.go:399](/D:/code2/agentchunzhi/internal/query/fulltext.go:399) 创建 session 后逐条、非事务地插入 item，[fulltext.go:403](/D:/code2/agentchunzhi/internal/query/fulltext.go:403)。中途失败会留下部分 session。

翻页又连接 active profile 和当前 chunk，[fulltext.go:409](/D:/code2/agentchunzhi/internal/query/fulltext.go:409)，profile 激活、重建或清理会让原候选消失；同时 [fulltext.go:394](/D:/code2/agentchunzhi/internal/query/fulltext.go:394) 要求权限 revision 和 projection fingerprint 完全不变，任何正常权限变更都直接判 cursor 无效。

最终 session item 必须保存 asset 级排序结果和最小引用快照；翻页重新终检当前权限，而不是依赖旧 chunk 仍处于 active。

### 3.7 当前 query audit 不在业务边界中

[frontend_query.go:73](/D:/code2/agentchunzhi/internal/httpapi/frontend_query.go:73) 由 handler 在调用后 best-effort 写日志，错误被 `_ =` 丢弃；Agent runtime 和其他入口还可能各写一份。当前表只有 actor user、endpoint、hash、count、outcome 和 latency，[0041_retrieval_query_audit.sql:3](/D:/code2/agentchunzhi/db/migrations/0041_retrieval_query_audit.sql:3)，无法表示技术身份、通道、执行模式、降级、阶段耗时和多工作区范围。

最终审计必须由 QueryService 先创建 execution，再完成 execution；任何入口都不能绕开。

### 3.8 当前运行配置会制造“假语义检索”

[config.go:72](/D:/code2/agentchunzhi/internal/config/config.go:72) 默认模型是 `hash-embedding`，[api/main.go:101](/D:/code2/agentchunzhi/cmd/api/main.go:101) 和 [worker/main.go:104](/D:/code2/agentchunzhi/cmd/worker/main.go:104) 在 development/test 自动启用 HashEmbedding。它只能用于算法单元测试，不能让本地或测试环境表现得像真实语义检索。

cursor secret 也有固定默认值，[config.go:79](/D:/code2/agentchunzhi/internal/config/config.go:79)。最终环境缺少 secret 或 provider manifest 时必须在启动/readiness 阶段显式失败或把 semantic 标成 unavailable，不能使用静默替代品。

### 3.9 当前数据库模型混合了配置、生命周期和可变行

[0015_retrieval_r3.sql](/D:/code2/agentchunzhi/db/migrations/0015_retrieval_r3.sql:70) 以 organization + resource model 建 profile，跨模型查询必须临时证明 embedding identity 一致；chunk 同时保存相同的 `content/search_text/canonical_text`；session item 没有稳定引用快照和完整租户外键。

后续 [0037_retrieval_query_modes.sql](/D:/code2/agentchunzhi/db/migrations/0037_retrieval_query_modes.sql:1)、[0044_unified_query_structured_ranking.sql](/D:/code2/agentchunzhi/db/migrations/0044_unified_query_structured_ranking.sql:1)、[0045_retract_unpublished_projections.sql](/D:/code2/agentchunzhi/db/migrations/0045_retract_unpublished_projections.sql:1) 又以补丁方式修枚举和旧数据。v2 空库基线中不保留这条迁移历史。

### 3.10 当前关键集成测试默认跳过

[integration_test.go:17](/D:/code2/agentchunzhi/internal/retrieval/integration_test.go:17) 在未提供环境变量时直接 skip，并用 HashEmbedding 验证 hybrid。这不能证明默认 CI 中 PGroonga、pgvector、真实 provider contract、权限终检和并发重建有效。

阶段 3 必须把带 PGroonga + pgvector 的 PostgreSQL 集成测试变成 CI 必跑项；provider contract 使用确定性的 fake HTTP server，算法单测才允许内存向量桩。

## 4. 最终架构与领域边界

### 4.1 组件职责

| 组件 | 职责 | 明确不负责 |
| --- | --- | --- |
| QueryAccessScopeCompiler | 把 Principal、membership、AgentAccessPolicy、channel policy 编译成不可扩大的访问范围 | 不执行全文/向量 SQL |
| QueryValidator | 规范化请求，读取 ResourceModelVersion schema，编译 typed filters | 不读取投影 |
| StructuredRepository | 从主数据查询当前已发布资产 | 不连接 chunk |
| LexicalRepository | 从 active profile 对应 projection head 指向的 ready lexical chunk 召回 | 不决定最终权限 |
| SemanticRepository | 生成 query embedding 并从 projection head 指向的 ready embedding 召回 | 不做 handler 降级决策 |
| RankingService | RRF、可选 rerank、chunk 到 asset collapse | 不读取成员角色 |
| SearchSessionRepository | 原子保存排序快照和 cursor 状态 | 不把 session 当授权事实 |
| QueryFinalAuthorizer | 批量重读主数据并终检当前权限/版本/过滤条件 | 不改变候选排序 |
| CitationService | 验证引用仍指向当前授权 published version | 不生成站点 URL |
| ProjectionProfileService | 管理 warming/active/retired profile 和激活门槛 | 不保存供应商凭证 |
| ProjectionCoordinator | 消费事实事件、创建 run 和内部 job | 不在事件事务中调用 provider |
| Canonicalizer/Chunker | 生成可复现 segment、locator、chunk 和 checksum | 不查询权限 |
| EmbeddingWorker | 批量调用 provider、短事务保存向量 | 不持有长事务 |
| QueryExecutionRepository | 查询开始/结束审计及无敏感内容指标 | 不保存 query 明文 |

### 4.2 依赖方向

```text
HTTP / Agent adapter / Future Site adapter
                  │
                  ▼
       QueryAccessScopeCompiler
                  │
                  ▼
         UnifiedQueryService
          │       │       │
          │       │       ├── QueryExecutionRepository
          │       │       └── SearchSessionRepository
          │       │
          │       ├── StructuredRepository
          │       ├── LexicalRepository
          │       └── SemanticRepository -> EmbeddingProvider
          │
          ├── RankingService -> optional Reranker
          └── QueryFinalAuthorizer -> Asset/Policy/Tag repositories

Domain fact events -> ProjectionCoordinator -> River internal jobs
                                              │
                         Canonicalizer -> ChunkRepository -> EmbeddingProvider
```

禁止以下依赖：

- Asset、Tag、ResourceModel service import `internal/retrieval`；
- HTTP handler 获得 `*store.Store` 并手写查询或索引 SQL；
- query package import Agent runtime、PublicSite 或 HTTP；
- retrieval package读取 session cookie 或 API key；
- Agent 和站点绕过 QueryService 直接读 `retrieval.*`；
- provider adapter 写业务表或决定访问范围。

### 4.3 一致性模型

| 对象 | 一致性要求 |
| --- | --- |
| Asset 发布事务 | 强一致；只提交主数据、审计和事实事件，不等待索引 |
| 投影可见 | 最终一致；目标正常 P95 小于 30 秒 |
| 查询候选 | 使用 active profile 下每个 asset 的 projection head 指向的 ready/degraded 投影 |
| 结果发布状态 | 返回前强一致终检 |
| visibility 与 channel policy | 返回前强一致终检 |
| membership / AgentAccessPolicy | 每次请求和每次翻页重新编译 |
| 标签/字段过滤 | 候选 SQL 先过滤，返回前基于当前 published version 再确认 |
| 搜索排序 | session 生命周期内固定，不因新内容插入而漂移 |
| 引用 | 返回时和被 Agent 使用时都可重新验证 |

索引延迟可以导致新发布内容暂时未被全文/语义召回，但绝不能导致已归档、已替换或失权内容继续返回。

```go
	ResourceModelIDs    []uuid.UUID
	AllowedVisibilities []asset.Visibility
	VersionScope        string // 阶段 3 固定 published
	PolicyRevision      int64
	ScopeFingerprint    [32]byte
}
```

固定规则：

- 所有 ID 在 compiler 中排序、去重；空切片表示无权限，不表示“不限制”；
- `ScopeFingerprint` 是 canonical scope 的 HMAC，不含角色显示名或明文凭证；
- Query request 只能对 scope 求交集，不能添加 workspace、model 或 visibility；
- 阶段 3 的 `VersionScope` 只有 `published`；
- ResourceModelVersion policy 的 channel 和 retrieval mode 在 planner 中继续收窄；
- Query repository 不再根据 `user_type`、role 字符串或 API endpoint 自行推导权限。

### 5.2 成员工作区查询

`ForWorkspaceMember` 必须：

1. 校验组织有效、用户有效和显式 WorkspaceMembership；
2. 校验 `query.execute`；
3. scope 只包含 path 中一个 workspace；
4. 允许读取该 workspace 内 `workspace/organization/public` visibility；
5. 只包含该 workspace 可用且 channel.workspace.enabled 的 ResourceModel；
6. 不因为 organization admin 身份自动加入未有 membership 的 workspace。

### 5.3 组织级已发布查询

`ForOrganizationMember` 面向跨工作区的组织知识查询：

- 调用者必须是该组织有效成员；同组织身份对 `organization/public` published 内容形成一条窄化的 organization-read grant，不要求借用某个 workspace role；
- 不要求每个 workspace membership；
- 只允许 `organization/public` visibility；
- `workspace` visibility 必须排除；
- 只读取 channel.workspace.enabled 且 retrieval mode 启用的模型；
- 返回项仍包含 workspace id，后续资产详情读取必须再次使用对应 AssetReadScope。

这与阶段 0 的 visibility 契约一致：组织可见内容就是面向组织成员的发布范围，不能被误缩成“只有工作区成员可见”。

阶段 0 权限矩阵中“Organization admin（无 membership）不能执行工作区查询”约束的对象是 workspace scope；它不应覆盖同一文档明确规定的 organization visibility grant。该 grant 只允许查询当前 published 的 `organization/public` 内容，不授予 workspace visibility、AssetDraft、working version、历史版本、模型管理或工作区 Agent 应用权限。

### 5.4 Agent 与 OpenAPI 查询

Agent 技术身份不继承创建者、调用成员或 organization admin 的权限。

`ForAgent` 的最终 scope 是以下交集：

```text
Agent identity organization
∩ AgentAccessPolicy.workspaces
∩ AgentAccessPolicy.resource_models
∩ AgentAccessPolicy.actions contains query.execute
∩ ResourceModelVersion.channels.agent
∩ ResourceModelVersion.retrieval.<requested mode>
∩ allowed visibility
∩ current published version
```

`ForOpenAPI` 使用 `channels.open_api`，并进一步受 API key scope 限制。API key 只保存 hash，不能把 key id 当成员 user id。

ResourceModel policy 即使允许 `channels.agent.content_scope=all`，阶段 3 统一检索仍只查询 published projection；`all` 只允许阶段 4 的受控资产工具读取 working 内容，不会使 draft 进入检索索引。

### 5.5 查询终检

候选召回时先连接主数据做一次 scope 过滤，避免把无权内容发送给 reranker。返回前 `QueryFinalAuthorizer` 再批量确认：

- Asset.organization_id/workspace_id/resource_model_id 仍在当前 scope；
- Asset.publication_status 为 `published`；
- Asset.current_published_version_id 等于候选 version；
- visibility 仍被 scope 允许；
- ResourceModelVersion channel 和对应 retrieval mode 仍启用；
- tag any/all/none 和 typed field filters 仍成立；
- Agent/OpenAPI policy 仍允许；
- 将来 PublicSite binding 仍有效。

终检失败不返回 403，也不暴露被跳过数量；该候选像不存在一样被过滤。

## 6. 统一查询契约

### 6.1 Query mode

| mode | 权威数据/投影 | query 文本 | 排序 |
| --- | --- | --- | --- |
| `structured` | Asset + current published AssetVersion + Tag relation | 必须为空 | `published_at DESC, asset_id DESC` |
| `fulltext` | active profile 下 projection head 指向的 lexical-ready chunk | 必填 | PGroonga score |
| `semantic` | active profile 下 projection head 指向的 semantic-ready embedding | 必填 | cosine similarity |
| `hybrid` | fulltext 与 semantic 并行召回 | 必填 | weighted RRF，可选 rerank |

不接受 `lexical`、`vector`、`keyword` 等别名。`ranking_method` 是响应元数据，不是请求 mode。

ResourceModel policy 不增加 `retrieval.hybrid` 开关。hybrid planner 对每个 bound ResourceModelVersion 分别求值：`retrieval.fulltext.enabled` 决定是否进入全文分支，`retrieval.semantic.enabled` 决定是否进入语义分支。显式请求某一个 ResourceModel 时，两路都关闭则返回 `query_mode_not_enabled`；多模型查询则排除两路都关闭的模型。只有一条策略允许的分支时按该分支执行，`executed_mode` 反映实际模式且不算技术降级；策略允许的分支因 provider/数据库故障未执行，才按 10.6 节标记 degraded。

### 6.2 Request

```json

```

固定限制：

- `query` trim 后最多 1,000 个 Unicode code point；全文类 mode 不允许为空；

- cursor 翻页请求必须携带同一规范化请求，服务校验 request HMAC；
- JSON 使用 `DisallowUnknownFields`，未知字段返回 422；
- mode 为 `structured` 时若 query 非空返回 `structured_query_text_not_allowed`。

### 6.3 typed field operator

QueryValidator 必须读取请求所指 ResourceModelVersion 的不可变 field schema，并按下表编译：

| field type | operator |
| --- | --- |
| text / markdown / url / email | `eq/neq/in/exists` |
| integer / decimal / currency | `eq/neq/in/gt/gte/lt/lte/exists` |
| date / datetime | `eq/neq/gt/gte/lt/lte/exists` |
| boolean | `eq/neq/exists` |
| enum | `eq/neq/in/exists` |
| multiselect / array scalar | `contains/contains_any/contains_all/exists` |
| object | 不允许参与阶段 3 查询 |

值先按 schema 解码成 typed Go value，再使用参数化 SQL。字段不存在、operator 不支持、值类型不符时返回带数组下标和字段 key 的 422；不得把客户端 JSON 直接交给通用 PL/pgSQL interpreter。

`field_filters` 查询 AssetVersion.fields，但从 Asset 当前 published pointer 出发。阶段 3 可以为常用 equality/containment 增加 `fields jsonb_path_ops` GIN；范围条件在授权 workspace/model 范围内执行 typed expression。动态字段规模证明需要专用 typed index table 之前，不提前复制第二份字段主数据。

### 6.4 标签过滤

使用阶段 2 的 `tag.Filter`：

```text
tags_any  -> 至少一个 EXISTS
tags_all  -> 每个规范 Tag ID 均 EXISTS
tags_none -> 所有规范 Tag ID 均 NOT EXISTS
```

解析结果是 workspace 范围内的 Tag ID。组织级多 workspace 查询中，同一个 key 要在各 workspace 独立 resolve，并形成 `(workspace_id, tag_id)` 条件；不能假设 Tag ID 或 display name 跨 workspace 全局唯一。

标签 display name 与 normalized key可以进入 canonical text 以支持全文命中，但结构化标签结果只由 relation 决定。

## 7. 投影模型

### 7.1 投影 eligibility 与 policy 版本

一个 AssetVersion 只有同时满足以下条件才需要 projection run：

1. 它仍是 Asset.current_published_version_id，且 Asset.publication_status=`published`；
2. 它绑定的 ResourceModelVersion policy 至少启用 `retrieval.fulltext` 或 `retrieval.semantic`；
3. 同一 policy 至少有一个消费 channel enabled；
4. policy、visibility 和版本所属组织/工作区关系合法。

仅启用 `retrieval.structured` 的模型不生成 chunk；structured 始终直接读主数据。`retrieval.semantic` 启用而 `retrieval.fulltext` 关闭时仍需生成 chunk 供 embedding 使用，但 LexicalRepository 必须按 bound policy 排除它。profile semantic disabled 时不影响 lexical projection；模型只启用 semantic 而组织 profile 不支持 semantic 时，该版本显示为 semantic ineligible，并在 profile/status 中给出固定原因，不能假装 ready。

field schema、searchable flag、channel 和 retrieval policy 始终取 `AssetVersion.resource_model_version_id` 绑定的不可变 ResourceModelVersion。发布一个新的 ResourceModelVersion policy 不会反向改变旧 AssetVersion 的解释，也不能让检索层把旧版本改绑到 model.current_version_id。

因此，`resource_model.policy_published` 的准确含义是触发 eligibility reconciliation，并为已经明确绑定到该新 version 的当前 published assets 补投影；通常旧资产要经过 ResourceModel migration 形成新 AssetVersion，再由随后的 `asset.published` 触发新投影。它不能无条件先把仍绑定旧 ResourceModelVersion 的 ready run 标 stale。这里是对阶段 0 第 7.2 节“模型相关投影 stale 并批量重建”宽泛措辞的具体收窄，目的是维持 AssetVersion 和 policy 同时不可变。

### 7.2 ProjectionProfile

ProjectionProfile 以 Organization 为 owner。一个组织最多一个 active profile、一个 warming profile；不同 ResourceModel 不再各自选择 embedding identity，从结构上保证跨模型语义查询可比较。

profile 固定记录：

```text
organization_id
generation
manifest_key
canonicalizer_version
chunker_version
tokenizer_version
semantic_enabled
embedding_provider_key
embedding_model
embedding_model_version
embedding_dimensions = 1024
distance_metric = cosine
status = warming | active | retired | failed
revision
created_by / created_at
activated_by / activated_at
retired_at
failure_code
```

v2 阶段 3 把 embedding ABI 固定为 1,024 维 cosine。更换模型通过新 generation 完整 backfill 和原子激活，不能原地修改 active profile。provider endpoint、token 和 secret 不进入数据库；`manifest_key` 必须映射到部署侧登记并通过 startup validation 的 `EmbeddingManifest`。

新组织由应用层 OrganizationProvisioner 创建初始 profile。投影流程不得在处理第一条资产时自动造 config。

### 7.3 CanonicalSegment

Canonicalizer 从不可变 AssetVersion 和关联 Tag 生成有序 segment：

1. `title`；
2. `summary`；
3. Markdown AST block，保留 heading path、block ordinal；
4. ResourceModelVersion 中 `searchable=true` 的非 object 字段，按 schema 顺序，再按 key 稳定排序；
5. 标签 segment，按 Tag ID 排序后包含 normalized key 与 display name。

每个 segment 包含：

```go
type CanonicalSegment struct {
	SourceType    string
	SourceLocator json.RawMessage
	Label         string
	Text          string
}
```

run 的 `canonical_checksum` 对完整有序 segment 集合计算；chunk 的 `source_checksum` 对其所属单个 segment 的规范文本计算。引用中的 char range 始终相对于该 source segment，因此不受其他 segment 新增、删除或重排影响。

规范化规则：

- Markdown 使用 Goldmark AST，不用正则解析 heading 或 block；
- CRLF 归一成 LF，Unicode 使用 NFC，移除行尾空白；
- 不改变大小写，不执行 HTML 渲染，不把附件 URL 或对象存储 secret写入正文；
- field label 来自绑定的 ResourceModelVersion，不读取可变 current model；
- object field 即使存在也不 flatten；阶段 0 schema 已禁止其 `searchable=true`；
- 空 segment 不生成 chunk；整个版本无可检索文本时 lexical projection 为 ready、chunk count 为 0；
- canonical checksum 是 ordered segments 的 canonical JSON SHA-256，不能直接复用 AssetVersion content checksum。

### 7.4 Chunk

Chunk 不跨 CanonicalSegment。chunker 绑定 profile 的 tokenizer：

- embedding 最大上下文 512 tokens；
- target 384 tokens；
- overlap 64 tokens；
- title/field label 作为 metadata prefix 计入 token budget；
- 先按 Markdown block/句界拆分，超长单元再按 tokenizer 切分；
- `char_start/char_end` 是 segment 文本内 Unicode code point offset；
- `source_locator + char range + source checksum` 可唯一解释引用；
- `chunk_checksum` 对 canonicalizer/chunker/version、locator 和文本共同计算。

tokenizer 必须与 manifest 明确绑定。不能继续用固定 rune 数假装 token 数，[projector.go:212](/D:/code2/agentchunzhi/internal/retrieval/projector.go:212) 的实现应删除。

### 7.5 ProjectionRun

每个 `(asset_version, profile, canonical_checksum)` 对应一个 run。状态机：

```text
queued -> building -> lexical_ready -> embedding -> ready
                    └───────────────-> degraded
queued/building/embedding ----------> failed
lexical_ready/ready/degraded --------> stale
degraded ---------------------------> embedding -> ready
```

状态含义：

- `lexical_ready_at != null`：chunk 已完整、不可变，可用于 fulltext；
- `semantic_status=disabled`：profile 不启用 semantic；
- `semantic_status=pending/ready/failed`：向量独立状态；
- `degraded`：lexical 完整但 semantic 失败；
- `failed`：canonicalization 或 chunk 持久化失败，不能用于任何全文召回；
- `stale`：不再是当前 published version 或 profile 已 retired；物理数据暂留给未过期 session。

重复事件命中已 ready/degraded run 时幂等返回；failed run 可在没有 session 引用的前提下清理 partial row 后重试。ready run、chunk 和 embedding 不允许 UPDATE 内容。

同一资产在同一 profile 下必须有显式的 serving pointer，不能靠 `status='ready'` 或时间排序猜当前 run。新增 `retrieval.projection_heads`：

```text
organization_id / workspace_id
asset_id / asset_version_id
projection_profile_id
active_run_id
generation
revision
updated_at
```

`(organization_id, asset_id, projection_profile_id)` 为主键，head 同时保存当前 `asset_version_id`；`active_run_id` 复合外键到同组织的 ready/degraded run。已有 head 时，新 run 必须完整 `ready` 才能替换；`degraded` 不能让已有 ready run 提前下线。首次投影没有旧 head 时允许 degraded 成为 head 以提供 lexical，并明确暴露 semantic incomplete。切换时在一个短事务中锁定 head、确认 Asset 当前 published pointer 仍匹配，再更新 `asset_version_id/active_run_id/generation/revision`；对于仍匹配当前 version 的重建（例如标签改名），切换前旧 run 继续提供查询；若 published pointer 已变化，旧 run 仅保留给未过期 session 的物理清理窗口，终检不得返回旧版本。切换后才标记旧 run `stale`。查询、翻页和引用终检都通过 head 选择 run，不能直接按 run status 取最新行。

### 7.6 Provider contract

```go
type EmbeddingManifest struct {
	Key          string
	ProviderKey  string
	Model        string
	ModelVersion string
	Dimensions   int
	Tokenizer    Tokenizer
	MaxTokens    int
}

type EmbeddingProvider interface {
	Manifest() EmbeddingManifest
	EmbedDocuments(ctx context.Context, texts []string) ([][]float32, error)
	EmbedQuery(ctx context.Context, text string) ([]float32, error)
}
```

要求：

- document/query 接口分开，支持模型要求的不同 prompt；
- 返回数量、维度、NaN/Inf、空向量和归一化约束全部验证；
- 每批最多 32 chunks，单次 5 秒，整体 job 30 秒；
- 429/5xx/timeout 可重试，4xx schema/model error 直接 terminal；
- 日志不写 token、query、正文或 provider body；
- endpoint 只允许 allowlist HTTPS 或明确登记的内网地址，阻断 SSRF；
- `HashEmbeddingProvider` 只能位于 `_test.go` 或 `internal/testkit`，不得由 api/worker 运行时引用。

Reranker 使用独立 manifest。未配置 reranker 是合法的 RRF 模式，不算降级；已配置且调用失败才记录 `reranker_unavailable`。

## 8. 数据库实施方案

### 8.1 空库基线

删除旧 `0015/0037/0041/0044/0045` 所表达的补丁链，把 retrieval schema 作为 v2 baseline 的单一创建脚本。迁移执行器只读取 `MIGRATION_PATH` 根目录直接子级 SQL；共享 v2 环境使用单调递增的 `0017_retrieval_v2.sql`，未共享环境可在生成阶段 0 baseline 时折叠为 `0009_retrieval.sql`，两种路径不能同时存在。脚本必须：

- 显式 `CREATE EXTENSION pgroonga` 和 `CREATE EXTENSION vector`；
- 启动 readiness 检查扩展存在且版本满足镜像锁定；
- 只 CREATE 最终表、约束和索引，不 DROP 旧表、不迁移旧枚举、不回填旧数据；
- schema reset 后从零运行；
- 同一脚本创建 `system.worker_heartbeats`，并为其 `worker_id`、manifest fingerprint、handler manifest 和 lease 建唯一约束/索引；
- 应用运行角色对 immutable projection 内容没有 UPDATE 权限，状态更新通过受控 repository/函数完成。

### 8.2 retrieval.projection_profiles

关键约束：

```text
PK (id)
UNIQUE (organization_id, generation)
UNIQUE (organization_id) WHERE status = 'active'
UNIQUE (organization_id) WHERE status = 'warming'
CHECK semantic_enabled 与 embedding identity 全空/全非空一致
CHECK embedding_dimensions = 1024
CHECK distance_metric = 'cosine'
CHECK active 必须有 activated_at/activated_by
revision > 0
复合 FK (organization_id) -> organization
```

profile immutable 字段在创建后禁止更新；只有 status、revision、激活/失败元数据可变。

### 8.3 retrieval.projection_runs

字段至少包括：

```text

organization_id
workspace_id
asset_id
asset_version_id
resource_model_id
resource_model_version_id
projection_profile_id
canonical_checksum
status
semantic_status

expected_embedding_count / ready_embedding_count
failure_code / failure_stage
queued_at / started_at / lexical_ready_at / completed_at / stale_at
created_at / updated_at
```

约束：

- `UNIQUE (organization_id, asset_version_id, projection_profile_id, canonical_checksum)`；
- 增加 `UNIQUE (organization_id, id)` 供 projection head 使用复合外键；
- 所有 organization/workspace/asset/version/model 使用阶段 0 约定的 composite FK，不能只用裸 UUID；
- counter 非负且 ready 不大于 expected；
- ready 要求 lexical counter相等，semantic enabled 时 embedding counter 相等；
- chunk 内容失败不能伪装成 ready；
- run status 与 semantic_status 使用数据库 CHECK 保证合法组合。

索引：

```text
(organization_id, projection_profile_id, status, updated_at)
(organization_id, workspace_id, resource_model_id, status)
(organization_id, asset_id, asset_version_id, projection_profile_id)
```

`retrieval.projection_heads` 必须作为独立表落地，而不是只写在 service 内存中：

```text
PRIMARY KEY (organization_id, asset_id, projection_profile_id)
asset_version_id
FOREIGN KEY (organization_id, active_run_id) -> projection_runs(organization_id, id)
CHECK revision > 0
```

head 的 `active_run_id` 只能指向 ready/degraded run；存在旧 head 时只有 ready run 可以替换，degraded 只允许初始化空 head。head 切换和旧 run stale 标记必须是同一事务，查询只读取 head 指向的 run。

### 8.4 retrieval.chunks

只保存一份规范检索文本：

```text
id
organization_id / workspace_id
asset_id / asset_version_id
resource_model_id / resource_model_version_id
projection_run_id / projection_profile_id / projection_generation
ordinal
source_type
source_locator jsonb
char_start / char_end
content
source_checksum
chunk_checksum
canonicalizer_version / chunker_version
created_at
```

约束与索引：

- `UNIQUE (projection_run_id, ordinal)`；
- `UNIQUE (projection_run_id, chunk_checksum, source_locator)`；
- run ready 后由 trigger 拒绝 INSERT/UPDATE/DELETE；
- PGroonga index 建在 `content pgroonga_text_full_text_search_ops_v2`；
- B-tree scope index：`(organization_id, workspace_id, resource_model_id, projection_profile_id, projection_run_id)`；
- 不再重复保存相同的 `content/search_text/canonical_text` 三列；
- `source_locator` 有 `jsonb_typeof='object'` check 和 source type对应的应用层 schema validation。

### 8.5 retrieval.chunk_embeddings

```text
chunk_id PK
organization_id
workspace_id
projection_run_id
projection_profile_id
projection_generation
embedding vector(1024)
created_at
```

要求：

- embedding identity 由 profile 定义，不在每行重复 model name/version；
- `vector_dims(embedding)=1024`；
- composite FK 确保 chunk/run/profile 属于同一 organization；
- HNSW `vector_cosine_ops WITH (m=16, ef_construction=64)`；
- scope B-tree 覆盖 organization/workspace/profile；
- 查询事务设置 pgvector 0.8+ iterative scan，并做受控 overfetch，避免 filter 后召回不足。

### 8.6 retrieval.projection_rebuilds

用于追踪 profile backfill、workspace rebuild 和单资产 rebuild：

```text
id / organization_id / workspace_id nullable
projection_profile_id
scope_type = organization | workspace | resource_model | asset
scope_id
reason = profile_warming | manual | policy_changed | repair
status = queued | running | succeeded | partially_failed | failed | cancelled
total / queued / ready / degraded / failed counts
idempotency_key / request_hash
requested_by / requested_at / completed_at
```

它是运维批次，不是领域事件；明细通过 projection_runs 查询，不再建立重复 job 明细表。

### 8.7 retrieval.search_sessions

```text
id
organization_id
subject_kind / subject_id
channel
request_hash
scope_fingerprint_at_create
policy_revision_at_create
query_execution_id
requested_mode / executed_mode / ranking_method
degraded / degradation_reasons text[]
projection_profile_id nullable / projection_generation nullable
result_count
expires_at / created_at
```

规则：

- 默认 TTL 10 分钟；
- request_hash 使用服务端 HMAC-SHA256，不保存 query 明文；
- session 绑定 subject、organization 和 channel；
- scope fingerprint/revision 只用于审计，不要求翻页时相等；
- structured session 的 profile 字段为空；
- 创建 session 与全部 item 必须在一个事务中完成。

### 8.8 retrieval.search_session_items

每行是 asset 级候选，不是 chunk 级候选：

```text
session_id / ordinal
organization_id / workspace_id
asset_id / asset_version_id
primary_chunk_id nullable
citation_id text nullable
lexical_rank / semantic_rank
rrf_score / rerank_score / final_score nullable
ranking_method
citation_source_type nullable
citation_source_locator jsonb nullable
citation_char_start / citation_char_end nullable
citation_excerpt nullable
citation_source_checksum / citation_chunk_checksum nullable
created_at
```

约束：

- `PRIMARY KEY (session_id, ordinal)`；
- `UNIQUE (session_id, asset_version_id)`；
- `UNIQUE (session_id, citation_id)`；`citation_id` 是服务端 HMAC 签名的 opaque `CitationRef`，包含 session/item/version/checksum 身份，不能由客户端自行构造；
- CHECK：`ranking_method='structured'` 时 `citation_id`、`primary_chunk_id` 和所有 citation 字段必须为空；其他 ranking method 的全文类 item 必须有 `citation_id`，semantic 无文本 citation 时也必须明确为空；
- citation excerpt 最多 500 Unicode code point；
- structured item 的 chunk/citation/score 为空；
- snapshot 是短期派生数据；终检确认同一 version 仍为 current published 后才可返回；
- 不要求 chunk 在翻页时仍属于 active profile。

### 8.9 retrieval.query_executions

查询审计使用 UUID execution：

```text
id / organization_id
subject_kind / subject_id / channel
request_id / request_hash
requested_mode / executed_mode / ranking_method
status = started | succeeded | failed | interrupted
degraded / degradation_reasons
resource_model_count
lexical_candidate_count / semantic_candidate_count / fused_candidate_count / result_count
projection_profile_id / generation nullable
embedding_model_identity nullable / reranker_model_identity nullable
stage_latency_ms jsonb
error_code nullable
search_session_id nullable
started_at / completed_at / expires_at
```

另建 `retrieval.query_execution_workspaces(execution_id, organization_id, workspace_id)`，使 workspace audit 只读取与自己相关的执行。

禁止保存：query 明文、field filter value、Tag key、snippet、embedding、provider request/response、API key、用户 cookie。`stage_latency_ms` 只允许固定 numeric keys，避免成为任意日志容器。

### 8.10 清理顺序

maintenance worker 每分钟执行有界批次：

1. 删除过期 search_session_items；
2. 删除过期 search_sessions；
3. 删除 stale/retired 且 `stale_at < now - session_ttl - 5min` 的 embedding/chunk/run；
4. 将长期 `started` query execution 标为 `interrupted`；
5. 按审计保留策略清理 query executions，默认 180 天；
6. 保留 rebuild 批次摘要 90 天。

任何清理 SQL 都按 organization + id 有界分页，不执行运行时全表 DELETE。

## 9. 投影业务流程

### 9.1 领域事件映射

retrieval consumer 直接订阅阶段 0/2 的事实：

| 事实事件 | retrieval 动作 |
| --- | --- |
| `asset.published` | 为 current version 在 active 与 warming profile 各 ensure run/job；旧 head 数据保留但主数据 current pointer 终检立即排除旧版本，新 run ready 后原子切换 head 并标 stale；不以返回旧版本换取零空窗 |
| `asset.archived` | previous published run 标 stale；不建新 run |
| `asset.restored` | 不建投影；恢复不等于发布 |
| `asset.visibility_changed` | 不重建正文；查询主数据终检立即生效，更新 policy revision/fingerprint |
| `asset.version_created` | 不投影；未发布版本不能入索引 |
| `tag.updated` | `changed_fields` 含 display_name 时，查找关联 current published versions，为 active/warming profile ensure 新 canonical run；新 run ready 后按 asset/profile 原子切换 head，切换前旧 run 继续 serving；不进入 canonical text 的字段变化不重建 |
| `tag.archived/restored` | relation 和文本不变，不重建；结构化目录显示由 Tag 状态决定 |
| `resource_model.policy_published` | 使 query scope revision 变化；按 7.1 的 version-bound policy 规则做 eligibility reconciliation，只为绑定新 version 的当前 published asset补 run，不反向改写旧 version |
| `workspace.membership_changed` | 不重建；权限终检立即生效 |
| `agent_access_policy.changed` | 不重建；Agent scope revision 立即变化 |
| `site.binding_changed` | 阶段 5 使用；不改变通用正文投影 |

`tag.created` 本身不影响任何资产，不触发重建。

删除 `asset.retrieval_projection_requested`、`ProjectionRebuild/Delete` 和 Asset 对 retrieval 的 import。Event registry 用 manifest 声明上述事实版本；未知 payload version 进入 dead delivery 并告警，不能猜测解析。

### 9.2 从事实到内部 job

事件 delivery 处理只做短事务：

1. 读取事实 payload 与当前主数据；
2. 幂等确保 projection run/rebuild batch；
3. 对 active + warming profile 插入 River `BuildProjectionRunArgs`；
4. 只有在新 run ready 后由 finalize 事务切换 projection head；本协调事务不得提前标记旧 run stale；
5. 提交 delivery success。

内部 job 类型：

```text
retrieval_build_projection_run
retrieval_embed_chunk_batch
retrieval_finalize_projection_run
retrieval_backfill_profile
retrieval_cleanup
retrieval_reconcile
```

这些是队列命令，不写入 outbox 伪装成领域事实。

### 9.3 BuildProjectionRun

1. 原子 claim queued/failed run，使用 lease 防止重复 worker；
2. 无事务读取不可变 AssetVersion、绑定 ResourceModelVersion、Tag relation；
3. 再确认它仍是 current published，若不是则短事务标 stale；
4. canonicalize 和 chunk 全部在内存完成；
5. 短事务写 chunks、counter、lexical_ready_at；
6. semantic disabled 时直接 ready；
7. semantic enabled 时按 32 个 chunk 拆 River embedding jobs；
8. 空 chunk run 直接 ready，expected embedding 为 0。

写 chunk 事务失败时整个批次回滚。不得逐 chunk 独立提交一个“看起来 ready”的 run。

### 9.4 EmbedChunkBatch

1. 读取 run/profile/chunk text并确认 semantic pending；
2. 释放数据库连接；
3. provider HTTP call；
4. 校验数量、维度、finite value；
5. 短事务 `INSERT ... ON CONFLICT DO NOTHING` 保存 embedding 并更新 counter；
6. 所有 batch 完成后 enqueue finalize；
7. 可重试失败记录 attempt 和分类错误，不修改 expected count。

同一 batch 重复执行必须不重复累计 ready count。counter 以数据库实际行数校准，不能依赖进程内自增。

### 9.5 FinalizeProjectionRun

- lexical 不完整：failed；
- semantic disabled：ready；
- embedding 行数等于 expected：ready；
- 存在 terminal embedding failure：degraded，lexical 可用；
- 仍有可重试 job：保持 embedding/pending；
- 当前 published pointer 已变化：stale；
- profile 已 retired：stale。

当 run 变为 ready（或没有旧 head 时首次变为 degraded）时，finalize 必须在同一短事务中锁定对应 `projection_heads` 行、重新读取当前 published pointer，并仅在版本仍匹配时切换 head；若已变化则该 run 直接 stale，不能覆盖较新的 head。旧 head 只有在切换提交后才进入 grace cleanup。

reconcile worker 定期修复 counter、补发丢失 job、识别超时 lease；不修改 ready chunk 内容。

### 9.6 Profile warming 与激活

1. organization admin 选择部署侧已登记 manifest，创建 warming profile；
2. 创建 organization 级 rebuild，扫描所有 current published assets；
3. warming 期间新发布/标签更新同时为 active 与 warming profile ensure 独立 run/head；
4. backfill 完成后计算覆盖率和失败清单；
5. semantic enabled 时要求所有 eligible version 的 lexical 与 semantic 均 ready；
6. 激活事务锁定 organization profile rows，将旧 active -> retired、warming -> active；
7. 激活后新查询只使用新 generation，既有 search session 继续使用自己的排序快照并做当前权限终检；
8. grace period 后清理 retired profile 数据。

首次 profile 无旧 active 时，`structured` 始终可用；全文类查询在激活前返回 `retrieval_profile_unavailable`。不允许用覆盖不完整的 profile 强制激活。

### 9.7 手工 rebuild

- workspace admin 可对自己的 workspace、resource model 或单个 asset 发起 rebuild；
- organization admin 可发起 organization profile repair，但无 workspace membership 时只能看数量、状态和 error code，不能看 title/snippet；
- rebuild endpoint 要求 Idempotency-Key；
- rebuild 不创建新 generation，只为当前 active profile ensure 缺失/失败 run；
- 单资产 rebuild 永远根据 current published pointer选择版本，客户端不能指定任意 version ID 把 draft 送进索引。

## 10. 查询执行流程

### 10.1 总流程

```text
Authenticate
 -> Capture raw request HMAC and minimal subject/channel metadata
 -> Begin QueryExecution audit
 -> Compile current QueryAccessScope
 -> Decode/normalize/validate request
 -> Validate requested ResourceModel schemas and channel/mode policy
 -> Execute candidate plan
 -> Rank and collapse to assets
 -> Persist SearchSession + all items in one transaction
 -> Re-resolve current scope
 -> Final-authorize and backfill page
 -> Complete QueryExecution audit
 -> Return response
```

provider、数据库和 request 都共享 handler context。默认总预算 5 秒：scope + validation 500ms，DB recall 2s，embedding 1.5s，rerank 1s，终检与 session 1s；未使用预算可向后传递，不用独立 `context.Background()`。

### 10.2 structured plan

从以下 join 开始：

```text
asset.assets a
JOIN asset.asset_versions v ON v.id = a.current_published_version_id
JOIN model.resource_model_versions mv ON mv.id = v.resource_model_version_id
LEFT/EXISTS asset.asset_version_tags avt + tag.tags t
```

先应用 organization/workspace/model/visibility/channel/published scope，再应用 typed fields、tags、origin、confirmation 和 published_at。按 `published_at DESC, asset_id DESC` 获取最多 500 个 asset ID，保存 session。

structured 不读取 projection profile，也不因为 embedding/PGroonga 不健康而降级。

### 10.3 fulltext plan

1. 获取 organization active profile；
2. escape PGroonga query syntax，默认把用户输入作为文本查询，不允许注入 PGroonga operator；
3. 连接 lexical-ready run/chunk 与主数据当前 pointer；
4. 应用 scope、policy、tag 和 field filters；
5. 候选上限 `min(max(200, top_k*10), 1000)`；
6. 按 PGroonga score、asset_id、chunk ordinal 稳定排序；
7. 每 asset 保留最高 3 chunk，最终主结果保留最高一个引用。

全文检索失败返回 503，不静默退化成 structured，因为两者语义不同。

### 10.4 semantic plan

1. active profile 必须 semantic enabled；
2. 用 profile manifest 的 `EmbedQuery` 生成一次 1024 维 query vector；
3. HNSW 查询 semantic-ready embeddings，设置 iterative scan 与 query-local `hnsw.ef_search`；
4. 先 overfetch 至目标的 5 倍，再连接主数据和 scope过滤；
5. cosine distance 转成单调 similarity，仅用于本次 profile 内排序；
6. 候选窗口与全文一致；
7. provider 不可用时返回 `semantic_provider_unavailable` 503。

如果部分 projection run 正处于 pending/failed，返回可用结果并标记 `semantic_projection_incomplete`；不得把 HashEmbedding 当 fallback。

### 10.5 hybrid plan

fulltext 与 semantic 使用 `errgroup.WithContext` 并行执行，随后按 chunk ID 做 weighted Reciprocal Rank Fusion：

```text
rrf(chunk) = 1.0 / (60 + lexical_rank)
           + 1.0 / (60 + semantic_rank)
```

阶段 3 固定 `k=60`、两路权重 1.0。常量集中在 `internal/query/config.go` 并通过测试锁定，不散落 SQL。

若配置 reranker：

1. 取 RRF 前 50 个已通过候选权限过滤的 chunk；
2. 只发送 query、必要正文和稳定 candidate index；
3. provider 返回值必须覆盖全部 candidate 且 index 唯一；
4. rerank score 排序，RRF score 做稳定 tie-break；
5. 调用失败时保留 RRF 顺序，标记 degraded。

若未配置 reranker，ranking_method=`rrf` 且 `degraded=false`。

### 10.6 降级矩阵

| 场景 | semantic | hybrid |
| --- | --- | --- |
| query embedding provider timeout | 503，无结果 | 执行 fulltext，`degraded=true`, reason=`semantic_provider_unavailable` |
| semantic projection 部分未完成 | 返回已有结果并标 degraded | 两路可用候选融合，标 `semantic_projection_incomplete` |
| fulltext repository失败 | 不受影响 | 只执行 semantic，标 `fulltext_unavailable` |
| reranker 未配置 | 不适用 | 正常 RRF，不降级 |
| reranker 已配置但失败 | 不适用 | 返回 RRF，标 `reranker_unavailable` |
| 两路召回都失败 | 503 | 503 `retrieval_unavailable` |
| requested mode 被 policy 禁止 | 无候选/受控错误 | 不把禁止当技术降级 |

`executed_mode` 反映实际执行：例如 hybrid 只剩 fulltext 时为 `fulltext`。degradation reason 使用固定枚举，绝不直接返回 provider error。

### 10.7 asset collapse

排序在 chunk 层完成后：

1. 依 final score 降序扫描；
2. 每个 AssetVersion 第一次出现时建立 asset candidate；
3. 第一 chunk 是 primary citation；
4. 同资产后续最多保留 2 个 alternate chunk，仅供内部引用扩展；
5. asset score 取 primary chunk final score，不对 chunk 数量求和，避免长文档天然占优；
6. 以 `asset_id` 做最终稳定 tie-break；
7. 截取前 500 个 asset candidates 建 session。

### 10.8 搜索会话与 cursor

cursor payload：

```json
{
  "version": 1,
  "session_id": "uuid",
  "next_ordinal": 20,
  "expires_at": 1787990400
}
```

使用至少 32-byte `SEARCH_CURSOR_SECRET` 做 HMAC-SHA256。生产、开发和测试运行服务都必须显式提供；单元测试可注入 test secret。

翻页流程：

1. 验证 HMAC、版本、过期时间；
2. 加载 session 并验证 organization、subject、channel、request_hash；
3. 重新编译当前 QueryAccessScope；
4. 从 next ordinal 向后批量取 snapshot items；
5. 对每批做主数据终检；
6. 跳过失权/已替换/已归档 item，直到填满 top_k 或候选耗尽；
7. next cursor 指向“最后已检查 ordinal + 1”，不是最后已返回 item；
8. 权限扩大不向旧 session 注入新结果，权限缩小立即过滤旧结果。

这样既保持排序稳定，又不会因为正常 membership/policy revision 变化整页报 cursor invalid。

### 10.9 QueryExecution 审计边界

对每一个已通过认证的 query request，QueryService 必须在 scope 编译和解码/业务校验前插入 status=`started` execution；raw request 只保存服务端 HMAC，不保存明文。插入失败时返回 `query_audit_unavailable`，不执行查询。随后即使 scope、validation、provider、超时或终检失败，也必须同步更新 succeeded/failed、stage latency、result count 和 session id；完成更新失败时不把结果返回给客户端。未认证请求不创建 execution，但必须走统一认证错误。

provider 异常、context timeout、validation 后的执行异常都要 finalize failed。进程崩溃留下 started row，由 reconcile 标 interrupted。

审计写入使用短事务，不用一个事务包住整个只读查询和网络调用。

## 11. HTTP API 契约

### 11.1 成员查询

```text
POST /api/v2/workspaces/{workspaceId}/query
POST /api/v2/organization/query
```

- 仅接收 session/Bearer member principal；
- workspace path 使用 `ForWorkspaceMember`；
- organization path 使用 `ForOrganizationMember`；
- 当前 organization 只从 Principal 获取，与阶段 1 的单数 `/api/v2/organization` 资源一致；不接受 path/body organization id；
- 不接收客户端传 organization_id/workspace_id 来扩大范围；
- 使用统一 Request/Response DTO 和错误 presenter。

### 11.2 OpenAPI 查询

```text
POST /api/open/v2/query
POST /api/open/v2/references/validate
```

- 只接收技术身份 API key；
- query 使用 `ForOpenAPI`；
- reference validate 接收 query 返回的 `citation_id` opaque refs，只有 HMAC、session subject、当前 published pointer、source/chunk checksum 和当前 scope 全部匹配才返回 validated；请求体字段固定为 `citation_refs`，不接受客户端自定义 asset/chunk ID。
- 阶段 4 的内置 Agent 直接调用 service + `ForAgent`，不通过 HTTP 自我回环。

阶段 3 不注册 `/api/public/v2/.../search`。阶段 5 的 Site handler 只负责把 site/binding 编译成 scope 并调用同一服务。

### 11.3 投影运维 API

```text
GET  /api/v2/organization/retrieval/profiles
POST /api/v2/organization/retrieval/profiles
POST /api/v2/organization/retrieval/profiles/{profileId}/activate

GET  /api/v2/workspaces/{workspaceId}/retrieval/status
POST /api/v2/workspaces/{workspaceId}/retrieval/rebuilds
GET  /api/v2/workspaces/{workspaceId}/retrieval/rebuilds/{rebuildId}

POST /api/v2/organization/retrieval/rebuilds
GET  /api/v2/organization/retrieval/rebuilds/{rebuildId}
```

权限：

- profile create/activate 和 organization rebuild：organization `organization.manage`；
- workspace status/rebuild：workspace admin；
- organization admin 无 workspace membership 时 status 只返回 aggregate counters/error code；
- rebuild/activate 要求 `Idempotency-Key`；

## 12. 事务、并发和幂等

### 12.1 事务边界

| 操作 | 单一事务内容 | 事务外内容 |
| --- | --- | --- |
| Asset publish/archive | 主数据 pointer/status、audit、事实 event、River dispatch insert | 所有投影和 provider call |
| Event projection coordination | ensure run/rebuild/job、在新 run ready 后切换 head 并标记旧 run stale、finish delivery | canonicalize/provider |
| Build run | 一次写全 chunks/counters/lifecycle | 读取不可变版本、Markdown parse |
| Embed batch | 一次写 batch embeddings 和校准 counter | HTTP call |
| Activate profile | lock profile rows、active/retired 切换 | backfill |
| Create search session | session + 全部 item | 召回/provider/ranking |
| Query audit begin/complete | 各自短事务 | query execution |

### 12.2 锁顺序

统一顺序：

```text
organization/profile
 -> asset
 -> asset version
 -> projection run
 -> chunks/embeddings
 -> rebuild/session/audit rows
```

profile activation使用 `pg_advisory_xact_lock(hash(organization_id, 'retrieval-profile'))` 或对应 organization row lock；run claim 使用 `FOR UPDATE SKIP LOCKED`；同一 asset/profile 不允许两个 build job 同时写。

### 12.3 幂等键

- fact delivery：`event_id + consumer_key`；
- build run：run unique key；
- embedding batch：`run_id + first_ordinal + last_ordinal` River unique args，数据库 chunk_id PK兜底；
- rebuild API：organization + actor + Idempotency-Key + request hash；
- profile activation：profile revision + Idempotency-Key；
- query POST 是只读，不要求 Idempotency-Key；cursor/session 保证分页稳定。

### 12.4 竞态处理

- publish v2 紧接 archive：archive 主数据先决定不可见；晚到 build job 在开始/结束都检查 current pointer并标 stale；
- publish v1 后 publish v2：v1 job 即使完成，也因候选 SQL和终检不满足 current pointer而不可返回；
- tag update 与 profile warming并发：active/warming 都 ensure 使用最新 canonical checksum 的 run；旧 checksum run stale；
- membership 在 rerank 时被移除：候选发送前已过滤，响应前再次过滤；失权内容不返回；
- profile 激活与查询并发：首次查询在读取 active profile时固定 generation；session 原子保存；翻页读 snapshot；
- session 创建中任一 item失败：整个 session事务回滚，不返回 cursor。

生产和开发服务都不能使用默认固定 secret。semantic manifest 不完整时：

- API readiness 标出 semantic unavailable；
- worker 不注册 embedding worker；
- structured/fulltext 在 semantic-disabled profile 下可用；
- semantic-enabled active profile 与运行 manifest 不匹配时 API/worker readiness 失败，避免 API 与 worker使用不同模型。

API 和 worker 启动时计算 manifest fingerprint，必须与 active/warming profile 完全匹配：provider key、model、version、dimension、tokenizer、distance 任一不一致都拒绝处理该 profile。

### 13.2 Metrics

```text

retrieval_query_requests_total{channel,requested_mode,executed_mode,outcome,degraded}
retrieval_query_stage_duration_seconds{stage,mode}
retrieval_query_candidates{source}
retrieval_query_final_authorization_skips_total{reason}
retrieval_search_sessions_active
retrieval_provider_circuit_state{provider,type}
```

metric label 不放 organization UUID、workspace UUID、query、Tag 或 field value。高基数租户分析进入 query execution 表，不进入时序指标。

### 13.3 Logs 与 tracing

- 一个 query execution 贯穿 request_id、execution_id、session_id；
- trace spans：scope、validate、audit_begin、lexical、embed_query、semantic、fuse、rerank、session、final_auth、audit_complete；
- projection spans：event_coordinate、canonicalize、persist_chunks、embed_batch、finalize；
- 日志只写 ID、计数、固定 error code、duration；
- provider response body、正文、query 和 embedding 不写 log；
- error summary 最多 500 字符且经过敏感字段清洗。

### 13.4 Readiness

跨进程 readiness 不能通过 API 进程内的“已注册 handler”布尔值推断。新增 `system.worker_heartbeats`（`worker_id`、`role`、`manifest_fingerprint`、`handler_manifest`、`last_seen_at`、`started_at`、`status`），worker 启动注册并每 10 秒续租，退出或租约超过 30 秒视为 not ready；handler manifest 至少列出 active profile 所需的 build/embed/finalize/reconcile/cleanup job。API `/readyz` 读取最近 heartbeat，并校验 fingerprint 与本地 manifest；worker 自身 readiness 也检查同一表和 River 注册结果。

`/readyz` 检查：

- PostgreSQL；
- `pgroonga`、`vector` extension 及最低版本；
- cursor/hash secret 合法；
- active profile 与本地 manifest identity 匹配；
- API 的 query embedding provider可初始化；
- 最近 heartbeat 的 worker 注册了 active profile 需要的 job handler，且租约未过期；
- River migration已应用。

provider 瞬时网络失败不让整个 API permanently unready，由 circuit breaker 和 mode错误处理；manifest 缺失/不匹配属于配置错误，readiness 失败。

## 17. 实施顺序与提交边界

阶段 3 是一个最终架构，不提供旧新双跑；以下是提交顺序，不是产品分期：

1. `query-contract-scope`：contract、scope compiler、typed validation。
2. `retrieval-v2-schema`：空库schema、constraints、extensions、grants。
3. `canonicalizer-chunker`：Goldmark、segments、tokenizer、checksums。
4. `profile-provider-registry`：manifest、profile lifecycle、严格config。
5. `projection-workers`：fact consumers、River jobs、run lifecycle。
6. `projection-operations`：backfill、activate、rebuild、cleanup、status。
7. `structured-query`：权威主数据查询、Tag/filter integration。
8. `lexical-semantic-hybrid`：两路repository、RRF、rerank、degradation。
9. `session-final-auth-citation`：稳定分页、终检、引用。
10. `query-execution-observability`：强制审计、metrics/tracing/readiness。
11. `v2-http-openapi`：handlers、routes、OpenAPI、contract tests。
12. `delete-legacy-retrieval`：旧文件、路由、事件、SQL和config清理。
13. `retrieval-integration-hardening`：真实扩展、权限/并发/性能测试。

每个提交必须编译并通过相关测试，但直到第12项完成前不得把阶段 3 标记完成。禁止用 wrapper把旧 Query暂时藏在新接口后提交最终结果。

## 18. 阶段 3 退出门槛

### 架构

- [ ] 只有一个 UnifiedQueryService；成员与技术身份没有复制查询实现。
- [ ] structured不依赖retrieval schema。
- [ ] fulltext/semantic/hybrid只处理当前published version。
- [ ] Asset/Tag/ResourceModel不依赖retrieval技术命令。
- [ ] Agent和未来PublicSite只能通过QueryService接入。

### 投影

- [ ] canonical含title、summary、Markdown locator、searchable fields和Tag文本。
- [ ] profile active/warming切换原子且可完整backfill；每个 asset/profile 的 projection head 也原子切换，不能在新 run ready 前清空旧 serving run。
- [ ] ready run/chunk/embedding不可变，stale在session grace后清理。
- [ ] provider调用均在事务外；发布不等待索引。
- [ ] embedding失败不会被伪装成ready或expected=0。
- [ ] 事件重复、乱序、晚到都不让旧版本重新成为 projection head；head 切换是原子的，旧 run 在切换前继续 serving。

### 查询

- [ ] 四种mode契约、typed filters、Tag any/all/none通过。
- [ ] 同一资产只返回一个item和一个primary citation。
- [ ] hybrid降级完全符合矩阵；无HashEmbedding fallback。
- [ ] 候选发送reranker前已过滤，返回前再终检。
- [ ] organization visibility跨workspace正确，workspace visibility不泄露。

### 分页与权限

- [ ] session与items单事务保存。
- [ ] cursor使用显式随机secret和request/subject绑定。
- [ ] 翻页权限变化会过滤并补页，不因revision变化直接失效。
- [ ] profile切换/重建不破坏未过期session。
- [ ] citation 使用 opaque `CitationRef`，可按 HMAC、session subject、当前 published pointer、scope 和 checksum 重新验证。

### 审计与运行

- [ ] 所有query恰好一条execution，成功/失败/中断可追踪。
- [ ] audit、log、trace无query/filter/snippet/provider body明文。
- [ ] API/worker manifest identity不一致会readiness失败。
- [ ] PGroonga/vector/River/secret配置有startup validation。
- [ ] 投影lag、mode耗时、degradation、provider健康有指标和告警。

### 清理

- [ ] 不存在`asset.retrieval_projection_requested`。

## 19. 工期估算与主要风险

在阶段 0 至阶段 2 已完成、两名熟悉 Go/PostgreSQL 的后端工程师并行投入情况下，建议按 6 至 8 周估算：

| 工作 | 估算 |
| --- | --- |
| contract、scope、schema | 1 周 |
| canonicalizer、profile、provider | 1 周 |
| event/jobs、rebuild、activation | 1.5 周 |
| structured/fulltext/semantic/hybrid | 1.5 周 |
| session、终检、citation、audit | 1 周 |
| HTTP/OpenAPI、旧代码删除 | 0.5 周 |
| 集成、并发、安全、性能收口 | 1 至 1.5 周 |

主要风险及控制：

| 风险 | 控制 |
| --- | --- |
| 阶段 0-2 未真正落地就开始阶段3 | 把前置contract测试设为merge gate |
| provider模型/维度漂移 | manifest fingerprint + profile不可变 + readiness fail |
| HNSW filter后召回不足 | iterative scan、overfetch、主数据终检、基准测试 |
| 长文档导致chunk/embedding成本爆炸 | token上限、batch、单资产chunk上限和明确错误码 |
| 权限SQL散落再次漂移 | scope compiler + final authorizer为唯一边界 |
| profile切换破坏分页 | session引用快照 + retired grace cleanup |
| audit记录敏感查询 | HMAC request hash + 固定metadata whitelist |
| 过度追求通用动态字段索引 | 首版直读权威JSONB并以真实profile决定后续索引 |
| provider故障阻塞发布 | outbox + async jobs + 网络调用事务外 |
| 旧代码“暂时保留”形成双系统 | 退出门槛强制删除，不做兼容层 |
