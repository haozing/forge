# Forge 前端后端接口契约

> 本文档是 Forge 完整前端的规范契约，不是兼容性说明。新系统以本文档定义的数据模型、状态机、权限边界和 API 为唯一基线；旧接口、旧数据和旧状态不需要兼容。

## 1. 目标和结论

Forge 是一个由用户定义资源模型的知识资产工作区。`经典镜头库` 不是代码中的固定类型，而是一个用户创建的 `resource_model`。镜头、FAQ、文档、会议纪要都使用同一套资产模型，由不同的资源模型版本定义字段和表单。

现有后端已经有对话、Agent 问答、检索、资产写入、发布、附件和单次 Agent 任务的底层能力，但完整前端还需要统一的成员端 API，覆盖：

- workspace 和成员权限
- resource model 及其版本化 schema
- asset 列表、详情、编辑、审核和发布
- container/文件夹和资产归属
- conversation 列表和导航计数
- review 队列和审核状态机
- automation job、task run 和重试控制
- workspace 设置、统计、导入和导出

浏览器只调用 `/api/frontend/*` 成员端 API；`/api/open/v1/*` 只供 Agent 用户或受控外部系统使用，浏览器不得持有 Agent API Key。

## 2. 领域模型

### 2.1 资源层级

```text
organization
  -> workspace
       -> resource_model
            -> resource_model_version
            -> asset
                 -> asset_version
       -> container
       -> conversation
       -> review
       -> automation_job
```

强制约束：

1. `workspace` 只属于一个 organization。
2. `resource_model` 只属于一个 workspace，不能跨 workspace 复用。
3. `asset` 只属于一个 workspace 和一个 resource model。
4. `asset_version` 必须记录 `workspace_id`、`resource_model_id`、`resource_model_version_id`，三者必须一致。
5. `container`、`conversation`、`review`、`automation_job` 都必须直接记录 `workspace_id`。
6. 所有成员端查询先按 session 得到 organization 和 workspace membership，再执行资源查询；前端提交的 organization、member、workspace 字段全部忽略。

### 2.2 资源模型

资源模型保存业务类型的名称、内容呈现类型和当前版本指针；资源模型版本保存不可变的字段 schema、表单 schema、列表列/筛选 schema、检索配置和 Agent 出口策略。

```text
resource_model
  id, workspace_id, model_key, name, description, content_kind,
  status, current_version_id, created_by, created_at, updated_at

resource_model_version
  id, resource_model_id, version_no, status,
  field_schema, form_schema, list_schema, policy,
  created_by, created_at, published_at, retired_at
```

资源模型状态：

```text
draft | active | archived
```

资源模型版本状态：

```text
draft | published | retired
```

只有 `draft` 版本可以修改；`published` 版本不可变；新版本发布后旧的 `published` 版本转为 `retired`。资源模型只能有一个当前 `published` 版本。

资源模型只有在存在当前 `published` 版本时才能为 `active`；没有已发布版本的模型必须是 `draft`。归档模型不能创建新资产、不能接收新的 Agent 任务，但历史资产仍可读取。

`content_kind` 为 `record | document | faq`，只用于决定工作台入口和默认交互，不决定字段结构；字段结构始终由版本 schema 定义。自定义模型也必须声明一个 `content_kind`，前端不得根据 `model_key` 写分支。

### 2.3 资产和版本

```text
asset
  id, workspace_id, resource_model_id,
  current_working_version_id, current_published_version_id,
  visibility, publication_status,
  created_by, created_at, updated_at

asset_version
  id, workspace_id, asset_id,
  resource_model_id, resource_model_version_id,
  version_no, title, markdown, fields, tags,
  quality, created_by, created_at, updated_at
```

历史 `asset_version` 永远不可修改。编辑操作必须创建新的工作版本；发布只移动 `current_published_version_id` 指针。

`quality` 枚举为 `raw | agent_prepared | human_confirmed | high_quality`，只能由 Agent 整理、人工审核或系统质量规则按状态机提升，前端不能任意提交质量等级。

### 2.4 容器和目录

目录、文档父子关系和资产归属是三个不同概念：

```text
container              文件夹树
document_parent        文档资产之间的父子关系
container_asset        资产属于哪个文件夹
```

一个资产可以属于多个文件夹；一个文档最多有一个文档父节点；文件夹不能形成环。删除文件夹只会删除目录关系，不删除资产。

### 2.5 审核、任务和尝试

```text
review
  id, workspace_id, asset_id, asset_version_id,
  status, submitted_by, reviewer_id, comment,
  created_at, decided_at

automation_job
  id, workspace_id, name, operation,
  agent_application_id, trigger, input_scope,
  enabled, created_by, created_at, updated_at

task_run
  id, workspace_id, automation_job_id nullable, source, operation,
  status, progress, input_asset_ids, candidate_version_ids,
  attempt_count, error_code, started_at, completed_at

task_attempt
  id, task_run_id, attempt_no, status, error_code,
  started_at, completed_at
```

`automation_job` 是长期配置，`task_run` 是一次执行，`task_attempt` 是一次重试。`source` 为 `automation | manual | agent`；手动整理和 Agent 触发的 run 可以没有 `automation_job_id`，但必须仍然使用同一套 `task_run` 和 `task_attempt` 实体。

## 3. 权限模型

### 3.1 成员端

成员端使用 `agent_session` Cookie。workspace membership 至少包含：

```text
viewer | editor | reviewer | owner
```

动作权限：

```text
workspace.read
workspace.manage
model.read
model.manage
asset.read
asset.create
asset.edit
asset.submit_review
asset.review
asset.publish
asset.archive
container.manage
conversation.read
conversation.write
conversation.derive
automation.read
automation.manage
settings.read
settings.manage
```

`viewer` 只能读；`editor` 可创建、编辑和提交审核；`reviewer` 可审核和发布；`owner` 拥有 workspace、模型、自动化和设置管理权限。服务端必须按 `workspace_id + resource_model_id + action` 校验，不能只校验组织级成员身份。

### 3.2 Agent 端

`/api/open/v1/*` 使用 Agent API Key 和 Agent capability。Agent 的数据范围由 workspace、resource model、action 和模型版本 `policy` 共同决定。成员权限不得通过浏览器参数传给 Agent；Agent 引用在返回前必须再次按当前策略校验。

### 3.3 模型元数据和用户能力分离

资源模型响应不能用 `supported_operations` 混合模型能力和当前用户权限，必须分开：

```json
{
  "model_capabilities": ["member_search", "agent_tool"],
  "allowed_actions": ["read", "create", "edit", "submit_review"],
  "member_role": "editor"
}
```

## 4. 状态机

### 4.1 三个独立维度

```text
visibility: private | workspace | internal
publication_status: internal | published | archived
review_status: none | pending | approved | rejected | superseded | cancelled
```

含义：

- `visibility` 控制成员可见范围：`private` 仅创建者和显式共享成员可见，`workspace` 对拥有 `asset.read` 的 workspace 成员可见，`internal` 仅 editor/reviewer/owner 可见且永不进入 Agent 出口。
- `publication_status` 控制发布指针和默认发布检索。
- `review_status` 控制人工审核流程。

`pending_review` 不是 `publication_status` 的合法值。

### 4.2 合法转换

```text
创建资产：       internal + none
提交审核：       internal + none/rejected -> internal + pending
审核通过：       internal + pending -> internal + approved
审核退回：       internal + pending -> internal + rejected
发布：           internal + approved -> published + none
归档：           published/internal -> archived + none
编辑已发布资产： 创建新的 internal + none 工作版本，原发布版本不变
```

以下规则必须由事务保证：

1. 一个 `asset_version` 同时最多有一个有效的 `pending` review。
2. 编辑或替换审核中的版本会使旧 review 变为 `superseded`，并要求新版本重新提交审核。
3. 发布请求必须指定 `asset_version_id` 和对应的 `approved review_id`；两者不匹配直接返回 `409`。
4. 只有 `reviewer` 或 `owner` 可以批准和发布。
5. 归档资产不能出现在默认发布检索结果中。
6. 自动发布不能绕过审核状态机；模型策略允许自动发布时，系统必须为目标版本创建带 `system` 操作者的审核记录并先转换为 `approved`。

`review_status` 是当前工作版本的派生状态，不在资产历史版本上重复写入；来源是该版本的有效 review 记录。资产列表返回当前工作版本的 `review_status`，已发布版本没有待审核状态时返回 `none`。

## 5. 动态 schema 规范

### 5.1 字段 schema

字段 schema 使用服务端定义的 DSL，不接受任意可执行 UI JSON。保留字段为 `title`、`markdown`、`tags`、`source`、`attachments`，用户字段 key 不得覆盖这些名称，格式为 `[a-z][a-z0-9_]{1,63}`。

支持类型：

```text
string, text, markdown, integer, number, boolean,
date, datetime, enum, multi_enum, user,
asset_reference, attachment, url
```

字段定义：

```json
{
  "key": "shot_size",
  "label": "景别",
  "type": "enum",
  "required": true,
  "multiple": false,
  "default": null,
  "options": [
    {"value": "wide", "label": "远景"},
    {"value": "medium", "label": "中景"}
  ],
  "searchable": true,
  "filterable": true,
  "sortable": false,
  "display_order": 10,
  "placeholder": "请选择景别"
}
```

服务端必须校验：字段 key 唯一、类型和值结构一致、required/default 合法、options 无重复值、引用字段目标模型存在、字段数量和文本长度受限。

### 5.2 表单 schema

`form_schema` 只能使用白名单组件和字段引用：

```json
{
  "sections": [
    {
      "key": "basic",
      "title": "基础字段",
      "fields": ["shot_size", "camera_angle"]
    }
  ]
}
```

不能向浏览器下发脚本、任意 HTML、远程组件地址或可执行表达式。

`policy.outlets.agent_tool` 只能由 `owner` 配置，并且服务端必须将其与 Agent capability、workspace 数据范围和最低质量要求求交集；模型创建者不能通过 schema JSON 绕过 Agent 出口授权。

### 5.3 列表 schema

`list_schema` 定义工作台表格列、默认排序和可用筛选器，前端不能根据模型名称猜测列：

```json
{
  "columns": [
    {"field": "title", "label": "标题", "visible": true, "width": 280},
    {"field": "shot_size", "label": "景别", "visible": true, "width": 120},
    {"field": "tags", "label": "标签", "visible": true, "width": 200}
  ],
  "default_sort": {"field": "updated_at", "direction": "desc"},
  "filters": ["shot_size", "tags", "publication_status", "review_status"]
}
```

`columns.field` 必须引用保留字段或当前 `field_schema` 中已定义且允许列表展示的字段；筛选器必须引用 `filterable=true` 字段或系统状态字段。列表 schema、form schema 和 field schema 必须在同一模型版本内原子校验。

### 5.4 模型版本迁移

已发布模型版本不可修改。新版本发布不会自动改写资产；迁移是显式的异步操作，只能创建新的资产工作版本，不能修改历史资产版本。

```text
POST /api/frontend/resource-models/{resourceModelId}/migration-previews
POST /api/frontend/resource-models/{resourceModelId}/migrations
GET  /api/frontend/resource-model-migrations/{migrationId}
POST /api/frontend/resource-model-migrations/{migrationId}/cancel
```

迁移请求中的 `source_version_id` 和 `target_version_id` 必须都属于 URL 中 `resourceModelId` 对应的模型，且两者不能相同；跨模型或版本关系不合法时直接返回 `422`。

迁移请求：

```json
{
  "source_version_id": "uuid",
  "target_version_id": "uuid",
  "asset_scope": {"all": true},
  "mapping": {"old_key": "new_key"},
  "defaults": {"new_field": "default value"}
}
```

迁移预览必须返回：受影响资产数、可自动迁移数、失败数、字段删除数、类型转换失败行、默认值使用数和重新索引数。正式迁移返回 `migration_id`，具有 `queued | running | succeeded | failed | cancelled` 状态，并支持幂等和审计。

## 6. 通用 API 约定

### 6.1 请求头

所有改变业务状态的成员端写接口必须携带：

```text
Idempotency-Key: 16-200 字符
```

资产版本更新、审核、发布和模型版本发布还必须携带：

```text
If-Match: 当前版本 ETag
```

相同主体、相同 endpoint、相同 Idempotency-Key 只能产生一次业务结果；请求体不同返回 `409 idempotency_key_reused`。

### 6.2 分页

所有列表接口使用稳定排序和 opaque cursor：

```text
limit: 1-100，默认 20
cursor: 不透明游标
sort: 字段 + asc/desc
```

排序必须包含唯一 ID 作为 tie-breaker。响应统一为：

```json
{"items": [], "has_more": true, "next_cursor": "..."}
```

不返回依赖实时计算的全局 total；统计使用独立 stats 接口。

### 6.3 错误

```json
{
  "code": "asset_version_conflict",
  "message": "resource was changed by another request",
  "request_id": "uuid",
  "details": {}
}
```

最低错误码：

```text
unauthorized, forbidden, not_found, validation_failed,
conflict, idempotency_key_reused, version_conflict,
invalid_state_transition, cursor_invalid, rate_limited,
model_schema_invalid, migration_failed
```

### 6.4 HTTP 状态和响应头

```text
200 读取、更新或同步状态转换成功
201 创建资源或版本成功
202 异步任务、迁移、导入、导出已受理
204 删除目录关系或附件解绑成功
400 请求格式错误
401 未登录或凭证无效
403 无 workspace/action 权限
404 资源不存在或当前主体不可见
409 幂等键、ETag、状态或唯一约束冲突
422 字段/schema/业务参数校验失败
429 超过限流
```

登录接口 `/api/sessions` 不要求幂等键；其余创建、更新、状态转换、上传、导入、导出、迁移和任务控制接口都要求幂等键。返回资产、模型版本或审核详情时必须带 `ETag`；异步 `202` 响应必须返回对应 job/run ID，不能只返回字符串消息。

所有 ID 使用 UUID，时间使用 UTC RFC 3339。枚举值在 API 中使用英文，中文只由前端展示层映射。

服务端必须按成员权限过滤结果；`internal` 只表示未发布，不表示自动可见。返回 `title`、`summary`、`fields`、`tags`、`visibility`、`publication_status`、`review_status`、`snippet`、`score`、`asset_id`、`asset_version_id` 和 `updated_at`。

### 7.7 审核


退回请求：

```json
{"comment": "请补充参考片段", "expected_version_id": "uuid"}
```

批量审核必须逐项返回结果，不能因为一项冲突导致其他合法项一起成功或一起失败；每项都使用独立幂等键派生值并记录审计。

```json
{
  "items": [
    {"review_id": "uuid", "decision": "approve", "expected_version_id": "uuid"},
    {"review_id": "uuid", "decision": "reject", "comment": "请补充来源", "expected_version_id": "uuid"}
  ]
}
```

### 7.9 自动化任务

```text
GET   /api/frontend/workspaces/{workspaceId}/automation-jobs

PATCH /api/frontend/automation-jobs/{jobId}
```

任务配置必须包含：`name`、`operation`、`agent_application_id`、`trigger`、`timezone`、`concurrency_policy`、`input_scope`、`max_attempts`、`retry_backoff`、`enabled`。`trigger` 为 `manual`、`cron` 或 `event`；cron 必须包含 timezone，event 必须包含 event type。任务运行状态：

```text
queued | running | succeeded | failed | cancelled
```

必须定义重复触发幂等、最大重试次数、退避策略、取消语义和运行进度。`success_rate` 是按时间窗口聚合的只读统计，不是用户直接写入的字段。

## 8. 现有底层能力的归位

现有对话、消息、note sync、derivation、media/transcription 能力归入成员端 conversation domain；现有开放 Query、Agent asset write、Agent task 能力归入 `/api/open/v1`，继续使用 Agent API Key。

成员端 asset、query、review 和 model API 与 Agent API 使用同一领域服务和状态机，但认证、授权范围和响应读模型不同。不能用 BFF 把 Agent Key 暴露给浏览器，也不能让浏览器自行传入 Agent 身份或资源范围。

## 9. 审计、并发和索引

以下操作必须记录审计事件：资产创建、编辑、提交审核、审核通过、审核退回、发布、归档、模型版本发布、模型迁移、目录移动、附件下载、任务暂停/恢复/重试/取消和设置修改。事件包含操作者、workspace、对象、旧状态、新状态、版本 ID、理由、request ID 和时间。

动态 schema 的 `searchable`、`filterable`、`sortable` 变更必须触发索引配置和投影任务。模型版本发布前返回索引状态；未完成必要投影时，不能宣称该字段可检索。

所有状态变更和版本指针切换必须在事务中完成。查询使用稳定 cursor 和权限快照，游标失效返回 `cursor_invalid`。

## 11. 验收标准

### 页面级

- 页面刷新后所有列表、计数、状态和字段都来自接口，不依赖静态数组。
- 切换 workspace 后所有资源都严格切换，不能看到其他 workspace 数据。
- 前端根据 resource model version 渲染列表列、详情字段、编辑表单和提取弹窗；代码中没有镜头专用字段分支。
- 创建、保存、审核、退回、发布和归档后，列表、状态徽标和计数保持一致。
- 并发编辑显示版本冲突，不覆盖他人的新版本。
- Agent 回答只展示当前权限有效的引用，流式中断后可重试且消息不重复。
- 模型版本发布后，旧资产字段仍可读取；迁移仅生成新工作版本并显示迁移结果。

### 接口级

- 未登录返回 `401`；无 workspace membership 返回 `403` 或按统一安全策略返回 `404`。
- 所有写接口支持幂等；重复 key 不重复创建业务对象。
- 所有版本写操作支持 ETag/If-Match；冲突返回 `409 version_conflict`。
- 所有列表使用稳定 cursor；游标失效返回 `cursor_invalid`。
- 所有状态转换拒绝非法路径并返回 `invalid_state_transition`。
- 所有审核、发布、迁移、任务控制和模型配置变更产生审计事件。

### 数据级

- workspace、resource model、asset、asset version、container、conversation 的组织和 workspace 归属一致。
- 资产版本始终绑定实际使用的 resource model version。
- 发布指针只能指向审核通过且字段校验通过的版本。
- 历史资产版本不可修改。
- 文件夹删除不删除资产正文；移动资产不改变资产 ID 和版本历史。
- 用户没有权限的 internal/private 资产不会出现在列表、查询、引用或 Agent 返回中。

## 12. 最终结论

这套契约的正确核心是：**用户定义资源模型，资源模型定义 schema，资产绑定模型版本，前端只实现通用渲染器**。

在实现 Forge 前端前，必须先完成 P0，并以本文档定义的 workspace 隔离、三维状态模型、审核发布状态机、动态 schema 版本和成员/Agent 分层作为不可变设计约束。完成 P0 后，镜头、FAQ、文档不需要任何写死的业务字段，即可由同一套前端运行时渲染。
