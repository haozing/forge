## 0. 总体结论

**一句话:四大核心域(审核、公开站点、统一查询、权限)实现质量很高、与契约高度一致;真正的缺口不在域内,而在"域的交界处"和"产品出口"——附件上传端点不存在、管理前端整块不存在、Agent 与审核的交界链路断裂、openapi 契约门只盖了一半。架构总体干净(路由退役彻底、无兼容层、无影子表),但有迁移碎片化、死代码、凭据残留三处集中的卫生债。过度设计是真实存在的:6 个空转工作流、automation 超范围框架、resourcemodel 类型表和迁移框架的零语义灵活性。**

| 维度 | 评价 | 说明 |
| --- | --- | --- |
| 核心对象落地 | ✅ 21/21 有表有服务有路由 | 唯一打折:AssetRelation 成员面读取薄弱 |
| 域内契约一致性 | ✅ 高 | draft/version/tag 语义、审核单级流、站点防绕过、查询复核几乎逐条吻合 |
| 域交界完整性 | ⚠️ 中 | Agent×审核、附件×归档、发布×幂等、关系×版本密封 4 处断裂 |
| 产品出口(P0) | ❌ 缺 | 附件上传 HTTP 端点、管理后台前端(13.1/13.2) |
| 架构干净度 | ✅ 总体干净 | 路由退役/依赖/配置全部干净;迁移基线碎片化 + 死代码若干 |
| 过度设计 | ⚠️ 确认存在 | 集中在 workflows/automation/resourcemodel/container 四处 |
| 文档同步 | ❌ 落后 | §11 路径、§16.4 引用文件、§4 关系类型均已与代码脱节 |

## 1. 缺失模块

### 1.1 P0 级缺口(产品 P0 明文要求但不可用)

**① 附件上传 HTTP 端点不存在** —— 最实质的功能缺口。
`attachment.Service.Upload`(`internal/attachment/service.go:96`,含 OSS 直传、ClamAV 扫描入队)是完整实现,但**全仓没有任何 handler/路由调用它**。已注册路由只有列表/详情/link/下载/预签名下载(`internal/httpapi/router_groups.go:304-308`),openapi.yaml 也无 attachments 路径。验收脚本 `tmp_qa/itd_p9.py:202-208` 是用宿主机程序直传 OSS 后**手工 SQL INSERT** 造的数据——即上传链路只对测试代码可达。产品文档 §11.1"附件上传和下载"的上传半边对用户不存在。

**② 管理后台与创作者工作区前端(§13.1/§13.2)整块不存在。**
仓库内无任何管理 UI:无 web/frontend 目录、无 package.json。阶段5-6 方案 §0 明示"前端以独立 React 工程交付,不在本仓范围",但该独立工程至今未见交付。`docs/yxt/` 下的静态原型绑定的是**已退役的 `/api/frontend/*` 前缀**(2026-08-31 全部 404),不可用。后端 API 面大体齐备(工作台=workspace summary、我的笔记=created_by 筛选、发布审核、标签、站点、检索、Agent 应用、查询审计),但 §18 验收标准 1/2/4/5/6/10(均以用户操作为口径)在前端缺失时无法宣称通过。唯一的"前端"是公开站点 SSR(§13.3,✅ 已交付,15 条 HTML 路由 + RSS/Sitemap/JSON-LD,两轮验收全过)。
连带缺口:SSR 报告 §7 明示 `tool_policy` 管理入口"待 React 管理端"——目前只能 SQL 直设;组织级"系统设置"域连后端 API 都没有。

**③ Agent 在 approval 策略下无法提交发布请求**(链路断裂,详见 2.3-⑥)。
