# 成员与 Agent 权限统一方案

日期：2026-09-12
状态：方案定稿（A–K 全部拍板，2026-09-12；未决项已落定，见各节）
关联：`公开站点简化方案-2026-09-12.md`（AI 改站的 agent 依本方案取得工作区身份）

## 1. 背景与问题

Agent 授权目前散落在五套并行机制里，没有一套回答"这个 agent 在这个工作区是什么角色"：

| 机制 | 管什么 | 问题 |
|------|--------|------|
| `identity.api_keys.capabilities` | key 能用哪些工具 | 只管工具上限，不管数据范围 |
| `authz.agentAllowedActions`（硬编码表） | agent 动作白名单 | 与人的角色矩阵**两套平行 authz**；asset.confirm 漏加致 agent 确认永远 403 的事故即源于此 |
| `content.workspace_agent_applications` | 应用×工作区绑定 | 只有 enabled 开关，无程度：启用即全有 |
| `content.agent_access_policies` | agent×工作区×模型的动作/字段/草稿范围 | 唯一细粒度表，但语义是"例外"不是"基线" |
| `integration.agent_applications.tool_policy` | 应用级能力上限 | 与 capabilities 概念重复，一内一外两套名字 |

两个已发生的事故佐证两套系统的维护成本：agentAllowedActions 漏 asset.confirm（agent 确认入库 403）；MemberService.require member-gated 三处拒绝 agent principal（403）。

**关键事实（已核实）**：`identity.users.user_type` 本就含 `'agent'`；`workspace_members.user_id` 外键直接指向 `identity.users`——agent 成为工作区成员在 schema 层**今天就能插入**，堵点只在 service 层假设与 UI 缺位。`integration.agent_applications.bound_agent_user_id` 已把每个应用绑定到自己的 agent 身份。

## 2. 决策

| # | 决策 | 状态 |
|---|------|------|
| A | Agent 以成员身份纳入工作区成员管理，与人共用同一张角色矩阵（admin/editor/reviewer/viewer → agent 子集） | 已拍板 |
| B | **直接废除** `workspace_agent_applications` 与 `agentAllowedActions`：应用在某工作区启用 = 其 bound agent 身份在该工作区有成员行；agent 与人走同一张判权矩阵 | 已拍板 |
| C | agent 成员角色**只开放 viewer / editor**（上限 editor）：不给 admin（人事权/配置权），不给 reviewer（审核必须是人的判断，agent 自动审核=没有审核）。实现上由决策 I 的 `human_only` 动作标记强制；**发布（`asset.publish`）亦为 human_only**（决策 J） | 已拍板 |
| D | 产品内 agent 会话的**实际权限 = min(agent 角色, 发起人角色)**：工具不能让员工越过自己的权限 | 已拍板 |
| E | 外部 key 的 capabilities 与内部应用的 tool_policy **统一为一个概念"Agent 能力"**（同一份枚举清单、同一个 UI 控件），载体可以是 key 也可以是应用 | 已拍板 |
| F | 公开访客 agent（给外部公开用户用的）**不是成员**，归站点设置 Agent 接入，权限 = visitor band（公开内容只读） | 已拍板 |
| G | `site.manage` **拆分**为 `site.design`（站点外观/页面/导航/发布 release，授予 editor）与 `site.lifecycle`（建站/停用/域名/删除，admin 专属）——解决"editor 进不了设计 Tab"的矛盾 | 已拍板 |
| H | **权限模型数据化**：动作集合为数据，内置角色（admin/editor/reviewer/viewer）仅作**预设**，支持**成员级覆写**（单独加/减权限）。"editor 但也要能设计站点"用覆写解决——不新增角色、不改代码 | 已拍板 |
| I | agent 上限改用**动作级 `human_only` 标记**（成员管理/审计/角色编辑/审核决策/站点生命周期 = 仅人可授；其余动作 agent 可授），替代"agent ≤ editor"的角色上限。**自定义角色 UI 延后**——数据模型就绪后属纯 UI 工作，不需要再重构 | 已拍板 |
| J | **内容发布（`asset.publish`）为 `human_only`**：agent 只能起草（`asset.write`）与确认（`asset.confirm`）内容，**发布必须人做**。与站点方案 D16「AI 起草 · 人工确认」的透明叙事一致——若 AI 能自行发布，"人工确认"标签即失真。含 MCP 的 `publish_asset` 工具一并取消（agent 侧） | 已拍板 |
| K | **Agent 成员参数**（2026-09-12 定，细则见实施规划 §8）：① **不计席位，改配额**——每工作区 Agent 成员上限默认 10（组织可调）；② 外部 key 采**集成级身份**——一个"外部集成"= 一个 agent user（成员行挂其上），可持多个 key，**轮换 key 不影响成员行与已授权限**；③ 成员行**不随 key 过期自动移除**，仅凭证失效，界面显示"无有效凭证"徽标并提供"清理无凭证 Agent 成员"手动动作 | 已拍板 |

## 3. 统一模型：一条基线 + 一个天花板 + 模型级例外

```
身份层      agent user（users.user_type='agent'）
             ├─ 内部：integration.agent_applications（bound_agent_user_id，应用=容器）
             └─ 外部：identity.api_keys（user_id 指向 agent user，key=凭证）
工作区授权层  content.workspace_members（agent 行；权限集合 = 角色预设 ± 成员覆写）  ← 唯一基线
能力天花板    "Agent 能力"清单（key.capabilities ≡ 应用 tool_policy）        ← 工具上限
模型级例外    content.agent_access_policies（字段白名单/草稿范围，保留）      ← 细粒度覆盖
最终权限      = 权限集合 ∩ 能力清单（− 模型级例外收紧）；动作带 human_only 标记则 agent 永不可授
```

- 人类成员路径完全不变（org 角色 + workspace_members.role + workspaceCan）。
- agent 判权改走**同一个** `workspaceCan`/角色矩阵；agentAllowedActions 表删除后，"agent 能干什么"只有一个答案来源。
- 撤销访问 = 移除成员行（或吊销 key），单一动作。

## 4. 三类 Agent 与归属

| 类型 | 是谁在用 | 身份 | 权限 | 归属 UI |
|------|----------|------|------|---------|
| 产品内 agent | 自己的成员（react runs 会话） | 应用 bound agent user | min(agent 权限, 发起人权限) ∩ 能力清单；发布为 human_only 不可授 | 应用定义在 /admin/agents（组织台）；**成员身份在成员管理** |
| 外部 agent | 自动化脚本 / 第三方客户端（MCP） | API key → agent user | agent 权限 ∩ key 能力清单；**发布为 human_only 不可授**（`publish_asset` 对 agent 下线） | 签发/吊销在组织台；**成员身份在成员管理** |
| 公开访客 agent | 外部公开用户（站点问答等，未来） | 站点配置，无成员行 | visitor band（三道闸过滤后的公开内容，只读） | 站点设置 → Agent 接入 |

定位一句话：**定义在组织台，身份在成员管理，公开面在站点设置。**

## 5. 数据模型变更（干净重做口径，不做兼容迁移）

1. `content.workspace_members`：直接插 agent user 行。加约束与列：
   - 冗余列 `principal_type text DEFAULT 'human'`（免 join 校验 member/agent）；
   - **权限集合数据化**（决策 H）：`granted_actions text[]` / `revoked_actions text[]`（在角色预设之上做加/减，空=纯用预设）；内置角色仍是预设（`role` 列保留 admin/editor/reviewer/viewer），**不建角色表、不做自定义角色 UI**；
   - **动作级 `human_only` 标记**（决策 I）：动作元数据（不再硬编码在 `roles.go`）标出成员管理/审计/角色编辑/审核决策/站点生命周期等"仅人可授"项；`principal_type='agent'` 的成员行及其覆写**不得包含** human_only 动作（写入与判权双重校验）——取代原"`role IN ('viewer','editor')` 部分 CHECK"；
   - agent 行 `granted_by` 必须是人（FK 只保证存在用户，需显式校验指向 member）。
2. drop `content.workspace_agent_applications`；drop authz 包 `agentAllowedActions` 及其调用点。
3. 能力清单统一：key.capabilities 与应用 tool_policy 收敛为同一 schema（`TOOL_CAPABILITIES` 枚举），字段名统一 `capabilities`；应用旧 `tool_policy` 字段在请求结构中更名（DisallowUnknownFields 三处同步坑）。
4. `content.agent_access_policies` 保留，行语义不变；入口迁至模型高级设置（"Agent 数据策略"）。
5. MCP：tools/list 过滤从 capabilities 读（不变）；鉴权第二闸门（agentAllowedActions）删除，改走成员角色矩阵——`search_assets` 等 query 能力与成员角色 query.read 的交集判定。
6. **权限矩阵数据化 + 发布封权（决策 H/I/J）**：`internal/authz/roles.go` 的硬编码动作表迁移为**数据**（动作元数据含 `human_only` 标记，`asset.publish` 即标 `human_only`）；`workspace_members` 增 `granted_actions` / `revoked_actions`；判权公式从"查 map"改为"角色预设 ± 成员覆写 ∩ 能力清单"，并强制 human_only 动作对 agent 不可授、不可覆写。**合并四套动作词表**为一份（`agentAllowedActions`、`admin/policy.go:supportedAgentActions`、`admin/agent.go:allowedAgentCapability`、key/应用 capabilities），并**补三处绕过判权的路径**（`search_assets` 走 OpenAPIQuery、`create/update_document`/`insert_record` 走 ScopeResolver）——这是"删两表即单一答案来源"真正成立的前提；顺带修 `asset.archive` 漏项（当前 agent 归档永远 403）。MCP 工具表移除 `publish_asset`（agent 侧）。

## 6. 成员管理 UI

- 成员 Tab 分两组：**人类成员 / Agent 成员**（或类型筛选）。
- Agent 成员行：名称（应用名 / key 名）、类型徽标（内部应用 / 外部 Key）、角色下拉（仅 viewer/editor）、授予人、最后活跃（key.last_used_at / 应用最近 run）、状态。
- 添加流：选组织应用目录中应用，或现场签发 key → 选角色 → 完成（secret 只展示一次）。agent 不走邮件邀请。
- **权限覆写**（决策 H）：成员行可展开"权限微调"——在角色预设基础上单独勾选/取消个别动作（如给某 editor 加 `site.design`）。human_only 动作在 agent 行的选项里**置灰不可选**（决策 I）。
- 权限透视（点开一行）：角色预设 + 覆写差异 + 能力清单摘要 + 模型级例外入口（跳模型设置）+ 该主体审计记录链接。
- 组织台 `/admin/agents` 保留，职责收窄为"应用与 key 的定义管理"（货架）：应用配置、能力清单、模型端点、key 签发/吊销；页面文案去掉权限语义，权限指向成员管理。
- **集成视图（K2）**：外部 Agent 按**集成**分组展示（一个 agent user = 一个外部集成，其下可挂多个 key）；支持"绑定现有集成"或"新建集成"，轮换 key 不影响成员行与权限。
- **配额与凭证状态（K1/K3）**：成员页显示配额占用（如"Agent 成员 3/10"），超限时禁止新增；key 全过期/吊销的 Agent 成员显示"无有效凭证"徽标并提供"清理无凭证 Agent 成员"手动动作（不自动移除）。

## 7. 安全规则

1. **防提权**（决策 D）：viewer 发起的会话里 editor agent 只按 viewer 干活；外部 key 无发起人，不适用。
2. **仅人可授动作**（决策 I/J）：agent 永远拿不到成员管理、审计、角色/权限编辑、审核决策、站点生命周期（`site.lifecycle`）、**内容发布（`asset.publish`）**——由动作级 `human_only` 标记强制，与角色/覆写无关，故在自定义角色下依然成立。agent 的内容能力止于**起草 + 确认**（产出走人的发布或人工审核队列）。
3. **通知屏蔽**：邀请邮件、通知流扇出跳过 agent 成员；**且覆盖按 `submitted_by` 写给 agent 的决策通知**（`internal/review/service.go:411`、`internal/asset/lifecycle.go:249`）——agent 无会话读不到，属"写而不可读"的脏行。另需修邮件入队对 NULL email 的扫描（`review/service.go:457-464`），否则 agent 提审后人工审批会让事务回滚。
4. **key 泄露面**：key 是字符串，泄露面大于人账号——editor 上限 + 可频控（MCP 写安全既有）+ 可吊销，三层兜底。
5. **可解释性**：审计按主体记录；"这件事是哪个 agent 干的、谁授的权、为什么能干"三个问题都能在一个页面回答。

## 8. 与站点简化方案的衔接

- 站点方案 P4 的 AI 改站为**设计会话**形态：agent 只 fork 沙盒并观察（`apply_patch`/`observe`，写会话级 session_config），**全程不写站点行**——能力清单只需读/观察类目，agent（editor）即满足；"应用会话结果"与"发布 release"是人的动作，归 `site.design`（决策 G，editor 可授）。此形态与决策 C（agent ≤ editor）天然无冲突，无需权限特例。
- 公开访客 agent（站点问答）依决策 F 不进成员表。

## 9. 分期（详见实施规划）

见《公开站点与权限统一实施规划-2026-09-12.md》§5。要点：**P0** 修两个现存缺陷 + 权限地基（成员表 agent 行、废两表、词表合并、human_only 标记、`site.manage` 拆分）；**P4** 成员 UI、能力清单统一、min 权限、AI 设计会话。本方案的 A–K 决策全部落在规划 P0 与 P4 两个阶段。

## 10. 已定参数与观察项

1. **席位/计费（K1）**：Agent 成员**不计席位，改配额**——每工作区 Agent 成员上限默认 10，组织可调。理由：Agent 是人授予的工具，计席位会让"5 个 Agent 的工作区付 5 倍"且 Agent 数量本无界。
2. **外部 key 身份（K2）**：采**集成级身份**——一个"外部集成"= 一个 agent user，一个集成可持多个 key；轮换/吊销 key 不影响成员行与已授权限（避免"每 key 一身份"导致轮换即掉权限）。签发时可选"绑定现有集成"或"新建集成"；审计按集成归属、按 key 记明细（`api_keys.id` 已可区分）。
3. **成员行有效期（K3）**：**不随 key 过期自动移除**——key 过期仅凭证失效（访问自然中断），成员行保留并显示"无有效凭证"徽标 + 提供"清理无凭证 Agent 成员"手动动作。理由：自动移除会让轮换 key 丢角色。
4. **观察项**（无需现在决策）：Agent 配额默认数值是否随组织套餐差异化。

## 11. 审计中发现的既有结构性问题（实施注意）

以下问题不影响 A–K 决策成立，但实施"权限矩阵数据化"时必须一并处理（详见《方案审计报告-2026-09-12.md》）：

- **四套动作词表**（`agentAllowedActions`、`admin/policy.go:supportedAgentActions`、`admin/agent.go:allowedAgentCapability`、key/应用 capabilities）需合并为一份动作来源，否则"废两表即单一答案"不成立。
- **三条绕过判权的路径**（`search_assets` 走 `OpenAPIQuery`、`create/update_document`/`insert_record` 走 `ScopeResolver`）需补角色/权限校验。
- **`asset.archive` 漏在硬编码表外** → Agent 归档永远 403（同类事故第二例）。
- **agent_access_policies 唯一键对 NULL 不去重**、`AgentDraftService.validateAgent` 只认非空 workspace 行，与 `authz.WorkspacePolicy` 接受 org 级 NULL 行语义不一致。
