# 标签系统最终设计架构

## 1. 文档定位

本文定义标签系统的最终领域模型和代码边界。设计只基于当前仓库的资产、版本、资源模型、检索、导入导出和 HTTP 实现，不依赖其他产品方案文档。

本文解决以下问题：

- 标签如何定义、归属和命名；
- 标签如何与资产版本绑定；
- 草稿、审核、发布和历史版本如何保持一致；
- 人工录入、开放 API、Webhook、导入和 Agent 如何使用同一套标签规则；
- 标签筛选、标签聚合、全文检索和公开内容如何获得一致结果；
- 标签权限、归档和重命名如何处理。

本文假设系统按全新数据模型部署，不承担旧字段、旧数据或旧接口的兼容责任。现有代码只用于定位必须被替换的边界。

## 2. 最终结论

当前实现中的 asset.asset_versions.tags jsonb 不是最终模型的一部分。新系统直接以标签定义表和版本关联表作为唯一数据来源。

最终模型采用标签定义、可变 draft 关联和不可变版本关联三个存储职责：

    asset.tags
        工作区内的标签定义和生命周期

    asset.asset_version_tags
        某个资产版本实际绑定的标签集合

    asset.asset_draft_tags
        编辑和自动保存期间的可变标签集合

标签定义和标签绑定必须分离，原因如下：

1. 标签需要稳定身份，而不是每次用字符串比较。
2. AssetDraft 需要支持自动保存，AssetVersion 需要保存不可变的标签身份关联快照，两者不能互相污染。
3. 标签需要统一的命名、大小写、归档和权限规则。
4. any/all/none 查询应该基于关系表表达，而不是复用普通 JSON 字段过滤器。
5. 标签聚合、标签页、公开查询和检索投影需要可靠的索引和权限范围。
6. AI、人工和导入产生的标签需要记录来源和置信度。

最终系统中不存在 asset_versions.tags 这一业务字段，业务代码只能通过标签领域服务读取和写入关系数据。

## 4. 领域定义

### 4.1 标签的边界

标签是工作区范围内可复用的内容元数据。标签不是资源模型的动态字段，也不是目录树节点。

标签本身只表达“内容属于某个语义集合”，不负责表达父子层级。如果未来需要层级分类，应建立独立的 taxonomy/category 领域，不能在标签表中混入目录树语义。

### 4.2 标签作用域

标签属于 organization_id + workspace_id 作用域。

同一个工作区内，规范化后的标签键只能有一个标签定义。不同工作区可以分别存在同名标签。

所有正式版本标签关联必须满足：

    tag.organization_id = asset_version.organization_id
    tag.workspace_id    = asset_version.workspace_id

draft 标签关联使用相同规则，但比较对象是 asset_draft.organization_id/workspace_id。

### 4.3 标签身份与展示

标签必须同时拥有内部身份和外部名称：

- id：稳定 UUID，内部关联使用；
- normalized_key：规范化后的唯一键，用于匹配和导入；
- display_name：用户可见名称，可以修改；
- slug：外部 URL 和 API 使用的稳定标识；
- status：active 或 archived。

规范化规则由应用层统一实现：Unicode 规范化、去除首尾空白、大小写折叠、拒绝空值和控制字符。建议单个标签最多 100 个 Unicode 字符，每个版本最多 100 个标签，具体数值作为系统配置而不是散落在各个 handler 中。

标签顺序没有业务含义。API 返回时必须按 normalized_key 或 display_name 稳定排序，避免数组顺序造成无意义的版本差异。

### 4.4 标签生命周期

- 新标签只能在工作区标签管理权限下创建；
- 资产编辑者只能绑定已有的 active 标签；
- archived 标签不能绑定到新版本，但已存在的版本关联仍然保留；
- normalized_key 是标签的稳定业务键，不允许直接修改；
- 修改 display_name 不改变标签身份；
- slug 由稳定业务键生成，作为当前系统的外部标识；
- archived 标签可以显式恢复为 active；key 和 slug 在归档期间不会释放；

## 5. 最终数据库模型

### 5.1 标签定义表

建议新增 asset.tags：

    CREATE TABLE asset.tags (
        id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        organization_id   uuid NOT NULL,
        workspace_id      uuid NOT NULL,
        normalized_key    text NOT NULL,
        display_name      text NOT NULL,
        slug              text NOT NULL,
        status            text NOT NULL DEFAULT 'active',
        revision          bigint NOT NULL DEFAULT 1 CHECK (revision > 0),
        created_by        uuid NOT NULL,
        updated_by        uuid NOT NULL,
        created_at        timestamptz NOT NULL DEFAULT now(),
        updated_at        timestamptz NOT NULL DEFAULT now(),
        archived_at       timestamptz,
        archived_by       uuid,
        UNIQUE (organization_id, workspace_id, normalized_key),
        UNIQUE (organization_id, workspace_id, slug),
        CHECK (status IN ('active', 'archived')),
        CHECK (
            (status = 'active' AND archived_at IS NULL AND archived_by IS NULL)
            OR
            (status = 'archived' AND archived_at IS NOT NULL AND archived_by IS NOT NULL)
        )
    );

为了让跨工作区绑定在数据库层直接失败，标签表应提供可用于复合外键的唯一键：

    UNIQUE (id, organization_id, workspace_id)

由于现有 asset.asset_versions 以 id 为单列主键，最终模型还需要为它增加：

    UNIQUE (id, organization_id, workspace_id)

组织、工作区和创建者的外键应遵循仓库已有的复合外键模式。

### 5.2 Draft 标签关联表

自动保存期间的标签选择属于可变 AssetDraft，不得提前写入不可变版本关联：

    CREATE TABLE asset.asset_draft_tags (
        asset_draft_id   uuid NOT NULL,
        tag_id           uuid NOT NULL,
        organization_id  uuid NOT NULL,
        workspace_id     uuid NOT NULL,
        source           text NOT NULL DEFAULT 'manual',
        confidence       numeric(5,4),
        updated_by       uuid,
        updated_at       timestamptz NOT NULL DEFAULT now(),
        PRIMARY KEY (asset_draft_id, tag_id),
        FOREIGN KEY (asset_draft_id, organization_id, workspace_id)
            REFERENCES asset.asset_drafts(id, organization_id, workspace_id),
        FOREIGN KEY (tag_id, organization_id, workspace_id)
            REFERENCES asset.tags(id, organization_id, workspace_id),
        CHECK (source IN ('manual', 'api', 'webhook', 'import', 'ai')),
        CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1))
    );

AssetDraft 使用 revision 做乐观并发控制。更新 draft 标签集合和递增 draft revision 必须在同一事务完成。

### 5.3 版本标签关联表

建议新增 asset.asset_version_tags：

    CREATE TABLE asset.asset_version_tags (
        asset_version_id  uuid NOT NULL,
        tag_id            uuid NOT NULL,
        organization_id   uuid NOT NULL,
        workspace_id      uuid NOT NULL,
        source            text NOT NULL DEFAULT 'manual',
        confidence        numeric(5,4),
        created_by        uuid,
        created_at        timestamptz NOT NULL DEFAULT now(),
        PRIMARY KEY (asset_version_id, tag_id),
        FOREIGN KEY (asset_version_id, organization_id, workspace_id)
            REFERENCES asset.asset_versions(id, organization_id, workspace_id),
        FOREIGN KEY (tag_id, organization_id, workspace_id)
            REFERENCES asset.tags(id, organization_id, workspace_id),
        CHECK (source IN ('manual', 'api', 'webhook', 'import', 'ai')),
        CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1))
    );

必须建立：

    CREATE INDEX asset_version_tags_tag_idx
        ON asset.asset_version_tags (tag_id, asset_version_id);

    CREATE INDEX asset_version_tags_version_idx
        ON asset.asset_version_tags (asset_version_id, tag_id);

### 5.4 Agent 标签建议表

Agent 的建议不是正式标签绑定，必须单独存储，避免未确认的 AI 结果污染公开内容：

    CREATE TABLE asset.asset_version_tag_suggestions (
        id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
        asset_version_id  uuid NOT NULL,
        tag_id            uuid,
        organization_id   uuid NOT NULL,
        workspace_id      uuid NOT NULL,
        suggested_key     text NOT NULL,
        confidence        numeric(5,4) NOT NULL,
        status            text NOT NULL DEFAULT 'pending',
        created_at        timestamptz NOT NULL DEFAULT now(),
        reviewed_at       timestamptz,
        reviewed_by       uuid,
        accepted_into_draft_id uuid,
        materialized_version_id uuid,
        FOREIGN KEY (asset_version_id, organization_id, workspace_id)
            REFERENCES asset.asset_versions(id, organization_id, workspace_id),
        FOREIGN KEY (tag_id, organization_id, workspace_id)
            REFERENCES asset.tags(id, organization_id, workspace_id),
        FOREIGN KEY (accepted_into_draft_id, organization_id, workspace_id)
            REFERENCES asset.asset_drafts(id, organization_id, workspace_id),
        FOREIGN KEY (materialized_version_id, organization_id, workspace_id)
            REFERENCES asset.asset_versions(id, organization_id, workspace_id),
        CHECK (status IN ('pending', 'accepted', 'rejected')),
        CHECK (confidence >= 0 AND confidence <= 1)
    );

建议表必须带 organization_id 和 workspace_id，并使用与前述表相同的复合外键约束；accepted_into_draft_id 和 materialized_version_id 也必须通过复合外键限制在同一边界内。接受建议时，在同一事务中解析或创建标签、写入 asset_draft_tags、递增 draft revision，并把建议标记为 accepted。后续提交 draft 时才写入 asset_version_tags，并回填 materialized_version_id；原 AssetVersion 和原版本标签永不修改。

## 6. 版本和发布语义

标签绑定属于资产版本内容的一部分，而不是资产根对象的全局属性。

编辑和创建新版本时：

1. 创建或重置 AssetDraft 时，从 base version 复制标签到 asset_draft_tags；
2. 人工编辑、Webhook、导入或接受 Agent 建议只替换 AssetDraft 的标签集合；
3. 提交指定 draft revision 时，在创建 AssetVersion 的同一事务中一次性插入该版本全部 asset_version_tags；
4. AssetVersion 提交后，不允许替换、追加或删除其标签关联；
5. 请求中的标签必须属于同一组织和工作区，且只有 active 标签可以进入新版本；
6. 关联集合按 tag_id 去重；
7. 版本 checksum 使用排序后的 tag_id 集合，而不是展示名称。

发布时不复制标签。资产的公开标签集合由 current_published_version_id 指向的版本关联决定。撤回发布后，公开查询不应读取工作版本标签。

## 7. 统一服务边界

### 7.1 TagService

新增独立的 TagService，负责：

- 创建、查询、更新和归档；
- 规范化标签输入；
- 按工作区解析 tag_id、normalized_key 和 slug；
- 校验组织、工作区和权限；
- 处理并发创建同名标签；
- 返回稳定排序的标签对象。

普通资产写入不得直接拼接 SQL 或直接操作标签表。

### 7.2 AssetDraftTagService

新增 draft 标签服务，负责：

- 从 base version 初始化 draft 标签；
- 在 revision 保护下替换 draft 标签集合；
- 接受或拒绝 TagSuggestion；
- 记录 source、confidence 和操作者；
- 不触发公开检索投影。

### 7.3 AssetVersionTagMaterializer

新增版本标签物化服务，负责：

- 读取指定 draft revision 的标签；
- 在创建 AssetVersion 的同一事务中一次性插入版本标签关联；
- 记录 source、confidence 和操作者；
- 参与版本 checksum；
- 保证提交后任何代码都不能修改版本标签；
- 发布事件触发检索投影和聚合缓存刷新，draft 标签变化不触发公开投影。

## 8. API 设计

### 8.1 标签管理 API

    GET    /api/v2/workspaces/{workspaceId}/tags
    POST   /api/v2/workspaces/{workspaceId}/tags
    GET    /api/v2/workspaces/{workspaceId}/tags/{tagId}
    PATCH  /api/v2/workspaces/{workspaceId}/tags/{tagId}
    POST   /api/v2/workspaces/{workspaceId}/tags/{tagId}/archive
    POST   /api/v2/workspaces/{workspaceId}/tags/{tagId}/restore

列表接口支持 q、status、limit、cursor，返回 id、normalized_key、display_name、slug、status 和使用计数。

### 8.2 资产写入 API

AssetDraft 写入使用稳定标签身份：

    {
      "tag_ids": ["tag-uuid-1", "tag-uuid-2"]
    }

响应返回新的 draft revision 和完整标签对象，而不是只有字符串数组。提交版本接口不单独接收另一份标签集合，只物化它所校验的 draft revision，避免内容和标签发生竞态。

导入和 Agent 可以提交 tag_keys，但必须经过显式的解析策略：

- create_missing = false：未知标签直接拒绝；
- create_missing = true：在有标签管理权限的受控入口创建。

普通资产 API 不应隐式创建标签，否则任何拼写错误都会污染工作区标签目录。

### 8.3 查询 API

标签不再使用通用 eq/neq/in 字段操作符，使用明确语义：

    {
      "tags_any": ["release", "cms"],
      "tags_all": ["public", "approved"],
      "tags_none": ["deprecated"]
    }

SQL 使用 EXISTS、NOT EXISTS 和按资产去重的聚合实现。空数组表示不增加过滤条件。

## 9. 检索、聚合和公开访问

### 9.1 结构化筛选

结构化标签筛选直接连接 asset_version_tags 和 asset.tags，并在查询入口统一注入：

- organization/workspace；
- 资产删除状态；
- 当前工作版本或当前发布版本；
- visibility；
- publication status；
- 调用者权限。

不得再调用 retrieval.matches_field_filters(jsonb_build_object('tags', ...)) 处理标签。

### 9.2 标签聚合

标签聚合统一由 TagFacetService 提供，计数默认按可见资产 COUNT(DISTINCT asset_id)，而不是按版本计数。

返回结构：

    {
      "id": "tag-uuid",
      "key": "release",
      "name": "Release",
      "slug": "release",
      "count": 42
    }

聚合必须与实际内容列表使用完全相同的权限和发布范围，避免出现“标签计数有内容但列表看不到”的情况。

### 9.3 检索投影

当前发布版本变化或标签定义变化必须触发检索投影刷新。AssetDraft 标签变化和未发布版本创建不刷新公开投影。全文检索至少包含 normalized_key 和 display_name 的可搜索文本；结构化筛选仍然以关联表为准，不能依赖全文匹配。

标签名称变更也必须使相关投影失效。语义检索是否包含标签文本由投影配置决定，但不能因为标签变化而保持旧索引不变。

### 9.4 公开访问

公开接口只能从当前已发布版本的关联表读取标签。AssetDraft、未发布 working version、已删除资产的标签不得出现在公开列表、搜索建议或聚合结果中。

## 10. 导入、导出和 Agent

### 10.1 导入导出

导出使用 normalized_key 或 slug，不使用内部 UUID 作为跨环境唯一依据：

    {
      "tags": ["release", "cms"]
    }

导入流程必须：

1. 识别顶层 tags 系统字段；
2. 解析工作区标签；
3. 按策略拒绝或创建未知标签；
4. 写入目标 AssetDraft 和对应 draft revision；
5. 提交 draft 后物化 asset_version_tags；
6. 保证导出再导入后标签集合不变。

### 10.2 Agent

Agent 输出应包含：

    {
      "tags": [
        {"key": "release", "confidence": 0.96}
      ]
    }

Agent 不应直接覆盖人工标签。版本准备时必须明确策略：replace、add 或 suggest。最终实现使用 suggest，写入 asset_version_tag_suggestions；用户接受后进入 AssetDraft，提交 draft 后才成为正式版本标签关联。

## 12. 最终一致性约束

系统必须保证以下不变量：

1. 标签和资产版本必须属于同一组织、同一工作区。
2. 一个版本不能重复关联同一个标签。
3. 新 AssetDraft 未明确修改标签时，必须从 base version 继承标签。
4. 版本 checksum 对标签集合是确定性的，与数组顺序无关。
5. 归档标签不能被新版本绑定，但不能破坏历史版本。
6. 当前发布版本或标签定义变化必须触发检索和聚合刷新；draft 标签变化不得污染公开投影。
7. 公开查询只能看到已发布版本标签。
8. 普通资产写入不能隐式创建标签。
9. 所有入口使用同一个规范化和权限校验逻辑。
10. 业务代码不得再直接读取或写入 asset_versions.tags。

## 13. 必须具备的测试

- 标签同名并发创建只能产生一个定义；
- 不同工作区可以有同名标签；
- tags_any、tags_all、tags_none 结果准确；
- draft 初始化、自动保存、版本提交和发布不会串标签；
- Agent、Webhook、普通 API、导入使用相同规范化规则；
- 导出再导入后标签集合一致；
- 归档和重命名不破坏历史版本；
- AssetDraft、未发布 working version 和删除资产不会出现在公开标签聚合；
- 标签变化会刷新全文和语义检索投影；
- 标签聚合按可见资产计数，而不是重复计算版本。

## 14. 最终架构决策

本系统最终采用：

    工作区标签定义
            +
    AssetDraft 可变标签关联
            +
    AssetVersion 不可变标签关联
            +
    TagService / AssetDraftTagService / AssetVersionTagMaterializer
            +
    专用 any/all/none 查询
            +
    受权限和发布范围约束的 Facet/Delivery 读取

不采用以下方案：

- 继续把标签作为 asset_versions.tags JSONB 数组扩展；
- 使用通用字段过滤器表达标签业务语义；
- 在资产写入时隐式创建任意字符串标签；
- 把标签层级、目录树和动态字段混在同一个模型；
- 只在资产根对象上绑定标签而忽略版本发布语义。

这个模型既保留了现有资产版本体系，又把标签的身份、治理、查询和发布边界明确下来，适合作为后续内容管理、检索、导入导出和 Agent 能力的共同基础。
