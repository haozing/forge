# 数据模型自由定制实施方案（WP/PHPCMS 对照结论落地）

日期：2026-09-03
状态：**已实施**（P1+P2 全部落地，2026-09-03；实施证据与偏差记录见《数据模型自由定制实施验收报告-2026-09-03.md》）
前提：开发阶段，**无兼容包袱、无存量数据迁移负担**；"小白用户 + Agent 唯一入口"适用于录入与建模入口。

---

## 1. 背景与结论

对照 WordPress / PHPCMS 的"数据模型自由定制"机制得出的结论：

| 机制 | WordPress | PHPCMS | 本仓库现状 |
|---|---|---|---|
| 模型定义载体 | 代码调用（`register_post_type`）或插件配置（ACF） | 数据库实体 + 管理界面表单 | 数据库实体 + 版本化 JSON schema |
| 加字段 | meta 表塞键值（EAV），无类型约束 | 真表 ALTER TABLE 加列 | 改 field_schema → validate → publish |
| 变更版本化/回退 | 无（旧 meta 永久残留） | 无（直接改活表） | draft→validated→published→retired 全生命周期（`internal/resourcemodel/service.go:306-507`） |
| 建模入口 | 代码/插件后台 | 管理界面表单向导 | REST API（`/api/workspaces/{id}/resource-models`），**AI 建模入口不存在** |

**结论：**
1. **骨架不动。** 本仓库 resourcemodel 是"PHPCMS 内容模型的现代化重写"，且模型版本化/校验/发布流水线超出两家前辈；不引入任何一方的代码或依赖。
2. **不学 WP 的代码式建模与 EAV**：模型定义留在数据层（值=数据、能力=代码）；JSONB payload + schema 校验是正确折中。
3. **分类路线服从既有产品决策**（2026-09-03 审计修正，原稿曾提议"向 WP 借独立 category 实体"）：产品文档 v2 §21.4 已把分类学裁定给《统一分类树重构整改方案》（folders 唯一组织源 + CMS 投影 + Release Manifest 冻结）。WP taxonomy 的两半在本产品各有归属——**多对多主题标注=标签（已建成），导航/栏目结构=文件夹投影**——没有第三个实体的产品空位。本方案不再涉及分类，详见 §6 移交说明。
4. **向 PHPCMS 借字段级默认值与"字段字典"心智**——便宜且直接服务 agent 建模。
5. **补两家都没有的入口：AI 从样本推断模型**——小白用户一句话建模型的闭环。

## 2. 现状盘点（已逐项对照代码验证）

### 2.1 已就绪、本方案不动

- **模型生命周期**：`Create / Patch / CreateVersion / ValidateVersion / PublishVersion / RetireVersion`（`internal/resourcemodel/service.go`），publish 原子退役旧版本并追加 `resource_model.policy_published` 事件；检索协调器订阅该事件自动重建投影（`internal/retrieval/coordinator.go:56`）。
- **字段类型词表**：13 种（string/text/markdown/integer/number/boolean/date/datetime/enum/multiselect/object/array/asset_reference），2026-09-02 过度设计清扫后收敛（`internal/resourcemodel/schema.go:323`）。
- **写路径校验**：draft commit 时锁定模型当前版本，`ValidateFields(schemaBytes, fields)` 在同一事务内校验快照（`internal/asset/draft_service.go:860-866`）。**因 payload 是 JSONB，schema 变更天然不需要数据迁移**——旧版本不可变、按旧 schema 继续成立，新 draft 按新 schema 校验。
- **标签实体**：`asset.tags` + draft/version 关联表（source/confidence）+ Rename/Archive/Restore/Usage + 建议（suggestion）流 + 公开站 tag 页（`db/migrations/0006_tags.sql`、`internal/tag/`）。WP 式多对多主题标注已建成，无缺口。
- **首图**：`asset_version_attachments.role ∈ ('body','cover')` 已落地（0016）。
- **Agent 读模型**：`get_schema` 工具把 field_schema 喂给 LLM（`internal/agentruntime/tool_factory.go:330`）。

### 2.2 缺口收敛（本方案范围）

| # | 缺口 | 证据 |
|---|---|---|
| G1 | 字段级默认值不存在 | `validateField` 不认识 `default` 键；写路径无默认填充 |
| G2 | AI 建模入口不存在 | `asset_candidate.go` 是"按已有 schema 抽字段值"，方向相反；agent 无任何模型写工具 |
| G3 | agent 资产工具不能挂标签 | `create/update_internal_asset` 只传 fields（`tool_factory.go:114-144`），连 `tag_ids` 都没有，与产品文档 §11.1"资产写入使用 tag_ids"不齐 |

**分类学不在本方案范围**：产品文档 §21.4 已裁定由《统一分类树重构整改方案》承担（folders + 投影，待实施）。原稿 P2/P4 曾按 WP 式独立 category 实体设计，审计判定与该决策三项正面冲突（不建通用 Category 领域 / 不保存第二份分类归属 / 不做逐节点分类 CRUD），已整体移交（§6）。

### 2.3 顺手清理项

- **孤儿表 `model.resource_model_migrations`**（0004 建）：全 Go 代码零引用（早期"迁移作业"设计未实施，产品文档 §16.4 已记录"模型 schema 迁移作业框架已下线"，JSONB 架构下也不需要）。开发期直接 DROP。

## 3. 设计原则（对齐既有定调）

1. **值=数据、能力=代码**：模型 schema、字段值全在 DB；agent 产出的永远是"值"（schema JSON、字段值），不是代码。
2. **agent 可草拟、人可发布**：agent 获得的模型写能力只到 draft 为止；`ValidateVersion / PublishVersion` 仍是 `model.manage` 人类权限，agent 工具面不暴露 publish。
3. **镜像既有先例，不发明新形状**：AI 建模复用 DeepSeek structured output + ModelRegistry + 结构化校验 issue 迭代（与 style_suggest / asset_candidate 同构）；标签挂载走 `tag_ids` + TagService 既有校验。
4. **不过度设计的显式取舍**（见 §7 不做清单）：无插件机制、无真列 ALTER、无独立分类实体、无引用类字段默认值。

## 4. P1：字段级默认值 + 孤儿表清理（约 1.5 天）

### 4.1 schema 校验扩展

文件：`internal/resourcemodel/schema.go`

- `validateField`（:305）增加可选 `default` 键校验，规则**逐类型强约束**：
  - string/text/markdown：string；integer/number：number（integer 另要求整值）；boolean：bool
  - date/datetime：string，格式分别对齐字段自身格式规则
  - enum：值必须 ∈ options；multiselect：数组且每个值 ∈ options
  - object/array/asset_reference：**不允许 default**（`unsupported_default` issue）——嵌套结构与引用的默认语义含糊，v1 一律拒绝
- `default` 不加入 reserved keys；进入 SchemaChecksum（整体 marshal，自动覆盖）。
- openapi.yaml 对字段定义无结构描述（仅 :5936 描述文字），**契约零变更**。

### 4.2 写路径应用默认值

文件：`internal/asset/`（与 `ValidateFields` 同包新增 `ApplyDefaults(schemaBytes []byte, fields map[string]any) map[string]any`）

- 语义：**只填缺失键，不覆盖显式值**（含显式 null——null 是用户意图）；填充后逐字段走与 `ValidateFields` 相同的类型校验，默认值本身非法则整个 commit 报 `ErrInvalidInput`。
- 应用点两处，均在 `ValidateFields` 之前：
  1. draft 创建（`draft_service.go` CreateDraft 组装 fields 后）——让 draft 一打开就看到默认值；
  2. draft commit（:866 前）——兜底防漏，幂等。
- AI 写入路径（agent `create_internal_asset` → `assets.Create`）经同一 CreateDraft/Commit 管道，自动生效，无单独分支。
- 发布语义说明：默认值随快照物化后，`policy.publishing.required_fields` 的发布校验按"快照含值即满足"执行，无需特判。

### 4.3 孤儿表清理

新迁移 `db/migrations/0020_field_defaults.sql`（append-only 直接追加，本方案唯一迁移文件；P2 无 DDL）：

```sql
DROP TABLE IF EXISTS model.resource_model_migrations;
```

（连同其索引；零 Go 消费者已验证。）

### 4.4 验收

- schema_test：每类型 default 合法/非法矩阵 + checksum 变化。
- draft service 测试：缺省填充、显式覆盖不覆盖显式值、默认值非法整体拒绝、multiselect 默认 ∉ options 拒绝。
- agent `create_internal_asset` 集成测试：不传带默认值的字段 → 版本快照含默认值 → 发布校验通过。

## 5. P2：agent 资产工具补 tag_ids + AI 建模闭环（约 3 天）

### 5.1 agent 资产工具补 tag_ids（先修真实遗漏）

文件：`internal/agentruntime/tool_factory.go`

- `create_internal_asset`（:114）与 `update_internal_asset` 增加 `tag_ids` 参数（**数组 of uuid**，走 `assets.CreateInput/UpdateInput` 的 `TagIDs` → TagService 既有校验：工作区身份、归档拒绝、`MaxTagsPerDraft=100`）。
- 依据产品文档 §11.1：agent 写入面用 tag_ids；字符串标签解析不在本期（那是导入/Webhook 的受控路径）。错误信息保持可被 LLM 直接理解后重试。

### 5.2 建模建议工具（纯计算，不落库）

文件：`internal/agentruntime/model_suggest.go`（新，模式复刻 `style_suggest.go` / `asset_candidate.go`）

- 工具名 `suggest_resource_model`，入参：`{ intent: string, samples: string[] (≤10，每条 ≤4KB), extend_model_id?: string }`。
- 走 ModelRegistry 固定的 structured-output 端点，输出 JSON：
  `{ model_key, name, description, content_kind, field_schema, rationale, ambiguities[] }`
- **服务端二次校验**：返回的 field_schema 立即过 `resourcemodel.Validate`，schema issue 随工具结果原样回给 LLM 迭代（最多 2 轮内建重试，超出即带 issue 返回，由会话层继续）。
- 门禁：`schema.read` 能力位（纯计算，无 DB 写）。

### 5.3 建模写入工具（只到 draft）

- 工具名 `create_resource_model`（创建模型+初始 draft 版本）与 `update_resource_model_draft`（对未发布 draft 版本 Patch），直接调 `resourcemodel.Service.Create / CreateVersion / PatchVersion`。
- **双层门禁**：工具策略层新能力位 `model.manage`（默认不在 `parseToolPolicy` 默认能力集 `tool_factory.go:316-321`，agent 应用必须显式授予）+ 服务层 `s.require(model.manage)` 实时校验。授予动作可审计。
- **不提供** publish/retire 工具；发布校验后由人在管理端执行（现有 `ValidateVersion/PublishVersion` 端点，`model.manage` 人类权限）。
- prompt 侧约定：工具描述写明"创建后需人工 validate+publish 才生效"，避免 LLM 空等。

### 5.4 字段字典（提示词资产，非代码）

`get_schema` 与建模工具的系统提示中补一份"字段类型字典"：13 类型各自的语义、取值示例、适用场景（PHPCMS 字段向导的等价物，一次写成静态文本）。这是提升 AI 建模质量性价比最高的一步。

### 5.5 产品文档同步条目（交付物，不可省）

按 2026-09-02 样式工具先例（产品文档 §7.3/§8.3 补充段），本期在 `docs/产品文档-v2.md` 追加：

- §8.1 Agent 整理能力清单补一条："从样本推断资源模型 schema（仅产出草稿建议）"；
- §8.3 例外段补充：模型工具属"agent 可草拟、人可发布"的写侧例外——`create_resource_model / update_resource_model_draft` 只落 draft 版本，publish 始终人类；
- §17 受控例外清单补这两个工具名（与 get_related_assets / get_attachment_text / get_schema / 样式工具同列）。

前端依赖提示：模型建议的确认/发布流由管理端 React（独立工程）消费现有 API，本仓库不包含前端改动，需给前端排期提一条 backlog。

### 5.6 验收

- 单测：schema issue 回传格式、2 轮迭代收敛、能力位缺省拒绝（默认集不含 model.manage）、tag_ids 校验（越权 tag、归档 tag、>100 拒绝）。
- 集成（全链闭环）：样本 5 条 → `suggest_resource_model` → `create_resource_model` → 人工 `validate` → `publish` → `get_schema` 可读 → `create_internal_asset`（带 `tag_ids`、省略有默认值字段）→ 版本快照含默认值与标签。
- 产品文档补充条目落地；`go test ./...` 绿 + `openapi_contract_test` 绿（本期零新增 HTTP 路由，agent 工具不进 openapi）。

## 6. 移交项：分类能力 → 《统一分类树重构整改方案》

原稿 P2（独立 category 实体）与 P4（公开分类页）经审计与该方案三项最终决策正面冲突（不建通用 Category 领域 / CMS 不保存第二份资产分类归属 / 不提供逐节点分类 CRUD），整体移交。原诉求与承接位置对照：

| 原诉求 | folders 方案承接位置 |
|---|---|
| 分类树 CRUD（建/改名/移动/归档） | §5.2 `content.folders` + §7.1 Folder API |
| 资产挂分类 | §5.3 `content.folder_assets`（资产级挂载、实时生效 §8.4——**不绑版本、不走发布审核**，语义正确） |
| 公开站分类页 / 导航挂分类 | §8 CMS 分类自动投影（Site Revision `category_projection` + Release Manifest 冻结 + `folder_projection_checksum` 409 并发控制） |
| 按分类过滤查询 | §7.2 资产查询 folder 过滤 |
| agent 挂分类 | folders API 落地后 agent 工具跟进（独立小改，另行提项） |

本方案不重复设计；分类相关实施以那份文档为准。产品文档 v2 §21.4 的裁定不变。

## 7. 明确不做清单（防过度设计回潮）

| 不做 | 理由 |
|---|---|
| 插件/钩子机制、模板内嵌逻辑 | WP 生态的黑盒化教训；能力=代码随发版演进 |
| 真列 ALTER TABLE | JSONB+校验已覆盖，锁表改活表是纯风险 |
| 独立 Category/taxonomy 实体（含版本级挂载、逐节点分类 CRUD） | 服从《统一分类树重构方案》最终决策；多对多主题=标签已建成，导航结构=文件夹投影 |
| agent 可 publish 模型 | 发布闸门必须留给人（信任模型） |
| object/array/asset_reference 默认值 | 默认语义含糊，校验成本 > 收益 |
| agent 工具字符串标签解析 | 产品文档 §11.1：字符串标签只允许导入/Webhook/Agent 受控解析入口，且必须过 TagService；本期只做 tag_ids |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| AI 建议 schema 质量差 | 字段字典 + samples 上限 + issue 回传迭代；3 组固定样本金标准集回归 |
| `model.manage` 能力位被滥授 | 默认能力集不含；授予经 agent 应用配置且可审计；写侧只落 draft，最坏结果是可废弃的草稿版本 |
| 工具面膨胀拉低 LLM 选择准确率 | 净增 2 个工具（suggest/create 系）、既有工具只加 1 个参数 |
| 分类需求催得急 | 依赖《统一分类树重构整改方案》排期，本方案不阻塞也不预埋半成品分类 |
