## 1. 文档结论

阶段 2 的唯一目标，是把标签从散落在 AssetVersion JSONB、查询参数和各类写入入口中的字符串数组，变成具备稳定身份、权限、生命周期、版本语义和统一查询语义的正式领域。

阶段 2 完成后必须形成以下闭环：

1. 每个工作区拥有独立标签目录，标签有稳定 ID、业务 key、slug、展示名、状态和 revision。
2. workspace admin 管理标签定义；editor 只能把已有 active 标签绑定到可编辑 AssetDraft。
3. AssetDraft 标签可自动保存，并与 draft revision 在同一事务中更新。
4. 提交 draft 时，把标签集合与正文、字段和附件一起物化为不可变 AssetVersion 快照。
5. 已提交并 sealed 的版本标签关联不能再 INSERT、UPDATE 或 DELETE；标签改名和归档不改写历史版本。
6. 成员资产列表、现有查询、导出筛选统一使用关系表实现 `tags_any/tags_all/tags_none`。
7. 标签 facet 与资产列表使用相同的资产范围、版本指针和权限，按 `COUNT(DISTINCT asset_id)` 计数。
8. 普通资产 API 只接收 `tag_ids`；导入和 Webhook 使用受控 `tag_keys`，不能隐式污染标签目录。
9. 导出使用 normalized key，导入后标签集合可以稳定 round-trip。
10. 标签定义变化产生事务内审计和领域事件；draft 标签变化不触发公开投影。
11. 运行时代码、schema、OpenAPI 和测试中不再存在 `asset_versions.tags` 或把标签包装成普通 JSON 字段过滤的旁路。

阶段 2 不是给现有 `tags []string` 再加一层 helper。当前所有标签写入、成员资产列表和导出入口必须迁移到同一组标签服务和关系表，然后删除字符串数组业务模型。阶段 2 只提供稳定的 `tag.Filter`/关系仓储边界和契约测试；全文、语义、混合 query 的最终实现替换及 `fulltext.go`、`member_search.go` 等旧检索文件的删除由阶段 3 一次完成，阶段 2 不修改这些最终会被删除的检索实现。

阶段 2 仍是首次共享部署前开发检查点；Tag 最终定义直接折叠回领域空库基线并重建数据库，不保留阶段 1 测试数据，不创建阶段追加迁移。

## 2. 阶段边界

### 2.1 前置条件

阶段 2 开始前必须满足：

- 阶段 0 的最终 Asset、AssetDraft、AssetVersion、PublicationRequest 和事件契约已经落地。
- 每个 Asset（包括 archived）恰好一个共享 AssetDraft，draft 使用 revision/committed_revision 表达 dirty/clean；archived 时冻结写入但保留 draft。
- AssetVersion 内容字段已经不可变，不存在版本 PATCH API。
- v2 空库基线已经包含 `asset.tags`、`asset.asset_draft_tags`、`asset.asset_version_tags` 和 `asset.asset_version_tag_suggestions` 的存储边界。
- 阶段 1 的 MemberPrincipal、WorkspacePolicy、四角色 membership、`/api/v2`、OpenAPI、幂等和 ETag 契约已经可用。
- organization admin 没有隐式工作区内容权限；标签操作只通过显式 membership 授权。
- `docs/route-retirement-ledger.md` 已建立；阶段 2 只负责标签、导入导出和 Webhook 所属旧字段/路由，不能越权删除 query 或 PublicSite 入口。

若当前代码仍在直接创建或更新带 `tags jsonb` 的 AssetVersion，说明阶段 0 尚未验收，不能通过阶段 2 的双写兼容来绕过。

### 2.2 阶段 2 包含

- 标签 key/display name/slug 规范化规则。
- Tag 创建、读取、改展示名、归档和恢复。
- 标签列表、搜索、游标分页和使用量统计。
- AssetDraft 标签初始化、替换、继承与 revision 冲突。
- draft 提交时的 AssetVersionTag 原子物化和 checksum 输入。
- 标签来源、操作者与 AI 置信度的关联级追踪。
- CMS 成员资产列表和现有 query 代码的关系型标签筛选。
- workspace 范围的标签 facet。
- 导入、导出和 Webhook 的标签解析闭环。
- ResourceModel migration worker 的关系标签改造，以及仍残留的旧公开资产读取旁路清理。
- ResourceModel 系统标签与动态 `multiselect` 字段分离。
- TagSuggestion 的最终数据与服务接口，供后续 Agent 阶段调用。
- 对应 OpenAPI、审计、事件、数据库约束和测试。

### 2.3 阶段 2 不包含

- Agent 生成标签建议、提示词、模型调用和建议 UI；这些属于阶段 4。
- 全文/语义投影中加入标签文本、embedding 重建和混合检索优化；这些属于阶段 3。
- 公开站点标签页、匿名 facet 和公开 URL；这些属于阶段 5。
- Web 前端标签管理器和选择器；前端仍在阶段 6。
- 层级分类、taxonomy、目录树、标签组、标签颜色、标签别名和标签合并。
- 跨工作区共享标签或组织级标签目录。
- 标签硬删除和历史关联重写。
- 旧 JSONB 标签的数据迁移、双写、兼容 view 或旧 API 适配。

## 3. 当前代码审计

本节描述阶段 0 实施前的实际仓库，用于固定替换范围，不代表目标实现继续保留这些结构。

### 3.1 当前标签没有领域身份

[0017_yxt_resource_models.sql](../db/migrations/0017_yxt_resource_models.sql)只给 `asset.asset_versions` 增加了 `tags jsonb NOT NULL DEFAULT '[]'`。当前没有：

- 标签定义表；
- 工作区唯一 key；
- 标签状态和 revision；
- draft 标签关联；
- 版本标签复合外键；
- JSONB 必须为字符串数组的数据库约束。

因此当前同一语义可以出现大小写、空白和 Unicode 形式不同的多个字符串，数据库无法判断它们是不是同一标签。

### 3.2 资产写入绕过统一标签规则

[member.go](../internal/asset/member.go)的创建和更新直接把 `[]string` 序列化到新版本；[member_versions.go](../internal/asset/member_versions.go)既创建版本，也可以原地更新版本标签。普通写入 [write.go](../internal/asset/write.go) 和 [webhook_input.go](../internal/asset/webhook_input.go)分别处理自己的字符串数组。

[resourcemodel/worker.go](../internal/resourcemodel/worker.go)在升级 ResourceModelVersion 时直接读取并复制 `v.tags`，再直接 INSERT 新 AssetVersion；它同样绕过统一 draft/commit、版本标签物化和不可变性规则。

这些入口没有共享以下规则：

- 标签是否属于当前 workspace；
- 是否 active；
- 大小写和 Unicode 是否同一 key；
- 调用者能否创建标签；
- 版本是否已经不可变；
- 来源和置信度如何保存。

### 3.3 当前筛选语义不正确

[member.go](../internal/asset/member.go)、[query/filters.go](../internal/query/filters.go)、[query/fulltext.go](../internal/query/fulltext.go)和[query/member_search.go](../internal/query/member_search.go)把标签包装成：

```sql
retrieval.matches_field_filters(jsonb_build_object('tags', v.tags), ...)
```

[0028_yxt_dynamic_filters.sql](../db/migrations/0028_yxt_dynamic_filters.sql)只理解普通 JSON 字段的 `eq/neq/in/contains/contains_any/exists`，不能稳定表达标签集合的 any/all/none，也不能使用关系索引。

当前资产列表还同时支持顶层 `tags` 参数和 `filters.tags`，形成两套输入语义。

### 3.4 标签聚合泄露了存储实现

[frontend_contract_gaps.go](../internal/httpapi/frontend_contract_gaps.go)中的搜索建议直接 `jsonb_array_elements_text(v.tags)`，并与 title 建议拼在 handler SQL 中。它没有复用统一资产可见范围，也没有独立的 TagService 或 facet service。

[public_assets.go](../internal/httpapi/public_assets.go)也直接返回 `[]string` 的 `v.tags`，并由当前 router 暴露 `/api/public/workspaces/{workspaceId}/assets` 和 `/api/public/assets/{assetId}`。这两条路径不是 v2 PublicSite 契约；若阶段 0 后仍残留，阶段 2 随旧列一起删除，不改造成另一套公开读取 API。阶段 5 再实现 `/api/public/v2/sites/...`。

### 3.5 导入导出没有 round-trip

[transfer_worker.go](../internal/asset/transfer_worker.go)的导出读取 `v.tags`，但导入创建版本时没有写入标签。更严重的是，当导入行没有显式 `fields` 对象时，`importFields` 只排除 title、markdown 和 source，顶层 `tags` 可能被错误塞进动态 fields。

当前导出筛选也使用 `v.tags @> jsonb`，和成员列表的过滤语义不一致。

### 3.6 Agent 与资源模型混淆系统标签

[asset_candidate.go](../internal/agentruntime/asset_candidate.go)只返回动态 Fields，不返回系统 TagSuggestion；[preparation.go](../internal/asset/preparation.go)读取源版本和创建候选版本时也没有完整标签链路。

[resourcemodel/schema.go](../internal/resourcemodel/schema.go)一方面把 `tags` 设为系统保留 key，另一方面又允许动态字段类型 `tags`。同一个名字同时代表系统关系和普通 JSON 字段，无法形成稳定 API。

### 3.7 HTTP 和测试缺少正式标签契约

当前路由只有 `/api/frontend/...` 资产、查询和传输入口，没有 Tag CRUD；现有归档 OpenAPI 也没有最终标签资源。测试主要验证 JSON 数组和通用过滤器，没有覆盖：

- 同 key 并发创建；
- 跨 workspace 绑定；
- archived 标签提交；
- draft revision；
- 版本标签不可变；
- any/all/none；
- facet 权限一致性。

## 4. 阶段 2 最终领域模型

### 4.1 聚合与依赖关系

```text
Workspace
└── Tag[]

Asset
├── AssetDraft
│   └── AssetDraftTag[] -> Tag
└── AssetVersion[]
    ├── AssetVersionTag[] -> Tag
    └── TagSuggestion[] -> optional resolved Tag
```

职责边界：

- Tag 是工作区内可复用的标签定义和生命周期聚合。
- AssetDraftTag 是可变编辑状态，随 draft revision 更新。
- AssetVersionTag 是版本内容快照的一部分，创建后不可变。
- TagSuggestion 是 AI 建议记录，不是正式标签关系。
- 标签不表达父子层级，不承担 Container、Department 或 ResourceModel 动态字段职责。

### 4.2 TagKey 规范化

Tag 创建输入包含 `display_name` 和可选 `key`。key 为空时从 display name 派生。

统一算法固定为：

1. 对输入执行 Unicode NFKC。
2. 去除首尾 Unicode 空白，把连续空白折叠成一个 ASCII 空格。
3. 使用 Unicode case folding，不使用 locale 特例。
4. 再执行一次 NFKC，得到 `normalized_key`。
5. 拒绝 Unicode `Cc`、`Cf`、`Zl`、`Zp` 字符、空结果和超过限制的结果。

限制：

- `display_name`：1-100 Unicode code point，UTF-8 不超过 400 bytes。
- `normalized_key`：1-100 Unicode code point，UTF-8 不超过 400 bytes。
- 单个 AssetDraft/AssetVersion：最多 100 个不同标签。
- 单个筛选请求：每组最多 50 个 key，三组去重后最多 100 个。

Go 实现统一放在 tag domain，使用 `golang.org/x/text/unicode/norm` 和 `golang.org/x/text/cases`；将 `golang.org/x/text` 从间接依赖提升为直接依赖。handler、导入 worker 和 Agent 不复制规范化代码。

### 4.3 slug 规则

slug 只在创建时生成，之后不可修改：

1. 以 normalized key 为输入。
2. 保留 Unicode letter/number 和 ASCII `-`。
3. 其他字符序列折叠成一个 `-`，去除首尾 `-`。
4. 最长 120 code point。
5. 若结果为空，使用 `tag-<uuid前12位>`。
6. 若工作区内发生 slug 冲突，追加 `-<uuid前8位>`。

不做拼音或其他语言转写。HTTP 路径负责标准 UTF-8 URL encoding。外部交换优先使用 normalized key；slug 主要供后续公开站点路径使用。

### 4.4 Tag 生命周期

```text
create -> active -> archived -> active
```

规则：

- normalized key、slug、organization_id、workspace_id 创建后不可修改。
- PATCH 只允许修改 display name。
- display name 可以相同；身份由 normalized key 和 ID 决定。
- archived 标签不能新加到 draft，也不能进入新 AssetVersion。
- 已经存在于 draft 的标签被归档后不自动删除；commit 明确返回冲突，编辑者必须移除或管理员恢复标签。
- archived 标签仍能出现在历史版本、已有 published version 和管理查询中。
- 同 key 的 archived 标签占用原 key；再次创建返回 `tag_archived`，应显式 restore。
- 不提供 DELETE 和 merge。

### 4.5 Tag 数据表

最终表 `asset.tags`：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 稳定身份 |
| `organization_id` | 必填 | 租户边界 |
| `workspace_id` | 必填 | 标签目录边界 |
| `normalized_key` | 不可变 | 统一匹配和导入导出 key |
| `display_name` | 1-100 code point | 展示名称 |
| `slug` | 不可变 | 稳定 URL 标识 |
| `status` | `active` / `archived` | 生命周期 |
| `revision` | bigint，初始 1 | ETag 与事件 aggregate version |
| `created_by` / `updated_by` | FK user | 操作者 |
| `created_at` / `updated_at` | timestamptz | 时间 |
| `archived_at` / `archived_by` | 可空 | 当前归档信息；restore 时清空 |

唯一键：

```text
(organization_id, workspace_id, normalized_key)
(organization_id, workspace_id, slug)
(id, organization_id, workspace_id)
```

Tag 不缓存全局 usage count；使用量按具体读范围实时聚合，避免发布指针、权限或归档变化后产生第二份不一致主数据。

### 4.6 AssetDraftTag

最终表 `asset.asset_draft_tags`：

| 字段 | 约束 |
| --- | --- |
| `organization_id` / `workspace_id` | 必填，复合外键范围 |
| `asset_draft_id` | FK draft |
| `tag_id` | FK tag |
| `source` | `manual` / `api` / `webhook` / `import` / `ai` |
| `confidence` | 仅 `ai` 必填，0-1；其他 source 必须为空 |
| `added_by` | FK user/agent principal |
| `added_at` | timestamptz |
| 主键 | `(asset_draft_id, tag_id)` |

集合替换采用差异更新：

- 仍然存在的 tag 保留原 source、confidence、added_by 和 added_at。
- 新增 tag 使用当前入口的 source 和操作者。
- 移除 tag 删除 draft relation。
- 从 base version 初始化 draft 时复制版本 relation 的 provenance。
- 接受 AI 建议时，如果 draft 已经有同一标签，保留原 relation，不把人工来源降级为 ai。

draft relation 本身没有独立 revision，父 AssetDraft.revision 是唯一并发控制版本。

### 4.7 AssetVersionTag

最终表 `asset.asset_version_tags`：

| 字段 | 约束 |
| --- | --- |
| `organization_id` / `workspace_id` | 必填，复合外键范围 |
| `asset_version_id` | FK version |
| `tag_id` | FK tag |
| `source` | 与 draft 相同枚举 |
| `confidence` | 与 draft 相同约束 |
| `created_by` | FK user/agent principal |
| `created_at` | timestamptz |
| 主键 | `(asset_version_id, tag_id)` |

数据库必须具备：

```text
FOREIGN KEY (asset_version_id, organization_id, workspace_id)
FOREIGN KEY (tag_id, organization_id, workspace_id)
INDEX (asset_version_id, tag_id)
INDEX (tag_id, asset_version_id)
```

AssetVersionTag 只能在父 AssetVersion 尚未 sealed 的创建事务中 INSERT。父版本 sealed 后，不可变 trigger 拒绝 INSERT/UPDATE/DELETE；Tag 改名、归档或恢复不会修改关联行。

版本关系冻结的是 Tag 身份和绑定 provenance，不复制 display_name/slug/status 快照。读取历史版本时关联当前 Tag 定义并返回当前状态；名称和状态变更由 Tag revision、审计日志与事件追踪，不触发新 AssetVersion。这样不会让同一 Tag 因改名产生多个身份，也不会伪造资产内容版本。

### 4.8 TagSuggestion 契约

阶段 2 固定 `asset.asset_version_tag_suggestions` 的最终结构，但不生成 AI 建议：

| 字段 | 说明 |
| --- | --- |
| `id` | UUID PK |
| `organization_id` / `workspace_id` | 复合租户边界 |
| `source_version_id` | 建议基于的不可变版本 |
| `suggested_key` | 已规范化候选 key |
| `suggested_display_name` | Agent 建议显示名 |
| `resolved_tag_id` | 可空；接受时最终选择的 Tag |
| `confidence` | 0-1 |
| `status` | `pending` / `accepted` / `rejected` |
| `reviewed_by` / `reviewed_at` | 决策人和时间 |
| `accepted_into_draft_id` | 接受后写入的 draft |
| `materialized_version_id` | 后续真正包含该 Tag 的版本 |
| `created_at` | 创建时间 |

服务规则：

- pending 建议不会出现在正式标签、筛选、facet 或公开读取中。
- 接受建议只修改 AssetDraft 并增加 draft revision，永不修改 source version。
- `resolved_tag_id` 为空时，调用者必须明确传目标 Tag；只有同时具备 `tag.manage` 的调用者才能显式创建后再接受。
- 不允许“接受建议时静默创建字符串标签”。
- draft commit 时，只为该 draft 中实际存在的 accepted suggestion 回填 `materialized_version_id`。

阶段 4 负责生成建议和注册 HTTP 决策路由；阶段 2 只交付可测试的 repository/service 接口和 materializer hook。

## 5. 权限模型

### 5.1 Action

继续使用阶段 0 动作：

```text
tag.read
tag.manage
asset.read
asset.write
```

所有权限由 WorkspacePolicy 判断，不在 TagService 中比较角色字符串。

### 5.2 权限矩阵

| 行为 | Org admin 无 membership | Workspace admin | editor | reviewer | viewer |
| --- | --- | --- | --- | --- | --- |
| 读取 active/archived 标签 | 拒绝 | 允许 | 允许 | 允许 | 允许 |
| 读取标签 usage/facet | 拒绝 | 允许 | 按可读资产允许 | 按可读资产允许 | 按可读资产允许 |
| 创建、改名、归档、恢复标签 | 拒绝 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 编辑 draft 标签 | 拒绝 | 允许 | 允许 | 拒绝 | 拒绝 |
| 提交版本标签 | 拒绝 | 允许 | 允许 | 拒绝 | 拒绝 |
| 接受/拒绝 TagSuggestion | 拒绝 | 允许 | 允许 | 拒绝 | 拒绝 |
| 接受未知建议并创建 Tag | 拒绝 | 允许，必须显式创建 | 拒绝 | 拒绝 | 拒绝 |
| 导入时创建未知标签 | 拒绝 | 允许，显式策略 | 拒绝 | 拒绝 | 拒绝 |

Agent Principal 不能获得 `tag.manage`。Webhook 和后续 Agent 只能解析已有 active 标签或生成 pending suggestions，不能直接扩张工作区标签目录。

### 5.3 读取范围

Tag 定义可由任意显式 workspace member 读取，但 usage 和 facet 只能统计调用者可读资产：

- working scope：当前 workspace membership 可读的非 archived Asset 的 `current_working_version_id`。
- published scope：只读取 `publication_status=published` 的 `current_published_version_id`，并继续执行 visibility 规则。
- 后续 organization/public 读取仍使用 published scope，由阶段 3/5 的访问入口构造范围。

TagService 不因为“标签存在”推断调用者能读取使用该标签的资产。

## 6. 核心业务流程

### 6.1 创建标签

```text
Workspace admin
  -> normalize display_name/key
  -> generate UUID and stable slug
  -> transaction
     -> verify active workspace membership + tag.manage
     -> insert Tag(active, revision=1)
     -> append audit tag.create
     -> append outbox tag.created
  -> return Tag + ETag
```

成员 Tag API 的同 key 并发创建不做隐式成功：一个成功，另一个返回 `409 tag_key_exists`。导入的显式 `unknown_tag_policy=create` resolver 可使用 `INSERT ... ON CONFLICT DO NOTHING` 后读取同一 Tag，因为它表达的是按策略解析 key，而不是创建管理资源。

### 6.2 替换 draft 标签

```text
Member PATCH AssetDraft with tag_ids + If-Match
  -> WorkspacePolicy(asset.write)
  -> transaction
     -> lock AssetDraft FOR UPDATE
     -> compare expected draft revision
     -> sort tag IDs, lock Tag rows FOR KEY SHARE
     -> verify same organization/workspace + active + max 100
     -> reconcile AssetDraftTag set
     -> update other draft fields and revision exactly once
     -> append transactional audit
  -> return new draft revision + sorted Tag summaries
```

请求省略 `tag_ids` 表示保留；明确传 `[]` 表示清空。标签与标题、正文、字段、附件在同一次 PATCH 中只增加一次 draft revision。

### 6.3 从 base version 初始化 draft

创建或重置 draft 时，在同一事务中：

1. 锁定 Asset 和目标 base version。
2. 复制正文、字段和附件。
3. 复制全部 AssetVersionTag 到 AssetDraftTag，包括 archived 标签和 provenance。
4. 设置 base_version_id、revision 和 clean 状态。

复制 archived 标签是为了忠实表示 base version；后续 commit 会拒绝 archived 标签，不能在初始化时静默丢失历史语义。

### 6.4 提交 draft

```text
commit-draft/direct-publish/publication-submit
  -> transaction
     -> lock Asset
     -> lock AssetDraft FOR UPDATE and verify revision/base_version_id
     -> load draft tags ordered by tag_id
     -> lock Tag rows FOR KEY SHARE and verify active/scope
     -> validate content/fields/clean attachments
     -> compute checksum with sorted tag IDs
     -> insert AssetVersion
     -> insert all AssetVersionTag rows
     -> materialize eligible accepted suggestions
     -> update Asset pointers + draft base/clean state
     -> append asset.version_created and audit
```

Tag archive/restore/update使用 `FOR UPDATE` 锁 Tag 行，因此和提交事务串行：只要 commit 在锁内确认 active，就不会在同一提交时刻产生“新版本绑定已归档标签”的竞态。

### 6.5 归档和恢复标签

归档：

- 要求 `tag.manage`、`Idempotency-Key` 和 `If-Match`。
- 锁 Tag，验证 active/revision，改为 archived，revision + 1。
- 不修改 drafts、versions 或 published pointers。
- 同事务写 audit、`tag.archived`。

恢复：

- 同样要求幂等键和 ETag。
- 因 key/slug 从未释放，不需要重新命名或合并。
- 改为 active，清空当前 archived_at/by，revision + 1。
- 同事务写 audit、`tag.restored`。

### 6.6 导入行

当前 worker 用一个大事务处理最多 10000 行，并直接 INSERT AssetVersion。阶段 2 改为每个导入行一个业务事务，并为 batch/row 增加可恢复租约：

`ImportBatch` 保存 `status`、`lease_owner`、`lease_until`、`attempt_count` 和 `last_error`；`ImportRow` 保存 `status`、`lease_owner`、`lease_until`、`attempt_count`、`idempotency_key` 和 `last_error`。状态为 `processing` 且租约过期的 batch/row 可被其他 worker 原子 reclaim；进程崩溃、SIGTERM 或数据库连接断开都不能留下永久 processing。claim 使用 `FOR UPDATE SKIP LOCKED`，每次续租和完成都校验 owner/token。

1. 重新校验 submitted_by 仍为 active 且仍具备 `asset.write`；`unknown_tag_policy=create` 额外要求 `tag.manage`。
2. 从顶层 `tag_keys` 解析标签，`tag_keys` 永不进入动态 fields。
3. 按 batch 冻结策略 reject 或显式创建未知标签。
4. 创建 RawInput、Asset 和 AssetDraft。
5. 写 AssetDraftTag(source=import)。
6. 调用标准 commit service 创建 AssetVersion 和 AssetVersionTag。
7. 更新 import row 状态、审计和事件后提交。

单行失败只回滚该行；其他 accepted 行保留。batch 汇总在全部行完成后单独更新。单 batch 最多允许创建 500 个不同新标签，防止导入文件无限扩张标签目录。

每行以稳定 `idempotency_key` 唯一约束 Asset/Version 创建和关系写入；重试必须先读取已完成的 row 结果再返回，不能重复创建 Asset、Version、Tag 或事件。batch 聚合统计采用可重放的 row 状态计算，不能依赖 worker 内存或“全部行都跑完”的单次回调。恢复测试必须覆盖 worker 在每个事务步骤后崩溃、租约过期 reclaim、重复完成和最终 batch 汇总。

ImportBatch 必须持久化 `unknown_tag_policy` 和 `created_tag_count`。create 模式每行事务先锁定 batch 行，再用 TagService 并发安全地创建/复用标签，并以实际新插入数量原子增加 `created_tag_count`；超过 500 时该行返回 `import_tag_create_limit_exceeded`。不能在 worker 内存中计数，也不能把同 key 的并发冲突重复计数。

## 7. 标签筛选与 Facet

### 7.1 统一 Filter 值对象

新增 `tag.Filter`：

```text
Any  []TagID
All  []TagID
None []TagID
```

HTTP 输入使用 normalized key：

```json
{
  "tags_any": ["release", "cms"],
  "tags_all": ["approved"],
  "tags_none": ["deprecated"]
}
```

解析规则：

- 对每个 key 执行统一 normalization。
- 在当前 workspace 一次性解析 active 和 archived Tag ID。
- 任一未知 key 返回 `422 unknown_tag`，不能静默忽略拼写错误。
- 同组去重并按 Tag ID 排序。
- Any/All 与 None 出现交集时返回 `422 contradictory_tag_filter`。
- 空数组等价于没有该条件。

AssetDraft 写入仍使用 `tag_ids`；筛选使用 key，是为了 URL、导入导出和跨环境调用稳定。

### 7.2 SQL 语义

在调用方已经选择有效 AssetVersion 后，关系条件固定为：

```sql
-- any
cardinality($any_ids::uuid[]) = 0 OR EXISTS (
  SELECT 1 FROM asset.asset_version_tags avt
  WHERE avt.asset_version_id = selected_version_id
    AND avt.tag_id = ANY($any_ids::uuid[])
)

-- all
cardinality($all_ids::uuid[]) = 0 OR (
  SELECT count(DISTINCT avt.tag_id)
  FROM asset.asset_version_tags avt
  WHERE avt.asset_version_id = selected_version_id
    AND avt.tag_id = ANY($all_ids::uuid[])
) = cardinality($all_ids::uuid[])

-- none
NOT EXISTS (
  SELECT 1 FROM asset.asset_version_tags avt
  WHERE avt.asset_version_id = selected_version_id
    AND avt.tag_id = ANY($none_ids::uuid[])
)
```

这些条件由 repository helper 生成参数和固定 SQL 片段，不接受调用者 SQL 字符串。不得再调用 `matches_field_filters(jsonb_build_object('tags', ...))`。

### 7.3 版本选择

标签过滤永远作用于入口已经选择的版本：

- CMS 资产列表：`current_working_version_id`。
- published 成员查询、Agent 查询和未来公开查询：`current_published_version_id`。
- 版本历史详情：指定 `asset_version_id`，不经过 Asset current pointer。

不得使用 `COALESCE(current_published_version_id, current_working_version_id)`，因为这会把 draft 内容混入要求 published 的出口。

### 7.4 TagFacetService

Facet 请求接收由授权层构造的 AssetReadScope 和与资产列表相同的结构化过滤条件。阶段 2 支持：

- scope：`working` 或 `published`；
- resource_model_id；
- publication status/visibility 的合法子集；
- `tags_any/tags_all/tags_none`；
- tag status：默认 active，可显式 all。

不在阶段 2 的 facet 中加入全文 q、向量条件或站点条件。

返回：

```json
{
  "items": [
    {
      "tag": {
        "id": "...",
        "key": "release",
        "display_name": "Release",
        "slug": "release",
        "status": "active"
      },
      "asset_count": 42
    }
  ]
}
```

计数语义：对应用全部当前过滤条件后的资产集合执行 `COUNT(DISTINCT asset_id)`，不是版本数或 chunk 数。facet 和资产列表必须共享同一个 AssetReadScope/版本选择器。阶段 3 如需 disjunctive facet，扩展 query orchestration，不改变 TagFacet 的权限边界。

### 7.5 标签目录 usage

标签管理列表可通过 `include_usage=true` 返回：

```json
{
  "working_assets": 12,
  "published_assets": 8,
  "open_drafts": 3
}
```

三个数字都按 distinct asset/draft 计数，并在当前 page 的 Tag IDs 上做一次 grouped query，禁止逐标签 N+1。`open_drafts` 精确定义为 active workspace 中 `revision <> committed_revision` 且包含目标 Tag 的非 archived AssetDraft 数量；归档 Asset 的冻结 draft 不计入。默认 `include_usage=false`，标签选择器不承担管理统计成本。

## 9. 导入、导出与 Webhook

### 9.1 导入契约

ImportInput 新增：

```json
{
  "resource_model_id": "...",
  "resource_model_version_id": "...",
  "unknown_tag_policy": "reject",
  "rows": [
    {
      "title": "...",
      "fields": {},
      "tag_keys": ["release", "cms"]
    }
  ]
}
```

规则：

- `unknown_tag_policy` 只允许 `reject/create`，默认 reject，并保存到 batch snapshot。
- create 在启动时和 worker 执行时都要求 submitted_by 仍具备 tag.manage。
- tag_keys 必须是字符串数组，最多 100，使用统一 normalization。
- archived key 按 unknown/invalid 处理，返回行错误 `tag_archived`，不自动 restore。
- 顶层 `tag_keys/tags/title/markdown/source` 都是系统字段，永不进入 dynamic fields。
- 输入旧 `tags` 返回 `legacy_tags_field_not_supported`，不做静默兼容；CSV 的正式列名是 `tag_keys`，单元格为 JSON string array。

### 9.2 导出契约

JSONL：

```json
{"tag_keys":["cms","release"]}
```

CSV/XLSX 的 `tag_keys` 单元格使用排序后的 JSON 数组文本。导出不使用内部 UUID、display name 或 slug 作为跨环境身份。

export query 使用相同 `tags_any/tags_all/tags_none` resolver 和关系 SQL，不再读取 `v.tags`。选择 published/working scope 必须由 export request 明确并经过权限校验，不使用 COALESCE 指针。

### 9.3 Webhook

最终 `/api/open/v2` Webhook 输入使用：

```json
{
  "tag_keys": ["release", "cms"]
}
```

Webhook technical principal 只能解析同 workspace 已有 active 标签；遇到 unknown/archived key 整个请求返回 422。AgentAccessPolicy 不授予 tag.manage，因此 Webhook 不提供 `unknown_tag_policy`，也不能自动创建标签。

Webhook 创建内容仍然先写 AssetDraft，再调用标准 commit service；不能直接 INSERT 带标签的新 AssetVersion。

## 11. 事务、审计与事件

### 11.1 事务边界

以下操作必须在一个事务内完成业务写入、审计和 outbox：

- Tag create/update/archive/restore。
- AssetDraft 标签替换和 revision 增加。
- draft commit、AssetVersion 和 AssetVersionTag 创建。
- TagSuggestion accept/reject。
- 每个导入行的 Asset/Draft/Version/Tag relations。

Tag repository 所有方法接受 `DBTX`，不能在 materializer 内部自行开启第二个事务。

### 11.2 锁顺序

内容事务统一使用：

```text
Asset -> AssetDraft -> Tag rows(tag_id asc) -> TagSuggestion rows(id asc)
```

单独 Tag lifecycle 只锁目标 Tag。它不会再反向锁 Asset，因此不会与 commit 形成锁环。导入显式创建缺失标签后，仍按 Tag ID 顺序读取/锁定最终集合。

### 11.3 审计动作

```text
tag.create
tag.update
tag.archive
tag.restore
asset.draft.tags_replaced
tag_suggestion.accept
tag_suggestion.reject
```

draft audit 保存 asset_id、draft_id、old/new tag ID 的排序 hash 与数量，不复制完整正文。Tag 管理审计保存 key、旧/新 display name、旧/新 status 和 request_id。

### 11.4 领域事件

```text
tag.created
tag.updated
tag.archived
tag.restored
asset.version_created
```

Tag 事件最小 payload：

| 事件 | payload |
| --- | --- |
| `tag.created` | `tag_id`, `workspace_id` |
| `tag.updated` | `tag_id`, `workspace_id`, `changed_fields` |
| `tag.archived` | `tag_id`, `workspace_id` |
| `tag.restored` | `tag_id`, `workspace_id` |

aggregate version 使用 Tag.revision。事件不放 display name 或完整标签使用资产列表；消费者凭 tag_id 读取当前定义。draft 标签变化不发公共 outbox 事件；version commit 继续只发 `asset.version_created`，消费者按 version_id 读取不可变的 tag ID/provenance 集合，并关联当前 Tag 定义。

阶段 2 只保证正确发出事实事件，不实现检索投影消费者；阶段 3 消费 `asset.version_created` 和 Tag 事件。事件信封和版本字段沿用阶段 0 的 `payload_version`，不得在本阶段引入 `schema_version` 平行字段。

## 12. 数据库实施方案

### 12.1 空库基线策略

阶段 2 只支持 v2 空库，不从 `asset_versions.tags` 复制旧数据。

本阶段最终字段和约束直接整理进 `db/migrations/0006_tags.sql` 及相关 Asset 基线，然后重建开发/测试数据库。不存在已经保留数据的共享 v2 baseline，也不创建 `0016_tag_domain_runtime.sql`；若发现共享环境，停止实施并先清空该环境。

### 12.2 数据库不变量

- Tag 的 key 和 slug 在 organization/workspace 内唯一。
- Tag、Draft、Version、Suggestion 的 organization/workspace 必须由复合外键一致。
- Draft/Version 每个 Tag 只能关联一次。
- source 枚举固定；只有 ai source 可以且必须保存 confidence。
- 一个版本最多 100 个标签由 service 保证并有数据库 constraint trigger 兜底。
- ImportBatch/ImportRow 的 `status`、lease、attempt、last_error 和 row `idempotency_key` 使用 CHECK、索引和唯一约束固化；过期 processing 租约可以被安全 reclaim，完成行不可重复创建 Asset/Version。
- sealed AssetVersion 的 AssetVersionTag INSERT/UPDATE/DELETE 被不可变 trigger 拒绝；只有统一版本 materializer 能在 seal 前插入。
- accepted suggestion 必须有 reviewed_by、reviewed_at、resolved_tag_id、accepted_into_draft_id。
- rejected suggestion 必须有 reviewed_by/reviewed_at，不能有 accepted draft/materialized version。
- materialized_version_id 与 suggestion source asset 必须属于同一 Asset、organization 和 workspace。
- Tag revision 单调递增，status 与 archived_at/by 的非空关系由 CHECK 保证。

### 12.3 索引

```text
asset.tags(workspace_id, status, normalized_key, id)
asset.tags(workspace_id, status, lower(display_name), id)
asset.tags(workspace_id, created_at desc, id desc)
asset.asset_draft_tags(asset_draft_id, tag_id)
asset.asset_draft_tags(tag_id, asset_draft_id)
```

### 12.4 SQL 权限与 trigger

- 受限应用运行角色对 `asset.asset_version_tags` 只有 SELECT/INSERT；没有 UPDATE/DELETE，且 INSERT 仍受父版本 seal trigger 约束。migration role 是唯一 object owner。
- 不可变 trigger 仍然存在，防止表 owner 或错误 repository 绕过 grant。
- 版本删除不作为运行时能力，因此关系表不设置业务 `ON DELETE CASCADE`。
- Tag archive/restore 不级联更新任何 relation。

## 17. 阶段 2 退出门槛

### 模型

- Tag、AssetDraftTag、AssetVersionTag、TagSuggestion 职责分离。
- normalized key、slug、status、revision 和 provenance 规则唯一。
- 系统 tags 不再是 ResourceModel 动态字段类型。
- 标签只属于 workspace，不存在 organization/global/personal 标签旁路。

### 写入

- 所有人工、导入、Webhook 和 suggestion 接受入口经过同一个 resolver/service。
- 普通资产写入不能隐式创建标签。
- draft 标签和 revision 原子更新。
- version 标签只在 commit 中创建，之后不可变。
- archived 标签不能进入新版本，且不会破坏历史版本。

### 读取

- Asset/Draft/Version/query DTO 返回 TagSummary。
- any/all/none 只走 relation table。
- facet 与实际资产列表使用同一版本选择和权限范围。
- usage/facet 按 distinct asset 计数，无 N+1。

### 通道

- 导入导出使用 sorted normalized key，并通过 round-trip 测试。
- Webhook 只解析已有 active 标签。
- Agent suggestion schema/service 可供阶段 4 调用，但阶段 2 不生成建议。
- Tag 事实事件可供阶段 3 检索消费者使用。

### 清理

- `asset_versions.tags` 不存在。
- 阶段 2 负责的运行时代码零 `v.tags`、零 `jsonb_build_object('tags', ...)`、零 `jsonb_array_elements_text(v.tags)`；`query/fulltext.go`、`query/member_search.go` 的残留必须列在阶段 3 台账，并在阶段 3 完成前不得扩展。
- 旧 `tags []string` DTO、`filters.tags` 和 `/api/frontend` 标签接口不存在；旧 public asset 读取路由按阶段 5 台账保留或退役，不在阶段 2 越权删除。
- 没有 JSONB/关系表双写和旧数据迁移。

### 工程质量

- OpenAPI 与实际 v2 路由一致。
- handler 无 Tag SQL，TagService 无 HTTP/query/retrieval 依赖。
- 单元、PostgreSQL、并发、通道、权限和性能测试通过。
- 阶段 3 可以直接使用 `tag.Filter + AssetVersionTag + Tag events`，无需再次修改标签主模型或重复设计导入恢复语义。

## 18. 工期估算与主要风险

按一名熟悉当前仓库的后端工程师估算：

| 工作 | 预计工程日 |
| --- | ---: |
| Tag contract、schema、CRUD、权限 | 3-4 |
| Draft/Version materialization/checksum | 3-4 |
| relational filter、facet、query DTO | 3-4 |
| import/export/Webhook | 3-4 |
| ResourceModel/Suggestion/OpenAPI | 2-3 |
| 并发、数据库、性能与回归测试 | 3-4 |
| 合计 | 17-23 |

主要风险：

1. 当前 tags 字符串数组读取点很多，漏掉任一入口都会重新产生双重主数据。
2. Tag archive 与 draft commit 并发时需要正确行锁，否则会产生新版本绑定 archived 标签。
3. published pointer 和 working pointer 不同，筛选/facet 选错版本会直接泄露未发布标签。
4. 导入 worker 当前是大事务且会把 tags 混入 fields，改造必须保持逐行错误和幂等行为。
5. facet 权限若和资产列表分开编写，会出现计数可见但资产不可见。

这些风险必须由共享 service、复合外键、不可变 trigger、真实 PostgreSQL 并发测试和零旧字段扫描解决，不能依靠代码评审约定。
