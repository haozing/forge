# 垂直领域知识资产运营平台

产品文档 v2.0

状态：产品基线

## 1. 文档定位

本文定义产品 v2 的统一产品边界、用户模型、核心对象、业务流程、能力范围和验收标准。

产品 v2 的设计依据是：

- 专业专家和专业创作者需要持续沉淀、整理和发布自己的知识；
- 真正的协作边界是团队工作区，而不是个人账号；
- 团队可以属于企业组织，但产品不引入部门层级；
- 同一份知识资产需要同时支撑内部管理、检索、博客/公开站点、Agent 和开放 API；
- 资产、版本、权限和发布状态必须由本系统统一维护；
- 标签是独立的工作区内容元数据，并绑定到资产版本。

本文不把博客、公开站点、Agent 或 API 设计成互相复制的数据系统。它们都是同一份已发布知识资产的不同使用出口。

### 1.1 v2 实施基线决策

v2 采用一次性干净重建，不兼容任何旧数据库、旧数据、旧路由或中间阶段数据。阶段 0 至阶段 6 都是首次共享部署前的开发检查点，不是可升级的发布版本；每个阶段开始时都允许直接重写 `db/migrations` 空库基线并重建开发、测试数据库。首次允许保存共享数据和部署到共享环境的时点固定为阶段 6 全部退出门槛通过之后，此后迁移才改为 append-only。

由此固定以下规则：

- 不设计 v1 -> v2 或 v2 阶段间的数据回填、双写、兼容 view、影子旧表和路由转发；
- 每个工作包以 schema、repository、service、HTTP/OpenAPI 和测试的垂直切片提交，任何提交都必须能从空库启动；
- API 和 worker 不在启动时执行迁移；迁移只由独立 migrator 使用 `DATABASE_MIGRATION_URL` 执行，运行进程只使用权限受限的 `DATABASE_URL`；
- `db/migrations` 在阶段 6 前是可重写的唯一空库基线，不存在 `0013/0016/0017` 等“共享环境追加”分支；
- 路由退役台账逐条记录精确 method + path，不接受 `/api/frontend/...` 一类通配项；
- 完成阶段 0 至阶段 3 只代表后端基础域与检索底座完成，不能宣称产品 v2 或 P0 完成；P0 必须等阶段 4 Agent、阶段 5 PublicSite 和阶段 6 前端一并验收。

## 2. 产品定义

### 2.1 一句话定义

面向专业专家、专业创作者团队和企业组织的知识资产生产与运营基础设施。

### 2.2 标准定位

把零散经验、工作笔记、人机共创内容和外部资料，沉淀为结构化、可追溯、可治理的知识资产，并通过博客/公开站点、知识库、智能 Agent 和开放 API 持续复用。

### 2.3 核心价值

1. 降低知识沉淀的起点：不要求用户先整理出完整文档，零散内容也可以直接进入系统。
2. 提高知识质量：通过资源模型、Agent 整理、人工编辑和版本发布形成可控质量链路。
3. 保证内容同源：博客、公开站点、检索、Agent 和 API 都读取同一份已发布资产。
4. 支持团队协作：专家负责内容判断，编辑负责整理、提交或按策略发布，reviewer 负责发布审批，管理员负责组织和权限。
5. 保持数据主权：资产、版本、来源、权限和检索主数据由本系统保存和控制。

### 2.4 产品边界

产品核心包括：

- 知识输入和原始资料留存；
- 通用文档/笔记和专业资源模型；
- 资产版本、整理、编辑、发布和归档；
- 工作区标签和标签筛选；
- 全文、语义、混合和结构化检索；
- 博客和公开站点发布；
- 内置 Agent 应用；
- 受权限控制的开放 API；
- 来源、引用、关联、任务和审计。

博客和公开站点是内容发布能力，不单独维护另一份文章数据。个人品牌和专家主页也归入博客/公开站点能力，不建立独立的品牌实体。

## 3. 用户、组织和工作区

### 3.1 企业组织

企业组织是数据、成员、工作区、资源模型、Agent 和权限的最高边界。

一个企业组织可以拥有多个工作区。组织负责成员身份、全局设置和工作区管理；内容默认归属于具体工作区。

### 3.2 工作区

工作区是最小的内容协作边界，也是标签、资源模型、资产、公开站点和 Agent 数据范围的归属边界。

工作区可以是：

- 一个专业创作者带领的小团队；
- 企业内负责一个知识领域的专业团队；
- 一个独立的专业内容项目。

工作区不是部门。产品不建立部门树、部门继承或跨部门权限模型。

### 3.3 个人专家

个人专家是内容领域的负责人或主要作者，不是独立的数据租户。

个人专家可以：

- 在团队工作区中负责专业内容；
- 作为资产作者、审核者或 Agent 应用的业务负责人；
- 维护自己的博客/公开站点内容视图；
- 与其他编辑共同维护同一个工作区。

资产归工作区和企业组织管理，不因作者变化而脱离工作区。

### 3.4 专业创作者

专业创作者是持续生产和维护专业知识资产的用户角色。专业创作者可以是个人专家，也可以是带领小团队的内容负责人。

产品不把“创作者”建模为另一种权限体系。创作者使用工作区成员身份和工作区权限完成内容生产。

### 3.5 成员角色

组织身份和工作区角色是两层不同概念。组织身份只有 `admin/member`；工作区角色保持简单但覆盖完整协作需要：

| 角色 | 职责 |
| --- | --- |
| admin | 管理当前工作区的成员、资源模型、标签、Agent、公开站点和全部资产 |
| editor | 创建、编辑、整理和归档被授权工作区资产；在 direct 发布策略下可以发布 |
| reviewer | 查看版本和审核队列，评论、批准或拒绝发布；不能修改资产内容 |
| viewer | 只读访问有权查看的工作区资产、已发布内容和查询能力 |

Organization 拥有 Workspace，因此不再设置 workspace `owner` 角色；`member` 只表示组织身份，不能作为含义模糊的工作区角色。组织 admin 可以创建、停用工作区和管理组织成员，但不自动获得工作区内容权限；读取或修改工作区内容仍需显式 workspace membership。组织 admin 为自己授予 workspace 角色属于可审计的管理操作。

工作区的发布策略只有两种：

- `direct`：拥有发布权限的成员可以直接发布；
- `approval`：editor 提交发布请求，由 reviewer 或 admin 单级批准后发布。

产品保留完整的单级发布审核领域，包括提交、审核队列、详情、筛选、评论、批准、拒绝、取消、批量处理、待审核统计、通知和审计。产品不做多级审批、部门审批和审批流编排。审批请求是独立的 PublicationRequest，不是 AssetVersion 的状态。

approval 模式禁止提交人批准自己的请求。资产产生新的 committed working version 或被归档后，旧版本的 pending PublicationRequest 自动取消，必须对新版本重新提交。审核评论线程属于 PublicationRequest；批准或拒绝时还可以填写独立的决定说明。

公开站点访客不需要成为工作区成员。需要访问内部内容的用户必须登录，并按 organization visibility 或 workspace membership 校验。

### 3.6 Agent 身份

Agent 用户是技术身份，不继承成员角色。Agent 用户通过 API Key 或内部运行时身份访问统一查询和写入 API，数据范围由 AgentAccessPolicy 控制。

AgentApplication 是面向用户的 Agent 应用。它绑定一个 Agent 用户、一个模型端点和一个运行模式，并可以绑定指定工作区和资源模型。

产品中的“专家 Agent”指一个面向用户的 AgentApplication，不是另一份知识库，也不是脱离资产系统的独立数据副本。

## 5. 知识资产模型

### 5.1 通用文档/笔记

通用文档/笔记是默认内容入口，至少包含：

- 标题；
- Markdown 正文；
- 附件；
- 工作区标签；
- 来源；
- 作者；
- 关联内容；
- 版本和发布状态。

用户可以把它当作团队知识记录入口，不需要先选择专业数据模型。

### 5.2 专业资源模型

资源模型用于描述需要稳定字段和固定录入方式的专业内容，例如经典镜头、设备资料、FAQ 或行业案例。

资源模型包含：

- 字段定义和字段类型；
- 枚举和校验规则；
- 表单布局；
- 默认可见性；
- 默认整理 Agent；
- 发布规则；
- 检索策略；
- API 出口策略。

普通内容用户使用已发布的资源模型，不直接设计数据库表。

### 5.3 原始资料和加工结果

原始资料必须与加工结果分离保存：

    RawInput
      -> ProcessingJob
      -> AssetVersion

Agent 只能生成候选版本、字段建议、摘要、标签建议和关联建议。原始资料不能被加工结果覆盖。

### 5.4 编辑草稿、版本和发布状态

`draft/published/archived` 是 Asset 的发布状态，不是 AssetVersion 的字段。AssetVersion 不保存 workflow、review 或 publication status，它在创建后始终不可变。

Asset 同时维护：

- 一个可变的 AssetDraft，用于编辑器自动保存和暂存标签、附件；
- `current_working_version_id`，指向最近一次提交的不可变版本；
- `current_published_version_id`，指向当前对外或对内发布的不可变版本；
- `publication_status`，只允许 `draft/published/archived`。
- `published_at`，仅在 `publication_status=published` 时非空，表示当前 published pointer 生效的时间；切换到新发布版本时更新，幂等重放同一发布命令时不变，归档时清空。

自动保存只更新 AssetDraft 并递增 draft revision，不产生版本历史。用户创建检查点、直接发布或提交审核时，系统把指定 draft revision 原子提交为新的 AssetVersion。已发布资产继续保留旧的 published pointer，直到新 working version 被直接发布或审核通过。

AssetVersion 的 `origin` 与人工确认分开表达：

- `origin`：`human/imported/ai_generated/ai_assisted`；
- `confirmation_status`：`unconfirmed/human_confirmed`；
- 人工确认记录 `confirmed_by/confirmed_at`，Agent 不能写入人工确认事实。

AssetDraft 不承载已确认事实；从任何版本初始化可编辑 draft 时，提交语义按 `unconfirmed` 处理。标题、摘要、正文、字段、标签或附件关系发生变化都清空可能缓存的来源确认元数据，只有创建不可变 AssetVersion 的确认动作才能写入 `human_confirmed`、`confirmed_by` 和 `confirmed_at`。

人工确认已有版本时创建内容相同的派生版本，不原地更新原版本。发布审批表示“允许该版本发布”，不自动等于人工确认；ResourceModelVersion 可以通过 `require_human_confirmation` 决定发布前是否必须确认。

每个 Asset 从创建到归档始终保留且只保留一个 AssetDraft。归档只冻结 draft 写入，不删除未提交内容；恢复后继续使用同一个 draft。AssetDraft 使用 `revision` 和 `committed_revision` 表达编辑状态：二者相等为 clean，不相等为 dirty；自动保存只增加 revision，提交成功后增加 revision 并把 committed_revision 设为新 revision。

## 6. 标签产品模型

标签不是普通动态字段，也不是目录树节点。标签是工作区范围内可复用的内容元数据。

最终数据模型使用：

    asset.tags
        工作区标签定义

    asset.asset_version_tags
        资产版本与标签的正式关联

    asset.asset_draft_tags
        AssetDraft 当前可变的标签选择

    asset.asset_version_tag_suggestions
        Agent 待确认的标签建议

标签要求：

- 同一工作区的 normalized_key 唯一；
- 标签有稳定 id、normalized_key、display_name、slug 和 status；
- 正式标签绑定到 AssetVersion，而不是 Asset 根对象；
- 编辑期间标签写入 asset_draft_tags，提交 draft 时一次性物化为 asset_version_tags；
- 新 draft 未修改标签时从 base version 继承；
- archived 标签不能绑定到新版本；
- 标签顺序没有业务含义；
- 所有入口使用相同的规范化、权限和数量校验；
- 标签查询使用 tags_any、tags_all、tags_none；
- 单个 AssetDraft/AssetVersion 最多 100 个不同标签；查询中 `tags_any`、`tags_all`、`tags_none` 各最多 50 个 key，三组去重后最多 100 个；
- 标签聚合按可见的已发布资产计数；
- draft 标签变化不触发公开投影；Asset 发布、标签定义变化才触发对应检索投影和聚合刷新。

详细数据库和服务设计见 [标签系统最终设计架构.md](/D:/code2/agentchunzhi/docs/标签系统最终设计架构.md)。

## 7. 博客与公开站点

### 7.1 产品定位

博客/公开站点是已发布知识资产的公开阅读出口。它不是独立 CMS 数据库，也不是把资产复制成另一套文章。

专家主页、作者介绍、专业栏目和博客文章都属于公开站点的展示能力。

### 7.2 公开站点对象

PublicSite 至少包含：

- site_id；
- workspace_id；
- 站点名称；
- slug 或绑定域名；
- 站点状态；
- 首页配置；
- 导航配置；
- 展示模板；
- 默认内容范围；
- 创建和更新时间。

SiteContentBinding 至少包含：

- site_id；
- asset_id；
- 展示路径；
- 内容类型；
- 排序；
- 是否显示在首页；
- 是否显示在导航；
- 发布时间。

公开站点绑定 Asset，不固定 AssetVersion。每次公开读取都解析 Asset 的 current_published_version_id，因此资产新版本发布后站点自动读取新版本；AssetDraft 和未发布的 working version 不能被公开 URL 访问。v2 不提供站点级版本固定能力。

### 7.3 站点能力

首版公开站点需要支持：

- 首页；
- 博客文章列表；
- 博客文章详情；
- 专业栏目/资源集合；
- 标签筛选和标签页；
- 站内搜索；
- 资产来源和更新时间展示；
- Markdown、结构化字段和附件的安全渲染；
- public/organization/workspace 范围控制。

站点内容的筛选、标签和搜索必须复用统一查询服务，不能另建一套数据查询逻辑。

### 7.4 站点与资产关系

资产是权威数据源，站点是展示配置和读取视图：

    Asset
      -> SiteContentBinding
      -> current_published_version_id
      -> AssetVersion
      -> PublicSite rendering

站点不得直接保存一份可编辑的文章正文。站点编辑行为应回到资产编辑和版本发布流程。

## 8. Agent 能力

### 8.1 Agent 整理

Agent 整理用于：

- 从原始资料抽取资源模型字段；
- 生成摘要；
- 提取和建议标签；
- 建立资产关系；
- 检测重复和缺失；
- 生成内部候选内容并写入 AssetDraft，或生成可追溯的候选 AssetVersion；
- 从样本推断资源模型 schema（2026-09-03 补充：`suggest_resource_model` 工具，纯计算、不落库，返回经 schema 校验的模型草稿与结构化 issue，详见《数据模型自由定制实施方案-2026-09-03》）。

Agent 结果必须附带处理任务、输入版本、引用依据、字段差异和置信度。

### 8.2 Agent 问答

Agent 问答使用统一查询服务获取已授权资产，查询结果包含：

- asset_id；
- version；
- title；
- snippet；
- source；
- updated_at；
- 引用位置。

Agent 不直接访问数据库、对象存储或检索投影。

### 8.3 Agent 发布

默认 Agent 只能更新受控 AssetDraft 或生成未发布的候选版本。只有获得资源模型 publish 动作白名单且满足 direct/approval 策略的 Agent，才可以触发发布或提交发布请求；Agent 不能设置 `human_confirmed`，也不能批准 PublicationRequest。

例外（2026-09-02 补充，公开站点样式工具）：只读样式工具可以保存**无生效影响的数据束**（如组织级样式预设——套用与发布仍需成员完成）；此类写入不改变任何线上状态，不属于"更新受控草稿"的字面限制范围。

例外（2026-09-03 补充，模型草拟工具，详见《数据模型自由定制实施方案-2026-09-03》）：`create_resource_model` / `update_resource_model_draft` 是"agent 可草拟、人可发布"的写侧受控例外——两者只创建/修改 **draft 状态**的 ResourceModel 与未发布模型版本，validate 与 publish 始终是成员动作（`model.manage`）。授权需三层显式：AgentAccessPolicy 对目标工作区含 `model.manage` 动作、agent 应用工具策略显式授予 `model.manage` 能力位（默认能力集不含）并开启 high-write（默认触发人工批准），授权记录可审计。authz 的 agent 动作白名单不变：Require 路径继续拒绝 agent 的 model.manage，该通道仅由模型草拟专用服务（`resourcemodel.AgentDraftService`）承载。

发布必须记录：

- Agent 用户；
- Agent 应用；
- 规则版本；
- 输入版本；
- 输出版本；
- 发布时间；
- 处理结果。

## 9. 检索与知识库

知识库不是独立复制的数据实体，而是对已发布资产的统一检索视图。

### 9.1 检索范围

统一查询支持：

- 资源模型和字段精确查询；
- 标签筛选；
- 全文检索；
- 语义检索；
- 混合检索；
- 资产详情；
- 来源和关联查询；
- 公开站点范围查询。

### 9.2 索引原则

- PostgreSQL 中的资产和版本是权威来源；
- 检索投影可以重建；
- 只有满足发布、可见性和出口策略的版本进入公开检索；
- 标签变化和发布变化都触发索引更新；
- 查询返回前必须再次校验主数据权限和发布状态；
- 未授权内容的标题、数量、分数和引用都不得泄露。

### 9.3 标签检索

标签结构化筛选直接连接 asset_version_tags 和 tags：

- tags_any：命中任意标签；
- tags_all：同时命中全部标签；
- tags_none：不包含指定标签。

标签名称可以进入全文检索文本，但全文命中不能替代结构化标签判断。

## 10. 权限模型

### 10.1 权限层级

权限层级固定为：

    Organization
      -> Workspace
        -> ResourceModel
          -> Asset / AssetVersion
            -> PublicSite / AgentApplication / OpenAPI

首版不建立部门层级和字段级 ACL。

Organization admin 负责组织治理，但内容授权仍落在 Workspace。它不会因为组织身份自动继承 workspace admin；如需进入工作区，必须通过一条显式、可审计的 membership 记录获得角色。

### 10.2 工作区权限

工作区成员权限控制：

- 查看资产；
- 创建资产；
- 编辑资产；
- 提交发布请求；
- 按发布策略直接发布或批准/拒绝发布请求；
- 处理 Agent 任务；
- 管理标签；
- 发布资产；
- 归档资产；
- 管理公开站点；
- 管理 Agent 应用。

动作权限和数据范围分开判断。拥有编辑权限不自动拥有发布权限；拥有 Agent 使用权限不等于拥有 Agent 数据读取权限。

资产可见性只允许 `workspace/organization/public`：`workspace` 面向当前工作区成员，`organization` 面向同组织已登录成员，`public` 只公开当前 published version。`login` 是认证方式，不是数据范围；`internal` 语义含混；v2 不提供个人 `private` 资产，个人视图通过作者和贡献者筛选实现。

### 10.3 公开站点权限

公开站点访问必须同时满足：

- 站点处于 published/active 状态；
- 资产有当前 published 版本；
- 资产可见性允许当前访客；
- 资源模型允许 public-site 出口；
- 资产未删除、未归档；
- 标签筛选和聚合使用相同的可见范围。

### 10.4 Agent 权限

Agent 用户使用独立 AgentAccessPolicy：

- 不继承 admin/editor/reviewer/viewer 成员角色；
- 绑定允许访问的工作区；
- 绑定允许访问的资源模型；
- 绑定允许执行的动作；
- 可单独限制数据范围：Agent 查询固定只读已发布版本，data_scope 再收窄可见带——public（仅公开带）/ organization（组织+公开，默认）/ workspace（含工作区内部带），多条策略取最窄生效；
- 每次调用都按实时权限校验。

## 11. 统一 API

### 11.1 资产 API

统一提供：

- 创建资产；
- 自动保存和读取 AssetDraft；
- 从指定 draft revision 创建版本；
- 提交、查看、评论、批准、拒绝、取消和批量处理 PublicationRequest；
- 获取版本；
- 发布；
- 归档；
- 获取来源和关联；
- 附件上传和下载。

2026-09-02 更新：路由已收敛为无版本单树——成员面 `/api`、公开面 `/api/public`、开放面 `/api/open`、运维面 `/api/admin`；历史 `/api/v2`、`/api/frontend` 前缀全部退役（见 route-retirement-ledger.md）。以下路径均为现行形态，完整契约以 openapi.yaml 为准（与真实路由表双向锁定测试）。

编辑草稿和版本接口：

    GET   /api/assets/{assetId}/draft
    PATCH /api/assets/{assetId}/draft
    POST  /api/assets/{assetId}/commit-draft
    POST  /api/asset-versions/{versionId}/confirm
    GET   /api/assets/{assetId}/relations

PATCH draft 必须使用 draft revision（If-Match）；创建版本（commit-draft）、直接发布和提交审核必须携带同一个非空 draft revision（缺失或为空返回 422），服务端在一个事务中物化正文、字段、标签和干净附件。提交审核与请求创建同事务：中途失败既不留下孤儿版本也不留下孤儿请求。

发布审批接口：

    POST /api/workspaces/{workspaceId}/publication-requests        （asset_id 在 body）
    GET  /api/workspaces/{workspaceId}/publication-requests
    GET  /api/workspaces/{workspaceId}/publication-requests/{requestId}
    GET  /api/workspaces/{workspaceId}/publication-requests/{requestId}/comments
    POST /api/workspaces/{workspaceId}/publication-requests/{requestId}/comments
    POST /api/workspaces/{workspaceId}/publication-requests/{requestId}/approve
    POST /api/workspaces/{workspaceId}/publication-requests/{requestId}/reject
    POST /api/workspaces/{workspaceId}/publication-requests/{requestId}/cancel
    POST /api/workspaces/{workspaceId}/publication-requests/batch

当已发布 ResourceModelVersion 使用 `direct` 策略时，不创建 PublicationRequest，直接调用资产发布接口；使用 `approval` 策略时，发布接口只能由批准动作在事务内触发。approval 模式下提交人不能批准自己的请求，Agent 可以按策略提交（`POST /api/open/workspaces/{workspaceId}/publication-requests`，需 AgentAccessPolicy 同时授予 publication.submit 与 asset.write），但不能批准。提审会站内通知工作区的 reviewer 与 admin；决定与自动取消（新版本提交/人工确认/归档触发）均写事件、通知与审计。

资产写入使用 tag_ids。字符串标签只允许在导入、Webhook 或 Agent 受控解析入口中出现，并必须通过 TagService；成员写入面携带 `tags` 字段一律 422（legacy_tags_field_not_supported）。

附件接口：上传为 `POST /api/workspaces/{workspaceId}/attachments`（multipart，字段名 file，落库后进入病毒扫描队列）；绑定草稿 `POST /api/attachments/{attachmentId}/link`（归档资产拒绝）；下载与预签名下载 `GET /api/attachments/{attachmentId}/download|presigned-download`。机器入口 origin 语义：开放 API（Agent 用户）创建为 ai_generated，Webhook 与导入为 imported。

### 11.2 标签 API

    GET    /api/workspaces/{workspaceId}/tags
    POST   /api/workspaces/{workspaceId}/tags
    GET    /api/workspaces/{workspaceId}/tags/{tagId}
    PATCH  /api/workspaces/{workspaceId}/tags/{tagId}
    POST   /api/workspaces/{workspaceId}/tags/{tagId}/archive
    POST   /api/workspaces/{workspaceId}/tags/{tagId}/restore

标签列表支持搜索、状态、排序、分页和使用计数。

归档只禁止新绑定，不删除已有版本关系；归档标签继续占用原 key 和 slug，并可由工作区管理员显式恢复。

### 11.3 查询 API

统一查询请求支持：

    {
      "query": "低机位远景",
      "mode": "hybrid",
      "data_models": ["shot", "document"],
      "tags_any": ["release"],
      "tags_all": ["approved"],
      "tags_none": ["deprecated"],
      "top_k": 10
    }

查询 API 是前台、公开站点、内置 Agent 和受控外部系统的共同入口。

### 11.4 公开站点 API

    GET /api/public/sites/{siteId}
    GET /api/public/sites/{siteId}/content
    GET /api/public/sites/{siteId}/content/{path}
    GET /api/public/sites/{siteId}/tags
    GET /api/public/sites/{siteId}/search

SSR 投递后另有服务端渲染的站点 HTML 面（/sites/{slug}/...，含首页、列表、详情、标签页、搜索、about、archive、RSS、Sitemap、媒体路由），与上述 JSON 面同权限同数据源。

站点 API 返回渲染所需的内容视图，不返回未发布版本和内部字段。

## 12. 核心业务流程

### 12.1 团队建立工作区

企业组织管理员创建工作区 → 邀请专业专家、编辑和可选 reviewer → 启用通用模型或专业资源模型 → 在 ResourceModelVersion 配置 direct/approval 发布策略、标签和权限 → 创建公开站点或 Agent 应用。

### 12.2 零散内容沉淀

用户打开通用笔记 → 输入标题、Markdown、附件和标签 → AssetDraft 自动保存 → 保存原始输入 → 可发起 Agent 整理 → 查看并采用字段、标签和关联建议 → 提交为不可变 working version。

### 12.3 专业资产发布

用户使用专业模型表单录入 → AssetDraft 自动保存 → 系统校验字段、标签和干净附件 → 提交不可变 working version → 必要时创建 human_confirmed 派生版本 → 按 direct 策略直接发布，或按 approval 策略进入审核队列并由 reviewer/admin 批准 → 更新检索投影和公开站点。

### 12.4 公开站点展示

站点管理员选择已发布资产 → 配置栏目、路径和首页展示 → 访客访问站点 → 站点按公开权限读取当前发布版本 → 标签和搜索调用统一查询服务。

### 12.5 Agent 问答

用户选择 Agent 应用 → 校验用户是否允许使用该应用 → Agent 以绑定技术身份调用统一查询 API → 查询服务按 AgentAccessPolicy 和发布范围过滤 → 返回答案、资产和引用。

### 12.6 外部系统接入

外部系统通过 Agent 用户 API Key 调用开放 API → 服务端校验组织、工作区、资源模型、动作和发布策略 → 返回授权资产、更新受控 AssetDraft 或创建未发布候选版本 → 记录调用审计。

## 16. 技术实现约束

### 16.1 主数据

PostgreSQL 保存组织、工作区、资源模型、资产、版本、标签、关系、任务和权限。对象存储保存附件二进制。

### 16.2 事件与索引

资产发布、版本更新、标签变化、站点绑定变化和权限变化产生事件。事件驱动检索投影和站点读取缓存更新。

索引和缓存均不可替代主数据。查询返回前必须以主数据重新校验权限、版本和发布状态。

### 16.3 Agent

Agent 使用 Eino Runtime。ModelEndpoint 管理模型连接，AgentApplication 管理用户可使用的 Agent 应用，AgentAccessPolicy 管理 Agent 数据范围。

Agent 整理必须输出候选版本和标签建议，不得覆盖原始输入。用户确认后才写入正式版本和标签关联。

### 16.4 代码现状（2026-09-02）

v2 阶段 0-7 已实施完毕，原 §16.4/16.5 的"改造前差距清单"已完成使命并删除。现行架构事实：

- internal/httpapi 以 router_groups.go 注册无版本单树路由，openapi.yaml 与真实路由表双向锁定（路径级测试对照源码解析，方法级对照契约表）；SSR HTML 面（/sites/{slug}/...）由 delivery 专用测试钉死，不进 JSON 契约。
- AssetDraft/AssetVersion/标签/审核（PublicationRequest 聚合在 internal/review）/公开站点（internal/site + internal/delivery）/统一查询（internal/query + internal/retrieval）均已按 §5-§9 落地；AssetVersion 不可变由数据库触发器封存。
- Agent 运行时（internal/agentruntime，Eino）承载问答、ReAct 工具与样式工具；AgentAccessPolicy 含工作区/资源模型/动作三维与 data_scope 数据范围（public/organization/workspace，最窄生效）。
- internal/automation 只保留 prepare_asset 处理链与 run 观测面（task-runs 读/取消/事件流）；定时任务管理面、外部任务回调与六个空转工作流图已于 2026-09-02 裁撤。
- 资源模型字段类型收敛为 13 种（string/text/markdown/integer/number/boolean/date/datetime/enum/multiselect/object/array/asset_reference）；模型 schema 迁移作业框架已下线（开发期免兼容，版本切换直接走新模型版本）。
- content.containers 表保留为会话正文容器存储；其上的文件夹树 API 已移除，待《统一分类树重构整改方案》按 folders 模型另行实施。

## 17. 非功能要求

- 权限默认拒绝，组织、工作区、资源模型、站点和 Agent 范围全部可审计；
- 原始输入、版本、标签、Agent 处理和人工修改可追溯；
- 公开站点只能返回当前已发布版本；
- 标签聚合、站点列表和搜索的权限范围必须一致；
- 检索索引可重建，索引失败可重试；
- 资产发布不依赖索引任务实时成功；
- API 支持稳定分页、限流、幂等和错误追踪；
- Markdown、附件和结构化字段必须安全渲染；
- 站点和 Agent 不能绕过统一查询服务访问主数据。受控例外：ReAct 工具 get_related_assets / get_attachment_text / get_schema 以组织+工作区+模型白名单谓词直读主数据表（读取面，非查询结果面），与 §8.3 样式工具同类；写侧（create_relation）只落草稿关系，提交事务物化。2026-09-03 补充：模型草拟工具 suggest_resource_model（纯计算，无主数据访问）与 create_resource_model / update_resource_model_draft（写侧只落 draft 模型与未发布版本，三层显式授权见 §8.3）加入受控例外清单。
- QueryLog 出于隐私只落 request_hash 不落查询原文；复盘问题时以 request_id 关联访问日志。

## 18. 核心验收标准

1. 专业专家、编辑、reviewer 和 viewer 可以加入同一个团队工作区，按角色共同维护或读取资产。
2. 一个企业组织可以拥有多个工作区，产品不需要部门层级即可完成权限管理。
3. 用户可以直接发表 Markdown 笔记，不需要先设计资源模型。
4. 专业资源模型可以通过动态表单录入结构化资产。
5. AssetDraft 可以自动保存且不污染版本历史；提交后形成不可变版本，原始资料不会被覆盖。
6. 标签具有工作区唯一身份，资产版本可以稳定绑定多个标签。
7. 标签创建、编辑、导入、Webhook 和 Agent 使用同一套校验规则。
8. tags_any、tags_all、tags_none 的结果准确，标签聚合不泄露不可见资产。
9. Agent 可以生成字段、摘要、标签和关联建议，但不会未经确认修改正式版本，也不能伪造人工确认事实。
10. direct 策略下授权成员可以显式发布；approval 策略下只有 reviewer/admin 批准 PublicationRequest 后才能发布，审核队列、评论、批量处理、通知和统计可用，公开站点只显示已发布内容。
11. 一个已发布资产可以同时出现在站点、检索、Agent 和开放 API 中，内容来自同一版本。
12. 专家主页、博客文章和资源目录都通过 PublicSite 渲染，不复制资产正文。
13. 站点标签页和搜索使用统一查询服务，权限和发布状态与资产 API 一致。
14. Agent 用户不继承成员权限，只能访问 AgentAccessPolicy 允许的数据。
15. 外部系统只能通过开放 API 访问数据，不能直接访问数据库、对象存储或检索投影。
16. 资产、标签、权限或发布状态变化后，检索投影和站点读取最终一致且可重试。
17. 资产详情可以查看版本、来源、引用、处理任务、标签和发布记录。
18. 所有公开读取、Agent 调用、资产发布、审核决定和标签管理操作都有审计记录。

## 19. 产品叙事

### 19.1 对外标准表述

沉淀专业经验，形成可运营的知识资产。

从零散笔记、人机共创和日常工作资料开始，经过结构化整理、版本治理和人工确认，形成可持续复用的专业内容。一次沉淀，同时服务于博客/公开站点、知识库、智能 Agent 和开放 API。

### 19.2 产品区别

我们不是单纯的文件存储工具，因为内容具备结构、版本、权限和来源。

我们不是单纯的博客工具，因为博客只是已发布知识资产的阅读视图。

我们不是单纯的 Agent 工具，因为 Agent 使用的是经过治理的资产，而不是一份无法追溯的提示词或知识库副本。

### 19.3 典型场景

一个专业创作者团队把日常笔记、访谈资料和专业案例录入工作区。系统保留原始资料，Agent 抽取字段、生成摘要、提出标签和关联建议；编辑确认后按策略直接发布，或提交给 reviewer/admin 单级批准。已发布内容自动进入团队检索、公开站点、博客文章和 Agent 问答，所有出口使用相同的内容、版本和权限。

## 20. 产品决策摘要

1. 产品面向专业专家、专业创作者团队和企业组织。
2. 个人专家是内容角色，团队工作区才是协作和数据边界。
3. 企业组织可以拥有多个工作区，产品不建立部门模型。
4. 个人品牌和专家主页统一归入博客/公开站点。
5. 资产是唯一权威来源，博客、检索、Agent 和 API 都是输出视图。
6. 标签使用独立定义表和资产版本关联表。
7. Agent 是受权限控制的资产使用应用，不维护独立知识副本。
8. 公开站点是 v2 的正式内容出口，读取已发布资产。
9. 统一查询服务负责筛选、标签、搜索、权限和审计。
10. 产品的核心竞争力是知识资产的生产、治理、发布和复用。
11. AssetDraft 承担自动保存，AssetVersion 只承担不可变历史，发布状态只属于 Asset。
12. 发布审核是保留的正式产品域，PublicationRequest 是其单级审批聚合，不是对审核能力的删减替代。
13. 工作区使用 admin/editor/reviewer/viewer；组织管理员不因身份自动读取所有工作区内容。
14. SiteContentBinding 绑定 Asset，并动态读取 current_published_version_id。
15. 发布治理采用可配置的 direct/approval 策略；approval 不把审批状态写入 AssetVersion。

## 21. v1 存量域范围裁定（2026-09-02）

以下能力在 v2 产品文档主体之外、但代码与路由活跃维护，正式裁定其归属，避免范围悬空：

1. 会话与笔记域（internal/conversation + internal/content：会话、消息块、笔记同步、派生思考、媒体转写 internal/transcription）：属于 v2 录入与创作面的一部分，规格由《关于录入页面的思考》《Eino内置Agent完整实现方案》《Agent回答姿态与开箱问答链路整改方案》这条文档线维护；笔记发布走资产版本同一发布治理。
2. 自动化运行域（internal/automation）：定位为处理任务载体（ProcessingJob 语义），仅承载 prepare_asset 与 ReAct 运行；定时调度、外部任务回调与 jobs 管理面不属于 v2 范围（2026-09-02 已裁撤）。
3. 导入导出与删除任务（internal/asset transfer + internal/deletion）：属于 §11 数据进出能力，导入资产 origin=imported。
4. 统一分类树（folders）：待《统一分类树重构整改方案》实施，实施前不提供文件夹树 API。
5. 前端管理后台与创作者工作区由独立 React 工程实现，消费 openapi.yaml 契约；本仓库不包含前端代码。
6. 前端团队消费契约以 openapi.yaml 为唯一权威（与真实路由表双向锁定）；本文 §11 的路径示例为产品语义描述，逐条形态以契约为准。
